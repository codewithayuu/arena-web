<h1 id="2-the-library-approach-and-its-limits">
  2. The Library Approach and Its Limits
</h1>

Traditionally, teams handled these concerns using libraries. Each service includes a networking library that provides retries, timeouts, circuit breakers, and metrics. Netflix, for example, built a well-known set of Java libraries for this purpose.

This works well when every service uses the same language. But suppose the order service is written in Java, the payment service in Go, and the recommendation service in Python.

Now the same networking features need to exist in three languages, and they may behave slightly differently in each one.

Upgrades also become difficult. If the security team wants to change how encryption works, every service team may need to update its library, rebuild the application, and redeploy it. Across fifty services, that can take a long time. And there is no guarantee every team will configure the library in exactly the same way.

So instead of putting this networking logic inside every application, can we move it into the infrastructure?

<h1 id="3-what-is-a-service-mesh">3. What Is a Service Mesh?</h1>

That is what a service mesh does. A service mesh is a dedicated infrastructure layer for handling communication between services.

Instead of embedding networking logic inside each application, the mesh places a proxy next to the service. Traffic entering or leaving the service passes through this proxy.

The proxy can handle retries, timeouts, load balancing, encryption, and metrics. The application itself makes a normal network call, while the proxy handles these concerns on its behalf.

Because the same infrastructure is used across the system, services get consistent networking behavior regardless of the language they are written in. Popular service meshes include Istio, Linkerd, and Consul.

A service mesh has two main parts:

- The **data plane** carries the actual traffic.
- The **control plane** tells the data plane how that traffic should be handled.
