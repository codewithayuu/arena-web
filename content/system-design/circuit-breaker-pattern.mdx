1. The order service keeps sending calls, and each one waits for a response.
2. Every waiting request holds a thread and a connection.
3. Before long, all of the order service's threads are stuck waiting for payments.
4. Now the order service cannot handle other requests either, even ones that have nothing to do with payments.
5. Services that depend on the order service start waiting on it in the same way.

A slowdown in one dependency has now spread through the system. This is called a **cascading failure**.

<h1 id="2-why-timeouts-and-retries-are-not-enough">
  2. Why Timeouts and Retries Are Not Enough
</h1>

The first protection we usually add is a timeout. If the payment service does not respond within two seconds, the order service stops waiting and fails the request.

That helps, but every request still spends two seconds waiting before it fails. Under heavy traffic, that can still tie up a large number of threads and connections. At 100 order requests per second, a two-second timeout means about 200 requests are always sitting and waiting on a payment service that is not going to answer.

Retries can make the problem even worse. Suppose every failed request is retried three times. The payment service, which is already overloaded, may now receive up to four times as many requests. That extra traffic makes recovery even harder.

What we need is a way for the order service to recognize that the payment service is unhealthy and temporarily stop calling it. That is what a circuit breaker does.
