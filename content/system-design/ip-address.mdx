But an IP address isn't a permanent identifier for a physical machine. A server can have multiple network interfaces, each with its own address. And those addresses can change when the server moves to another network or its configuration changes. A container may get a new address every time it starts.

So it's more useful to think of an IP address as a **network location** rather than a machine's permanent identity.

<h3 id="ip-addresses-vs-mac-addresses">IP Addresses vs MAC Addresses</h3>

This is different from a **MAC address**, which is primarily used to deliver data within a local network, such as from your laptop to your home router. IP addresses let packets travel between different networks.

As a packet crosses routers, the destination MAC address changes at each hop, because each hop is a new local delivery. The destination IP usually stays the same until the packet reaches its target, unless a device such as a NAT gateway or proxy rewrites it.

Today, there are two main versions of IP: **IPv4** and **IPv6**. Let's start with IPv4.

<h1 id="2-ipv4-addresses">2. IPv4 Addresses</h1>

An IPv4 address is 32 bits long. We usually write it as four decimal numbers separated by dots. Each number represents 8 bits, so its value ranges from `0` to `255`.

```plaintext
192    .    168    .     1     .    10
11000000   10101000   00000001   00001010
 (8 bits)   (8 bits)   (8 bits)   (8 bits)
```

With 32 bits in total, IPv4 has `2^32`, or about 4.3 billion, possible addresses. That sounded like a lot when IPv4 was introduced. But as billions of phones, computers, servers, and other devices connected to the internet, the available address space became a limitation.

Not all those addresses can be used publicly, either. Some ranges are reserved for private networks and other purposes.

This shortage helped drive the adoption of private IP addresses and NAT, and eventually IPv6. The regional registries that hand out public IPv4 space ran through their free pools during the 2010s, and IPv4 keeps working today largely because of private addressing, NAT, and careful allocation.

But before we get into those, we need to understand how IP address ranges are organized.

<h1 id="3-network-and-host-portions">3. Network and Host Portions</h1>

An IP address can be divided into two logical parts:

- **Network portion:** identifies which network the address belongs to.
- **Host portion:** identifies a specific address within that network.

But how do we know which part of an IP address represents the network and which part represents the host?

That's where **CIDR notation** comes in. It adds a slash followed by a number at the end of an IP address. This number is called the **prefix length**, and it tells us how many bits, starting from the left, identify the network.

In `192.168.1.10/24`, the `/24` means the first 24 bits belong to the network portion, leaving the remaining 8 bits for the host portion.

Routers typically use network prefixes to make forwarding decisions, rather than maintaining a separate route for every individual IP address. A single route for `192.168.1.0/24` covers all 256 addresses in that network.

A simplified routing table might look like this:

```plaintext
Destination        Next Hop
192.168.1.0/24     network A
192.168.2.0/24     network B
0.0.0.0/0          default gateway
```

When more than one route matches, the router picks the most specific one, the route with the longest prefix. This is called **longest prefix match**. `0.0.0.0/0` matches every IPv4 address, so it is only used when nothing more specific matches.

By adjusting the prefix length, we can divide larger address blocks into smaller subnets or combine multiple address blocks into larger routing ranges. For example, `192.168.1.0/24` can be split into two halves, `192.168.1.0/25` and `192.168.1.128/25`.

<h1 id="4-cidr-notation">4. CIDR Notation</h1>

**CIDR** stands for **Classless Inter-Domain Routing**. It's a way to represent blocks of IP addresses using a network prefix and its length.

For `192.168.1.0/24`, the 24 tells us that the first 24 bits identify the network. That leaves 8 bits for addresses within the network, giving us `2^8`, or 256, addresses.

The important thing to understand is that **the longer the prefix length, the smaller the address block**. Each extra bit of prefix halves the block.

| CIDR | Subnet Mask     | Total Addresses | Typical Use                                      |
| ---- | --------------- | --------------- | ------------------------------------------------ |
| /16  | 255.255.0.0     | 65,536          | VPCs, corporate networks                         |
| /20  | 255.255.240.0   | 4,096           | Medium subnets or environment ranges             |
| /24  | 255.255.255.0   | 256             | Common subnet size                               |
| /28  | 255.255.255.240 | 16              | Small network segments                           |
| /32  | 255.255.255.255 | 1               | A single address, such as an exact firewall rule |

Keep in mind that these are total address counts, not necessarily the number of addresses available to devices. Some addresses may be reserved for special purposes:

- In a traditional IPv4 subnet, the first address is the network address and the last is the broadcast address. That leaves 254 usable addresses in a `/24`.
- Cloud providers reserve a few more in each subnet. AWS, for example, reserves five addresses in every subnet.
- A `/32` identifies exactly one address, so the "minus two" rule does not apply to it.

<h3 id="example-1000020">Example: 10.0.0.0/20</h3>

The prefix `/20` leaves 12 host bits:

- Address count: `2^12 = 4,096`
- Range: `10.0.0.0` through `10.0.15.255`
- Traditional usable host range: `10.0.0.1` through `10.0.15.254`

You'll encounter CIDR frequently, especially when working with cloud networks, routing tables, firewall rules, and subnet configuration.

<h1 id="5-subnets">5. Subnets</h1>

A **subnet**, short for subnetwork, is a smaller network carved out of a larger address range.

Suppose your application has the range `10.0.0.0/16`. Instead of putting every resource into one large subnet, you could divide it into smaller ones. For example, one could be for public-facing resources, another for application servers, and another for databases.

| Range         | Purpose                                      |
| ------------- | -------------------------------------------- |
| `10.0.0.0/16` | The whole application network                |
| `10.0.1.0/24` | Public subnet: internet-facing load balancer |
| `10.0.2.0/24` | Private subnet: application servers          |
| `10.0.3.0/24` | Private subnet: databases                    |

Each subnet has its own range and can be configured with different routing and security rules. You might place an internet-facing load balancer in a public subnet, while application servers and databases stay in private subnets.

This makes your network easier to organize and gives you more control over communication between components. For example, the database subnet can accept connections only from the application subnet.

But simply placing resources in separate subnets doesn't secure them. You still need the right routes and security rules.

<h1 id="6-virtual-networks-and-cidr-planning">
  6. Virtual Networks and CIDR Planning
</h1>

In cloud environments, these resources usually live inside a virtual network, such as an AWS **Virtual Private Cloud**, or **VPC**. Azure calls it a Virtual Network (VNet), and Google Cloud also calls it a VPC.

When you create a VPC, you assign it a CIDR block, such as `10.0.0.0/16`, and divide that space into subnets based on your workloads. A public subnet can contain an internet-facing load balancer. Private subnets can hold application servers and databases.

In AWS, a public subnet has a route to an **internet gateway**. A private subnet doesn't provide that direct route to the internet. The difference shows up in each subnet's route table:

```plaintext
Public subnet route table
Destination        Target
10.0.0.0/16        local
0.0.0.0/0          internet gateway

Private subnet route table
Destination        Target
10.0.0.0/16        local
0.0.0.0/0          NAT gateway
```

Routing tables, NAT gateways, and security rules determine how resources communicate and which connections are permitted.

Choosing address ranges carefully matters. Two mistakes are especially expensive to fix later:

- **Overlapping ranges** make it difficult to connect networks later. If two VPCs both use `10.0.0.0/16`, routing between them through peering or a VPN becomes difficult, because the same address could exist on both sides.
- **Subnets that are too small** can run out of IP addresses as your system scales. Kubernetes clusters are a common cause, since pods can consume addresses much faster than expected.

A few habits help:

- Avoid using the same default range for every VPC.
- Reserve space for future environments and regions.
- Check existing corporate, VPN, partner, and data-center ranges before choosing cloud CIDRs.
- Size subnets for growth, not just for the servers you have today.

<h1 id="7-public-and-private-ip-addresses">
  7. Public and Private IP Addresses
</h1>

Another important distinction is between public and private IP addresses.

A **public IP address** can be routed over the internet. Public address space is coordinated through regional registries, ISPs, and cloud providers, so unrelated networks don't use the same public ranges.

A **private IP address** is used within internal networks and cannot be routed directly over the public internet. IPv4 defines three main ranges of private IP addresses:

| Range                              | CIDR             | Address Count | Common Use                           |
| ---------------------------------- | ---------------- | ------------- | ------------------------------------ |
| `10.0.0.0` to `10.255.255.255`     | `10.0.0.0/8`     | 16,777,216    | Cloud VPCs, large corporate networks |
| `172.16.0.0` to `172.31.255.255`   | `172.16.0.0/12`  | 1,048,576     | Enterprise networks, containers      |
| `192.168.0.0` to `192.168.255.255` | `192.168.0.0/16` | 65,536        | Home networks, small offices         |

These ranges are defined in RFC 1918. Private addresses only need to be unique inside the network where they are used. Your laptop and your neighbor's laptop can both be `192.168.1.10` because those addresses live behind different routers.

In a typical application, users send requests to a public-facing load balancer, which forwards them to application servers using private IP addresses. These servers then communicate with a database over the private network.

This setup allows your application servers and database to remain private, without exposing them directly to the internet.

Keep in mind that a public IP only means an address is reachable. Whether it is safe still depends on firewall rules, authentication, and the application itself.

But what happens when an application server needs to call an external API or download a software update? Since its private IP address cannot be routed over the public internet, it needs a way to communicate with external services.

That's where Network Address Translation, or NAT, comes in.

<h1 id="8-network-address-translation-nat">
  8. Network Address Translation (NAT)
</h1>

**NAT** stands for **Network Address Translation**. It allows devices with private IPv4 addresses to communicate with services on the public internet without needing their own public IP addresses.

Imagine three application servers, each with a different private IP address. When one of these servers sends a request to an external service, the packet first passes through a NAT device.

1. The NAT device replaces the private source IP address with its public IP address before forwarding the packet.
2. It typically also changes the source port, allowing multiple internal servers to share the same public IP address while keeping their connections separate.
3. When a response comes back, the NAT device uses its translation records to identify which internal server made the request and forwards the response to the correct destination.

The translation records might look like this:

| Private Source    | Public Source        |
| ----------------- | -------------------- |
| `10.0.2.10:51000` | `203.0.113.20:40000` |
| `10.0.2.11:51000` | `203.0.113.20:40001` |
| `10.0.2.12:52010` | `203.0.113.20:40002` |

When a reply arrives at `203.0.113.20:40001`, the NAT device looks up that port and sends the reply to `10.0.2.11`.

In cloud environments, **NAT gateways** are commonly used for this purpose. They allow private servers to access external APIs, download software updates, and communicate with internet services without assigning a public IP address to each server.

NAT also helps conserve the limited IPv4 address space. It is one of the main reasons IPv4 is still usable today. The same idea lets a home router put a phone, a laptop, and a TV behind one public address.

However, NAT itself is not a security mechanism. We still need proper firewall rules and network policies to control which connections are allowed.

NAT also adds some operational concerns:

- Inbound connections to a private server need a load balancer, port forwarding, a VPN, or a proxy.
- The translation table is state. It can fill up under heavy connection churn, and a single NAT gateway can run out of source ports when many connections go to the same destination.
- Long-lived idle connections can be dropped when NAT entries time out.
- Many clients can share one public IP, so rate limiting by IP can affect unrelated users.
- NAT gateways become a capacity, cost, and availability dependency for everything in the private subnets.

<h1 id="9-static-and-dynamic-ip-addresses">
  9. Static and Dynamic IP Addresses
</h1>

IP addresses can also be static or dynamic.

A **static IP** stays the same until someone deliberately changes it. That's useful when another service needs a predictable address. For example, a partner API might allow incoming requests only from a list of approved public IPs. In AWS, an Elastic IP is a common way to get one.

A **dynamic IP** is assigned automatically and may change over time. On home and office networks, **DHCP** (Dynamic Host Configuration Protocol) commonly assigns these addresses.

Dynamic addressing is also common in the cloud, where instances are constantly created, replaced, and scaled. A replacement server might receive a completely different IP. Containers and Kubernetes pods change addresses even more often.

That's why we generally avoid hardcoding server IP addresses into applications. Instead, we rely on DNS, load balancers, and service discovery to find services as their underlying machines change.

<h1 id="10-dns-and-ip-addresses">10. DNS and IP Addresses</h1>

Most people don't access websites by typing an IP address. Instead, they use domain names like `api.example.com`.

**DNS**, or the **Domain Name System**, translates these names into IP addresses so clients can find the servers they need to connect to.

```text
$$ dig +short api.example.com
203.0.113.20
```

This also makes it easier to manage services. If a service moves to a different IP address, we can simply update its DNS record instead of changing every client. Clients gradually start using the new address as their cached DNS records expire, which is controlled by each record's TTL (time to live).

In larger systems, a domain name often points to a load balancer rather than an individual server. The load balancer then distributes incoming requests across healthy backend servers.

For communication between internal services, we use a similar concept called **service discovery**. It allows services to find available instances without needing to know their IP addresses in advance. Kubernetes Services, Consul, and AWS Cloud Map are common examples.

Together, DNS, load balancing, and service discovery allow applications to communicate reliably, even as the servers and their IP addresses change behind the scenes.

<h1 id="11-ipv6-addresses">11. IPv6 Addresses</h1>

One of the main reasons **IPv6** was introduced is that IPv4 simply doesn't have enough addresses to support the growing number of devices connected to the internet.

While IPv4 uses 32-bit addresses, IPv6 uses 128-bit addresses, providing a vastly larger address space: about `3.4 × 10^38` addresses.

IPv6 addresses are written in hexadecimal, as eight groups separated by colons:

```plaintext
2001:0db8:85a3:0000:0000:8a2e:0370:7334
```

To make them shorter and easier to read, two rules apply:

- Leading zeros in a group can be dropped, so `0db8` becomes `db8`.
- One run of consecutive zero groups can be compressed using a double colon (`::`).

The address above can be written as:

```plaintext
2001:db8:85a3::8a2e:370:7334
```

With so many addresses available, IPv6 greatly reduces the need for NAT just to conserve IP addresses. Every device can have a globally unique address. Firewalls are still needed to decide which of those devices can be reached.

Today, IPv4 and IPv6 continue to coexist. Many networks and services support both, which is called **dual-stack**. A dual-stack service publishes an `A` record for its IPv4 address and an `AAAA` record for its IPv6 address. Which version gets used depends on the client's network connectivity and the service's configuration. Clients usually try IPv6 when it is available and fall back to IPv4.

Running both means firewall rules, load balancers, logs, and monitoring need to handle both address families.

<h1 id="12-common-pitfalls-in-system-design">
  12. Common Pitfalls in System Design
</h1>

A few mistakes come up often when systems depend on IP addresses.

<h3 id="treating-an-ip-as-identity">Treating an IP as Identity</h3>

An IP address can change, be shared through NAT, or belong to a load balancer or proxy instead of one machine. It is a useful signal, but not a reliable user or device identity.

- Rate limiting by public IP can group many unrelated users behind one NAT.
- Allowlisting office IPs breaks when employees work over VPNs or mobile networks.
- Containers and pods often have short-lived addresses.

<h3 id="losing-the-clients-ip">Losing the Client's IP</h3>

Once traffic passes through a load balancer or proxy, the source IP the application sees is often the proxy's address. To keep the original client IP for logs, abuse detection, and rate limiting, proxies pass it along in headers such as `X-Forwarded-For` or through the Proxy Protocol.

Only trust these values when they are set by infrastructure you control. A client can send a fake `X-Forwarded-For` header unless your proxy overwrites it.

<h3 id="special-addresses">Special Addresses</h3>

Some addresses have special meanings that are worth recognizing during debugging:

| Address           | Meaning                                                                     |
| ----------------- | --------------------------------------------------------------------------- |
| `127.0.0.1`       | Loopback. Traffic stays on the same machine (`::1` in IPv6)                 |
| `0.0.0.0`         | As a bind address, listen on all IPv4 interfaces                            |
| `0.0.0.0/0`       | In a route table or firewall rule, any IPv4 address                         |
| `169.254.0.0/16`  | Link-local. A laptop with one of these usually failed to get a DHCP address |
| `169.254.169.254` | Cloud instance metadata endpoint, which can expose credentials              |

A common bug: a service bound to `127.0.0.1` works locally but cannot be reached from another machine. Binding to `0.0.0.0` makes it listen on all interfaces.

<h1 id="summary">Summary</h1>

IP addresses identify network interfaces and let routers forward packets between networks. They describe a network location, not a machine's permanent identity.

CIDR and subnetting help us organize address ranges. The prefix length decides how many bits identify the network, and a longer prefix means a smaller block.

Public and private addressing, routing rules, and NAT determine how resources connect to each other and to the internet. In the cloud, a VPC is split into public and private subnets, and its range should be chosen to avoid overlaps and leave room to grow.

IPv6 removes the address shortage of IPv4, and most services today run both side by side.

And because servers can move, scale, or be replaced, distributed systems usually use DNS, load balancers, and service discovery rather than relying on hardcoded IP addresses. That gives applications stable ways to reach services without tying them to individual machines.
