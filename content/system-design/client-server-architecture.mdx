The key distinction is that the client handles user interactions, while the server typically manages shared data and enforces the application's core business rules.

<h3 id="key-components">Key Components</h3>

- **Client:** The program that starts the conversation, such as a browser, a mobile app, a desktop app, or another backend service.
- **Server:** The program that accepts requests and returns responses. In production, "the server" is often many server processes running behind a load balancer, not one physical machine.
- **Network:** The path between the client and server. It may include DNS, routers, firewalls, and proxies.
- **Protocol:** The agreed format for communication. HTTP, gRPC, WebSocket, SMTP, and database protocols are common examples.

<h1 id="2-the-request-response-cycle">2. The Request-Response Cycle</h1>

Let's see how this communication works when you open a website.

1. **Find the server.** Your browser uses DNS to find the IP address associated with the domain name, such as `mindflare.tech`.
2. **Connect and send a request.** It establishes a network connection and sends an HTTP request to the server, asking for the website's home page.
3. **Process the request.** The server receives the request and processes it. Depending on the application, it might query a database, execute business logic, or generate an HTML page.
4. **Send a response.** Once processing is complete, the server sends back an HTTP response containing a status code, such as `200` for success or `404` for a missing resource, along with the requested content.
5. **Display the result.** The browser processes the response and displays the page.

This request-response cycle is the foundation of most client-server communication.

> - **DNS:** Helps the client find the server for a name such as `mindflare.tech`.
> - **HTTP/HTTPS:** The main protocol used by websites and many APIs. HTTPS adds encryption.
> - **TCP:** A transport protocol that delivers bytes reliably and in order.
> - **TLS:** Encrypts traffic and helps the client verify that it is talking to the right server.
> - **Ports:** Identify which application should receive traffic on a machine. HTTPS usually uses port `443`.

<h1 id="3-what-the-client-does">3. What the Client Does</h1>

Now let's look at what each side is responsible for, starting with the client.

The client's main responsibility is handling user interactions. It displays the interface, collects input, sends requests to the server, and presents the responses. For example, when you enter something into a search box, the client sends your query to the server and displays the results when they come back.

Clients can take different forms:

- A web browser is a client.
- A mobile application is a client.
- A backend service can also act as a client when it communicates with another service.

So a client isn't necessarily a device with a user interface. It's simply the program making a request.

<h1 id="4-what-the-server-does">4. What the Server Does</h1>

The server handles incoming requests and typically performs work that needs to happen centrally. This includes managing data, executing business logic, authenticating users, and checking permissions. For example, an e-commerce server might calculate an order total, verify inventory, and process a purchase.

Servers usually listen for incoming connections on specific network ports. An HTTPS server, for instance, commonly uses port `443`.

<h3 id="never-trust-the-client">Never Trust the Client</h3>

One important principle is that the server should never blindly trust the client.

Suppose an e-commerce application calculates a product's price on the client and sends that amount to the server. A malicious user could modify the request and change the price of a laptop to $1. If the server accepts that number, the user gets the laptop for $1.

> A safer checkout request sends only what the user chose, such as `{ "productId": "laptop-15", "quantity": 1 }`. The server looks up the current price itself, applies any discounts it knows are valid, and calculates the total. Any price the client sends is ignored.

That's why the server must independently verify prices, validate inputs, and enforce permissions. The client can perform validation too, especially to provide immediate feedback, like showing that an email address is missing an `@`. But the server must enforce the rules that matter for security and data integrity.

<h1 id="5-why-centralize-on-the-server">5. Why Centralize on the Server</h1>

Keeping shared data and business logic on the server provides several advantages.

<h3 id="a-central-source-of-truth">A Central Source of Truth</h3>

Instead of maintaining independent copies, clients access the same underlying data. This makes it easier to keep information consistent across devices. The to-do list from the introduction shows the same tasks on your phone, laptop, and your teammate's computer because they all read from one place.

<h3 id="better-security-control">Better Security Control</h3>

Sensitive operations and authoritative data can remain on infrastructure you manage rather than relying on users' devices. A mobile app should never contain a database password or a private API key, because anything shipped to a user's device can eventually be extracted. The client talks to your backend, and your backend talks to protected systems.

<h3 id="easier-maintenance-and-updates">Easier Maintenance and Updates</h3>

Suppose you discover a bug in your application's pricing logic. If that logic runs on the server, you can fix and deploy it centrally. Every client benefits without needing to install a new version. This becomes especially valuable when you have millions of users.

The same goes for other server-side changes, such as adding fraud checks or improving search ranking. As long as the API contract stays compatible, old clients keep working.

<h1 id="6-thin-clients-and-thick-clients">6. Thin Clients and Thick Clients</h1>

Not every application divides responsibilities between clients and servers the same way.

A **thin client** performs relatively little processing locally. It mainly displays information from the server and forwards user actions back for processing. A traditional server-rendered website is a good example: each click asks the server for a new page.

A **thick client**, also called a fat client, handles more processing locally. A modern single-page web application might manage complex interface logic and update the screen without contacting the server. A video editing application is another example, since much of its processing happens on the user's device.

Thin clients are generally easier to maintain centrally because more logic lives on the server. Thick clients can feel faster and more responsive because many operations don't require a network round trip. However, they introduce more client-side complexity, especially when keeping data and business rules synchronized with the server.

Most applications use a combination of both approaches. Even a thick client should leave the final decision on important rules, like prices and permissions, to the server.

<h1 id="7-who-starts-the-conversation">7. Who Starts the Conversation?</h1>

In a typical client-server interaction, the client sends a request, and the server responds. But what happens when the server has new information that the client needs immediately?

Consider a messaging application. When someone sends you a message, the server receives it. But with basic HTTP request-response communication, your application won't receive it until it makes another request.

<h3 id="polling">Polling</h3>

One solution is **polling**. The client periodically asks the server whether any new messages are available, for example every few seconds.

The problem is that most requests might return nothing, wasting bandwidth and server resources. And a new message can still wait up to one full polling interval before the client sees it.

<h3 id="websockets">WebSockets</h3>

For real-time applications, a better option is often **WebSockets**. With WebSockets, the client establishes a persistent connection to the server. Once connected, both sides can send messages whenever needed. This allows the server to deliver new messages immediately without waiting for another request.

Note that the client still opens the WebSocket connection. The model is still client-server. What changes is that, once the connection is open, the server no longer has to wait for a request before sending data.

<h1 id="8-stateless-and-stateful-servers">8. Stateless and Stateful Servers</h1>

Another important design decision is whether the server maintains client-specific information between requests.

- A **stateless server** processes each request independently. Every request contains the information needed to handle it, such as authentication credentials and request parameters.
- A **stateful server** maintains information between requests. For example, it might store a user's session or shopping cart directly in memory.

The challenge becomes clear when you have multiple servers. If a user's session is stored on server one, subsequent requests may need to reach that same server. Otherwise, the session information won't be available. This makes distributing traffic more complicated, and if server one crashes, the session is lost.

With stateless application servers, any instance can process a request as long as it can access the required shared data. That's why many production systems keep application servers stateless and store shared session data in an external database or distributed cache like Redis.

<h1 id="9-tiers-in-client-server-architecture">
  9. Tiers in Client-Server Architecture
</h1>

Client-server systems can also be organized into multiple **tiers**. A tier is a layer with a clear job. Some tiers are separate deployable services. Others are logical layers inside the same system. The point is to separate responsibilities so the system is easier to secure, change, and scale.

<h3 id="1-tier-architecture">1-Tier Architecture</h3>

Before looking at client-server tiers, it helps to see the starting point. In **1-tier architecture**, the user interface, business logic, and data storage all live together on one machine. There is no remote server involved. The to-do list running on a single computer is a 1-tier application, and so is a local spreadsheet or a single-user desktop accounting tool.

<h3 id="2-tier-architecture">2-Tier Architecture</h3>

In a **2-tier architecture**, the client communicates directly with a server, which might be a database server. A common example is an internal desktop app that connects straight to a central PostgreSQL or SQL Server database.

This can work for smaller applications, but it creates challenges around security, maintenance, and business logic. Each client needs database credentials, business rules end up inside every copy of the client, and a schema change can break clients that are already installed.

<h3 id="3-tier-architecture">3-Tier Architecture</h3>

A more common approach in modern web applications is **3-tier architecture**. Here, the system is divided into three parts:

- **Presentation tier:** Handles the user interface. This is the browser, mobile app, or desktop UI.
- **Application tier:** Processes requests and executes business logic. It also checks who the user is and what they are allowed to do.
- **Data tier:** Stores and manages application data in databases, caches, and object storage.

> When a user opens their order history, the client contacts the application server. The server checks that the user is signed in, retrieves that user's orders from the database, and returns them. The client doesn't need direct database access.

This separation makes each tier easier to secure, maintain, and scale independently.

<h3 id="n-tier-architecture">N-Tier Architecture</h3>

Larger systems may introduce additional layers and components, resulting in what's called **n-tier architecture**. Teams usually add these layers when the system needs more scale, security, or independent ownership.

Common additions include:

- **Edge layer:** CDN, web application firewall, or reverse proxy.
- **API layer:** API gateway or backend-for-frontend.
- **Application services:** Separate services for orders, payments, users, or search.
- **Background processing:** Queues, event streams, and workers for slow tasks like sending emails or generating reports.

<h1 id="10-the-server-as-a-single-point-of-failure">
  10. The Server as a Single Point of Failure
</h1>

One downside of relying on a central server is that it can become a single point of failure.

Suppose a food delivery application runs on one server. If that server crashes during peak dinner hours, customers may be unable to place orders until it's restored.

To reduce this risk, production systems introduce redundancy:

- **Application servers:** Instead of one application server, we run multiple instances behind a load balancer. The load balancer sends traffic only to healthy instances, so one crash doesn't take the application down.
- **Databases:** We can maintain replicas and configure failover so another instance can take over if the primary fails.
- **Other shared components:** Caches, load balancers, and queues also need redundancy, or they become the new single point of failure.

The architecture is still client-server, but the server side now consists of multiple machines working together. From the client's perspective, it still communicates with a single logical service.

<h1 id="11-network-latency-and-dependency">
  11. Network Latency and Dependency
</h1>

Another limitation is that clients and servers communicate over a network. Every request takes time to reach the server, get processed, and return.

For example, a user in India accessing a server in the United States might experience hundreds of milliseconds of network round-trip latency. If an application makes several sequential requests, those delays add up. Five sequential requests at 250 ms each means the user waits more than a second before the screen is ready.

Connectivity is another concern. If a user loses their internet connection, a client that depends entirely on the server may stop working.

Applications address these problems in several ways:

- **Local caching:** The client stores data it has already loaded, so users can still view previously loaded content offline.
- **CDNs:** Content delivery networks serve static assets such as images, scripts, and stylesheets from locations closer to users, which reduces network latency.
- **Fewer round trips:** A well-designed API lets the client fetch what a screen needs in one or two requests instead of many.

<h1 id="12-security-in-client-server-systems">
  12. Security in Client-Server Systems
</h1>

Security is especially important because the client and server operate across a **trust boundary**. Anything running on the client's device can potentially be inspected or modified. So the server must treat incoming requests as untrusted, even when they come from an official application.

The server applies several checks to each request:

1. **Authentication:** It identifies the user, often using a session cookie or authentication token.
2. **Authorization:** It checks that the user has permission to access the requested data or perform the action. Being signed in doesn't mean you can view someone else's orders.
3. **Input validation:** It validates incoming inputs, regardless of whether the client already performed validation.
4. **Encryption in transit:** Communication should use HTTPS to protect data from interception or modification in transit.

A client can hide a button in the UI, but only the server can reliably prevent the action. Keeping sensitive operations on the server allows these security controls to be enforced centrally.

<h1 id="13-where-you-see-client-server">13. Where You See Client-Server</h1>

Once you understand client-server architecture, you'll notice it throughout modern software systems.

- **Websites:** When you visit a website, your browser is the client, and the web server processes its requests.
- **Databases:** When an application queries PostgreSQL or MySQL, the application acts as the client, and the database acts as the server.
- **Email:** Email apps like Gmail, Outlook, and Apple Mail are clients that connect to mail servers to send and sync messages.
- **Backend services:** The same pattern appears inside distributed backend systems.

For example, an order service might call a payment service, which then contacts a fraud detection service. Here, the payment service acts as a server when handling requests from the order service, and as a client when calling the fraud detection service.

So client and server aren't fixed labels for particular machines or programs. They describe the roles components play during communication.

<h1 id="14-trade-offs-and-when-it-fits">14. Trade-offs and When It Fits</h1>

Client-server architecture works well when an application needs centralized data management, shared business logic, and consistent access control. It makes supporting multiple users and devices easier while keeping important operations under central control.

But there are trade-offs:

- **Scaling:** The server side can become a bottleneck as traffic grows, requiring additional infrastructure to scale.
- **Availability:** Centralized components can become single points of failure unless redundancy and failover are in place.
- **Network dependency:** Because clients communicate over a network, performance and availability depend partly on network latency and connectivity.

Despite these challenges, client-server remains the foundation of most modern applications. Architectural approaches like monoliths, microservices, and serverless often build on the same underlying model. The main difference is how server-side responsibilities are organized, deployed, and scaled.

<h1 id="summary">Summary</h1>

- Client-server architecture divides responsibilities between clients, which send requests, and servers, which process them and return responses.
- The client handles user interactions. The server manages shared data, executes business logic, and enforces permissions.
- The server should never trust the client. It must verify prices, validate inputs, and check permissions on its own.
- Centralizing on the server gives you one source of truth, better security control, and easier updates.
- Thin clients keep most logic on the server. Thick clients do more on the device. Most applications mix both.
- When the server needs to send data first, polling works but wastes requests. WebSockets keep a connection open so the server can push updates.
- Stateless application servers with an external session store make it easy to run many servers behind a load balancer.
- 3-tier architecture (presentation, application, data) is the common baseline for web applications. Larger systems grow into n-tier designs.
- The main limitations are single points of failure, network latency, and the trust boundary. Redundancy, caching, CDNs, and server-side security checks address them.
- Client and server are roles, not machines. The same service can be a server for one call and a client for the next.
