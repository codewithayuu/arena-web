The direct approach is to build all of this into every application. But that creates several problems.

- Our services are written in Java, Go, Python, and Node.js, so each capability may need to be implemented in four different languages.
- If the logging system changes, every team may need to update its code and redeploy.
- Some applications may be legacy systems or third-party software whose code we cannot easily modify.

What we need is a way to add these capabilities without putting them directly inside every application.

<h1 id="2-what-is-the-sidecar-pattern">2. What Is the Sidecar Pattern?</h1>

The Sidecar pattern solves this by running a separate helper process next to the main application.

The name comes from a motorcycle sidecar. It is attached to the motorcycle, travels wherever it goes, and adds extra functionality while remaining a separate unit.

The software version follows the same idea. The main application focuses on business logic, while the sidecar handles a supporting task, such as shipping logs, managing secrets, or proxying network traffic.

They run as separate processes, often in separate containers, but are deployed together on the same machine and share the same lifecycle. When an application instance starts, its sidecar starts with it. When that instance is removed, the sidecar is removed too. So every application instance gets its own sidecar.

Because the sidecar is a separate program, it can be written in a different language from the application and released on its own schedule. A sidecar written once can serve every service, whatever language that service uses.
