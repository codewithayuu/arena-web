From the destination server's point of view, the request appears to come from the proxy, not directly from the original client.

<h3 id="proxy-vs-vpn">Proxy vs VPN</h3>

A proxy is not the same thing as a VPN.

> No. Both can hide the client's IP address, but a VPN typically creates an encrypted tunnel for broader network traffic, while a proxy usually forwards traffic for specific protocols or applications.

<h1 id="2-why-use-a-forward-proxy">2. Why Use a Forward Proxy</h1>

So why would you put a forward proxy between clients and the internet? There are a few common reasons.

<h3 id="privacy">Privacy</h3>

Since the destination server sees the proxy's IP address, the client's network address is not directly exposed to that server.

Hiding an IP address is not the same as anonymity, though. The proxy operator can still log who connects and where, and the destination site can still recognize you through cookies, logins, or browser fingerprints.

<h3 id="access-control">Access Control</h3>

Organizations can use a forward proxy to block certain websites or restrict which external services employees can access.

<h3 id="monitoring-and-logging">Monitoring and Logging</h3>

Because outbound traffic passes through the proxy, the organization can track requests and enforce security policies.

<h3 id="caching">Caching</h3>

If many users request the same resource, the proxy may cache the response and serve it directly, reducing bandwidth usage and latency.

<h3 id="access-through-another-network">Access Through Another Network</h3>

A forward proxy can provide access through another network or location when direct access is restricted.

So forward proxies are mainly about controlling and managing outbound traffic from clients.

<h1 id="3-how-a-reverse-proxy-works">3. How a Reverse Proxy Works</h1>

A **reverse proxy** sits in front of backend servers and acts on their behalf.

The client sends its request to the reverse proxy, often without even knowing that a proxy is involved. The reverse proxy then decides which backend server should handle the request, forwards it, receives the response, and sends that response back to the client.

Request flow:

1. The client sends its request to the reverse proxy.
2. The reverse proxy decides which backend server should handle the request.
3. It forwards the request to that server.
4. The backend server sends its response to the reverse proxy.
5. The reverse proxy sends that response back to the client.

From the client's point of view, it is simply talking to one endpoint. It doesn't need to know which backend server handled the request.

This gives you a single entry point in front of many backend servers, while keeping the internal architecture hidden from the client.

<h1 id="4-why-use-a-reverse-proxy">4. Why Use a Reverse Proxy</h1>

So why put a reverse proxy in front of your backend servers?

<h3 id="traffic-management">Traffic Management</h3>

The biggest reason is traffic management. A reverse proxy can distribute incoming requests across multiple backend servers, helping the system handle more traffic and avoid overloading a single server.

<h3 id="tls-termination">TLS Termination</h3>

Instead of every backend server managing HTTPS certificates and encryption, the reverse proxy can handle that in one place.

<h3 id="caching">Caching</h3>

If the same response is requested frequently, the reverse proxy can serve a cached copy without sending every request to the backend.

Be careful with personalized responses. A cached copy of one user's data must never be served to another user.

<h3 id="security-and-access-control">Security and Access Control</h3>

A reverse proxy can provide security and access control by hiding backend servers from direct public access, enforcing rate limits, filtering requests, and applying authentication rules.

<h3 id="request-routing">Request Routing</h3>

In systems with multiple services, a reverse proxy can perform request routing. For example, requests to `/users` can go to the User Service, while `/payments` goes to the Payment Service.

<h1 id="5-reverse-proxy-vs-load-balancer">5. Reverse Proxy vs Load Balancer</h1>

A reverse proxy and a load balancer are closely related, but they're not exactly the same thing.

A **load balancer** has one primary job: distribute incoming traffic across multiple backend servers.

A **reverse proxy** is a broader concept. It also sits in front of backend servers, but it can do much more than distribute traffic.

Many reverse proxies, such as NGINX, HAProxy, and Envoy, can also act as load balancers.

So a simple way to think about it: **load balancing is one capability a reverse proxy can provide**, but a reverse proxy can handle many other responsibilities as well.

<h1 id="6-common-reverse-proxy-technologies">
  6. Common Reverse Proxy Technologies
</h1>

There are several popular technologies that can act as reverse proxies.

| Technology             | Known For                                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| NGINX                  | One of the most widely used. Reverse proxying, load balancing, caching, TLS termination, and static content |
| HAProxy                | High-performance load balancing and proxying at both Layer 4 and Layer 7                                    |
| Envoy                  | Cloud-native and microservices architectures. Advanced routing, observability, retries, circuit breaking    |
| Managed cloud services | Load balancers and gateways run by the cloud platform that perform similar roles                            |

A Layer 4 proxy forwards TCP or UDP connections without reading what is inside them. A Layer 7 proxy understands the application protocol, usually HTTP, so it can make decisions using paths, headers, or hostnames.

Envoy also handles service-to-service communication, which is why it often runs next to every service in a microservices system.

So in practice, you may not always deploy something explicitly called a "reverse proxy." A load balancer, API gateway, ingress controller, or CDN may already be performing reverse proxy behavior as part of the architecture.

<h1 id="7-nginx-reverse-proxy-example">7. NGINX Reverse Proxy Example</h1>

Here is a small NGINX reverse proxy for an HTTP backend.

<h3 id="install-and-reload">Install and Reload</h3>

Start by installing NGINX, checking that the config is valid, and reloading the service.

```text
sudo apt update
sudo apt install nginx
sudo nginx -t
sudo systemctl reload nginx
```

<h3 id="basic-reverse-proxy">Basic Reverse Proxy</h3>

This server block sends every request to one backend and sets headers that help the backend understand the original client request.

```plaintext
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://backend1.internal.example.com:8080;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID $request_id;

        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
        proxy_send_timeout 30s;
    }
}
```

<h3 id="load-balancing-across-backends">Load Balancing Across Backends</h3>

Adding an `upstream` block lets one proxy spread traffic across several backends. The failure settings help NGINX stop sending traffic to a server that is repeatedly failing.

```plaintext
upstream backend_app {
    least_conn;

    server backend1.internal.example.com:8080 max_fails=3 fail_timeout=10s;
    server backend2.internal.example.com:8080 max_fails=3 fail_timeout=10s;
    server backend3.internal.example.com:8080 max_fails=3 fail_timeout=10s;

    keepalive 64;
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://backend_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

NGINX uses round robin by default, which means it cycles through the backend servers. `least_conn` is useful when some requests take longer than others because it sends new requests to the server with the fewest active connections.

Sticky routing is possible, but use it carefully. It can hide the fact that the backend depends on local server state.

This example is intentionally small. Production configs also need HTTPS, access logs, request size limits, buffering choices, health checks or failure policy, compression, security headers, and timeouts that match the application.

<h1 id="summary">Summary</h1>

The key idea is simple: a forward proxy represents the client, while a reverse proxy represents the server.

| Aspect            | Forward Proxy                                                                | Reverse Proxy                                                   |
| ----------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Acts on behalf of | Clients                                                                      | Backend servers                                                 |
| Sits between      | Clients and the internet                                                     | Clients and backend servers                                     |
| Traffic           | Outbound, leaving a client network                                           | Inbound, entering a service                                     |
| Hides             | The client from the destination server                                       | The backend servers from the client                             |
| Common uses       | Privacy, access control, monitoring, caching, access through another network | Traffic management, TLS termination, caching, security, routing |
| Examples          | Company outbound proxy, Squid                                                | NGINX, HAProxy, Envoy, CDN, API gateway, ingress controller     |

A forward proxy controls and manages outbound traffic from clients.

A reverse proxy gives many backend servers a single entry point, and load balancing is only one of the jobs it can take on.
