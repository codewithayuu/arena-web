This design creates three problems.

<h3 id="the-client-knows-too-much-and-calls-too-often">
  The Client Knows Too Much and Calls Too Often
</h3>

The client has to know the address of every service it talks to. It also has to make several network calls over a mobile connection, where each round trip can be slow.

| Product Page Dependency | Service         | Example Latency on Mobile |
| ----------------------- | --------------- | ------------------------- |
| Product details         | Product service | 150 ms                    |
| Reviews                 | Review service  | 180 ms                    |
| Saved addresses         | User service    | 130 ms                    |

If these calls run one after another, the page waits for all of them. If they run in parallel, the page still waits for the slowest one, and the client has to handle retries, timeouts, and the case where one call fails and the others succeed.

<h3 id="every-service-repeats-the-same-work">
  Every Service Repeats the Same Work
</h3>

Every service now has to handle the same concerns on its own, such as checking whether the user is logged in, enforcing rate limits, and logging requests.

| Concern              | Problem When Every Service Is Exposed               |
| -------------------- | --------------------------------------------------- |
| Authentication       | Each service validates external tokens separately   |
| Rate limiting        | Limits are inconsistent across endpoints            |
| TLS and certificates | Every service manages its own public certificates   |
| CORS                 | Browser policy is configured in many places         |
| Request logging      | Logs use different fields, formats, and request IDs |

Duplicated code also means a higher chance that one service gets it wrong. Since the public boundary is also the first security boundary, a single inconsistent service is enough to open a gap.

<h3 id="the-backend-structure-leaks-to-clients">
  The Backend Structure Leaks to Clients
</h3>

Suppose we later split the product service into two smaller services, one for the catalog and one for pricing. Every client that calls the product service directly may need to change.

So the internal structure of the backend leaks out to the clients. Mobile apps make this worse, because old app versions can stay installed for months after a new release.

This is the problem the API Gateway pattern solves.
