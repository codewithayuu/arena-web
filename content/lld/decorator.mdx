<LessonCard>

> TheÂ **Decorator Design Pattern**Â is aÂ **structural pattern**Â that lets youÂ **dynamically add new behavior or responsibilities to objects**Â without modifying their underlying code.

Itâs particularly useful in situations where:

- You want toÂ **extend the functionality**Â of a class without subclassing it.
- You need toÂ **compose behaviors at runtime**, in various combinations.
- You want to avoid bloated classes filled withÂ `if-else`Â logic for optional features.

Letâs walk through a real-world example to see how we can apply the Decorator Pattern to build aÂ **modular, flexible, and easily composable system**Â for enhancing object functionality.

<h1 id="1-the-problem-adding-features-to-a-text-renderer">
  1. The Problem: Adding Features to a Text Renderer
</h1>

Imagine you are building a rich text rendering system, something like a simplified word processor or a markdown preview tool. At the core of your system is aÂ `TextView`Â component that renders plain text on screen.

The first version works great. Then the requirements start growing:

- SupportÂ **bold**Â text
- SupportÂ **italic**Â text
- SupportÂ **underlined**Â text
- Support anyÂ **combination**Â of the above (bold + italic, bold + underline, italic + underline, all three together)

<h3 id="the-naive-approach-subclassing-for-every-combination">
  The Naive Approach: Subclassing for Every Combination
</h3>

Your first instinct might be to create a subclass for each variation:

The red nodes are combination subclasses that only exist because inheritance cannot mix and match behaviors.

With just 3 features (bold, italic, underline), you already need 7 subclasses to cover every possible combination. Add a 4th feature like highlight, and that jumps to 15. A 5th feature (strikethrough) brings it to 31. The formula isÂ **2^n - 1**, where n is the number of features.

<h3 id="whats-wrong-with-this-approach">What's Wrong with This Approach?</h3>

While this code works for a small number of features, it collapses under its own weight as the system grows:

<h4 id="1-class-explosion">1. Class Explosion</h4>

For every new combination of features, you need a new subclass. The number of subclasses grows exponentially: n features produce 2^n - 1 combinations. With 5 formatting options (bold, italic, underline, highlight, strikethrough), that is 31 subclasses, most of which are just recombinations of the same logic.

<h4 id="2-rigid-design">2. Rigid Design</h4>

You cannot change features at runtime. Want to let the user toggle bold on and off based on a preference? You need to swap the entire object with a different subclass. There is no way to add or remove a single behavior dynamically.

<h4 id="3-violates-the-openclosed-principle">
  3. Violates the Open/Closed Principle
</h4>

Every time a new feature likeÂ `highlight`Â orÂ `shadow`Â is introduced, you need to create new subclasses for every existing combination that includes the new feature. Existing classes stay untouched, but the number of new classes you must add grows with every feature.

<h4 id="4-code-duplication">4. Code Duplication</h4>

The bold logic is duplicated acrossÂ `BoldTextView`,Â `BoldItalicTextView`,Â `BoldUnderlineTextView`, and every other class that includes bold. If you change how bold rendering works, you must update every class that includes it.

<h3 id="what-we-really-need">What We Really Need</h3>

We need a way to:

- Add features like bold, italic, underlineÂ **dynamically and independently**
- **Compose features**Â in flexible combinations (e.g., bold + underline, or italic + highlight + underline)
- Avoid creating dozens of subclasses for every possible variation
- Follow theÂ **Open/Closed Principle**: add new features by writing new code, not changing existing code

This is exactly where the **Decorator pattern** fits in.

<h1 id="2-the-decorator-pattern">2. The Decorator Pattern</h1>

The Decorator pattern is a structural pattern that attaches additional responsibilities to an object dynamically. Instead of extending a class through inheritance, it wraps the original object inside another object that adds the new behavior.

Two characteristics define the pattern:

1. **Same interface preservation:**Â Every decorator implements the same interface as the object it wraps. The client cannot tell whether it is talking to a plain object or a decorated one.
2. **Dynamic composition:**Â Decorators can be stacked at runtime in any combination and any order. You choose what to add and when, not at compile time.

This creates aÂ **layered effect**, where decorators can beÂ **stacked**Â to apply multiple enhancements without creating a complex inheritance tree.

> Think of a plain coffee. Now add milk. Now add sugar. Each addition enhances the original but doesnât change the base.
>
> The Decorator Pattern works the same way: stacking behaviors while keeping the core intact.

<h2 id="class-diagram">Class Diagram</h2>

Decorator has four participants.

<h4 id="component-ega-textview">Component (e.g.,Â TextView)</h4>

Declares the common interface that both the core object and all decorators implement.

In our text rendering example,Â `TextView`Â is the Component. It declares a singleÂ `render()`Â method that every participant implements.

<h4 id="concretecomponent-ega-plaintextview">
  ConcreteComponent (e.g.,Â PlainTextView)
</h4>

The base object that can be wrapped with decorators. It provides the default behavior.

In our example,Â `PlainTextView`Â renders raw text with no formatting. It is the starting point that decorators build upon.

<h4 id="decorator-eg-textdecorator">Decorator (e.g, TextDecorator)</h4>

An abstract class that implements the Component interface and holds a reference to another Component. It forwards calls to the wrapped object.

In our example,Â `TextDecorator`Â is the abstract base for all formatting decorators. It accepts anyÂ `TextView`Â in its constructor and delegatesÂ `render()`Â to it.

<h4 id="concretedecorator-bolddecoratora-italicdecorator-etc">
  ConcreteDecorator (BoldDecorator,Â ItalicDecorator, etc.)
</h4>

Extend the base decorator to add new functionality before/after calling the wrapped componentâs method.

In our example,Â `BoldDecorator`Â wraps the output inÂ `<b>`Â tags,Â `ItalicDecorator`Â inÂ `<i>`Â tags, andÂ `UnderlineDecorator`Â inÂ `<u>`Â tags.

<h1 id="3-how-it-works">3. How It Works</h1>

Here is the Decorator workflow, step by step:

<h4 id="step-1-create-the-base-component">Step 1: Create the base component</h4>

The client creates aÂ `PlainTextView`Â with the text "Hello". This is the core object.

<h4 id="step-2-wrap-it-in-a-decorator">Step 2: Wrap it in a decorator</h4>

The client wraps the plain text view inside aÂ `BoldDecorator`. The decorator stores a reference to the plain text view.

<h4 id="step-3-stack-more-decorators">Step 3: Stack more decorators</h4>

The client wraps the bold decorator inside anÂ `ItalicDecorator`, then wraps that inside anÂ `UnderlineDecorator`. Each decorator stores a reference to the previous one.

<h4 id="step-4-call-the-operation">Step 4: Call the operation</h4>

The client callsÂ `render()`Â on the outermost decorator (UnderlineDecorator).

<h4 id="step-5-decorators-add-behavior-and-delegate-inward">
  Step 5: Decorators add behavior and delegate inward
</h4>

UnderlineDecorator printsÂ `<u>`, then callsÂ `render()`Â on its inner object (ItalicDecorator). ItalicDecorator printsÂ `<i>`, then callsÂ `render()`Â on its inner object (BoldDecorator). BoldDecorator printsÂ `<b>`, then callsÂ `render()`Â on its inner object (PlainTextView).

<h4 id="step-6-results-propagate-outward">Step 6: Results propagate outward</h4>

PlainTextView prints "Hello". BoldDecorator printsÂ `</b>`. ItalicDecorator printsÂ `</i>`. UnderlineDecorator printsÂ `</u>`. The final output isÂ `<u><i><b>Hello</b></i></u>`.

<h1 id="4-implementing-decorator-pattern">4. Implementing Decorator Pattern</h1>

Instead of creating a subclass for every combination, we create one class per feature and wrap them around each other. Each decorator adds its behavior and delegates the rest to the next object in the chain.

<h3 id="step-5-using-the-decorator-from-the-client">
  Step 5: Using the Decorator from the Client
</h3>

The client creates the base component and wraps it with any combination of decorators at runtime. No subclass explosion. No hardcoded combinations.

```java
public class TextRendererApp {
    public static void main(String[] args) {
        TextView text = new PlainTextView("Hello, World!");

        // Plain text
        System.out.print("Plain:                   ");
        text.render();
        System.out.println();

        // Single decorator: Bold
        System.out.print("Bold:                    ");
        TextView boldText = new BoldDecorator(text);
        boldText.render();
        System.out.println();

        // Two decorators: Italic + Underline
        System.out.print("Italic + Underline:      ");
        TextView italicUnderline = new UnderlineDecorator(new ItalicDecorator(text));
        italicUnderline.render();
        System.out.println();

        // Three decorators: Bold + Italic + Underline
        System.out.print("Bold + Italic + Underline: ");
        TextView allStyles = new UnderlineDecorator(
            new ItalicDecorator(new BoldDecorator(text)));
        allStyles.render();
        System.out.println();
    }
}
```

<h3 id="what-we-achieved">What We Achieved</h3>

- **Dynamic layering:**Â We can add, remove, or combine decorators at runtime
- **Modular design:**Â Each decorator is focused on one formatting feature
- **No class explosion:**Â 3 features require 5 classes (interface + component + decorator base + 3 decorators), not 8
- **Open/Closed Principle:**Â New formatting options can be added without modifying existing classes
- **Flexible ordering:**Â Any combination and ordering of features is possible
