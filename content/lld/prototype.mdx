<LessonCard>

> TheÂ **Prototype Design Pattern**Â is aÂ **creational design pattern**Â that lets you create new objects byÂ **cloning existing ones**, instead of instantiating them from scratch.

Itâs particularly useful in situations where:

- Creating a new object isÂ **expensive**,Â **time-consuming**, orÂ **resource-intensive**.
- You want to avoid duplicating complex initialization logic.
- You need many similar objects with only slight differences.

The Prototype Pattern allows you to create new instances byÂ **cloning a pre-configured prototype object**, ensuring consistency while reducing boilerplate and complexity.

<h1 id="1-the-challenge-of-cloning-objects">
  1. The Challenge of Cloning Objects
</h1>

Imagine you have an object in your system, and you want to create anÂ **exact copy**Â of it. How would you do it?

Your first instinct might be to:

1. Create aÂ **new object**Â of the same class.
2. **Manually copy**Â each field from the original object to the new one.

Simple enough, right?

Well, **not quite**.

<h3 id="problem-1-encapsulation-gets-in-the-way">
  Problem 1: Encapsulation Gets in the Way
</h3>

This approach assumes that all fields of the object are publicly accessible. But in a well-designed system, many fields areÂ **private**Â andÂ **hidden behind encapsulation**. That means your cloning logic canât access them directly.

Unless you break encapsulation (which defeats the purpose of object-oriented design), you canât reliably copy the object this way.

<h3 id="problem-2-class-level-dependency">Problem 2: Class-Level Dependency</h3>

Even if you could access all the fields, you'd still need toÂ **know the concrete class**Â of the object to instantiate a copy.

This tightly couples your cloning logic to the object's class, which introduces problems:

- It violates theÂ **Open/Closed Principle**.
- It reduces flexibility if the object's implementation changes.
- It becomes harder to scale when you work with polymorphism.

<h3 id="problem-3-interface-only-contexts">
  Problem 3: Interface-Only Contexts
</h3>

In many cases, your code doesnât work with concrete classes at all, it works withÂ **interfaces**.

For example:

```java
public void processClone(Shape shape) {
    Shape cloned = ???; // we only know it implements Shape
}
```

Here, you know the object implements a certain interface (`Shape`), but youÂ **donât know what class it is**, let alone how to create a new instance of it. Youâre stuck unless the object knows how to clone itself.

<h3 id="the-better-way-let-the-object-clone-itself">
  The Better Way: Let the Object Clone Itself
</h3>

This is where theÂ **Prototype Design Pattern**Â comes in.

Instead of having external code copy or recreate the object, the object itselfÂ **knows how to create its clone**. It exposes aÂ `clone()`Â orÂ `copy()`Â method that returns a new instance with the same data.

This:

- Preserves encapsulation
- Eliminates the need to know the concrete class
- Makes the system more flexible and extensible

> This is the most important concept to understand when implementing Prototype. Getting it wrong produces bugs that are subtle, intermittent, and painful to debug.
>
> A shallow copy duplicates the object itself but shares references to any objects it contains. Primitive fields (int, double, boolean) get copied by value. Reference fields (lists, maps, other objects) get copied by reference, meaning both the original and the clone point to the same underlying object.
>
> A deep copy duplicates everything: the object, all objects it references, all objects those reference, and so on recursively. The clone is completely independent.
>
> This is what Prototype implementations should do when the object contains mutable reference types.

Letâs walk through a real-world example to see how we can apply the Prototype Pattern to build a moreÂ **efficient**Â andÂ **maintainable**Â object creation workflow.

<h1 id="2-the-problem-spawning-enemies-in-a-game">
  2. The Problem: Spawning Enemies in a Game
</h1>

Letâs say youâre developing a 2D shooting game where enemies appear frequently throughout the gameplay.

You have several enemy types with distinct attributes:

- **BasicEnemy**: Low health, slow speed. Used in early levels.
- **ArmoredEnemy**: High health, medium speed. Harder to defeat, appears later.
- **FlyingEnemy**: Medium health, fast speed. Harder to hit, used for surprise attacks.

Each enemy type comes with predefined properties such as:

- **Health**Â (how much damage they can take)
- **Speed**Â (how quickly they move across the screen)
- **Armor**Â (whether they take reduced damage)
- **Weapon type**Â (e.g., laser, cannon, missile)
- **Sprite or appearance**Â (the visual representation)

Now, imagine you need to spawn aÂ `FlyingEnemy`. You might write code like this:

```java
Enemy flying1 = new Enemy("Flying", 100, 10.5, false, "Laser");
Enemy flying2 = new Enemy("Flying", 100, 10.5, false, "Laser");
```

And youâll do the same for dozens, maybe hundreds, of similar enemies during the game.

<h4 id="but-hereas-the-problem">But Hereâs the Problem</h4>

- **Repetitive Code**: Youâre duplicating the same instantiation logic again and again.
- **Scattered Defaults**: If the default speed or weapon ofÂ `FlyingEnemy`Â changes, you need to update it inÂ **every single place**Â you created one.
- **Error-Prone**: Forget to set one property? Use a wrong value? Bugs will creep in silently.
- **Cluttered Codebase**: Your main game loop or spawn logic becomes bloated with object construction details.

As your game scales (adding more enemy types, behaviors, or configurations) this naive approach quickly becomesÂ **hard to manage and maintain**.

You need a clean, centralized, and reusable way to create enemy instances with consistent defaults while allowing minor tweaks.

To avoid repetitive instantiation and duplicated setup logic, we turn to theÂ **Prototype Design Pattern.**

<h1 id="3-the-prototype-design-pattern">3. The Prototype Design Pattern</h1>

Instead of configuring every new object line-by-line, we define aÂ **pre-configured prototype**Â and simplyÂ **clone**Â it whenever we need a new instance.

Two ideas define the pattern:

1. **Self-cloning:**Â The object itself knows how to create a copy of itself. No external code needs to understand its internal structure.
2. **Decoupled creation:**Â The client does not need to know the concrete class of the object it is cloning. It works through a common interface with aÂ `clone()`Â method.

<h2 id="class-diagram">Class Diagram</h2>

Prototype has four participants, three required and one optional:

<h4 id="1-prototype-interface">1. Prototype (Interface)</h4>

- Declares theÂ `clone()`Â method that all cloneable objects must implement
- Defines the contract for self-cloning and allows clients to clone objects without knowing their concrete class

<h4 id="2-concreteprototype">2. ConcretePrototype</h4>

- Implements theÂ `clone()`Â method to produce a copy of itself
- Copies all fields to the new instance (shallow or deep, depending on the fields)

<h4 id="3-client">3. Client</h4>

- Creates new objects by asking a prototype to clone itself
- Holds a reference to a prototype instance and calls `clone()`Â when a new object is needed
- Optionally customize the clone after creation

<h4 id="4-prototype-registry-optional">4. Prototype Registry (Optional)</h4>

- Stores a collection of pre-configured prototypes, indexed by a key (string, enum, etc.)
- Returns clones (not originals) when clients request objects by key

<h1 id="4-how-it-works">4. How It Works</h1>

The Prototype workflow follows five steps:

<h4 id="step-1-create-prototype-instances">
  Step 1: Create Prototype Instances
</h4>

You configure a set of fully initialized objects that represent the "template" for each type you need. For our game, this means creating one FlyingEnemy with the correct health, speed, armor, and weapon.

<h4 id="step-2-register-prototypes-optional">
  Step 2: Register Prototypes (Optional)
</h4>

Store these prototypes in a registry, keyed by a meaningful name likeÂ `"flying"`Â orÂ `"armored"`. This centralizes configuration and makes it easy to add new types.

<h4 id="step-3-client-requests-a-clone">Step 3: Client Requests a Clone</h4>

When the game needs to spawn a new enemy, it asks the registry for a clone by key. The registry looks up the prototype and calls itsÂ `clone()`Â method.

<h4 id="step-4-prototype-copies-itself">Step 4: Prototype Copies Itself</h4>

The prototype creates a new instance and copies its own fields into it. The clone is a separate object in memory with the same values as the original.

<h4 id="step-5-client-customizes-the-clone">
  Step 5: Client Customizes the Clone
</h4>

The client can modify the clone without affecting the original. For example, reducing a spawned enemy's health to create a "weakened" variant.

The client never calls a constructor directly. It asks the registry for a clone, gets back a fully configured object, and optionally tweaks it. The original prototype stays untouched for future cloning.

<h4 id="key-points">Key Points:</h4>

- TheÂ `clone()`Â method creates a new instance using the copy constructor pattern, passing its own fields as arguments
- This is a shallow clone: all fields here are primitives or immutable (strings), so shallow is sufficient
- The clone is a completely independent object. CallingÂ `setHealth()`Â on the clone does not affect the original

But what happens when we add a mutable reference field? That is where shallow cloning breaks.

<h3 id="step-3-deep-clone-handling-mutable-fields">
  Step 3: Deep Clone (Handling Mutable Fields)
</h3>

Let us add anÂ `inventory`Â field, a list of items the enemy carries. With shallow cloning, the original and clone share the same list. To fix this, theÂ `clone()`Â method must create a new copy of every mutable reference field:

```java
public class Enemy implements EnemyPrototype {
    private String type;
    private int health;
    private double speed;
    private boolean armored;
    private String weapon;
    private List<String> inventory;

    public Enemy(String type, int health, double speed, boolean armored,
                 String weapon, List<String> inventory) {
        this.type = type;
        this.health = health;
        this.speed = speed;
        this.armored = armored;
        this.weapon = weapon;
        this.inventory = new ArrayList<>(inventory);
    }

    @Override
    public Enemy clone() {
        return new Enemy(type, health, speed, armored, weapon, new ArrayList<>(inventory));
    }

    public void setHealth(int health) { this.health = health; }
    public void addItem(String item) { inventory.add(item); }

    public void printStats() {
        System.out.println(type + " [Health: " + health +
                ", Speed: " + speed + ", Armored: " + armored +
                ", Weapon: " + weapon + ", Inventory: " + inventory + "]");
    }
}
```

<h3 id="step-4-prototype-registry">Step 4: Prototype Registry</h3>

The registry stores pre-configured prototypes and returns clones on request. This centralizes all configuration in one place.

```java
import java.util.HashMap;
import java.util.Map;

public class EnemyRegistry {
    private Map<String, Enemy> prototypes = new HashMap<>();

    public void register(String key, Enemy prototype) {
        prototypes.put(key, prototype);
    }

    public Enemy get(String key) {
        Enemy prototype = prototypes.get(key);
        if (prototype == null) {
            throw new IllegalArgumentException("No prototype registered for: " + key);
        }
        return prototype.clone();
    }
}
```
