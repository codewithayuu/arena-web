<LessonCard>

> TheÂ **Visitor Design Pattern**Â is aÂ **behavioral pattern**Â that lets youÂ **add new operations to existing object structures**Â without modifying their classes.

It achieves this by allowing you to separate the algorithm from the objects it operates on.

Itâs particularly useful in situations where:

- You have aÂ **complex object structure**Â (like ASTs, documents, or UI elements) that you want toÂ **perform multiple unrelated operations**Â on.
- You want toÂ **add new behaviors**Â to classes without changing their source code.
- You need toÂ **perform different actions depending on an objectâs concrete type**, without resorting to a long chain ofÂ `if-else`Â orÂ `instanceof`Â checks.

Letâs walk through a real-world example to see how we can apply the Visitor Pattern to cleanly separate behavior from structure and make our system easier to extend without touching existing classes.

<h1 id="1-the-problem-adding-operations-to-a-shape-hierarchy">

</h1>

Imagine you are building a vector graphics editor that supports multiple shape types:

- `Circle`
- `Rectangle`

- **Rendering**Â on screen
- **Calculating area**

<h3 id="why-this-breaks-down">Why This Breaks Down</h3>

This solution seems fine for a couple of operations, but quickly becomes problematic as new operations or shape types are added.

<h4 id="1-violates-the-single-responsibility-principle">
  1. Violates the Single Responsibility Principle
</h4>

Each shape class now contains multiple unrelated responsibilities: geometry calculations, drawing, serialization, and format exporting. This bloats the class and makes it harder to maintain.

<h4 id="2-hard-to-extend">2. Hard to Extend</h4>

If you need to add a new operation (e.g.,Â `generatePdf()`), you must modify every class in the hierarchy, recompile everything, and risk breaking existing logic. This violates the Open/Closed Principle.

<h4 id="3-you-donat-always-control-the-classes">
  3. You Donât Always Control the Classes
</h4>

What if the shape classes are part of a third-party library or generated code? You cannot easily add new behavior directly.

<h3 id="what-we-really-need">What We Really Need</h3>

We need a solution that lets us:

- **Separate operations**Â from the shape classes
- Add new behaviorsÂ **without modifying existing classes**
- Avoid duplicatingÂ `instanceof`Â checks or using type switches to handle different shapes

This is exactly what the Visitor pattern is designed to solve.

<h1 id="2-what-is-the-visitor-pattern">2. What is the Visitor Pattern</h1>

Two characteristics define the pattern:

1. **Separation of algorithm and structure:**Â The data classes (elements) stay clean. All operational logic lives in visitor classes that are entirely separate from the element hierarchy.
2. **Double dispatch:**Â The correct method to call is determined by both the type of the element and the type of the visitor. The element calls back the visitor withÂ `this`, which resolves the element's concrete type at compile time. This two-step dispatch is what makes the pattern work withoutÂ `instanceof`Â checks.

> Think about a home inspection. You have a house with different components: plumbing, electrical wiring, structural framing, and HVAC. Each specialist (a plumber, an electrician, a structural engineer, an HVAC technician) "visits" the house and inspects only what they understand.
>
> The house does not need to know how to evaluate its own plumbing or wiring. It just opens the door and lets each inspector do their job. Adding a new type of inspection (say, a fire safety audit) does not require remodeling the house. You just bring in a new inspector.
>
> The Visitor pattern works the same way: the elements (house components) accept visitors (inspectors), and new operations are new visitors.

<h2 id="class-diagram">Class Diagram</h2>

<h3 id="1-element-interface">1. Element (Interface)</h3>

Declares theÂ `accept(Visitor)`Â method that every element in the object structure must implement. This is the entry point for the double dispatch mechanism.

TheÂ `accept()`Â method exists purely to enable double dispatch. Without it, the visitor would needÂ `instanceof`Â checks to figure out the element's concrete type. With it, the element tells the visitor "I am a Circle" by callingÂ `visitor.visitCircle(this)`, and the correct overloaded method is invoked at compile time.

<h3 id="2-concrete-elements-ega-circlea-rectangle">
  2. Concrete Elements (e.g.,Â Circle,Â Rectangle)
</h3>

Each concrete element implements theÂ `accept()`Â method by calling the visitor's corresponding visit method, passingÂ `this`.

<h3 id="3-visitor-interface">3. Visitor (Interface)</h3>

Declares aÂ `visit`Â method for each concrete element type. This is the interface that all operations implement.

<h3 id="4-concrete-visitors-ega-areacalculatorvisitor">
  4. Concrete Visitors (e.g.,Â AreaCalculatorVisitor)
</h3>

Each concrete visitor implements the Visitor interface with a specific operation. One visitor might calculate areas, another might export to SVG, a third might validate constraints.

<h1 id="3-how-it-works">3. How It Works</h1>

The Visitor workflow involves a two-step dispatch that routes execution to the right method based on both the element type and the visitor type.

**Step 1:**Â The client creates a concrete visitor (e.g.,Â `AreaCalculatorVisitor`).

**Step 2:**Â The client iterates over the element collection and callsÂ `element.accept(visitor)`Â on each one.

**Step 3:**Â InsideÂ `accept()`, the element calls back the visitor's specific method:Â `visitor.visitCircle(this)`Â for a Circle,Â `visitor.visitRectangle(this)`Â for a Rectangle. This is the double dispatch: the element resolves its own type.

**Step 4:**Â The visitor'sÂ `visitCircle()`Â orÂ `visitRectangle()`Â method runs, performing the operation using the element's data.

**Step 5:**Â To add a new operation, you create a new visitor class. No element classes change.
