<LessonCard>

> TheÂ **Factory Method Design Pattern**Â is aÂ **creational pattern**Â that provides an interface for creating objects in aÂ **superclass**, but allowsÂ **subclasses**Â to alter the type of objects that will be created.

Itâs particularly useful in situations where:

- The exact type of object to be created isn't known until runtime.
- Object creation logic isÂ **complex**,Â **repetitive**, or needsÂ **encapsulation**.
- You want to follow theÂ **Open/Closed Principle, **open for extension, closed for modification.

When you have multiple objects of similar type, you might start with basic conditional logic (likeÂ `if-else`Â orÂ `switch`Â statements) to decide which object to create.

But as your application grows, this approach becomes rigid, harder to test, and tightly couples your code to specific classes, violating key design principles.

Factory method lets you create different objects without tightly coupling your code to specific classes.

Letâs walk through a **real-world example** to see how we can apply the Factory Method Pattern to build a moreÂ **scalable**Â andÂ **maintainable**Â object creation workflow.

<h1 id="2-simple-factory-a-first-attempt">
  2. Simple Factory: A First Attempt
</h1>

Before jumping to the full Factory Method pattern, there is a common intermediate step: extract the creation logic into a separate class.

This is called theÂ **Simple Factory**. It is not a formal Gang of Four (GoF) pattern, but it is one of the most practical refactoring techniques in real-world codebases.

The idea is straightforward: create a separate class whose only job is to centralize and encapsulate object creation. The notification service no longer needs to know which concrete class to instantiate. It asks the factory.

```java
class SimpleNotificationFactory {
    public static Notification createNotification(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailNotification();
            case "SMS" -> new SMSNotification();
            case "PUSH" -> new PushNotification();
            default -> throw new IllegalArgumentException("Unknown type");
        };
    }
}
```

```python

                raise ValueError("Unknown type")
```

But as your product grows and you keep adding new notification types, something starts to feel off again. YourÂ `SimpleNotificationFactory`Â is beginning to look eerily similar to the bloated code you just refactored away from.

Every time you introduce a new type, you are right back to modifying the factory'sÂ **switch**Â orÂ **if-else**Â statements.

That is not very Open/Closed, is it?

Your system is better, but it is still not open to extension without modification. You are still hardcoding the decision logic and centralizing creation in one place. You need to give each type of notification its own responsibility for knowing how to create itself.

And thatâs exactly the type of problemsÂ **Factory Method Design Pattern**Â solves.

<h1 id="3-what-is-factory-method">3. What is Factory Method</h1>

TheÂ **Factory Method Pattern**Â takes the idea of object creation and hands it off toÂ **subclasses**. Instead of one central factory deciding what to create, youÂ **delegate the responsibility to specialized classes**Â that know exactly what they need to produce.

In simpler terms:

- Each subclass defines itsÂ **own way**Â of instantiating an object.
- The base class defines aÂ **common interface**Â for creating that object, but doesnât know what the object is.
- The base class also often defines common behavior, using the created object in some way.

So now, instead of having:

```java
if type == "EMAIL" â return new EmailNotification()
if type == "SMS" â return new SMSNotification()
```

You have:

```java
// EmailNotificationCreator knows it should return new EmailNotification
// SMSNotificationCreator knows it should return new SMSNotification
```

YourÂ **creation logic is decentralized**.

> Think of aÂ **food delivery platform**. You place an order. If the system is designed like a Simple Factory, thereâs one centralized kitchen deciding whether to cook pizza, sushi, or burgers.
>
> But with the Factory Method, each restaurant (Pizza Place, Sushi Bar, Burger Joint) hasÂ **its own kitchen**Â and knows how to prepare its food. The platform just asks the appropriate kitchen to handle it.

<h2 id="class-diagram">Class Diagram</h2>

<h4 id="1-product-eg-notification">1. Product (e.g., Notification)</h4>

The interface or abstract class that defines the contract for all objects the factory method creates. Every concrete product implements this interface, which means the rest of the system can work with any product without knowing its concrete type.

In our notification example, this is theÂ `Notification`Â interface with itsÂ `send()`Â method. The creator and client code only ever reference this interface, neverÂ `EmailNotification`Â orÂ `SMSNotification`Â directly.

<h4 id="2-concreteproduct-eg-emailnotification">
  2. ConcreteProduct (e.g., EmailNotification)
</h4>

The actual classes that implement the Product interface. Each one provides its own behavior.` EmailNotification`Â connects to an SMTP server.Â `SMSNotification`Â calls a telephony API.Â `PushNotification`Â talks to Firebase or APNs.

They all share the sameÂ `send()`Â method signature but do completely different things internally.

<h4 id="3-creator-eg-notificationcreator">
  3. Creator (e.g., NotificationCreator)
</h4>

An abstract class (or an interface) that declares the factory method, which returns an object of type Product.

The Creator does two things:

1. **Declares the factory method**Â (`createNotification()`) that subclasses must implement.
2. **Contains shared logic**Â that uses the product. For example, theÂ `send()`Â method in ourÂ `NotificationCreator`Â callsÂ `createNotification()`Â to get a product, then uses it. The Creator defines theÂ *workflow*, the subclasses fill in theÂ *details*.

<h4 id="4-concretecreator-eg-emailnotificationcreator">
  4. ConcreteCreator (e.g., EmailNotificationCreator)
</h4>

Subclasses of Creator that override the factory method to return a specific ConcreteProduct.Â Each creator is paired with exactly one product type.

- `EmailNotificationCreator`Â returnsÂ `new EmailNotification()`.
- `SMSNotificationCreator`Â returnsÂ `new SMSNotification()`

<h1 id="4-how-it-works">4. How It Works</h1>

Here is the Factory Method workflow, step by step:

<h4 id="step-1-client-selects-a-creator">Step 1: Client selects a Creator</h4>

The client code decides which ConcreteCreator to use based on configuration, user input, or business logic. For example, if the user wants an email notification, the client instantiatesÂ `EmailNotificationCreator`.

<h4 id="step-2-client-calls-a-method-on-the-creator">
  Step 2: Client calls a method on the Creator
</h4>

The client callsÂ `send()`Â (or whatever the high-level operation is). This method lives in the abstract Creator class.

<h4 id="step-3-creator-calls-the-factory-method">
  Step 3: Creator calls the factory method
</h4>

InsideÂ `send()`, the Creator callsÂ `createNotification()`. Since the Creator is abstract, this call is dispatched to the ConcreteCreator's override.

**Step 4: ConcreteCreator returns a ConcreteProduct**

`EmailNotificationCreator.createNotification()`Â returns aÂ `new EmailNotification()`. The Creator receives it as theÂ `Notification`Â interface type.

<h4 id="step-5-creator-uses-the-product">Step 5: Creator uses the product</h4>

The Creator callsÂ `notification.send(message)`Â on the product it just received. The correct concrete behavior executes.

<h3 id="3-define-an-abstract-creator">3. Define an Abstract Creator</h3>

We create anÂ **abstract class**Â that declares the factory methodÂ `createNotification()`, and optionally includes shared behavior likeÂ `send()`that defines the high-level logic of sending a notification by using whatever objectÂ `createNotification()`Â provides.

The Creator defines the flow, subclasses fill in the details.

```java
abstract class NotificationCreator {
    // Factory Method - subclasses decide what to create
    public abstract Notification createNotification();

    // Shared logic that uses the factory method
    public void send(String message) {
        Notification notification = createNotification();
        notification.send(message);
    }
}
```

```python
class NotificationCreator(ABC):
    # Factory Method - subclasses decide what to create
    @abstractmethod
    def create_notification(self) -> Notification:
        pass

    # Shared logic that uses the factory method
    def send(self, message: str) -> None:
        notification = self.create_notification()
        notification.send(message)
```

```cpp
class NotificationCreator {
public:
    // Factory Method - subclasses decide what to create
    virtual unique_ptr<Notification> createNotification() = 0;

    // Shared logic that uses the factory method
    void send(const string& message) {
        auto notification = createNotification();
        notification->send(message);
    }

    virtual ~NotificationCreator() = default;
};
```

  getFooter(): string {

  }

    return ".pdf";
  }

  getHeader(): string {
    return "<html><body><table>";
  }
  formatRow(data: string[]): string {
    const cells = data.map((cell) => `<td>${cell}</td>`).join("");
    return `<tr>${cells}</tr>`;
  }
  getFooter(): string {
    return "</table></body></html>";
  }
  getFileExtension(): string {
    return ".html";
  }

    return ".csv";

abstract class ExportCreator {
  abstract createDocument(): Document;

    if (footer) console.log(footer);
