<h1 id="declaring-a-generic-class">Declaring a Generic Class</h1>

A generic class looks like a normal class with an extra pair of angle brackets after the class name. The names inside the brackets are **type parameters**: placeholders that act like types throughout the class body. A single-letter convention is universal: `T` for "type", `E` for "element", `K` and `V` for "key" and "value". The names are arbitrary, but the convention is widely recognized, so stick with it unless there's a reason not to.

Here's a `Box` class that can hold any single value:

```java
public class Box<T> {
    private T content;

    public Box(T content) {
        this.content = content;
    }

    public T getContent() {
        return content;
    }

    public void setContent(T content) {
        this.content = content;
    }
}
```

`T` appears in four places: the class header, the field type, the constructor parameter, and the getter's return type. Inside the class body, `T` behaves like any other type name. Fields of type `T` are valid, methods can return `T`, methods can take `T` parameters, and `T` references can be stored in collections. What is not allowed is treating `T` as a specific type like `String`; the class has to work for any choice the caller makes, so `T` has the powers of `Object` and nothing more.

The compiler enforces the rule that every use of `T` inside the class refers to the same type for a given object. A `Box<String>` instance holds a `String` in its `content` field, returns a `String` from `getContent`, and only accepts a `String` in `setContent`. A `Box<Integer>` does the same with `Integer`. Each instance picks one concrete type at construction time and sticks with it.

```java
public class BoxDemo {
    public static void main(String[] args) {
        Box<String> productBox = new Box<>("Notebook");
        Box<Integer> stockBox = new Box<>(42);

        System.out.println("Product: " + productBox.getContent());
        System.out.println("Stock: " + stockBox.getContent());

        productBox.setContent("Pen");
        System.out.println("Product: " + productBox.getContent());
    }
}
```

The diamond `<>` on the right side of `new Box<>("Notebook")` tells the compiler "figure out the type argument from context". Since the left side declares the variable as `Box<String>`, the compiler infers that the diamond expands to `<String>`. Diamond inference (added in Java 7) is the standard way to write generic constructors today. The pre-Java-7 form `new Box<String>("Notebook")` still works, just longer.

<h1 id="type-parameter-scope">Type Parameter Scope</h1>

A type parameter declared in the class header is visible everywhere inside that class: fields, constructors, instance methods, nested classes. It is not visible in `static` members of the class, and not visible outside the class body. The scope is exactly the class body, just like a field name.

A `Container<T>` that uses `T` in several places makes this clear:

```java
import java.util.ArrayList;
import java.util.List;

public class Container<T> {
    private final List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
    }

    public T get(int index) {
        return items.get(index);
    }

    public boolean contains(T item) {
        return items.contains(item);
    }

    public int size() {
        return items.size();
    }

    public T first() {
        if (items.isEmpty()) {
            return null;
        }
        return items.get(0);
    }
}
```

Every method that needs to talk about elements uses `T`. The `List<T> items` field is itself parameterized by the same `T`, so a `Container<String>` holds a `List<String>` and a `Container<Integer>` holds a `List<Integer>`. The two `T`s in the field and the methods refer to the same type because they live in the same class.

```java
public class ContainerDemo {
    public static void main(String[] args) {
        Container<String> wishlist = new Container<>();
        wishlist.add("Notebook");
        wishlist.add("Pen");
        wishlist.add("Eraser");

        System.out.println("Size: " + wishlist.size());
        System.out.println("First: " + wishlist.first());
        System.out.println("Has Pen: " + wishlist.contains("Pen"));
    }
}
```

The `T` in the class header acts as a binding declaration; every later mention of `T` in the class is a use of that binding. Renaming the header to `Container<E>` requires renaming every use to `E` as well. The compiler doesn't accept a class where the header says `T` and the body says `E`, because the two names would be unrelated.

Type parameters live entirely in the type system. After compilation, they're erased to `Object`. At runtime, a `Container<String>` and a `Container<Integer>` look identical to the JVM. The cost of generics is paid by the compiler, not by the running program.

What `T` cannot do is appear in a `static` field or `static` method of the same class:

**What's wrong with this code?**

```java
public class BrokenContainer<T> {
    private static T defaultValue;  // does not compile

    public static T getDefault() {  // does not compile
        return defaultValue;
    }
}
```

**Fix:**

A `static` member belongs to the class itself, not to any particular instance, so it can't refer to an instance-level type parameter. To tie a default to a specific type, either keep it on instances or declare a separate generic method with a method-level type parameter:

```java
public class FixedContainer<T> {
    private final T defaultValue;

    public FixedContainer(T defaultValue) {
        this.defaultValue = defaultValue;
    }

    public T getDefault() {
        return defaultValue;
    }
}
```

The instance field `defaultValue` is fine because every `FixedContainer<T>` instance carries its own `T`.

<h1 id="multiple-type-parameters">Multiple Type Parameters</h1>

A class can declare more than one type parameter by listing them in the angle brackets, separated by commas. `Pair<K, V>` is the canonical example: a small holder for two related values that don't have to be the same type.

```java
public class Pair<K, V> {
    private final K key;
    private final V value;

    public Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    public K getKey() {
        return key;
    }

    public V getValue() {
        return value;
    }

    @Override
    public String toString() {
        return "(" + key + ", " + value + ")";
    }
}
```

Both `K` and `V` are scoped to the class body. They can be different types or the same type; the caller decides at construction time.

```java
public class PairDemo {
    public static void main(String[] args) {
        Pair<String, Integer> productStock = new Pair<>("Notebook", 42);
        Pair<String, Double> productPrice = new Pair<>("Notebook", 12.99);
        Pair<Integer, Integer> orderRange = new Pair<>(1001, 1500);

        System.out.println("Stock entry: " + productStock);
        System.out.println("Price entry: " + productPrice);
        System.out.println("Order range: " + orderRange);

        Integer stock = productStock.getValue();
        System.out.println("Stock count: " + stock);
    }
}
```

The `getValue` call on `productStock` returns an `Integer` because `V` is bound to `Integer` for that instance. On `productPrice`, the same method returns a `Double` because `V` is bound to `Double`. The same source code produces different return types depending on how the class was parameterized at the call site.

Three parameters work the same way. A `Triple<A, B, C>` extends the idea to three values:

```java
public class Triple<A, B, C> {
    private final A first;
    private final B second;
    private final C third;

    public Triple(A first, B second, C third) {
        this.first = first;
        this.second = second;
        this.third = third;
    }

    public A getFirst() {
        return first;
    }

    public B getSecond() {
        return second;
    }

    public C getThird() {
        return third;
    }

    @Override
    public String toString() {
        return "(" + first + ", " + second + ", " + third + ")";
    }
}
```

```java
public class TripleDemo {
    public static void main(String[] args) {
        Triple<String, Integer, Double> productEntry =
            new Triple<>("Notebook", 42, 12.99);

        System.out.println("Product: " + productEntry.getFirst());
        System.out.println("Stock: " + productEntry.getSecond());
        System.out.println("Price: $" + productEntry.getThird());
        System.out.println("Full: " + productEntry);
    }
}
```

Two practical points about multiple type parameters. First, the order matters: `Pair<String, Integer>` and `Pair<Integer, String>` are different types. A method that takes a `Pair<String, Integer>` will not accept a `Pair<Integer, String>`. Second, beyond three or four parameters, the angle brackets get hard to read and a dedicated class with named fields is usually clearer than a generic tuple. The standard library doesn't ship a `Pair` or `Triple` for this reason; small, named domain classes are clearer.

<h1 id="instantiating-generic-classes-with-the-diamond">
  Instantiating Generic Classes with the Diamond
</h1>

Every generic class needs a type argument when instantiated. There are two ways to provide it: explicitly or via diamond inference.

**Explicit form:**

```java
Box<String> productBox = new Box<String>("Notebook");
```

**Diamond form (preferred):**

```java
Box<String> productBox = new Box<>("Notebook");
```

The diamond `<>` tells the compiler to infer the type argument from the target type. The target type is whatever the result is being assigned to, returned from, or passed into. In the line above, the target type of the right-hand expression is `Box<String>` (the variable's declared type), so the diamond expands to `<String>`.

A few examples of the diamond doing its job:

```java
import java.util.ArrayList;
import java.util.List;

public class DiamondInference {
    public static void main(String[] args) {
        // Inferred from variable type
        Box<String> productBox = new Box<>("Notebook");

        // Inferred from method parameter type
        List<Pair<String, Integer>> catalog = new ArrayList<>();
        catalog.add(new Pair<>("Notebook", 42));
        catalog.add(new Pair<>("Pen", 100));

        // Inferred from method return type
        Box<Double> priceBox = createPriceBox();

        System.out.println(productBox.getContent());
        System.out.println(catalog);
        System.out.println(priceBox.getContent());
    }

    private static Box<Double> createPriceBox() {
        return new Box<>(12.99);
    }
}
```

In the second example, `catalog.add(new Pair<>("Notebook", 42))` passes a `Pair<?, ?>` whose type arguments are inferred from the list's element type `Pair<String, Integer>`. In the third, `createPriceBox` declares its return type as `Box<Double>`, so the `new Box<>(12.99)` inside the method picks up `<Double>` from that return type.

The one place the diamond doesn't help is when there's no target type at all. With `var box = new Box<>("Notebook");`, the compiler has to fall back on the constructor argument and infer `Box<String>`, which works for this simple case but can produce unexpected types when the argument is more complicated. With `var`, an explicit type argument is sometimes clearer:

```java
public class VarInference {
    public static void main(String[] args) {
        var productBox = new Box<String>("Notebook"); // explicit is clearer with var
        System.out.println(productBox.getContent());
    }
}
```

Diamond inference is a compile-time convenience. The generated bytecode is identical to the explicit form, so there's no runtime impact either way. Pick the form that reads better at the call site.

<h1 id="boxstring-and-boxinteger-are-unrelated-types">
  Box&lt;String&gt; and Box&lt;Integer&gt; Are Unrelated Types
</h1>

A single generic class definition produces a family of types when you instantiate it with different type arguments, but those types are not related to each other in the inheritance hierarchy. `Box<String>` is not a subtype of `Box<Object>`, and `Box<Integer>` is not a subtype of `Box<Number>`. Each parameterized type is its own thing.

Even though `String` is a subtype of `Object`, `Box<String>` is not a subtype of `Box<Object>`. Consider what would happen if it were:

**What's wrong with this code?**

```java
public class BrokenSubtype {
    public static void main(String[] args) {
        Box<String> stringBox = new Box<>("Notebook");
        Box<Object> objectBox = stringBox;  // does not compile
        objectBox.setContent(42);            // would put an Integer in stringBox
        String content = stringBox.getContent(); // ClassCastException
    }
}
```

If the second line compiled, the fourth line would crash at runtime because `stringBox` would actually hold an `Integer`. To prevent this, the compiler rejects the assignment outright. Generic classes are **invariant** in their type parameters: `Box<X>` is only assignable to `Box<X>`, never to `Box<Y>` for a different `Y`, even when `X` is a subtype of `Y`.

`Box<String>` and `Box<Integer>` are siblings under `Object`, not relatives of each other:

Each parameterized type stands alone. Any of them can be held in an `Object` reference (everything extends `Object`), but assignments between them are not allowed.

The same rule applies to multi-parameter classes. `Pair<String, Integer>` and `Pair<String, Number>` are unrelated, even though `Integer` is a subtype of `Number`. Each type parameter is invariant independently.

<h1 id="a-realistic-example-resultt">A Realistic Example: Result&lt;T&gt;</h1>

A `Result<T>` wrapper is a common pattern for methods that can either return a value or fail. It carries an outcome flag, the value (when successful), and an error message (when failed), all parameterized by the type of the value the operation produces.

```java
public class Result<T> {
    private final boolean success;
    private final T value;
    private final String error;

    private Result(boolean success, T value, String error) {
        this.success = success;
        this.value = value;
        this.error = error;
    }

    public static <T> Result<T> ok(T value) {
        return new Result<>(true, value, null);
    }

    public static <T> Result<T> fail(String error) {
        return new Result<>(false, null, error);
    }

    public boolean isSuccess() {
        return success;
    }

    public T getValue() {
        return value;
    }

    public String getError() {
        return error;
    }
}
```

The `ok` and `fail` factory methods are static, so they need their own method-level type parameter `<T>` in front of the return type. This is how static factories on a generic class re-declare a type parameter. The instance methods (`isSuccess`, `getValue`, `getError`) use the class's `T` without re-declaring it because they're not static.

A small program that uses `Result` to model a stock lookup:

```java
public class ResultDemo {
    public static void main(String[] args) {
        Result<Integer> found = lookupStock("Notebook");
        Result<Integer> missing = lookupStock("Stapler");

        printResult(found);
        printResult(missing);
    }

    private static Result<Integer> lookupStock(String product) {
        if (product.equals("Notebook")) {
            return Result.ok(42);
        }
        if (product.equals("Pen")) {
            return Result.ok(100);
        }
        return Result.fail("Product not found: " + product);
    }

    private static void printResult(Result<Integer> result) {
        if (result.isSuccess()) {
            System.out.println("Stock: " + result.getValue());
        } else {
            System.out.println("Error: " + result.getError());
        }
    }
}
```

Two calls, two outcomes, one class. `Result<Integer>` is the parameterized type used for both because both calls return stock counts; if the operation produced a `Double` (a price) or a `String` (a product name), the variable's declared type would change to `Result<Double>` or `Result<String>` and the rest of the code would adjust at compile time.

<h1 id="a-tiny-generic-stack">A Tiny Generic Stack</h1>

A stack is a classic example of a data structure that benefits from being generic. The same operations (`push`, `pop`, `peek`, `isEmpty`) make sense for any element type, so writing them once and parameterizing the class is the natural choice.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.NoSuchElementException;

public class Stack<T> {
    private final List<T> items = new ArrayList<>();

    public void push(T item) {
        items.add(item);
    }

    public T pop() {
        if (items.isEmpty()) {
            throw new NoSuchElementException("Stack is empty");
        }
        return items.remove(items.size() - 1);
    }

    public T peek() {
        if (items.isEmpty()) {
            throw new NoSuchElementException("Stack is empty");
        }
        return items.get(items.size() - 1);
    }

    public boolean isEmpty() {
        return items.isEmpty();
    }

    public int size() {
        return items.size();
    }
}
```

The backing storage is a `List<T>`, which inherits its generics from the same `T` declared on the class. `push` appends, `pop` removes from the end, and `peek` reads the last element without removing it. The runtime cost of each operation is the cost of the underlying `ArrayList` method.

```java
public class StackDemo {
    public static void main(String[] args) {
        Stack<String> recentlyViewed = new Stack<>();
        recentlyViewed.push("Notebook");
        recentlyViewed.push("Pen");
        recentlyViewed.push("Eraser");

        System.out.println("Top: " + recentlyViewed.peek());
        System.out.println("Size: " + recentlyViewed.size());

        System.out.println("Popped: " + recentlyViewed.pop());
        System.out.println("Popped: " + recentlyViewed.pop());
        System.out.println("Top after pops: " + recentlyViewed.peek());
    }
}
```

The same class works just as well for a stack of integers:

```java
public class IntStackDemo {
    public static void main(String[] args) {
        Stack<Integer> orderIds = new Stack<>();
        orderIds.push(1001);
        orderIds.push(1002);
        orderIds.push(1003);

        while (!orderIds.isEmpty()) {
            System.out.println("Processing order " + orderIds.pop());
        }
    }
}
```

Storing primitives in `Stack<Integer>` triggers autoboxing on every `push` and unboxing on every `pop`. For a stack of millions of `int` values, a dedicated `IntStack` backed by an `int[]` is faster. For everyday application code, the cost is invisible.

The standard library does ship a `java.util.Stack` class, but it's a legacy class from Java 1.0 with synchronized methods. Modern code uses `ArrayDeque` when a stack-like data structure is needed. Writing a custom `Stack<T>` is a teaching exercise; the production answer is `ArrayDeque<T>`.
