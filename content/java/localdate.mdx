<h1 id="what-localdate-represents">What LocalDate Represents</h1>

A `LocalDate` is an immutable value object that stores three numbers: a year, a month (1 to 12), and a day of the month (1 to 28, 29, 30, or 31 depending on the month). It uses the ISO-8601 calendar system, the standard proleptic Gregorian calendar that most software and most of the world runs on. There is no hour, no minute, no second, and no time zone. For "what date is the next Black Friday sale," `LocalDate` is the right type. For "at exactly what instant did the sale start in New York," `ZonedDateTime` or `Instant` is more appropriate.

The class lives in `java.time.LocalDate` and was added in Java 8 as part of the JSR-310 redesign. Every method that looks like it changes a `LocalDate` actually returns a new `LocalDate`, because instances are immutable. This point comes up several times in this lesson.

The diagram is intentionally simple: three numbers go in, one `LocalDate` comes out. That's the conceptual model. Everything else in this lesson is about constructing that object, reading fields from it, and deriving new dates from it.

<h1 id="building-a-localdate">Building a LocalDate</h1>

There are three common ways to get a `LocalDate`: ask for today, build one from explicit year/month/day values, or parse one from an ISO-formatted string.

<h3 id="localdatenow">LocalDate.now()</h3>

`LocalDate.now()` reads the system clock and returns today's date in the JVM's default time zone. This is the version for stamping an order with the day it was placed, or recording the day a product was released.

```java
import java.time.LocalDate;

public class TodayOnInvoice {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.now();
        System.out.println("Order placed on: " + orderDate);
    }
}
```

The exact output depends on the day the code runs. The string form is ISO-8601 (`YYYY-MM-DD`), which is what `toString()` returns by default. For now, the ISO format is fine.

`LocalDate.now()` reads the system clock and the default time zone every call. That's cheap, but it's also non-deterministic, which makes tests flaky. Production code that needs to be testable usually accepts a `Clock` and calls `LocalDate.now(clock)` so tests can pin "today" to a known value.

<h3 id="localdateofyear-month-day">LocalDate.of(year, month, day)</h3>

For a known exact date, build it with `LocalDate.of`. There are two overloads: one that takes three `int` values and one that takes a `Month` enum constant in the middle. Both behave the same. The `Month` form reads a little better in code review.

```java
import java.time.LocalDate;
import java.time.Month;

public class BlackFridaySale {
    public static void main(String[] args) {
        LocalDate saleStartInts = LocalDate.of(2026, 11, 27);
        LocalDate saleStartEnum = LocalDate.of(2026, Month.NOVEMBER, 27);

        System.out.println("Sale start (ints): " + saleStartInts);
        System.out.println("Sale start (enum): " + saleStartEnum);
        System.out.println("Same date?         " + saleStartInts.equals(saleStartEnum));
    }
}
```

A note on month numbering. `LocalDate.of(2026, 11, 27)` is November 27, 2026. Months in `java.time` are 1-based, matching the numbering humans use. The older `java.util.Calendar` used 0-based months (January was `0`), and it caused so many bugs over the years that the `java.time` designers fixed it.

Passing an invalid combination causes `LocalDate.of` to throw a `DateTimeException` rather than silently rolling over to a "close" date. February 30 isn't a date, so the call fails:

```java
import java.time.LocalDate;

public class InvalidDate {
    public static void main(String[] args) {
        try {
            LocalDate bad = LocalDate.of(2026, 2, 30);
            System.out.println(bad);
        } catch (Exception e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}
```

That's a feature, not a bug. The old `java.util.Date` would happily accept February 30 and silently convert it to March 2. A wrong return-window deadline typed into an admin tool would never have surfaced.

<h3 id="localdateparse">LocalDate.parse()</h3>

When the date arrives as a string in ISO format (`YYYY-MM-DD`), `LocalDate.parse` handles it directly without any formatter setup.

```java
import java.time.LocalDate;

public class ParseSubscriptionDate {
    public static void main(String[] args) {
        String renewalText = "2026-08-01";
        LocalDate renewalDate = LocalDate.parse(renewalText);

        System.out.println("Renewal text:   " + renewalText);
        System.out.println("Renewal parsed: " + renewalDate);
        System.out.println("Year:           " + renewalDate.getYear());
    }
}
```

The single-argument form of `parse` only understands the ISO format. For `"08/01/2026"` or `"Aug 1, 2026"` or any other format, a custom `DateTimeFormatter` is required, which is the topic of lesson 08 in this section.

<h1 id="reading-fields-from-a-localdate">Reading Fields From a LocalDate</h1>

A `LocalDate` has a getter for every field of interest. The names are predictable; the return types vary.

| Method            | Returns      | Range                              |
| ----------------- | ------------ | ---------------------------------- |
| `getYear()`       | `int`        | Any 4-digit year (and beyond)      |
| `getMonth()`      | `Month` enum | `JANUARY` to `DECEMBER`            |
| `getMonthValue()` | `int`        | 1 to 12                            |
| `getDayOfMonth()` | `int`        | 1 to 31                            |
| `getDayOfWeek()`  | `DayOfWeek`  | `MONDAY` to `SUNDAY`               |
| `getDayOfYear()`  | `int`        | 1 to 365 (or 366 in a leap year)   |
| `isLeapYear()`    | `boolean`    | `true` if divisible-by-4 leap rule |
| `lengthOfMonth()` | `int`        | 28, 29, 30, or 31                  |
| `lengthOfYear()`  | `int`        | 365 or 366                         |

A working example pulls a handful of them together. Consider a product release date displayed on a "release info" admin page:

```java
import java.time.LocalDate;
import java.time.DayOfWeek;
import java.time.Month;

public class ReleaseInfo {
    public static void main(String[] args) {
        LocalDate releaseDate = LocalDate.of(2026, Month.FEBRUARY, 29);

        System.out.println("Release date:    " + releaseDate);
        System.out.println("Year:            " + releaseDate.getYear());
        System.out.println("Month enum:      " + releaseDate.getMonth());
        System.out.println("Month value:     " + releaseDate.getMonthValue());
        System.out.println("Day of month:    " + releaseDate.getDayOfMonth());
        System.out.println("Day of week:     " + releaseDate.getDayOfWeek());
        System.out.println("Day of year:     " + releaseDate.getDayOfYear());
        System.out.println("Leap year?       " + releaseDate.isLeapYear());
        System.out.println("Days in month:   " + releaseDate.lengthOfMonth());
        System.out.println("Days in year:    " + releaseDate.lengthOfYear());
    }
}
```

Two suspicious things here. `LocalDate.of(2026, Month.FEBRUARY, 29)` should fail, because 2026 isn't a leap year. And the printed `Release date` is `2026-02-29`, which would mean the date succeeded. That's a contrived bug to highlight: as shown earlier `LocalDate.of(2026, 2, 30)` throws, and the same is true for `2026, 2, 29`. The code above throws a `DateTimeException` before reaching the print statements. Run it to confirm. The teachable point is that `LocalDate` doesn't accept invalid dates.

The same example with a real leap year so the code actually runs:

```java
import java.time.LocalDate;
import java.time.Month;

public class ReleaseInfoLeap {
    public static void main(String[] args) {
        LocalDate releaseDate = LocalDate.of(2024, Month.FEBRUARY, 29);

        System.out.println("Release date:    " + releaseDate);
        System.out.println("Day of week:     " + releaseDate.getDayOfWeek());
        System.out.println("Day of year:     " + releaseDate.getDayOfYear());
        System.out.println("Leap year?       " + releaseDate.isLeapYear());
        System.out.println("Days in month:   " + releaseDate.lengthOfMonth());
        System.out.println("Days in year:    " + releaseDate.lengthOfYear());
    }
}
```

A few details. `getDayOfWeek()` returns a `DayOfWeek` enum, not a string or a number. That's intentional: enums prevent off-by-one bugs and allow `switch` without magic numbers. `getDayOfYear()` is the 1-based count of the day in the year, useful for "days since New Year" calculations like "how long until the holiday sale starts." And `lengthOfMonth()` knows about February's leap-year quirk.

<h1 id="doing-arithmetic-with-localdate">Doing Arithmetic With LocalDate</h1>

Date math by hand is error-prone: months have different lengths, leap years exist, and "30 days from January 31" doesn't have an obvious answer. `LocalDate` has methods that handle all of this correctly.

<h3 id="plusdays-plusweeks-plusmonths-plusyears">
  plusDays, plusWeeks, plusMonths, plusYears
</h3>

The four `plusX` methods cover the common cases. Each takes a `long` count and returns a new `LocalDate`. The originals are never modified.

Suppose an order is placed today, and the shipping policy is "delivers in 5 business days, but we promise 7 calendar days." The promise date is computed as:

```java
import java.time.LocalDate;

public class DeliveryPromise {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);
        LocalDate deliverBy = orderDate.plusDays(7);

        System.out.println("Order date:   " + orderDate);
        System.out.println("Deliver by:   " + deliverBy);
    }
}
```

`plusWeeks(n)` is a shortcut for `plusDays(n * 7)`. The two are equivalent. Use whichever reads better in context:

```java
import java.time.LocalDate;

public class ReturnWindow {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);
        LocalDate returnDeadline = orderDate.plusWeeks(4);

        System.out.println("Order date:        " + orderDate);
        System.out.println("Return deadline:   " + returnDeadline);
    }
}
```

`plusMonths` and `plusYears` work the same way, but they have a wrinkle around month-end, covered below. First, a subscription renewal example to show the basic case:

```java
import java.time.LocalDate;

public class SubscriptionRenewal {
    public static void main(String[] args) {
        LocalDate signupDate = LocalDate.of(2026, 5, 14);
        LocalDate nextRenewal = signupDate.plusMonths(1);
        LocalDate annualRenewal = signupDate.plusYears(1);

        System.out.println("Signup date:     " + signupDate);
        System.out.println("Next renewal:    " + nextRenewal);
        System.out.println("Annual renewal:  " + annualRenewal);
    }
}
```

<h3 id="minusdays-minusweeks-minusmonths-minusyears">
  minusDays, minusWeeks, minusMonths, minusYears
</h3>

Every `plusX` has a `minusX` counterpart. They subtract instead of add. The signatures and behavior mirror the `plusX` methods, including the month-end quirk.

```java
import java.time.LocalDate;

public class SaleWindow {
    public static void main(String[] args) {
        LocalDate saleEnd = LocalDate.of(2026, 11, 30);
        LocalDate saleStart = saleEnd.minusDays(10);
        LocalDate previewStart = saleEnd.minusWeeks(3);

        System.out.println("Sale end:        " + saleEnd);
        System.out.println("Sale start:      " + saleStart);
        System.out.println("Preview start:   " + previewStart);
    }
}
```

Date arithmetic methods allocate a new `LocalDate` every call. For a one-off `orderDate.plusDays(7)`, that's negligible. If you chain twenty calls in a tight loop processing millions of rows, the allocations add up, though garbage collection of small short-lived objects is cheap on the JVM. The shape of the API is "return a new immutable value," not "mutate in place."

<h3 id="month-end-edge-cases">Month-End Edge Cases</h3>

"What is one month after January 31, 2026?" There's no February 31, so the answer can't be "31st of next month." `LocalDate` handles this by clamping the day of month to the last valid day of the target month:

```java
import java.time.LocalDate;

public class MonthEndArithmetic {
    public static void main(String[] args) {
        LocalDate jan31 = LocalDate.of(2026, 1, 31);
        LocalDate plusOne = jan31.plusMonths(1);
        LocalDate plusTwo = jan31.plusMonths(2);
        LocalDate plusThree = jan31.plusMonths(3);

        System.out.println("Start:        " + jan31);
        System.out.println("+1 month:     " + plusOne);
        System.out.println("+2 months:    " + plusTwo);
        System.out.println("+3 months:    " + plusThree);
    }
}
```

January 31 plus one month becomes February 28, the last day of February (2026 isn't a leap year, so it's 28, not 29). Adding two months from the original January 31 lands on March 31 again. The clamping only happens when the target month is shorter. This matters for any monthly billing or renewal logic where a customer signed up on the 31st. A subscription that renews "on the same day of the month" sometimes has no matching day in a target month.

A leap-year version makes the difference clearer:

```java
import java.time.LocalDate;

public class LeapYearMonthEnd {
    public static void main(String[] args) {
        LocalDate jan31_2024 = LocalDate.of(2024, 1, 31);
        LocalDate jan31_2025 = LocalDate.of(2025, 1, 31);

        System.out.println("Jan 31, 2024 + 1 month = " + jan31_2024.plusMonths(1));
        System.out.println("Jan 31, 2025 + 1 month = " + jan31_2025.plusMonths(1));
    }
}
```

2024 is a leap year, so February has 29 days. 2025 isn't, so February stops at 28. `plusMonths` knows the rule.

<h3 id="plusperiod-and-pluslong-temporalunit">
  plus(Period) and plus(long, TemporalUnit)
</h3>

Adding a combination like "1 year, 2 months, and 10 days" in a single step uses `Period`. `Period` packages a year/month/day offset into one value that goes to `plus`. This section shows the shape of the call.

```java
import java.time.LocalDate;
import java.time.Period;

public class ExtendedWarranty {
    public static void main(String[] args) {
        LocalDate purchaseDate = LocalDate.of(2026, 5, 14);
        Period warrantyLength = Period.of(2, 0, 0);

        LocalDate warrantyExpires = purchaseDate.plus(warrantyLength);
        System.out.println("Purchased: " + purchaseDate);
        System.out.println("Expires:   " + warrantyExpires);
    }
}
```

There's also a more general `plus(long amount, TemporalUnit unit)` that takes a count and a unit (`ChronoUnit.DAYS`, `ChronoUnit.WEEKS`, `ChronoUnit.MONTHS`, `ChronoUnit.YEARS`, etc.). It's useful when the unit is chosen dynamically:

```java
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;

public class FlexibleOffset {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);

        LocalDate plus3Days = orderDate.plus(3, ChronoUnit.DAYS);
        LocalDate plus6Weeks = orderDate.plus(6, ChronoUnit.WEEKS);

        System.out.println("Order date:    " + orderDate);
        System.out.println("+ 3 days:      " + plus3Days);
        System.out.println("+ 6 weeks:     " + plus6Weeks);
    }
}
```

In most code, `plusDays`, `plusMonths`, and friends read better. `plus(amount, unit)` is useful when the unit is itself a parameter, such as a configurable promotion length stored in a database.

<h1 id="replacing-fields-with-withx">Replacing Fields With withX</h1>

The `withX` methods return a copy of the date with one field replaced. They're useful for anchoring to a specific year, month, or day without throwing away the rest.

```java
import java.time.LocalDate;
import java.time.Month;

public class AnchorSaleDate {
    public static void main(String[] args) {
        LocalDate template = LocalDate.of(2025, 7, 15);

        LocalDate nextYear = template.withYear(2026);
        LocalDate sameDayDecember = template.withMonth(12);
        LocalDate firstOfMonth = template.withDayOfMonth(1);
        LocalDate hundredthDayOfYear = template.withDayOfYear(100);

        System.out.println("Template:                " + template);
        System.out.println("withYear(2026):          " + nextYear);
        System.out.println("withMonth(12):           " + sameDayDecember);
        System.out.println("withDayOfMonth(1):       " + firstOfMonth);
        System.out.println("withDayOfYear(100):      " + hundredthDayOfYear);
    }
}
```

`withMonth` also has to handle the month-end case. March 31 with `withMonth(2)` would request February 31, which doesn't exist. The method clamps the day, same as `plusMonths`:

```java
import java.time.LocalDate;

public class WithMonthClamp {
    public static void main(String[] args) {
        LocalDate march31 = LocalDate.of(2025, 3, 31);
        LocalDate febSomething = march31.withMonth(2);

        System.out.println("Original:        " + march31);
        System.out.println("withMonth(2):    " + febSomething);
    }
}
```

Same rule as before. Invalid combinations get clamped to the closest valid date in the target month rather than throwing.

<h1 id="comparing-dates">Comparing Dates</h1>

Checking whether one date is before, after, or equal to another is a common operation. A typical case: deciding whether a return request landed inside the return window.

```java
import java.time.LocalDate;

public class ReturnEligibility {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 4, 1);
        LocalDate returnDeadline = orderDate.plusDays(30);
        LocalDate requestedReturn = LocalDate.of(2026, 4, 25);

        boolean inWindow = !requestedReturn.isAfter(returnDeadline);
        boolean alreadyExpired = requestedReturn.isAfter(returnDeadline);

        System.out.println("Order date:        " + orderDate);
        System.out.println("Return deadline:   " + returnDeadline);
        System.out.println("Requested:         " + requestedReturn);
        System.out.println("In window?         " + inWindow);
        System.out.println("Already expired?   " + alreadyExpired);
    }
}
```

`isBefore`, `isAfter`, and `isEqual` each return a `boolean` and take another `LocalDate` as the argument. They compare by calendar position. There's also `compareTo`, which returns a negative number, zero, or a positive number, matching the `Comparable` interface so `LocalDate` instances sort naturally.

One detail: `equals` and `isEqual` behave the same way for `LocalDate` (both check that the year, month, and day match), but they differ on types higher up the hierarchy where chronology can matter. For `LocalDate`, either works, and `equals` makes a `LocalDate` a correct `HashMap` key.

```java
import java.time.LocalDate;

public class CompareSaleDates {
    public static void main(String[] args) {
        LocalDate saleStart = LocalDate.of(2026, 11, 27);
        LocalDate saleEnd = LocalDate.of(2026, 11, 30);

        System.out.println("Start before end? " + saleStart.isBefore(saleEnd));
        System.out.println("End after start?  " + saleEnd.isAfter(saleStart));
        System.out.println("Start equals end? " + saleStart.isEqual(saleEnd));
        System.out.println("compareTo:        " + saleStart.compareTo(saleEnd));
    }
}
```

`compareTo` returned `-3` here, which happens to be the day difference for these two dates, but the result should be treated as just "negative means before, zero means equal, positive means after." The exact magnitude is an implementation detail, not part of the contract.

<h1 id="temporaladjusters-for-common-date-patterns">
  TemporalAdjusters for Common Date Patterns
</h1>

Some date queries don't fit cleanly into "add N days" or "set the day to X." Examples from an e-commerce context: "the first day of next month for monthly billing," "the next Saturday for weekend delivery," "the last day of the current month for an end-of-month report." The `TemporalAdjusters` class (note the plural) has static methods that produce these adjusters, passed to `LocalDate.with`.

The pattern is always the same. Build an adjuster, hand it to `with`, get a new `LocalDate` back. The original date is never modified.

```java
import java.time.LocalDate;
import java.time.DayOfWeek;
import java.time.temporal.TemporalAdjusters;

public class BillingDates {
    public static void main(String[] args) {
        LocalDate today = LocalDate.of(2026, 5, 14);

        LocalDate firstOfMonth = today.with(TemporalAdjusters.firstDayOfMonth());
        LocalDate lastOfMonth = today.with(TemporalAdjusters.lastDayOfMonth());
        LocalDate firstOfNextMonth = today.with(TemporalAdjusters.firstDayOfNextMonth());
        LocalDate nextMonday = today.with(TemporalAdjusters.next(DayOfWeek.MONDAY));
        LocalDate nextOrSameSunday = today.with(TemporalAdjusters.nextOrSame(DayOfWeek.SUNDAY));
        LocalDate firstFridayOfMonth = today.with(TemporalAdjusters.firstInMonth(DayOfWeek.FRIDAY));

        System.out.println("Today:                  " + today);
        System.out.println("First of month:         " + firstOfMonth);
        System.out.println("Last of month:          " + lastOfMonth);
        System.out.println("First of next month:    " + firstOfNextMonth);
        System.out.println("Next Monday:            " + nextMonday);
        System.out.println("Next or same Sunday:    " + nextOrSameSunday);
        System.out.println("First Friday of month:  " + firstFridayOfMonth);
    }
}
```

A few details. `next(DayOfWeek.MONDAY)` always returns a date strictly after today, even if today is already Monday. `nextOrSame(DayOfWeek.X)` returns today if today is already that day of the week, otherwise it advances to the next occurrence. `firstInMonth(DayOfWeek.FRIDAY)` finds the first Friday in the current month, a common pattern for "first Friday is payday" or "first Friday of the month is the early-access sale."

A more realistic use case: a monthly billing job needs to know the next billing date for each customer.

```java
import java.time.LocalDate;
import java.time.temporal.TemporalAdjusters;

public class NextBillingDate {
    public static void main(String[] args) {
        LocalDate today = LocalDate.of(2026, 5, 14);
        LocalDate nextBillingDate = today.with(TemporalAdjusters.firstDayOfNextMonth());

        System.out.println("Today:               " + today);
        System.out.println("Next billing date:   " + nextBillingDate);
    }
}
```

That's a one-liner that took ten lines of buggy `java.util.Calendar` code before Java 8. The adjuster handles year rollover automatically: when `today` is in December, `firstDayOfNextMonth()` returns January 1 of the next year. No special case to remember.

`TemporalAdjusters.next(X)` walks day by day, up to 7 days. That's fine for any normal call but means it's not a constant-time lookup; it's bounded by 7 iterations. For one-off queries this never matters.

<h1 id="immutability-and-chaining">Immutability and Chaining</h1>

Every method covered so far returns a new `LocalDate`. The original is untouched. Writing `orderDate.plusDays(7)` and ignoring the return value leaves `orderDate` unchanged.

```java
import java.time.LocalDate;

public class ImmutabilityTrap {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);
        orderDate.plusDays(7);

        System.out.println("Order date after plusDays(7): " + orderDate);
    }
}
```

The `plusDays(7)` call returned a new `LocalDate` representing May 21, but nothing captured it, so the result was discarded. `orderDate` still points to May 14. To use the new date, assign it: `orderDate = orderDate.plusDays(7);`, or store it in a new variable.

The same property makes chaining safe and easy to read. Each method returns a `LocalDate`, so another method can be called on the result:

```java
import java.time.LocalDate;
import java.time.DayOfWeek;
import java.time.temporal.TemporalAdjusters;

public class ChainedAdjustments {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);

        LocalDate firstSaturdayAfterDelivery = orderDate
                .plusDays(7)
                .with(TemporalAdjusters.next(DayOfWeek.SATURDAY));

        System.out.println("Order date:                        " + orderDate);
        System.out.println("First Saturday after delivery:     " + firstSaturdayAfterDelivery);
    }
}
```

Each step in the chain produces an intermediate `LocalDate` that the next step consumes. Because everything is immutable, there's no chance of one step corrupting another, and the original `orderDate` is unchanged at the end.

A long chain of `plusX` / `with` calls allocates one intermediate `LocalDate` per call. They're small (three primitive fields plus the object header), and the JVM collects them quickly, so the cost is real but usually invisible.

<h1 id="dayofweek-and-month-enums">DayOfWeek and Month Enums</h1>

Two enums show up alongside `LocalDate` often enough to deserve their own section: `DayOfWeek` and `Month`. Both are real Java enums, not constants, so they can be switched on, stored in collections, and called as methods.

```java
import java.time.LocalDate;
import java.time.DayOfWeek;
import java.time.Month;

public class WeekendDelivery {
    public static void main(String[] args) {
        LocalDate orderDate = LocalDate.of(2026, 5, 14);
        DayOfWeek day = orderDate.getDayOfWeek();
        Month month = orderDate.getMonth();

        System.out.println("Order date:        " + orderDate);
        System.out.println("Day of week:       " + day);
        System.out.println("Day numeric value: " + day.getValue());
        System.out.println("Is weekend?        " + (day == DayOfWeek.SATURDAY || day == DayOfWeek.SUNDAY));
        System.out.println("Month name:        " + month);
        System.out.println("Month numeric:     " + month.getValue());
        System.out.println("Days in month:     " + month.length(orderDate.isLeapYear()));
    }
}
```

`DayOfWeek.getValue()` follows the ISO numbering: Monday is `1`, Sunday is `7`. That's different from some older APIs where Sunday was `1`. `Month.getValue()` is 1 to 12, with January being `1`. `Month.length(boolean leapYear)` returns 28 or 29 for February depending on the flag, and a constant for every other month.

A clean weekend-check using `switch`:

```java
import java.time.LocalDate;
import java.time.DayOfWeek;

public class DeliveryFee {
    public static void main(String[] args) {
        LocalDate deliveryDate = LocalDate.of(2026, 5, 16);
        DayOfWeek day = deliveryDate.getDayOfWeek();

        double fee;
        switch (day) {
            case SATURDAY, SUNDAY -> fee = 9.99;
            default -> fee = 4.99;
        }

        System.out.println("Delivery date: " + deliveryDate + " (" + day + ")");
        System.out.println("Delivery fee:  $" + fee);
    }
}
```

Switching on `DayOfWeek` constants is more readable than checking magic numbers like `day == 6 || day == 7`. The enums also work well with `EnumSet` for representing "delivery days" or "blackout days" as a set.

<h1 id="a-common-mistake-forgetting-immutability">
  A Common Mistake: Forgetting Immutability
</h1>

A bug that shows up in real code: a developer wants to advance a date in a loop and writes:

**What's wrong with this code?**

```java
import java.time.LocalDate;

public class BrokenLoop {
    public static void main(String[] args) {
        LocalDate saleDay = LocalDate.of(2026, 11, 27);
        for (int i = 0; i < 5; i++) {
            saleDay.plusDays(1);
            System.out.println("Day " + i + ": " + saleDay);
        }
    }
}
```

The same date prints five times because `plusDays(1)` returns a new `LocalDate` and the code throws it away. `saleDay` is never reassigned.

**Fix:**

```java
import java.time.LocalDate;

public class FixedLoop {
    public static void main(String[] args) {
        LocalDate saleDay = LocalDate.of(2026, 11, 27);
        for (int i = 0; i < 5; i++) {
            System.out.println("Day " + i + ": " + saleDay);
            saleDay = saleDay.plusDays(1);
        }
    }
}
```

The fix is one character: an `=` sign. Reassigning the return value of `plusDays(1)` back to `saleDay` advances it on each iteration. The same issue exists for `String`, `BigDecimal`, and every other immutable type.
