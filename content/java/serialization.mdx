<h1 id="what-serialization-solves">What Serialization Solves</h1>

Consider a program that holds a shopping cart in memory. The cart has a customer, a list of products, quantities, and a running total. The moment the program exits, every object in that cart disappears. To make the cart survive a restart, or to ship the cart from a web server to a background job on another machine, you need a way to capture the object as bytes and reconstruct it later.

Plain text formats (CSV, your own delimited file) work for flat data, but they fall apart when you have one object pointing at another, which points at a list of more objects. Walking that graph by hand and writing each field is tedious and error-prone. Serialization automates the walk: you hand it the root object, and it follows every reference and writes the whole graph as one byte stream.

The diagram shows what a typical `Order` graph looks like in memory. The `Order` holds a reference to a `Customer`, plus references to two `LineItem` objects, each of which points at a `Product`. Serialization starts at the root (`Order`) and follows every arrow, writing each object exactly once. When you read the bytes back, you get the whole shape restored, with the same references wired up.

The byte stream is binary and Java-specific. It is not designed for humans to read, and it is not designed for other languages or platforms to consume. That trade-off is the source of most of serialization's strengths (compact, automatic, preserves graphs) and most of its weaknesses (brittle, Java-only, hard to debug).

<h1 id="the-serializable-marker-interface">
  The Serializable Marker Interface
</h1>

Java does not let you serialize any object you please. A class has to opt in by implementing `java.io.Serializable`. The interface has no methods. It is a marker, a flag that says "instances of this class are safe to write as bytes."

```java
import java.io.Serializable;

public class Product implements Serializable {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public String getName() {
        return name;
    }

    public double getPrice() {
        return price;
    }
}
```

That `implements Serializable` line is the entire opt-in. There is nothing to override, nothing to annotate, nothing to register. The JVM checks the marker at write time and refuses to serialize objects whose class does not have it.

The opt-in is per class, but it cascades. If `Order` is `Serializable` and holds a `Customer`, the `Customer` class also has to be `Serializable`. Same for any class reachable through any field. The whole graph has to be Serializable, transitively.

In the diagram, every class except `Address` implements `Serializable`. The moment you try to serialize an `Order`, the writer walks down through `Customer` to `Address` and throws `NotSerializableException` because `Address` is not on the approved list. One missing marker anywhere in the reachable graph poisons the whole write.

The fix is either to make `Address` implement `Serializable`, or to mark the `address` field as `transient` so the writer skips it.

<h1 id="writing-objects-with-objectoutputstream">
  Writing Objects with ObjectOutputStream
</h1>

`ObjectOutputStream` is the class that does the actual writing. You wrap it around any `OutputStream` (a `FileOutputStream` for disk, a `ByteArrayOutputStream` for an in-memory buffer, a socket's output stream for a network), and you call `writeObject` to push an object into it.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;

public class WriteOneProduct {
    public static void main(String[] args) throws IOException {
        Product notebook = new Product("Notebook", 4.99);

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("product.ser"))) {
            out.writeObject(notebook);
        }

        long size = Files.size(Path.of("product.ser"));
        System.out.println("Wrote product.ser, " + size + " bytes");
    }
}

class Product implements Serializable {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

The byte count will vary by a few bytes depending on the field names and class name, but the shape is the same. A handful of bytes for the stream header, more bytes for the class descriptor, and the field values packed in. We print the size rather than the contents because the file is binary; opening it in a text editor would show mostly gibberish with a few readable strings.

`ObjectOutputStream` exposes a `writeObject(Object)` method for objects and a family of methods for primitives: `writeInt`, `writeLong`, `writeDouble`, `writeBoolean`, `writeByte`, `writeShort`, `writeChar`, `writeFloat`, plus `writeUTF` for strings. Mixing them is allowed when you want a custom binary format, but for everyday "save an object", `writeObject` is the standard call.

The try-with-resources block matters. `ObjectOutputStream` buffers data internally, so anything you write may be sitting in memory until the stream is closed or flushed. If your program crashes before close, you can end up with a truncated file that the reader cannot parse. `try (...)` guarantees `close()` runs, which in turn flushes the buffer.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class WriteOrder {
    public static void main(String[] args) throws IOException {
        Customer ana = new Customer("Ana", "ana@example.com");
        List<Product> items = List.of(
            new Product("Notebook", 4.99),
            new Product("Pen", 1.49)
        );
        Order order = new Order(1001, ana, items);

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("order.ser"))) {
            out.writeObject(order);
        }

        long size = Files.size(Path.of("order.ser"));
        System.out.println("Wrote order.ser, " + size + " bytes");
    }
}

class Order implements Serializable {
    private int id;
    private Customer customer;
    private List<Product> items;

    public Order(int id, Customer customer, List<Product> items) {
        this.id = id;
        this.customer = customer;
        this.items = items;
    }
}

class Customer implements Serializable {
    private String name;
    private String email;

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }
}

class Product implements Serializable {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

A single `writeObject(order)` call wrote the whole `Order`, the `Customer` inside it, the `List` of products, and each `Product`. The writer figured out the graph on its own. There is no per-field code, no recursion to write, no schema to declare in advance.

The reason a list of two products serializes cleanly is that `java.util.ArrayList` (which `List.of` returns under a different backing type, also Serializable) and the built-in collection types implement `Serializable`. That's a hidden convenience: most of the standard collection types already opt in, so you don't have to wrap them.

The writer also detects shared references. If the same `Customer` object is referenced from two different `Order` objects in one write, the bytes for that `Customer` appear only once. The second reference is stored as a back-pointer. When you read the bytes back, both `Order` objects point at the same `Customer` instance, just like before.

The diagram shows the pipeline. Your code hands an object to `ObjectOutputStream`. The stream walks the graph, encodes each object using the class descriptor and field values, and pushes bytes into the underlying `FileOutputStream`. The file stream pushes bytes to disk. The split between `ObjectOutputStream` (logic) and `FileOutputStream` (destination) is what lets the same serializer write to disk, memory, or a socket without changing how you call it.

Java serialization is slow compared to JSON or Protocol Buffers, often by an order of magnitude or more. The serializer uses reflection to read fields, writes a full class descriptor (class name, field names, types, `serialVersionUID`) on the first occurrence of each class, and tracks every object reference to handle cycles. None of that is free.

<h1 id="what-gets-written-fields-the-whole-tree-not-methods">
  What Gets Written: Fields, the Whole Tree, Not Methods
</h1>

The serializer writes the instance state and the class identity. It does not write methods, because methods belong to the class, and the class is identified by name when the bytes are read back later. The deserializer looks the class up by its fully qualified name and uses the local `.class` file's methods. If the class isn't on the classpath when you read, the read fails.

Concretely, for each object the writer emits:

| What                | Example                         | Notes                                             |
| ------------------- | ------------------------------- | ------------------------------------------------- |
| Class descriptor    | `com.shop.Product`              | Name, `serialVersionUID`, field list              |
| Each instance field | `name="Notebook"`, `price=4.99` | All non-`transient`, non-`static` fields          |
| Super-class state   | Fields inherited from a parent  | Walked up the chain if the parent is Serializable |

The class descriptor is written once per class in the stream. If you write twenty `Product` objects, the descriptor for `Product` appears once at the top and each of the twenty bodies references it. That's a small but meaningful optimization for streams that contain many objects of the same type.

Super-class fields are included if the super-class is itself Serializable. If a Serializable class extends a non-Serializable class, the super-class fields are not written, and on deserialization that super-class is reconstructed by calling its no-arg constructor. Make the whole hierarchy Serializable when you can.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;

public class WriteSeveralProducts {
    public static void main(String[] args) throws IOException {
        Product[] catalog = {
            new Product("Notebook", 4.99),
            new Product("Pen", 1.49),
            new Product("Eraser", 0.79),
            new Product("Pencil", 0.99),
            new Product("Stapler", 6.49)
        };

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("catalog.ser"))) {
            for (Product p : catalog) {
                out.writeObject(p);
            }
        }

        long size = Files.size(Path.of("catalog.ser"));
        System.out.println("Wrote catalog.ser, " + size + " bytes for "
            + catalog.length + " products");
    }
}

class Product implements Serializable {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

The first `Product` carries the full class descriptor with it. The next four reference that descriptor instead of repeating it, which is why the byte cost per product drops after the first one. The same pattern holds for any class that appears multiple times in one stream.

<h1 id="transient-fields-the-serializer-should-skip">
  transient: Fields the Serializer Should Skip
</h1>

Some fields shouldn't be written. Common cases:

- **Secrets**: passwords, API keys, payment tokens. Writing these to disk turns one secret into two, and now you have a file to secure.
- **Derived data**: a `totalPrice` field that can be recomputed from line items. Writing it duplicates information and lets the stored value drift out of sync with the source data.
- **External resources**: a database connection, an open file handle, a thread. These can't survive being turned into bytes anyway; they'd be invalid on the way back.

The `transient` keyword marks a field as "skip during serialization." It is a Java language modifier, not an annotation, and it goes on the field declaration.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;

public class WriteCustomerWithToken {
    public static void main(String[] args) throws IOException {
        Customer ana = new Customer("Ana", "ana@example.com", "tok_secret_xyz");

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("customer.ser"))) {
            out.writeObject(ana);
        }

        long size = Files.size(Path.of("customer.ser"));
        System.out.println("Wrote customer.ser, " + size + " bytes "
            + "(paymentToken excluded)");
    }
}

class Customer implements Serializable {
    private String name;
    private String email;
    private transient String paymentToken;

    public Customer(String name, String email, String paymentToken) {
        this.name = name;
        this.email = email;
        this.paymentToken = paymentToken;
    }
}
```

The `paymentToken` field never made it into the bytes. When `Customer` is read back later, that field will be reset to `null` (the default for a reference type). The same rule applies for primitives: a `transient int` reads back as `0`, a `transient boolean` as `false`, and so on. That's by design. The writer skips the field, and the reader doesn't have anything to assign, so it leaves the default in place.

The diagram shows the two fields that make it to disk and the one that doesn't. The `transient` token branch terminates at the field; it never reaches the file. To make the token survive, store it elsewhere (a secrets manager, an encrypted vault) and re-attach it after deserialization.

<h1 id="static-fields-are-not-serialized">static Fields Are Not Serialized</h1>

`static` fields belong to the class, not to any single instance. Serialization writes instance state, so `static` fields are not part of the picture. The serializer ignores them whether they're marked `transient` or not.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;

public class WriteWithStatic {
    public static void main(String[] args) throws IOException {
        Product.taxRatePercent = 8;
        Product notebook = new Product("Notebook", 4.99);

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("static.ser"))) {
            out.writeObject(notebook);
        }

        System.out.println("Wrote. The static taxRatePercent is NOT in the file.");
    }
}

class Product implements Serializable {
    static int taxRatePercent = 0;
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

The current value of `taxRatePercent` is `8` when we write, but that value lives on the `Product` class object, not on the `notebook` instance. The file captures `name` and `price` and nothing else. After deserialization in some other program (or in a later JVM run), the static field will have whatever value that program assigns to it, which might be the class default (`0`) if nothing else has touched it.

For a value to round-trip through serialization, it must be an instance field. Class-level state has to be managed separately.

<h1 id="serialversionuid-versioning-the-class">
  serialVersionUID: Versioning the Class
</h1>

When `ObjectOutputStream` writes an object, it tags the bytes with a class identity. The identity is not just the class name; it also includes a 64-bit hash called `serialVersionUID`. The reader uses this hash to confirm that the class it has on disk matches the class that wrote the bytes. If the hashes don't match, the reader throws `InvalidClassException` and refuses to load.

If you don't declare a `serialVersionUID`, the compiler generates one based on the class structure (class name, modifiers, super-class, fields, methods). The generated value is sensitive to almost any change. Add a field, the UID changes. Rename a method, the UID changes. Bump the JDK version on a different machine, sometimes the UID changes.

The common IDE warning ("The serializable class Foo does not declare a static final serialVersionUID field") is asking you to take control of this number instead of leaving it to the compiler. The fix is one line:

```java
import java.io.Serializable;

public class Customer implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private String email;

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

With `serialVersionUID = 1L` declared explicitly, the UID is whatever you say it is, regardless of how the class evolves. When you intentionally make a backward-incompatible change (remove a field, change a field's type), you bump the UID to a new value (`2L`) and you've consciously broken compatibility. When you make a backward-compatible change (add a new field with a sensible default), you leave the UID alone, and old serialized files still read.

The choice of literal doesn't matter. `1L`, `42L`, or some auto-generated long are all fine. What matters is that the value is declared, stable, and only changed when you mean it.

The diagram describes the check the reader performs. The value you choose at write time determines what readers see later. Picking `1L` and sticking with it across compatible changes means old files keep working. Forgetting to declare a UID and shipping a class change means future code, even with the same source-level intent, may refuse to read old files.

Letting the compiler auto-generate `serialVersionUID` is error-prone. A change as small as adding a `toString()` method can change the generated UID, breaking every file written by the old class. Declaring it explicitly costs one line and removes the risk entirely.

A common convention is to start at `1L` for a new class and bump the value only when you make a deliberately incompatible change. Some teams prefer the IDE-generated value (a long pseudo-random number) so it's obvious the field was added on purpose. Either is fine. Don't leave the field undeclared.

<h1 id="custom-serialization-with-writeobject">
  Custom Serialization with writeObject
</h1>

The default serializer reads every non-`transient`, non-`static` field via reflection and writes it. For most classes, that's exactly what you want. But occasionally you need to do something extra: encrypt a field on the way out, derive a value, validate before writing, or write a transient field in a controlled way.

You can override the write step by defining a private method with this exact signature on the class:

```java
private void writeObject(ObjectOutputStream out) throws IOException
```

The signature is checked by name and parameter types. If it matches, the serializer calls your method instead of the default routine. Inside it, you typically call `out.defaultWriteObject()` first to write the standard fields, then write extra data with the `writeXxx` methods.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;

public class WriteCartWithChecksum {
    public static void main(String[] args) throws IOException {
        ShoppingCart cart = new ShoppingCart("cust-42");
        cart.addItem("Notebook", 4.99);
        cart.addItem("Pen", 1.49);

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("cart.ser"))) {
            out.writeObject(cart);
        }

        long size = Files.size(Path.of("cart.ser"));
        System.out.println("Wrote cart.ser, " + size + " bytes");
    }
}

class ShoppingCart implements Serializable {
    private static final long serialVersionUID = 1L;

    private String customerId;
    private java.util.List<String> itemNames = new java.util.ArrayList<>();
    private java.util.List<Double> itemPrices = new java.util.ArrayList<>();

    public ShoppingCart(String customerId) {
        this.customerId = customerId;
    }

    public void addItem(String name, double price) {
        itemNames.add(name);
        itemPrices.add(price);
    }

    private int checksum() {
        return itemNames.hashCode() ^ itemPrices.hashCode();
    }

    private void writeObject(ObjectOutputStream out) throws IOException {
        out.defaultWriteObject();
        out.writeInt(checksum());
    }
}
```

The `writeObject` method runs as part of the default write pipeline. `out.defaultWriteObject()` writes all the regular instance fields (`customerId`, `itemNames`, `itemPrices`). Then `out.writeInt(checksum())` appends one extra `int` to the stream. The reader, on the deserialization side, would call `in.defaultReadObject()` and then `in.readInt()` to recover the checksum. Whatever you write in `writeObject` is what the reader has to mirror.

A few rules about the custom `writeObject`:

- **It must be `private`.** The signature is part of an implicit contract with the serialization machinery, not part of your public API.
- **It must not be `static`.** It's invoked on the instance being written.
- **The return type must be `void`** and the throws clause must include `IOException`.
- **Call `defaultWriteObject` first** if you also want the normal field writing. If you skip it, you're responsible for writing every field yourself.

Custom serialization is a precision tool. Use it when you need the control, not as a default. Most classes work fine with the built-in field walker.

<h1 id="externalizable-total-control-total-responsibility">
  Externalizable: Total Control, Total Responsibility
</h1>

`Externalizable` is an alternative to `Serializable` that hands you complete control over the byte format. Instead of letting the serializer walk your fields, you implement two methods:

```java
public void writeExternal(ObjectOutput out) throws IOException
public void readExternal(ObjectInput in) throws IOException, ClassNotFoundException
```

`Externalizable` extends `Serializable`, so anything Externalizable is also Serializable. The difference is that the serializer recognizes Externalizable classes and skips its own field-walking logic entirely. Whatever you write in `writeExternal` is the only data that goes on the wire. Whatever you read in `readExternal` is the only data the reader gets back.

```java
import java.io.Externalizable;
import java.io.IOException;
import java.io.ObjectInput;
import java.io.ObjectOutput;

public class CompactProduct implements Externalizable {
    private String name;
    private double price;

    // Required: public no-arg constructor for Externalizable
    public CompactProduct() {
    }

    public CompactProduct(String name, double price) {
        this.name = name;
        this.price = price;
    }

    @Override
    public void writeExternal(ObjectOutput out) throws IOException {
        out.writeUTF(name);
        out.writeDouble(price);
    }

    @Override
    public void readExternal(ObjectInput in) throws IOException {
        this.name = in.readUTF();
        this.price = in.readDouble();
    }
}
```

There is no `serialVersionUID` requirement for Externalizable (the framework doesn't use it to validate compatibility), but the class still needs a public no-arg constructor because the framework instantiates the class via that constructor before calling `readExternal`. Forget the no-arg constructor and reads fail at runtime.

| Property                | `Serializable`                   | `Externalizable`                         |
| ----------------------- | -------------------------------- | ---------------------------------------- |
| Method overrides needed | None (or optional `writeObject`) | Both `writeExternal` and `readExternal`  |
| Field writing           | Automatic via reflection         | Manual: you write each field by hand     |
| No-arg constructor      | Not required                     | Required, must be public                 |
| `transient` honored     | Yes (those fields are skipped)   | Irrelevant (you write what you want)     |
| Performance             | Slower (reflection)              | Faster (direct field access)             |
| Maintenance             | Lower (fields just work)         | Higher (every field change is two edits) |

`Externalizable` shows up rarely in modern code. The maintenance burden of keeping two methods in sync with the field list outweighs the speed boost in almost every codebase. When raw performance matters, teams usually move off Java serialization entirely (to Protocol Buffers, FlatBuffers, or a custom binary format) rather than chase milliseconds with `Externalizable`. Knowing it exists is mostly an interview thing.

<h1 id="limitations-and-when-not-to-use-it">
  Limitations and When Not to Use It
</h1>

Java's built-in serialization has real weaknesses, and the modern advice is to avoid it for new code unless you have a specific reason to use it. The main issues:

**`NotSerializableException` at runtime.** The "every reachable class must be Serializable" rule is checked when you call `writeObject`, not at compile time. A long-running service can run fine for weeks until someone adds an `Address` object to a cart and the write fails. Compile-time formats (Protocol Buffers, Avro) catch this at build time.

**Brittleness across class changes.** Even with an explicit `serialVersionUID`, certain changes break old files: renaming a field, changing a field's type, removing a field, moving a class to a different package. Long-lived serialized data is a maintenance liability.

**Java-only.** The byte format is undocumented in detail and tied to the JVM's reflection system. A Python service can't deserialize it. A Go service can't deserialize it. A future Java version might tighten compatibility rules and break it. Cross-language data exchange needs a portable format.

**Security risk on the read side.** Deserialization runs constructors, executes class initializers, and can be tricked into instantiating classes the attacker chose if the attacker controls the byte stream. This has been the source of major real-world vulnerabilities. Never deserialize bytes from an untrusted source. Writing is safer (you control what goes in), but the format carries security baggage on the way back.

**Performance.** Reflective field access plus full class descriptors per stream plus reference tracking adds up. For high-throughput systems, JSON parsers and binary formats like Protocol Buffers are usually faster, sometimes by an order of magnitude.

**Modern alternatives in one sentence each.** JSON (with Jackson or Gson) is human-readable, cross-language, and widely supported, at the cost of larger byte sizes. Protocol Buffers (and similar formats like Avro and Thrift) are compact binary formats with explicit schemas, fast, cross-language, and designed for evolution.

When does Java serialization still make sense? In short-lived, in-process scenarios: caching an object graph to a temp file during a single program run, passing an object between threads via a `ByteArrayOutputStream`, or working in legacy code that already uses it. For anything that crosses a process boundary, lives longer than a release, or comes from outside your trust boundary, pick a different format.

A graph with deep cycles or huge collections can balloon the byte count and the time to write. The serializer has to track every object it has already seen to handle cycles, so the bookkeeping scales with the number of reachable objects. For very large graphs, write the data in chunks or pick a streaming format instead of trying to serialize everything in one call.

<h1 id="putting-it-together">Putting It Together</h1>

A small program that exercises most of what this lesson covered: a class with an explicit `serialVersionUID`, a `transient` field for a secret, a `static` field that is silently skipped, a custom `writeObject` that adds a checksum, and a single call that walks the whole object graph to disk.

```java
import java.io.FileOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

public class WriteOrderFull {
    public static void main(String[] args) throws IOException {
        Customer ana = new Customer("Ana", "ana@example.com", "tok_secret_xyz");
        Order order = new Order(1001, ana);
        order.addItem("Notebook", 4.99, 2);
        order.addItem("Pen", 1.49, 1);

        try (ObjectOutputStream out =
                 new ObjectOutputStream(new FileOutputStream("full-order.ser"))) {
            out.writeObject(order);
        }

        long size = Files.size(Path.of("full-order.ser"));
        System.out.println("Wrote full-order.ser, " + size + " bytes");
    }
}

class Order implements Serializable {
    private static final long serialVersionUID = 1L;
    static int nextOrderId = 1;

    private int id;
    private Customer customer;
    private List<LineItem> items = new ArrayList<>();

    public Order(int id, Customer customer) {
        this.id = id;
        this.customer = customer;
    }

    public void addItem(String name, double price, int quantity) {
        items.add(new LineItem(name, price, quantity));
    }

    private int checksum() {
        return items.hashCode();
    }

    private void writeObject(ObjectOutputStream out) throws IOException {
        out.defaultWriteObject();
        out.writeInt(checksum());
    }
}

class Customer implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private String email;
    private transient String paymentToken;

    public Customer(String name, String email, String paymentToken) {
        this.name = name;
        this.email = email;
        this.paymentToken = paymentToken;
    }
}

class LineItem implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private double price;
    private int quantity;

    public LineItem(String name, double price, int quantity) {
        this.name = name;
        this.price = price;
        this.quantity = quantity;
    }
}
```

A few things happen in those bytes. The `Order`'s `serialVersionUID` is stamped in. The `static nextOrderId` is ignored. The `Customer`'s `paymentToken` is omitted because it's `transient`. Both `LineItem` objects are written, and the second one uses the back-reference shortcut for the class descriptor that the first one introduced. The custom `writeObject` appends a checksum after the default fields. All of that came from one `out.writeObject(order)` call.
