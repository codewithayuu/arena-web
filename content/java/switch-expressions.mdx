<h1 id="whats-wrong-with-the-classic-switch">
  What's Wrong with the Classic Switch
</h1>

Before we look at the new syntax, it helps to name the problems the new form is solving. Each one shows up in real codebases, and the new form was designed specifically to make these mistakes impossible.

**Problem 1: missing `break` causes fall-through.** This is the bug from the classic switch lesson. If you forget a `break`, control flows into the next case and overwrites your value.

```java
public class ClassicFallThroughBug {
    public static void main(String[] args) {
        String customerTier = "SILVER";
        int discount = 0;

        switch (customerTier) {
            case "BRONZE":
                discount = 5;
            case "SILVER":
                discount = 10;
            case "GOLD":
                discount = 20;
            default:
                discount = 0;
        }

        System.out.println("Discount: " + discount + "%");
    }
}
```

The author wanted `10`, got `0`. Every case fell through, and `default` overwrote everything with `0`.

**Problem 2: a switch statement can't return a value.** If you want a `discount` variable to come out of a switch, you've to declare it before the switch, assign to it in each case, and trust yourself to handle every branch.

```java
int discount;
switch (customerTier) {
    case "BRONZE":
        discount = 5;
        break;
    case "SILVER":
        discount = 10;
        break;
    default:
        discount = 0;
}
```

The variable lives outside the switch, gets assigned inside it, and there's no compiler check that you assigned a value in every branch. Forget one and the compiler complains about "may not have been initialized," which forces you to add a `default` or write `int discount = 0;` up top, hiding bugs where a real case wasn't handled.

**Problem 3: every case repeats `break`.** It's boilerplate that exists only to opt out of a default behavior that's rarely wanted. Reading a switch with twelve `break` statements is harder than reading one without them.

**Problem 4: variables declared in cases need scope hacks.** As the classic switch lesson covered, two cases that declare a variable with the same name require `{}` braces around each case body. The braces are noise that exists only to work around a quirk of fall-through scoping.

The new switch form (arrow cases, expressions, `yield`, exhaustiveness) was designed to make every one of these problems either impossible or loud.

<h1 id="arrow-form-no-more-forgotten-break">
  Arrow Form: No More Forgotten break
</h1>

The simplest change is the new case syntax. Instead of `case "X":` followed by a body that runs until the next `break`, you write `case "X" ->` followed by a single statement or expression that runs and then exits the switch. No fall-through, ever.

```java
public class ArrowFormStatement {
    public static void main(String[] args) {
        String orderStatus = "SHIPPED";

        switch (orderStatus) {
            case "PLACED" -> System.out.println("We received your order.");
            case "SHIPPED" -> System.out.println("Your order is on its way.");
            case "DELIVERED" -> System.out.println("Your order has arrived.");
            case "CANCELLED" -> System.out.println("Your order was cancelled.");
            default -> System.out.println("Unknown status.");
        }
    }
}
```

Read the case bodies down the right side. No `break`, no semicolons hanging in space, no chance that `SHIPPED` falls through to `DELIVERED`. The arrow means "if this matches, run exactly this and you're done."

The two forms compared side by side at the dispatch level:

The classic form has that extra `break found?` loop because forgetting a `break` is what fall-through means. The arrow form removes the loop entirely. After the matched body runs, control jumps to the end of the switch. There's no way to fall through, even on purpose, with arrow syntax.

The right side of an arrow case can be one of three things: a single expression statement (like the `println` calls above), a `throw` statement, or a block in braces. For one-line bodies, the arrow form reads as a clean dispatch table, which is what most switches want to be.

<h1 id="multi-label-cases-with-commas">Multi-Label Cases with Commas</h1>

In the classic form, sharing a body between cases meant stacking labels with no code in between:

```java
case "STANDARD":
case "ECONOMY":
    cost = 5.00;
    break;
```

The arrow form replaces that with a comma-separated list on a single line:

```java
public class ShippingCostArrow {
    public static void main(String[] args) {
        String shippingMethod = "ECONOMY";

        switch (shippingMethod) {
            case "STANDARD", "ECONOMY" -> System.out.println("Shipping cost: $5.00");
            case "EXPRESS", "TWO_DAY" -> System.out.println("Shipping cost: $12.00");
            case "OVERNIGHT" -> System.out.println("Shipping cost: $25.00");
            default -> System.out.println("Unknown shipping method.");
        }
    }
}
```

`"STANDARD"` and `"ECONOMY"` both match the first arrow and run the same body. The intent is right there in one line: either of these values means $5.00. There's no chance of accidentally inserting code between the labels and confusing the next reader.

The comma works for any number of labels:

```java
public class OrderInProgress {
    public static void main(String[] args) {
        String orderStatus = "CONFIRMED";

        switch (orderStatus) {
            case "PLACED", "CONFIRMED", "PACKED", "SHIPPED" ->
                System.out.println("in-progress");
            case "DELIVERED" ->
                System.out.println("complete");
            case "CANCELLED", "REFUNDED" ->
                System.out.println("closed");
            default ->
                System.out.println("unknown");
        }
    }
}
```

Four statuses share the `in-progress` body. The comma list reads naturally as "any of these."

<h1 id="switch-as-an-expression">Switch as an Expression</h1>

This is the bigger change. In addition to being a statement that runs side effects, `switch` can now be an **expression** that produces a value. You write it on the right side of `=` and the matched case's value becomes the result.

```java
public class DiscountAsExpression {
    public static void main(String[] args) {
        String customerTier = "GOLD";

        int discount = switch (customerTier) {
            case "BRONZE" -> 5;
            case "SILVER" -> 10;
            case "GOLD" -> 20;
            case "PLATINUM" -> 30;
            default -> 0;
        };

        System.out.println("Discount: " + discount + "%");
    }
}
```

Three details. First, the switch is on the right side of `=`, same place as any other expression. Second, each arrow case produces a number, not a side effect. Third, the whole thing ends with a semicolon, because `int discount = switch (...) { ... };` is a single statement (a variable assignment whose right-hand side happens to be a switch expression).

The expression form fixes the boilerplate from the classic form. Instead of declaring `discount` first, assigning to it in every case, and relying on `default` to catch the rest, you bind `discount` once to whatever the switch evaluates to. There's no chance that a case forgets to assign, because every case must produce a value. The compiler enforces it.

It also works with `var`, which is convenient when the type is obvious from the cases:

```java
public class StatusGroupWithVar {
    public static void main(String[] args) {
        String orderStatus = "SHIPPED";

        var group = switch (orderStatus) {
            case "PLACED", "CONFIRMED", "SHIPPED" -> "in-progress";
            case "DELIVERED" -> "complete";
            case "CANCELLED", "REFUNDED" -> "closed";
            default -> "unknown";
        };

        System.out.println("Status group: " + group);
    }
}
```

All four arms produce `String`, so `var` infers `String`. The code reads as "compute `group` from `orderStatus` by dispatching on these cases."

A switch expression is no slower than the classic form. The compiler generates the same `tableswitch` or `lookupswitch` bytecode internally. The benefits are at the source level: fewer ways to write a bug, less boilerplate, and a value comes out the end.

<h1 id="yield-block-bodies-in-expression-form">
  yield: Block Bodies in Expression Form
</h1>

Sometimes one case needs more than a single expression. Maybe it logs, computes an intermediate value, and then returns a result. The arrow's right-hand side can be a `{}` block, and inside that block you use `yield` to say "this is the value of the case."

```java
public class DiscountWithLogging {
    public static void main(String[] args) {
        String customerTier = "GOLD";

        int discount = switch (customerTier) {
            case "BRONZE" -> 5;
            case "SILVER" -> 10;
            case "GOLD" -> {
                System.out.println("Applying premium GOLD perks.");
                int baseDiscount = 20;
                int bonusForGold = 5;
                yield baseDiscount + bonusForGold;
            }
            case "PLATINUM" -> 30;
            default -> 0;
        };

        System.out.println("Discount: " + discount + "%");
    }
}
```

The `GOLD` case runs three statements, then `yield baseDiscount + bonusForGold;` produces the value (`25`). The other cases stay one-liners and don't need `yield`. You mix and match per case.

Two rules to remember about `yield`:

- It's required inside a block body of an arrow case in an expression form. The compiler won't accept a block that doesn't yield a value.
- It's a keyword only inside a switch expression block. Outside one, `yield` is still a valid variable or method name (the language designers call this a "contextual keyword"). You can have a method called `yield` in your code and the compiler won't complain.

Another example using `yield` for a shipping cost that depends on weight inside one branch:

```java
public class ShippingCostByMethodAndWeight {
    public static void main(String[] args) {
        String shippingMethod = "OVERNIGHT";
        double weightKg = 7.5;

        double cost = switch (shippingMethod) {
            case "STANDARD", "ECONOMY" -> 5.00;
            case "EXPRESS", "TWO_DAY" -> 12.00;
            case "OVERNIGHT" -> {
                double base = 25.00;
                double surcharge = weightKg > 5 ? 10.00 : 0;
                yield base + surcharge;
            }
            default -> 0.00;
        };

        System.out.println("Shipping cost: $" + cost);
    }
}
```

The `OVERNIGHT` arm needs a calculation, so it uses a block and `yield`s the final number. Every other arm produces a value with a simple expression.

The diagram traces what `yield` does inside the block: run any setup statements, then produce one value that becomes the result of the whole switch expression. Think of `yield` as "return, but only from this case, not from the surrounding method."

<h1 id="exhaustiveness-the-compiler-has-your-back">
  Exhaustiveness: The Compiler Has Your Back
</h1>

When `switch` is an expression, the compiler insists that every possible value of the input is handled. If it's not, the code doesn't compile. This is what "exhaustiveness" means: every reachable input must lead to a value, no exceptions.

For a `String` selector, exhaustiveness almost always means including a `default`, because `String` has infinite possible values. The compiler can't prove that "BRONZE", "SILVER", "GOLD" are the only inputs that will appear.

For an `enum` selector, exhaustiveness can be reached without `default`, because the compiler knows the full list of constants. Cover them all and you're done.

```java
public class ExhaustiveEnumSwitch {
    enum OrderStatus { PLACED, CONFIRMED, SHIPPED, DELIVERED, CANCELLED }

    public static void main(String[] args) {
        OrderStatus status = OrderStatus.SHIPPED;

        String label = switch (status) {
            case PLACED -> "Order received";
            case CONFIRMED -> "Order confirmed";
            case SHIPPED -> "On its way";
            case DELIVERED -> "Arrived";
            case CANCELLED -> "Cancelled";
        };

        System.out.println(label);
    }
}
```

No `default` and the code compiles. The five constants in `OrderStatus` are listed exactly once each. The compiler walks the enum, checks the cases, and confirms full coverage.

Drop one of them and the code stops compiling. What happens if you forget `CANCELLED`:

```java
String label = switch (status) {
    case PLACED -> "Order received";
    case CONFIRMED -> "Order confirmed";
    case SHIPPED -> "On its way";
    case DELIVERED -> "Arrived";
};
```

The compiler reports something like:

```text
error: the switch expression does not cover all possible input values
        String label = switch (status) {
                       ^
```

This is one of the strongest reasons to prefer the expression form with enums. If someone adds a new constant to `OrderStatus` later (say, `REFUNDED`), every exhaustive switch expression on that enum becomes a compile error, pointing to the places that need updating. The classic switch statement would ignore the new constant without warning.

You can still add a `default` to an enum switch expression if you want a catch-all, but it's no longer the only way to satisfy the compiler. Many codebases skip `default` on exhaustive enum switches specifically to get the compile-time safety net.

The diagram traces the compiler's logic. Cover every constant or supply a `default`. Either path produces a complete switch expression. Neither path leaves a hole.

A small note on Java 21: the same exhaustiveness rule also covers `case null` and sealed-type hierarchies. For now, treat exhaustiveness as "all enum constants OR a default for any other type."

<h1 id="classic-vs-arrow-statement-vs-switch-expression">
  Classic vs Arrow Statement vs Switch Expression
</h1>

Three forms now coexist in modern Java: the classic colon-syntax statement, the arrow-syntax statement (no value), and the switch expression (produces a value). They're easy to mix up. This table summarizes the differences.

| Feature              | Classic statement              | Arrow statement         | Switch expression                            |
| -------------------- | ------------------------------ | ----------------------- | -------------------------------------------- |
| Syntax               | `case X: ... break;`           | `case X -> ...;`        | `var v = switch (...) { case X -> value; };` |
| Returns a value      | No                             | No                      | Yes                                          |
| Fall-through         | Yes (default behavior)         | No                      | No                                           |
| Needs `break`        | Yes, on every case             | No                      | No                                           |
| Multi-label cases    | Stacked labels                 | Comma list              | Comma list                                   |
| Block body           | Inside `{}`, ends with `break` | Inside `{}`, no `break` | Inside `{}`, must `yield`                    |
| Exhaustiveness check | No                             | No                      | Yes                                          |
| `default` required   | Optional                       | Optional                | Required unless enum is fully covered        |
| Variable scope       | Shared across cases            | Per-case scope          | Per-case scope                               |
| Available since      | Java 1.0 (Java 7 for `String`) | Java 14                 | Java 14                                      |

A simple rule of thumb: if you want a value out, use the expression form. If you want side effects with no value, use the arrow statement form. Use the classic colon form when you're in an existing codebase that hasn't migrated, or for the rare case where intentional fall-through is exactly what you want.

<h1 id="backward-compatibility-and-mixing-styles">
  Backward Compatibility and Mixing Styles
</h1>

The classic colon syntax still works. You don't have to rewrite anything. Existing code keeps compiling and behaving as before. The new arrow and expression forms are additions, not replacements.

You can technically mix colon-syntax and arrow-syntax cases within the same switch:

```java
// Don't do this, but it compiles
switch (orderStatus) {
    case "PLACED":
        System.out.println("Received");
        break;
    case "SHIPPED" -> System.out.println("On its way");
    default -> System.out.println("Other");
}
```

This compiles, but don't do it. The mixed style reads as a mess: some cases have `break`, others don't, and the reader has to track which syntax each case uses to know whether fall-through can happen. Pick one form per switch and stick with it.

A simple convention works well: arrow form for new code, classic form when editing inside an existing classic switch. If you start refactoring one case, refactor them all together. Half-converted switches are worse than either pure form.

<h1 id="when-not-to-use-a-switch-expression">
  When NOT to Use a Switch Expression
</h1>

Switch expressions work well when each case **produces a value**: a discount percent, a status label, a shipping cost. They're a poor fit when each case has different **side effects** and no value to return.

A case that fits the expression form. Each branch produces a number.

```java
int taxRate = switch (productCategory) {
    case "BOOKS" -> 0;
    case "ELECTRONICS" -> 8;
    case "CLOTHING" -> 5;
    case "GROCERIES" -> 2;
    default -> 6;
};
```

Clean, one variable comes out, every case is a tiny arrow.

A case where the arrow **statement** form fits, not the expression form. Each branch runs different side-effect code and doesn't compute a single value.

```java
public class OrderActionDispatch {
    public static void main(String[] args) {
        String orderStatus = "DELIVERED";

        switch (orderStatus) {
            case "PLACED" -> {
                sendConfirmationEmail();
                logEvent("order_received");
            }
            case "SHIPPED" -> sendTrackingLink();
            case "DELIVERED" -> {
                markAsComplete();
                requestReview();
            }
            case "CANCELLED" -> refundCustomer();
            default -> logEvent("unknown_status");
        }
    }

    static void sendConfirmationEmail() { System.out.println("Email sent."); }
    static void sendTrackingLink()      { System.out.println("Tracking link sent."); }
    static void markAsComplete()        { System.out.println("Order completed."); }
    static void requestReview()         { System.out.println("Review requested."); }
    static void refundCustomer()        { System.out.println("Customer refunded."); }
    static void logEvent(String event)  { System.out.println("Logged: " + event); }
}
```

Each case fires off different actions. There's no single value to compute, so wrapping the switch in `var x = ...` would be awkward. The arrow statement form keeps the dispatch-table feel of the expression form (no `break`, no fall-through, multi-label cases) without forcing you to return a value you don't have.

The choice between expression and statement is really the choice between "every case produces a value of the same type" and "every case does different things." If you find yourself writing `yield;` with no value, or every arm calling a `void` method, that's a sign the statement form is the better fit.

<h1 id="a-note-on-case-null-and-pattern-matching">
  A Note on case null and Pattern Matching
</h1>

Java 21 added two more upgrades to `switch`: a special `case null` label that lets you handle `null` inputs without a separate `if` check, and pattern matching that lets `case` labels be types (`case Integer i ->`) or deconstructed records.

For now, the rule is simple: if you switch on a `String` or other reference type that can be `null`, the switch still throws `NullPointerException` exactly like the classic form. Guard with an `if` before the switch.

```java
public class NullStringGuard {
    public static void main(String[] args) {
        String customerTier = null;

        if (customerTier == null) {
            System.out.println("Tier not set.");
            return;
        }

        int discount = switch (customerTier) {
            case "BRONZE" -> 5;
            case "SILVER" -> 10;
            case "GOLD" -> 20;
            default -> 0;
        };

        System.out.println("Discount: " + discount + "%");
    }
}
```

The `if` check runs before the switch, so the switch never sees `null`.
