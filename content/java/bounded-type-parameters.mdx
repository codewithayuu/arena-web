<h1 id="why-unbounded-generics-are-limiting">
  Why Unbounded Generics Are Limiting
</h1>

Consider a tiny utility class that picks the cheapest item from a list. With an unbounded type parameter, the body has nothing to work with:

```java
import java.util.List;

public class CheapestPicker<T> {
    public T pickCheapest(List<T> items) {
        T cheapest = items.get(0);
        for (T item : items) {
            if (item.getPrice() < cheapest.getPrice()) {
                cheapest = item;
            }
        }
        return cheapest;
    }
}
```

This doesn't compile. The error is direct:

```text
error: cannot find symbol
            if (item.getPrice() < cheapest.getPrice()) {
                    ^
  symbol:   method getPrice()
  location: variable item of type T
```

From the compiler's view, `T` could be any reference type. `String` doesn't have `getPrice`. Neither does `Integer`, or `URL`, or any class you might invent next week. With no constraint on `T`, the only methods the compiler trusts are the ones on `Object`: `equals`, `hashCode`, `toString`, and a few more.

The fix is to constrain `T` to types that do have `getPrice`. Bounded type parameters do exactly that: they narrow the universe of allowed type arguments so the body has methods to call.

<h1 id="single-upper-bound-with-extends">Single Upper Bound With extends</h1>

The syntax is `<T extends SomeType>`. It says "any type argument for `T` must be `SomeType` or a subtype of it." The `extends` keyword here doesn't mean class inheritance specifically; it means "is a subtype of," which covers both class inheritance and interface implementation. There is no `implements` keyword in generic bounds. Whether `SomeType` is a class or an interface, you still write `extends`.

Here's a fixed `CheapestPicker` with `T` bounded to `Product`:

```java
import java.util.ArrayList;
import java.util.List;

public class CheapestPickerDemo {
    public static void main(String[] args) {
        List<Product> products = new ArrayList<>();
        products.add(new Product("Headphones", 79.99));
        products.add(new Product("Notebook", 5.50));
        products.add(new Product("Keyboard", 39.99));

        CheapestPicker<Product> picker = new CheapestPicker<>();
        Product cheapest = picker.pickCheapest(products);
        System.out.println("Cheapest: " + cheapest);
    }
}

class CheapestPicker<T extends Product> {
    public T pickCheapest(List<T> items) {
        T cheapest = items.get(0);
        for (T item : items) {
            if (item.getPrice() < cheapest.getPrice()) {
                cheapest = item;
            }
        }
        return cheapest;
    }
}

class Product {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() {
        return price;
    }

    public String toString() {
        return name + " ($" + price + ")";
    }
}
```

The body of `pickCheapest` now calls `item.getPrice()` freely. The compiler is convinced that any `T` plugged into this class is a `Product` (or one of its subclasses), so every `Product` method is fair game.

A bound on `T` is a promise about what `T` supports. Inside the method, the compiler treats `T` as if it were that bound. From the outside, callers see the more precise type they passed in.

Adding a bound doesn't add runtime overhead. The bound is checked at compile time, and at runtime `T` is erased to its bound, not to `Object`. A `<T extends Product>` parameter erases to `Product`, which means fewer casts inserted by the compiler.

<h1 id="bounds-work-with-subtypes">Bounds Work With Subtypes</h1>

A bound admits the bound type and everything below it. If `DigitalProduct` and `PhysicalProduct` both extend `Product`, then a `CheapestPicker<DigitalProduct>` and a `CheapestPicker<PhysicalProduct>` are both legal. A `CheapestPicker<String>` is not.

```java
import java.util.ArrayList;
import java.util.List;

public class SubtypeBoundDemo {
    public static void main(String[] args) {
        List<DigitalProduct> downloads = new ArrayList<>();
        downloads.add(new DigitalProduct("Audiobook", 14.99, 250));
        downloads.add(new DigitalProduct("E-Book", 9.99, 12));
        downloads.add(new DigitalProduct("Course", 49.00, 1200));

        CheapestPicker<DigitalProduct> picker = new CheapestPicker<>();
        DigitalProduct cheapest = picker.pickCheapest(downloads);
        System.out.println("Cheapest download: " + cheapest);
        System.out.println("Size on disk: " + cheapest.getFileSizeMb() + " MB");
    }
}

class DigitalProduct extends Product {
    private int fileSizeMb;

    public DigitalProduct(String name, double price, int fileSizeMb) {
        super(name, price);
        this.fileSizeMb = fileSizeMb;
    }

    public int getFileSizeMb() {
        return fileSizeMb;
    }
}
```

The call site uses `DigitalProduct` as the type argument and gets back a `DigitalProduct`, not a `Product`. The bound is the floor on what `T` can be, but the type argument can be any subtype, and the return type tracks it. That's the second reason bounds beat using `Product` directly as the parameter and return type: you don't lose type information about subclasses.

For `<T extends Number>`, the green nodes under `Number` are allowed: `Integer`, `Double`, `Long`. `String` is not. For `<T extends Product>`, the green nodes under `Product` are allowed: `DigitalProduct`, `PhysicalProduct`. A class higher up like `Object` is not, because `Object` is a _supertype_ of `Product`, not a subtype.

<h1 id="bounds-on-interfaces">Bounds On Interfaces</h1>

Bounds with `extends` accept interfaces just as readily as classes. A bound like `<T extends Comparable<T>>` says "T must be a type that knows how to compare itself to other instances of T." Inside the body, you can call `compareTo` on any `T`.

```java
import java.util.ArrayList;
import java.util.List;

public class MaxFinderDemo {
    public static void main(String[] args) {
        List<Integer> orderCounts = new ArrayList<>();
        orderCounts.add(120);
        orderCounts.add(45);
        orderCounts.add(310);
        orderCounts.add(78);

        MaxFinder<Integer> finder = new MaxFinder<>();
        System.out.println("Largest count: " + finder.max(orderCounts));

        List<String> productNames = new ArrayList<>();
        productNames.add("Notebook");
        productNames.add("Headphones");
        productNames.add("Keyboard");

        MaxFinder<String> stringFinder = new MaxFinder<>();
        System.out.println("Last name alphabetically: " + stringFinder.max(productNames));
    }
}

class MaxFinder<T extends Comparable<T>> {
    public T max(List<T> items) {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }
}
```

`Integer` and `String` both implement `Comparable`, so both are accepted as type arguments. The body calls `item.compareTo(best)` without any cast or instanceof check, because the bound has already promised that `T` supports it.

The `extends` keyword reads strangely when the right-hand side is an interface. English-language intuition says you "implement" an interface and "extend" a class. Generic bounds smooth over the distinction. The Java designers picked one word for both cases so the syntax doesn't fork. Whenever you see `<T extends X>`, read it as "T is a subtype of X," whether X is a class or an interface.

<h1 id="calling-methods-on-bounded-t">Calling Methods On Bounded T</h1>

The rule is simple. Inside a class or method whose type parameter is bounded by `B`, every method available on `B` is available on any value of type `T`. No casts. No checks. If `B` defines `getPrice()`, then `someT.getPrice()` compiles. If `B` is `Comparable<T>`, then `someT.compareTo(other)` compiles.

A short example with a class bound for context. `Cart<T extends Product>` can compute totals because it knows every `T` has `getPrice`:

```java
import java.util.ArrayList;
import java.util.List;

public class CartDemo {
    public static void main(String[] args) {
        Cart<Product> cart = new Cart<>();
        cart.add(new Product("Notebook", 5.50));
        cart.add(new Product("Headphones", 79.99));
        cart.add(new Product("Keyboard", 39.99));

        System.out.println("Cart total: $" + cart.total());
    }
}

class Cart<T extends Product> {
    private List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
    }

    public double total() {
        double sum = 0.0;
        for (T item : items) {
            sum += item.getPrice();
        }
        return sum;
    }
}

class Product {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() {
        return price;
    }

    public String toString() {
        return name + " ($" + price + ")";
    }
}
```

The body of `total` calls `item.getPrice()` on each `T`. Without the bound, that call wouldn't compile. With the bound, it's as natural as if the field were typed `Product` directly. The extra value of the bound is that `Cart<DigitalProduct>` keeps the precise element type, which matters when you read items back out.

<h1 id="multiple-bounds">Multiple Bounds</h1>

A type parameter can require more than one supertype. The syntax uses `&` to separate the bounds:

```java
<T extends ClassOrInterface1 & Interface2 & Interface3>
```

This says "T must be a subtype of _all_ of these." The rules are strict:

- If a class is among the bounds, it must come first. You can list at most one class.
- Everything after the first bound must be an interface.
- Bounds are separated by `&`, not commas (commas separate distinct type parameters).

The standard use case is "T must be a `Product` and also `Comparable`." Then the body can both ask `T` for its price and ask one `T` to compare itself to another.

```java
import java.util.ArrayList;
import java.util.List;

public class SortedCatalogDemo {
    public static void main(String[] args) {
        SortedCatalog<RatedProduct> catalog = new SortedCatalog<>();
        catalog.add(new RatedProduct("Headphones", 79.99, 4.5));
        catalog.add(new RatedProduct("Notebook", 5.50, 4.2));
        catalog.add(new RatedProduct("Keyboard", 39.99, 4.7));

        System.out.println("Top rated: " + catalog.topRated());
        System.out.println("Total: $" + catalog.total());
    }
}

class SortedCatalog<T extends Product & Comparable<T>> {
    private List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
    }

    public T topRated() {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }

    public double total() {
        double sum = 0.0;
        for (T item : items) {
            sum += item.getPrice();
        }
        return sum;
    }
}

class Product {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() {
        return price;
    }

    public String getName() {
        return name;
    }

    public String toString() {
        return name + " ($" + price + ")";
    }
}

class RatedProduct extends Product implements Comparable<RatedProduct> {
    private double rating;

    public RatedProduct(String name, double price, double rating) {
        super(name, price);
        this.rating = rating;
    }

    public double getRating() {
        return rating;
    }

    public int compareTo(RatedProduct other) {
        return Double.compare(this.rating, other.rating);
    }

    public String toString() {
        return super.toString() + " (rating " + rating + ")";
    }
}
```

`SortedCatalog` requires _both_ `extends Product` (so it can read prices) and `Comparable<T>` (so it can rank items). `RatedProduct` satisfies both: it's a `Product`, and it implements `Comparable<RatedProduct>`. Plug in any other type and the compiler rejects it.

Try swapping the order, and the compiler complains:

```java
class Broken<T extends Comparable<T> & Product> { }
```

```text
error: interface expected here
class Broken<T extends Comparable<T> & Product> { }
                                       ^
```

The class bound must come first. Everything after the first `&` is interpreted as an interface, and `Product` is a class. Swap them and the code compiles. This rule exists because Java has single inheritance for classes: a type can extend only one class but implement many interfaces, so at most one of the bounds can be a class, and putting it first makes that explicit.

<h1 id="recursive-self-referential-bounds">
  Recursive (Self-Referential) Bounds
</h1>

A recursive bound is one where `T` appears in its own constraint. The most common is `<T extends Comparable<T>>`. Read it as "T must be a type that knows how to compare itself to other Ts." This pattern shows up everywhere in the JDK because it's a clear way to say "items in this collection can be ordered against each other."

Here's the pattern as a generic method:

```java
import java.util.ArrayList;
import java.util.List;

public class MaxDemo {
    public static void main(String[] args) {
        List<Integer> stocks = new ArrayList<>();
        stocks.add(8);
        stocks.add(15);
        stocks.add(3);
        System.out.println("Max stock: " + max(stocks));

        List<String> names = new ArrayList<>();
        names.add("Notebook");
        names.add("Headphones");
        names.add("Keyboard");
        System.out.println("Last name: " + max(names));
    }

    public static <T extends Comparable<T>> T max(List<T> items) {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }
}
```

The bound `T extends Comparable<T>` is what makes `item.compareTo(best)` legal inside the method. Without the recursive bound, `item.compareTo(...)` wouldn't type-check, because the compiler would have no idea what `T` is comparable against.

The JDK uses a useful variant for `Collections.max`:

```java
public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)
```

The `Comparable<? super T>` part allows a type that's comparable to _any of its supertypes_, not strictly to itself. That lets you call `max` on a `List<DigitalProduct>` when the comparison logic lives in `Product`. The takeaway here is that the recursive bound is the structural idea, and the wildcard is a refinement that buys flexibility.

The pattern works because every type that implements `Comparable<Self>` satisfies the bound at the call site, and inside the method the compiler can rely on `compareTo` being there.

<h1 id="bounds-on-classes-methods-and-interfaces">
  Bounds On Classes, Methods, And Interfaces
</h1>

Bounds aren't limited to one shape. The same syntax works on generic classes, generic methods, and generic interfaces. Here's a quick example of each.

A generic class with a bound:

```java
import java.util.ArrayList;
import java.util.List;

public class PriceSorter<T extends Product> {
    private List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
    }

    public List<T> sortedByPrice() {
        List<T> copy = new ArrayList<>(items);
        copy.sort((a, b) -> Double.compare(a.getPrice(), b.getPrice()));
        return copy;
    }
}
```

A generic method with a bound (the method is generic even though its enclosing class isn't):

```java
import java.util.List;

public class Catalog {
    public static <T extends Product> double averagePrice(List<T> items) {
        double sum = 0.0;
        for (T item : items) {
            sum += item.getPrice();
        }
        return sum / items.size();
    }
}
```

A generic interface with a bound:

```java
public interface Ranker<T extends Comparable<T>> {
    T best(java.util.List<T> items);
    T worst(java.util.List<T> items);
}
```

The bound's effect is the same in every case: inside the body, the compiler treats `T` as if it were the bound type. The body of `averagePrice` calls `getPrice` on each `T`. An implementation of `Ranker` can call `compareTo` on any `T`. A `PriceSorter<T extends Product>` can sort items by price because every `T` is a `Product`.

What you can't do is escape the bound. A `PriceSorter<String>` is rejected before the body ever runs. The bound is enforced at every call to the constructor, every call to the method, and every assignment to a variable typed `PriceSorter<...>`.

A bounded `T` erases to its bound, not to `Object`. For `<T extends Product>`, the compiled bytecode treats `T` as `Product`, which means fewer synthetic casts when callers read the result. For `<T>` with no bound, erasure goes to `Object`, and the compiler inserts casts at every read. The runtime cost difference is usually negligible, but it's there.

<h1 id="bounds-vs-wildcards">Bounds vs Wildcards</h1>

The lesson next door is about wildcards (`<? extends Product>`, `<? super Product>`). The two ideas look similar but live on opposite sides of a declaration.

| Feature          | Bounded type parameter                                            | Wildcard                                                           |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| Where it appears | On a class/method declaration: `<T extends Product>`              | On a _use_ of a generic type: `List<? extends Product>`            |
| What it names    | A type variable you can refer to elsewhere in the signature       | An anonymous type position                                         |
| Use case         | "I need to know this type inside the body and possibly return it" | "I just want to consume or produce values without naming the type" |
| Reusable name    | Yes (the same `T` can appear in multiple places)                  | No (each `?` is independent)                                       |

A bounded type parameter is for declaring a generic class or method. A wildcard is for using a generic type with flexibility about its argument. They cover different problems.

<h1 id="common-mistakes">Common Mistakes</h1>

A short list of common bugs:

**Using `implements` instead of `extends` for an interface bound.**

```java
class Sorter<T implements Comparable<T>> { }
```

```text
error: > expected
class Sorter<T implements Comparable<T>> { }
                ^
```

In generic bounds, you always write `extends`, even when the bound is an interface.

**Putting a class after an interface in multiple bounds.**

```java
class Catalog<T extends Comparable<T> & Product> { }
```

```text
error: interface expected here
```

The class must come first. Swap to `<T extends Product & Comparable<T>>`.

**Listing more than one class in the bounds.**

```java
class X<T extends Product & Order> { }
```

If both `Product` and `Order` are classes, this is rejected. Java's single inheritance for classes means at most one class can be in the bounds.

**Expecting the bound to grant access to subclass methods.**

```java
class Stocker<T extends Product> {
    public int sizeOnDisk(T item) {
        return item.getFileSizeMb();
    }
}
```

This fails because `getFileSizeMb` lives on `DigitalProduct`, not on `Product`. The bound only promises `Product`'s API. Even if every caller passes `DigitalProduct`, the compiler binds the body to the bound, not to whatever specific subtype shows up later.

<h1 id="a-worked-end-to-end-example">A Worked End-to-End Example</h1>

A small program that ties it all together: bounded class, bounded method, multiple bounds, recursive bound. The shop has a wishlist that can only hold `Product` subtypes, and it can rank items by their natural order when those items happen to be `Comparable`.

```java
import java.util.ArrayList;
import java.util.List;

public class WishlistDemo {
    public static void main(String[] args) {
        Wishlist<RatedProduct> wishlist = new Wishlist<>();
        wishlist.add(new RatedProduct("Headphones", 79.99, 4.5));
        wishlist.add(new RatedProduct("Notebook", 5.50, 4.2));
        wishlist.add(new RatedProduct("Keyboard", 39.99, 4.7));
        wishlist.add(new RatedProduct("Mouse", 19.99, 4.0));

        System.out.println("Wishlist total: $" + wishlist.total());
        System.out.println("Top pick: " + wishlist.topPick());
        System.out.println("Best by name: " + Catalog.max(List.of("Headphones", "Keyboard", "Notebook")));
    }
}

class Wishlist<T extends Product & Comparable<T>> {
    private List<T> items = new ArrayList<>();

    public void add(T item) {
        items.add(item);
    }

    public double total() {
        double sum = 0.0;
        for (T item : items) {
            sum += item.getPrice();
        }
        return sum;
    }

    public T topPick() {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }
}

class Catalog {
    public static <T extends Comparable<T>> T max(List<T> items) {
        T best = items.get(0);
        for (T item : items) {
            if (item.compareTo(best) > 0) {
                best = item;
            }
        }
        return best;
    }
}

class Product {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() {
        return price;
    }

    public String toString() {
        return name + " ($" + price + ")";
    }
}

class RatedProduct extends Product implements Comparable<RatedProduct> {
    private double rating;

    public RatedProduct(String name, double price, double rating) {
        super(name, price);
        this.rating = rating;
    }

    public int compareTo(RatedProduct other) {
        return Double.compare(this.rating, other.rating);
    }

    public String toString() {
        return super.toString() + " (rating " + rating + ")";
    }
}
```

`Wishlist` requires two things from its type argument: that it's a `Product` (so it can read prices) and that it's `Comparable` to itself (so it can rank). `RatedProduct` satisfies both, and the wishlist works smoothly. `Catalog.max` is a generic method with a recursive bound, and it works on any `Comparable` type, from `String` to `RatedProduct`. The same pattern, three different scopes.
