<h1 id="what-localtime-represents">What LocalTime Represents</h1>

A `LocalTime` is a point on a 24-hour clock. It does not know what day it is, and it does not know what time zone the clock is set to. `LocalTime.of(9, 30)` for a store that opens at 9:30 AM is just "the moment when a clock reads 09:30." Whether that means 09:30 in Mumbai, New York, or anywhere else is a separate concern that `ZonedDateTime` handles.

The internal layout is four fields:

| Field      | Range            | Notes                                        |
| ---------- | ---------------- | -------------------------------------------- |
| Hour       | 0 to 23          | 24-hour clock. There is no `24` and no `-1`. |
| Minute     | 0 to 59          |                                              |
| Second     | 0 to 59          | No leap second 60.                           |
| Nanosecond | 0 to 999,999,999 | Sub-second precision.                        |

That gives a resolution of one nanosecond and a range that wraps cleanly at midnight. The class is immutable and thread-safe, so every method that "changes" a value actually returns a new `LocalTime`.

The diagram shows the cycle a `LocalTime` lives on. `MIN` is `00:00`, `MAX` is `23:59:59.999999999`, and arithmetic wraps around at midnight in both directions. The wrap behavior comes up again in the `plusHours` and `minusMinutes` section below.

<h1 id="building-a-localtime">Building a LocalTime</h1>

There are three common ways to get a `LocalTime`: ask for the current wall-clock time, construct one from fields, or parse one from a string.

<h3 id="from-the-system-clock">From the system clock</h3>

`LocalTime.now()` reads the system clock and returns the current time of day in the default zone.

```java
import java.time.LocalTime;

public class StoreClock {
    public static void main(String[] args) {
        LocalTime now = LocalTime.now();
        System.out.println("Current time: " + now);
    }
}
```

The exact output depends on when the program runs. The printed form is ISO-8601: hour, minute, second, and a fractional part if the nanos are non-zero. Trailing zero nanos are trimmed, so a value of `09:30:00.000000000` prints as `09:30`.

<h3 id="from-fields">From fields</h3>

`LocalTime.of(...)` has four overloads, one per level of precision.

```java
import java.time.LocalTime;

public class StoreHours {
    public static void main(String[] args) {
        LocalTime opening = LocalTime.of(9, 30);
        LocalTime closing = LocalTime.of(21, 0);
        LocalTime cronStart = LocalTime.of(2, 0, 15);
        LocalTime flashSale = LocalTime.of(18, 0, 0, 500_000_000);

        System.out.println("Store opens at: " + opening);
        System.out.println("Store closes at: " + closing);
        System.out.println("Inventory job: " + cronStart);
        System.out.println("Flash sale start: " + flashSale);
    }
}
```

Each overload adds one more field. Passing an out-of-range value throws `DateTimeException` at construction time, which is one of the main advantages over the old `Date` and `Calendar` classes that rolled bad input over.

<h3 id="from-a-string">From a string</h3>

`LocalTime.parse` accepts any ISO-8601 time. The seconds and fractional seconds are optional.

```java
import java.time.LocalTime;

public class ParseTimes {
    public static void main(String[] args) {
        LocalTime opening = LocalTime.parse("09:30");
        LocalTime cutoff = LocalTime.parse("13:00:00");
        LocalTime precise = LocalTime.parse("18:00:15.123");

        System.out.println("Opening: " + opening);
        System.out.println("Lunch cutoff: " + cutoff);
        System.out.println("Precise: " + precise);
    }
}
```

Custom formats like `"9:30 AM"` are not handled by `LocalTime.parse` directly; those require a `DateTimeFormatter`. The default `parse` method only understands ISO-8601.

<h1 id="constants">Constants</h1>

`LocalTime` ships four named constants that come up often:

| Constant             | Value                | Use For                                           |
| -------------------- | -------------------- | ------------------------------------------------- |
| `LocalTime.MIN`      | `00:00`              | Start-of-day boundary checks.                     |
| `LocalTime.MAX`      | `23:59:59.999999999` | End-of-day boundary checks.                       |
| `LocalTime.MIDNIGHT` | `00:00`              | Same as `MIN`, but reads better in some contexts. |
| `LocalTime.NOON`     | `12:00`              | Reads better than `LocalTime.of(12, 0)`.          |

```java
import java.time.LocalTime;

public class StoreBoundaries {
    public static void main(String[] args) {
        System.out.println("MIN:      " + LocalTime.MIN);
        System.out.println("MAX:      " + LocalTime.MAX);
        System.out.println("MIDNIGHT: " + LocalTime.MIDNIGHT);
        System.out.println("NOON:     " + LocalTime.NOON);
    }
}
```

`MIN` and `MIDNIGHT` are the same value with two names. Use whichever reads better in context: `MIDNIGHT` for "the start of a new day," `MIN` for "the smallest valid `LocalTime`."

<h1 id="reading-fields">Reading Fields</h1>

The getters mirror the four fields:

```java
import java.time.LocalTime;

public class FlashSaleFields {
    public static void main(String[] args) {
        LocalTime saleStart = LocalTime.of(18, 30, 15, 250_000_000);

        System.out.println("Hour:   " + saleStart.getHour());
        System.out.println("Minute: " + saleStart.getMinute());
        System.out.println("Second: " + saleStart.getSecond());
        System.out.println("Nano:   " + saleStart.getNano());
    }
}
```

`getHour` returns an `int` in `[0, 23]`, `getMinute` and `getSecond` return `int` in `[0, 59]`, and `getNano` returns an `int` in `[0, 999_999_999]`. There is no `getMillisecond` because the underlying storage is nanos; for milliseconds, divide nanos by one million.

<h1 id="arithmetic-and-wrap-around">Arithmetic and Wrap-Around</h1>

Every `plus*` and `minus*` method returns a new `LocalTime`. The original is untouched.

```java
import java.time.LocalTime;

public class ShiftTimes {
    public static void main(String[] args) {
        LocalTime opening = LocalTime.of(9, 30);

        LocalTime breakStart = opening.plusHours(3);
        LocalTime breakEnd = breakStart.plusMinutes(45);
        LocalTime closing = opening.plusHours(12).plusMinutes(30);

        System.out.println("Opening:     " + opening);
        System.out.println("Break start: " + breakStart);
        System.out.println("Break end:   " + breakEnd);
        System.out.println("Closing:     " + closing);
    }
}
```

The interesting case is what happens when arithmetic crosses midnight. `LocalTime` has no concept of "the next day," so the value wraps around. Adding three hours to `23:00` gives `02:00`, not `26:00`.

```java
import java.time.LocalTime;

public class CronWrap {
    public static void main(String[] args) {
        LocalTime closing = LocalTime.of(23, 0);
        LocalTime threeHoursLater = closing.plusHours(3);

        LocalTime midnightCron = LocalTime.of(0, 30);
        LocalTime tenMinutesEarlier = midnightCron.minusMinutes(40);

        System.out.println("23:00 + 3h = " + threeHoursLater);
        System.out.println("00:30 - 40m = " + tenMinutesEarlier);
    }
}
```

That wrap is a feature, not a bug, but it is also a sharp edge. An inventory cron starting at `02:00` with "run it three hours earlier" produces `23:00` on the same `LocalTime`, with no information about which day. When the day matters, combine `LocalTime` with a `LocalDate` into a `LocalDateTime`.

`plusHours`, `plusMinutes`, and friends allocate a new `LocalTime` every call. For one-off calls that does not matter. Inside a tight loop that builds thousands of times per second, compute the offset once and reuse it.

The available arithmetic methods cover all four fields:

| Add                 | Subtract             | Effect                                      |
| ------------------- | -------------------- | ------------------------------------------- |
| `plusHours(long)`   | `minusHours(long)`   | Adds or subtracts hours, wraps at midnight. |
| `plusMinutes(long)` | `minusMinutes(long)` | Same, by minutes.                           |
| `plusSeconds(long)` | `minusSeconds(long)` | Same, by seconds.                           |
| `plusNanos(long)`   | `minusNanos(long)`   | Same, by nanoseconds.                       |

There is no `plusMillis` on `LocalTime`. For a `long` of milliseconds, multiply by one million and call `plusNanos`, or use the more general `plus(amount, unit)` overload with `ChronoUnit.MILLIS`.

<h1 id="setting-individual-fields">Setting Individual Fields</h1>

The `with*` methods return a copy with one field changed. Like `plus*`, they never mutate the original.

```java
import java.time.LocalTime;

public class AdjustClosing {
    public static void main(String[] args) {
        LocalTime weekdayClosing = LocalTime.of(21, 0);

        LocalTime weekendClosing = weekdayClosing.withHour(23);
        LocalTime holidayClosing = weekdayClosing.withMinute(30);
        LocalTime cleanClose = weekdayClosing.withSecond(0).withNano(0);

        System.out.println("Weekday: " + weekdayClosing);
        System.out.println("Weekend: " + weekendClosing);
        System.out.println("Holiday: " + holidayClosing);
        System.out.println("Clean:   " + cleanClose);
    }
}
```

Out-of-range arguments throw `DateTimeException`. `withHour(24)` fails the same way `LocalTime.of(24, 0)` does.

<h1 id="comparing-times">Comparing Times</h1>

`LocalTime` implements `Comparable<LocalTime>` and provides three convenience methods:

| Method             | Returns   | Use For                      |
| ------------------ | --------- | ---------------------------- |
| `isBefore(other)`  | `boolean` | Strict less-than.            |
| `isAfter(other)`   | `boolean` | Strict greater-than.         |
| `compareTo(other)` | `int`     | Negative, zero, or positive. |
| `equals(other)`    | `boolean` | All four fields match.       |

The classic use case is checking whether the store is open right now.

```java
import java.time.LocalTime;

public class StoreOpen {
    public static void main(String[] args) {
        LocalTime opening = LocalTime.of(9, 30);
        LocalTime closing = LocalTime.of(21, 0);
        LocalTime now = LocalTime.of(14, 15);

        boolean open = !now.isBefore(opening) && now.isBefore(closing);
        System.out.println("Store is open at " + now + ": " + open);
    }
}
```

The `!now.isBefore(opening)` form is the standard way to say "now is at or after opening," because `LocalTime` has no `isBeforeOrEqual` method. The other half, `now.isBefore(closing)`, uses strict less-than so that `21:00` itself counts as closed.

Equality compares every field, including nanos. Two values that print the same can still be unequal if their nanoseconds differ:

```java
import java.time.LocalTime;

public class NanoEquality {
    public static void main(String[] args) {
        LocalTime a = LocalTime.of(9, 30, 0, 0);
        LocalTime b = LocalTime.of(9, 30, 0, 1);

        System.out.println("a = " + a);
        System.out.println("b = " + b);
        System.out.println("equal? " + a.equals(b));
    }
}
```

Both values print as `09:30` when their nanos are zero, but the one with a single non-zero nano prints with the full fractional second. Times parsed from outside sources can carry nanos that break what looks like an obvious equality.

<h1 id="truncation">Truncation</h1>

A `LocalTime` parsed from a system source often carries more precision than is needed. `truncatedTo(unit)` zeros out everything below the given unit.

```java
import java.time.LocalTime;
import java.time.temporal.ChronoUnit;

public class TruncateOrderTime {
    public static void main(String[] args) {
        LocalTime orderPlaced = LocalTime.of(14, 37, 22, 845_123_000);

        LocalTime toSecond = orderPlaced.truncatedTo(ChronoUnit.SECONDS);
        LocalTime toMinute = orderPlaced.truncatedTo(ChronoUnit.MINUTES);
        LocalTime toHour = orderPlaced.truncatedTo(ChronoUnit.HOURS);

        System.out.println("Raw:    " + orderPlaced);
        System.out.println("Second: " + toSecond);
        System.out.println("Minute: " + toMinute);
        System.out.println("Hour:   " + toHour);
    }
}
```

Truncation fits grouping orders into time buckets ("how many orders came in during the 14:00 hour?") or for comparing two times at minute granularity without nanosecond noise. It reads better than `withSecond(0).withNano(0)`.

Truncation is O(1) and allocates one new `LocalTime`. For bucketing millions of events by minute, this is the cheap operation, not the expensive one.

Truncation only works for units smaller than or equal to a day. `ChronoUnit.DAYS` is the upper bound; passing `ChronoUnit.WEEKS` throws `UnsupportedTemporalTypeException`.

<h1 id="nanosecond-precision-and-what-a-second-actually-stores">
  Nanosecond Precision and What a Second Actually Stores
</h1>

`LocalTime` stores nanoseconds, not milliseconds. That matters when mixing it with older APIs that only offer milliseconds, like `System.currentTimeMillis()`. The conversion is straightforward but easy to get wrong.

```java
import java.time.LocalTime;

public class NanoPrecision {
    public static void main(String[] args) {
        LocalTime t1 = LocalTime.of(10, 0, 0).plusNanos(500_000_000);
        LocalTime t2 = LocalTime.of(10, 0, 0).plusNanos(1);

        System.out.println("t1 (half a second past 10): " + t1);
        System.out.println("t2 (one nanosecond past 10): " + t2);
    }
}
```

The toString format trims trailing zeros in the fractional part, so half a second prints as `.500` and a single nanosecond prints as the full nine-digit form. The underlying storage is the same: one `int` field for nanos in the range `[0, 999_999_999]`.

<h1 id="forbidden-values-2400-and-second-60">
  Forbidden Values: 24:00 and Second 60
</h1>

Two corner cases come up enough to call out. `LocalTime` does not accept `24:00` as a representation of midnight, and it does not accept second `60` for leap seconds.

```java
import java.time.LocalTime;

public class ForbiddenValues {
    public static void main(String[] args) {
        try {
            LocalTime.of(24, 0);
        } catch (Exception e) {
            System.out.println("24:00 -> " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }

        try {
            LocalTime.of(23, 59, 60);
        } catch (Exception e) {
            System.out.println("23:59:60 -> " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}
```

The hour rule means midnight is always `00:00`. The "end of day" representation `24:00` from some other systems is not valid here; `LocalTime.MAX` is `23:59:59.999999999`. The second rule means `LocalTime` does not model leap seconds. UTC has had 27 of them since 1972, but the Java time-line treats every minute as 60 seconds. Leap-second awareness requires a different abstraction; for almost every business application, this isn't a concern.

<h1 id="differences-between-two-times">Differences Between Two Times</h1>

For quick "how far apart are these two times?" calculations, `ChronoUnit.between(a, b)` returns a `long` in the requested unit. It treats both times as points on the same 24-hour clock and returns the signed gap.

```java
import java.time.LocalTime;
import java.time.temporal.ChronoUnit;

public class SupportSla {
    public static void main(String[] args) {
        LocalTime ticketRaised = LocalTime.of(10, 15);
        LocalTime firstReply = LocalTime.of(10, 47, 30);

        long minutes = ChronoUnit.MINUTES.between(ticketRaised, firstReply);
        long seconds = ChronoUnit.SECONDS.between(ticketRaised, firstReply);

        System.out.println("First reply time: " + minutes + " minutes");
        System.out.println("First reply time: " + seconds + " seconds");
    }
}
```

`ChronoUnit.MINUTES.between` truncates toward zero. The actual gap is 32 minutes and 30 seconds, so the minute count is 32, not 33. For a richer object that knows about hours and minutes together, `Duration.between(a, b)` fits better. For now, `ChronoUnit.between` is enough for SLA checks and similar one-shot math.

One detail: `ChronoUnit.between` on two `LocalTime` values assumes they are on the same day. If `ticketRaised` is `23:30` and `firstReply` is `00:15`, the result is `-1395` minutes, not `45`. That is consistent with the wrap-around behavior of arithmetic. To span midnight, use `LocalDateTime`.

<h1 id="forward-link-combining-with-a-date">
  Forward Link: Combining with a Date
</h1>

A `LocalTime` on its own answers "what does the clock read?" but not "on which day?" For both, `LocalTime` has an `atDate(LocalDate)` method that returns a `LocalDateTime`.

```java
import java.time.LocalDate;
import java.time.LocalTime;
import java.time.LocalDateTime;

public class FlashSaleDateTime {
    public static void main(String[] args) {
        LocalTime saleStart = LocalTime.of(18, 0);
        LocalDate saleDate = LocalDate.of(2026, 5, 14);

        LocalDateTime saleMoment = saleStart.atDate(saleDate);
        System.out.println("Flash sale starts at: " + saleMoment);
    }
}
```
