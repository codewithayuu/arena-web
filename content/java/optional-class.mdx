<h1 id="the-problem-optional-solves">The Problem Optional Solves</h1>

A method that returns a reference type can return `null`, and the compiler doesn't force the caller to think about it. A search for a product by id is the obvious case: sometimes the product exists, sometimes it doesn't, and the difference matters.

```java
import java.util.HashMap;
import java.util.Map;

public class NullableLookup {
    public static void main(String[] args) {
        ProductCatalog catalog = new ProductCatalog();
        catalog.add(new Product(1L, "Notebook", 5.50));

        Product found = catalog.findById(99L);
        System.out.println("Price: $" + found.price);
    }
}

class Product {
    long id;
    String name;
    double price;

    Product(long id, String name, double price) {
        this.id = id;
        this.name = name;
        this.price = price;
    }
}

class ProductCatalog {
    private final Map<Long, Product> store = new HashMap<>();

    void add(Product p) {
        store.put(p.id, p);
    }

    Product findById(long id) {
        return store.get(id);
    }
}
```

The signature `Product findById(long id)` doesn't whisper a hint that the return value might be `null`. The caller treats it like a guaranteed `Product`, dereferences `.price`, and the program crashes.

`Optional<T>` makes the "absent" case part of the signature. A method declared as `Optional<Product> findById(long id)` is telling the caller, in the type system, that emptiness is a possible outcome. The caller has to deal with it before they can reach the underlying value.

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class OptionalLookup {
    public static void main(String[] args) {
        ProductCatalog catalog = new ProductCatalog();
        catalog.add(new Product(1L, "Notebook", 5.50));

        Optional<Product> result = catalog.findById(99L);
        if (result.isPresent()) {
            System.out.println("Price: $" + result.get().price);
        } else {
            System.out.println("Product not found");
        }
    }
}

class Product {
    long id;
    String name;
    double price;

    Product(long id, String name, double price) {
        this.id = id;
        this.name = name;
        this.price = price;
    }
}

class ProductCatalog {
    private final Map<Long, Product> store = new HashMap<>();

    void add(Product p) {
        store.put(p.id, p);
    }

    Optional<Product> findById(long id) {
        return Optional.ofNullable(store.get(id));
    }
}
```

That's the contract `Optional` enforces.

`Optional` is not a general "make this field nullable safely" tool. It was designed for return types where absence is meaningful, especially the stream terminal operations that return `Optional` for empty inputs.

<h1 id="creating-optionals">Creating Optionals</h1>

There are three factory methods. Each one captures a different intent.

```java
import java.util.Optional;

public class CreateOptionals {
    public static void main(String[] args) {
        Optional<String> name = Optional.of("Notebook");
        Optional<String> maybeName = Optional.ofNullable(null);
        Optional<String> empty = Optional.empty();

        System.out.println("name: " + name);
        System.out.println("maybeName: " + maybeName);
        System.out.println("empty: " + empty);
    }
}
```

`Optional.of(value)` insists the value is non-null. Passing a `null` throws a `NullPointerException` immediately. Use it when the value has already been established as present and a loud failure on an unexpected null is desired.

`Optional.ofNullable(value)` is the safe wrapper. A `null` becomes `Optional.empty()`; anything else becomes a present `Optional`. This is the method that lives next to legacy APIs which may or may not return `null`.

`Optional.empty()` returns a shared empty instance. Use it when there's nothing to wrap.

**What's wrong with this code?**

```java
Product p = catalog.findRaw(99L); // returns Product or null
Optional<Product> result = Optional.of(p);
```

If `p` is `null`, `Optional.of(p)` throws `NullPointerException` immediately. To allow either outcome, the call needs to be `Optional.ofNullable(p)`.

**Fix:**

```java
Product p = catalog.findRaw(99L);
Optional<Product> result = Optional.ofNullable(p);
```

A useful rule: use `Optional.of` when the value is known to be non-null and a fail-fast guard against bugs is desired; use `Optional.ofNullable` when wrapping something that may legitimately be null.

<h1 id="checking-presence">Checking Presence</h1>

`isPresent()` returns `true` if a value is inside. Java 11 added `isEmpty()` for the opposite check. Both exist mostly for branching cases that don't involve reading the value.

```java
import java.util.Optional;

public class PresenceChecks {
    public static void main(String[] args) {
        Optional<String> found = Optional.of("Headphones");
        Optional<String> missing = Optional.empty();

        System.out.println("found.isPresent(): " + found.isPresent());
        System.out.println("found.isEmpty():   " + found.isEmpty());
        System.out.println("missing.isPresent(): " + missing.isPresent());
        System.out.println("missing.isEmpty():   " + missing.isEmpty());
    }
}
```

`get()` returns the contained value, or throws `NoSuchElementException` if the Optional is empty. It looks tempting, especially paired with `isPresent()`, but that pattern is usually wrong.

```java
// Works, but it's an anti-pattern
if (result.isPresent()) {
    Product p = result.get();
    System.out.println(p.name);
}
```

The shape is identical to the `if (x != null) ...` shape that `Optional` was supposed to replace. The compiler isn't catching anything here; the result is the same null check with two extra method calls. Worse, a later reader might forget the `isPresent` guard and call `.get()` directly, which is a runtime hazard.

The functional methods are usually cleaner. Use `get()` only when no other method fits, and treat every `get()` as a place that needs justification.

<h1 id="reading-values-orelse-orelseget-orelsethrow">
  Reading Values: orElse, orElseGet, orElseThrow
</h1>

These three methods all answer the same question: what to produce when the Optional is empty. The differences are about evaluation timing and intent.

```java
import java.util.Optional;

public class FallbackValues {
    public static void main(String[] args) {
        Optional<String> nickname = Optional.of("AlgoFan");
        Optional<String> missing = Optional.empty();

        System.out.println("Present, orElse: " + nickname.orElse("Guest"));
        System.out.println("Empty,   orElse: " + missing.orElse("Guest"));
    }
}
```

`orElse(other)` always evaluates `other`. Java is a strict language, so the argument expression is computed before the method runs. This is fine when the fallback is a cheap literal. It's a problem when the fallback is expensive or has side effects.

`orElse(expensiveCall())` runs `expensiveCall()` even when the Optional is present. The returned value is then ignored. Use `orElseGet` to skip the work when there's already a value.

`orElseGet(Supplier)` accepts a supplier and only invokes it when the Optional is empty.

```java
import java.util.Optional;

public class LazyFallback {
    static String defaultGreeting() {
        System.out.println("(building default)");
        return "Hello, Guest";
    }

    public static void main(String[] args) {
        Optional<String> name = Optional.of("Hello, AlgoFan");

        System.out.println("Using orElse:");
        String a = name.orElse(defaultGreeting());
        System.out.println("  result: " + a);

        System.out.println("Using orElseGet:");
        String b = name.orElseGet(() -> defaultGreeting());
        System.out.println("  result: " + b);
    }
}
```

`orElse` printed `(building default)` even though the value was present. `orElseGet` didn't, because the supplier was never invoked.

When no fallback is desired, `orElseThrow()` (added in Java 10) throws `NoSuchElementException` from an empty Optional. The two-argument form, `orElseThrow(Supplier<? extends X>)`, throws whatever exception type the supplier produces.

```java
import java.util.Optional;

public class ThrowOnEmpty {
    public static void main(String[] args) {
        Optional<String> productName = Optional.empty();

        try {
            String name = productName.orElseThrow(
                () -> new IllegalStateException("Product is not in the catalog"));
            System.out.println(name);
        } catch (IllegalStateException e) {
            System.out.println("Caught: " + e.getMessage());
        }
    }
}
```

A small comparison table:

| Method                  | Returns when present | Returns when empty                   | Notes                                          |
| ----------------------- | -------------------- | ------------------------------------ | ---------------------------------------------- |
| `get()`                 | The value            | Throws `NoSuchElementException`      | Avoid unless presence is already proven        |
| `orElse(T other)`       | The value            | `other`                              | `other` is always evaluated, even when present |
| `orElseGet(Supplier)`   | The value            | `supplier.get()`                     | Supplier only runs when empty                  |
| `orElseThrow()`         | The value            | Throws `NoSuchElementException`      | Java 10+                                       |
| `orElseThrow(Supplier)` | The value            | Throws whatever the supplier returns | Use for a meaningful exception type            |

<h1 id="transforming-map-flatmap-filter">Transforming: map, flatMap, filter</h1>

The factory methods and fallback methods cover the basic shape. The real power comes from the transformation methods, which chain operations without pulling the value out.

`map(Function)` applies a function to the value if present, and leaves an empty Optional alone.

```java
import java.util.Optional;

public class MapExample {
    public static void main(String[] args) {
        Optional<Product> product = Optional.of(new Product("Headphones", 80.00));

        Optional<Double> price = product.map(p -> p.price);
        Optional<Double> discounted = price.map(p -> p * 0.9);

        System.out.println("Discounted price: " + discounted.orElse(0.0));

        Optional<Product> missing = Optional.empty();
        Optional<Double> noPrice = missing.map(p -> p.price);

        System.out.println("Missing price: " + noPrice.orElse(0.0));
    }
}

class Product {
    String name;
    double price;

    Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

`map` is null-safe in both directions. If the function returns `null`, `map` returns an empty Optional rather than wrapping the `null`. This is important: `Optional` never holds `null` inside, only "present with a value" or "absent".

`flatMap(Function)` is used when the mapping function itself returns an `Optional`. Without `flatMap`, the result would be `Optional<Optional<T>>`, which is awkward to read from.

```java
import java.util.Optional;

public class FlatMapExample {
    public static void main(String[] args) {
        Customer customer = new Customer("Alice", new Address("221B Baker Street"));
        Customer guest = new Customer("Guest", null);

        Optional<Customer> opt1 = Optional.of(customer);
        Optional<Customer> opt2 = Optional.of(guest);

        // With map: returns Optional<Optional<String>>
        Optional<Optional<String>> doubleWrapped = opt1.map(Customer::getAddress);

        // With flatMap: returns Optional<String> directly
        Optional<String> street1 = opt1.flatMap(Customer::getAddress)
                                       .map(Address::street);
        Optional<String> street2 = opt2.flatMap(Customer::getAddress)
                                       .map(Address::street);

        System.out.println("double-wrapped: " + doubleWrapped);
        System.out.println("Alice's street: " + street1.orElse("(none)"));
        System.out.println("Guest's street: " + street2.orElse("(none)"));
    }
}

class Customer {
    String name;
    Address address;

    Customer(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    Optional<Address> getAddress() {
        return Optional.ofNullable(address);
    }
}

class Address {
    String street;

    Address(String street) {
        this.street = street;
    }

    String street() {
        return street;
    }
}
```

Pick `map` when the function returns a plain value. Pick `flatMap` when the function itself returns an `Optional`. The pattern shows up whenever chained calls cross methods that each model their own "might be absent" outcome.

`filter(Predicate)` keeps the value only if it satisfies the predicate, otherwise the Optional becomes empty.

```java
import java.util.Optional;

public class FilterExample {
    public static void main(String[] args) {
        Optional<Product> expensive = Optional.of(new Product("Headphones", 80.00));
        Optional<Product> cheap = Optional.of(new Product("Pen", 1.99));

        Optional<Product> qualifying1 = expensive.filter(p -> p.price >= 50.0);
        Optional<Product> qualifying2 = cheap.filter(p -> p.price >= 50.0);

        System.out.println("Qualifies (expensive): " + qualifying1.isPresent());
        System.out.println("Qualifies (cheap):     " + qualifying2.isPresent());
    }
}

class Product {
    String name;
    double price;

    Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

The predicate is only invoked when a value is present. An empty Optional passes through `filter` unchanged.

Chained together, these three methods turn null-check ladders into pipelines that read top to bottom.

```java
import java.util.Optional;

public class ChainedTransforms {
    public static void main(String[] args) {
        Optional<Order> order = Optional.of(new Order(42L, 120.00, "SAVE10"));

        double finalTotal = order
            .filter(o -> o.couponCode != null)
            .map(o -> o.total * 0.9)
            .orElse(0.0);

        System.out.println("Final total: $" + finalTotal);
    }
}

class Order {
    long id;
    double total;
    String couponCode;

    Order(long id, double total, String couponCode) {
        this.id = id;
        this.total = total;
        this.couponCode = couponCode;
    }
}
```

<h1 id="side-effects-ifpresent-and-ifpresentorelse">
  Side Effects: ifPresent and ifPresentOrElse
</h1>

For side effects with no return value, use `ifPresent(Consumer)`. It calls the consumer with the value if present, and does nothing if empty.

```java
import java.util.Optional;

public class IfPresentExample {
    public static void main(String[] args) {
        Optional<Product> match = Optional.of(new Product("Headphones", 80.00));
        Optional<Product> noMatch = Optional.empty();

        match.ifPresent(p -> System.out.println("Found: " + p.name));
        noMatch.ifPresent(p -> System.out.println("This won't print"));

        System.out.println("done");
    }
}

class Product {
    String name;
    double price;

    Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

Java 9 added `ifPresentOrElse(Consumer, Runnable)`, which adds the "absent" branch.

```java
import java.util.Optional;

public class IfPresentOrElseExample {
    public static void main(String[] args) {
        Optional<Product> match = Optional.empty();

        match.ifPresentOrElse(
            p -> System.out.println("Adding " + p.name + " to cart"),
            () -> System.out.println("Sorry, item is out of stock"));
    }
}

class Product {
    String name;
    double price;

    Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}
```

The two-branch form is the functional analogue of an `if/else`. When the body of both branches is one expression each, it reads better than a boolean check plus `get`.

<h1 id="optional-meets-streams">Optional Meets Streams</h1>

The most common place `Optional` appears in practice is as the return type of stream terminal operations: `findFirst`, `findAny`, `min`, `max`, and the single-argument form of `reduce`. Each of those can return nothing if the stream is empty, and they advertise it with `Optional`.

```java
import java.util.List;
import java.util.Optional;

public class StreamTerminalsReturnOptional {
    public static void main(String[] args) {
        List<Product> catalog = List.of(
            new Product("Notebook", 5.50, 4.2),
            new Product("Headphones", 79.99, 4.8),
            new Product("Keyboard", 39.99, 4.5));

        Optional<Product> topRated = catalog.stream()
            .max((a, b) -> Double.compare(a.rating, b.rating));

        topRated.ifPresent(p -> System.out.println("Top rated: " + p.name));

        Optional<Product> firstCheap = catalog.stream()
            .filter(p -> p.price < 10.0)
            .findFirst();

        System.out.println("Cheap pick: " + firstCheap.map(p -> p.name).orElse("none"));

        Optional<Double> totalPrice = catalog.stream()
            .map(p -> p.price)
            .reduce(Double::sum);

        System.out.println("Catalog value: $" + totalPrice.orElse(0.0));
    }
}

class Product {
    String name;
    double price;
    double rating;

    Product(String name, double price, double rating) {
        this.name = name;
        this.price = price;
        this.rating = rating;
    }
}
```

Going the other direction, Java 9 added `Optional.stream()`. It turns the Optional into a `Stream<T>` of either one element (when present) or zero elements (when empty). The classic use is inside a stream pipeline's `flatMap`, applied to a list of inputs paired with a lookup that might return nothing for some of them.

```java
import java.util.List;
import java.util.Optional;
import java.util.stream.Collectors;

public class OptionalToStream {
    public static void main(String[] args) {
        ProductCatalog catalog = new ProductCatalog();
        catalog.add(new Product(1L, "Notebook", 5.50));
        catalog.add(new Product(3L, "Headphones", 79.99));

        List<Long> wantedIds = List.of(1L, 2L, 3L, 4L);

        List<String> foundNames = wantedIds.stream()
            .map(catalog::findById)
            .flatMap(Optional::stream)
            .map(p -> p.name)
            .collect(Collectors.toList());

        System.out.println("Found: " + foundNames);
    }
}

class Product {
    long id;
    String name;
    double price;

    Product(long id, String name, double price) {
        this.id = id;
        this.name = name;
        this.price = price;
    }
}

class ProductCatalog {
    private final java.util.Map<Long, Product> store = new java.util.HashMap<>();

    void add(Product p) {
        store.put(p.id, p);
    }

    Optional<Product> findById(long id) {
        return Optional.ofNullable(store.get(id));
    }
}
```

Without `Optional.stream()`, the alternative is `.filter(Optional::isPresent).map(Optional::get)`, which is the pattern `Optional` was meant to discourage. `Optional::stream` plus `flatMap` removes the empty Optionals in one step, and no `get()` appears anywhere.

The factories on the left produce either a present or empty Optional. From there, the same method names work in both states; the difference is whether the function runs (present) or the Optional is passed through (empty).

<h1 id="equality-and-tostring">Equality and toString</h1>

`Optional` overrides `equals` and `hashCode` to compare the contained values. Two present Optionals are equal when their values are equal; two empty Optionals are always equal; a present Optional and an empty one are not equal.

```java
import java.util.Optional;

public class OptionalEquality {
    public static void main(String[] args) {
        Optional<String> a = Optional.of("Notebook");
        Optional<String> b = Optional.of("Notebook");
        Optional<String> c = Optional.of("Headphones");
        Optional<String> d = Optional.empty();
        Optional<String> e = Optional.empty();

        System.out.println("a.equals(b): " + a.equals(b));
        System.out.println("a.equals(c): " + a.equals(c));
        System.out.println("a.equals(d): " + a.equals(d));
        System.out.println("d.equals(e): " + d.equals(e));
    }
}
```

`toString` is also defined: `Optional[Notebook]` for a present Optional and `Optional.empty` for an empty one. The format is good enough for log messages but not something to rely on programmatically.

<h1 id="where-not-to-use-optional">Where Not to Use Optional</h1>

`Optional` was designed for one specific job: a method's return type. Java's own designers have been explicit about this, and the language-server linters reflect it. There are four places it shows up that almost always turn out poorly.

**Don't use Optional for fields.**

```java
// Avoid
class Customer {
    long id;
    String name;
    Optional<String> phoneNumber; // bad
}
```

`Optional` is not `Serializable`, so any class with an `Optional` field can't be serialized through Java's built-in mechanism without extra work. Beyond that, it adds an extra object allocation per field and obscures the type, which makes reflection, JSON binding, and database mapping more painful. Use a plain reference (with documentation, validation, or a `@Nullable` annotation when available) for fields and reserve `Optional` for return types.

**Don't use Optional for method parameters.**

```java
// Avoid
void applyDiscount(Order order, Optional<String> couponCode) { ... }
```

A caller can still pass `null` instead of the `Optional`, defeating the purpose. The signature is noisier than necessary, and the typical use site at the caller looks like `applyDiscount(order, Optional.ofNullable(maybeCode))`, which adds ceremony with no benefit. Either accept a regular nullable parameter or add an overload without the parameter.

**Don't return Optional from a method that could return an empty collection.**

```java
// Avoid
Optional<List<Product>> findAllInCategory(String category) { ... }
```

Lists, sets, and maps already model "nothing here" via empty collections. Wrapping the collection in an Optional forces callers to do two unwraps (`Optional` first, then iterate the collection), and "empty Optional" versus "Optional of empty list" becomes an artificial distinction. Return `Collections.emptyList()` (or `List.of()`) and document that an empty result is possible.

**Don't unbox just to test for null.**

```java
// Pointless
if (opt.get() != null) { ... } // never makes sense
```

An `Optional` returned by `of` or `ofNullable` never contains a `null` value; that's the point. Either the Optional is empty (use `isPresent` or `isEmpty` or a functional method) or it's present (use the value directly). Calling `get()` first and then comparing to `null` is a category error.

| Use Optional                                                           | Don't use Optional                 |
| ---------------------------------------------------------------------- | ---------------------------------- |
| Return type of a lookup that may fail                                  | A field on a class                 |
| Return type of stream terminal ops (`findFirst`, `max`, etc.)          | A method parameter                 |
| Composing functional pipelines where absence has to be carried through | Wrapping a collection return value |
| Distinguishing "found, with value" from "not found"                    | A null check on `get()`            |

<h1 id="primitive-specializations">Primitive Specializations</h1>

`Optional<Integer>`, `Optional<Long>`, and `Optional<Double>` work, but each one boxes the primitive. To avoid that, the JDK ships three specializations: `OptionalInt`, `OptionalLong`, and `OptionalDouble`. These appear naturally from streams such as `IntStream.max()` and `DoubleStream.average()`.

```java
import java.util.OptionalDouble;
import java.util.stream.DoubleStream;

public class PrimitiveOptional {
    public static void main(String[] args) {
        double[] ratings = {4.2, 4.8, 4.5, 4.0};

        OptionalDouble avg = DoubleStream.of(ratings).average();
        System.out.println("Average rating: " + avg.orElse(0.0));

        OptionalDouble empty = DoubleStream.empty().average();
        System.out.println("Empty average: " + empty.orElse(0.0));
    }
}
```

The primitive variants have `isPresent`, `getAsInt`/`getAsLong`/`getAsDouble`, `orElse`, `orElseGet`, `orElseThrow`, and `ifPresent`. They do not have `map`, `flatMap`, or `filter`. This is a deliberate scope reduction: these types are meant for arithmetic results from primitive streams, not as a chainable functional container. To get the full Optional API on a numeric result, convert with something like `OptionalInt.stream().boxed().findFirst()` or accept the boxing.

Boxing an `int` into `Optional<Integer>` allocates two objects (the `Optional` and the `Integer`). `OptionalInt` allocates one. The difference matters in tight loops or large stream pipelines.

<h1 id="a-larger-worked-example">A Larger Worked Example</h1>

A short program combines most of this lesson: a catalog lookup followed by a chain of transformations and a typed fallback.

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class CartCheckout {
    public static void main(String[] args) {
        ProductCatalog catalog = new ProductCatalog();
        catalog.add(new Product(1L, "Notebook", 5.50, 12));
        catalog.add(new Product(2L, "Headphones", 79.99, 0));
        catalog.add(new Product(3L, "Keyboard", 39.99, 4));

        printQuote(catalog, 1L);   // in stock
        printQuote(catalog, 2L);   // out of stock
        printQuote(catalog, 999L); // not in catalog
    }

    static void printQuote(ProductCatalog catalog, long productId) {
        String quote = catalog.findById(productId)
            .filter(p -> p.stock > 0)
            .map(p -> p.name + " at $" + p.price)
            .orElseGet(() -> reasonNotAvailable(catalog, productId));
        System.out.println("Quote for id=" + productId + ": " + quote);
    }

    static String reasonNotAvailable(ProductCatalog catalog, long id) {
        return catalog.findById(id)
            .map(p -> p.name + " is out of stock")
            .orElse("Product id=" + id + " is not in the catalog");
    }
}

class Product {
    long id;
    String name;
    double price;
    int stock;

    Product(long id, String name, double price, int stock) {
        this.id = id;
        this.name = name;
        this.price = price;
        this.stock = stock;
    }
}

class ProductCatalog {
    private final Map<Long, Product> store = new HashMap<>();

    void add(Product p) {
        store.put(p.id, p);
    }

    Optional<Product> findById(long id) {
        return Optional.ofNullable(store.get(id));
    }
}
```

`findById` returns `Optional<Product>`. The pipeline narrows it (`filter` on stock), reshapes it (`map` to a quote string), and supplies a context-aware fallback (`orElseGet` to a method that itself queries the catalog to distinguish "missing" from "out of stock"). No null appears anywhere in the main flow, no `if`/`else` ladder, and the three outcomes are explicit.

`orElseGet` matters here: the fallback function does work (another lookup) and shouldn't run on every call, only on the empty path. `orElse(reasonNotAvailable(...))` would have triggered the lookup on every product whether it was in stock or not.
