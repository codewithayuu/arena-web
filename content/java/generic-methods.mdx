<h1 id="why-a-method-needs-its-own-type-parameter">
  Why a Method Needs Its Own Type Parameter
</h1>

A class-level type parameter, like the `T` in `Box<T>`, lives on the instance. Every method inside `Box<T>` sees the same `T`, and that `T` is fixed when you build the box. Use this approach when a single object should hold one type of thing.

A lot of useful operations don't fit that shape. Consider a helper that picks the first non-null of two arguments. The two arguments should have the same type, the return should be that same type, but there's no object to "hold" the type. Each call is independent. The type parameter belongs on the method, not on the class.

The simplest version:

```java
public class NullFallback {
    public static <T> T firstNonNull(T a, T b) {
        return (a != null) ? a : b;
    }

    public static void main(String[] args) {
        String coupon = firstNonNull(null, "WELCOME10");
        Integer stock = firstNonNull(null, 25);

        System.out.println("Coupon: " + coupon);
        System.out.println("Stock: " + stock);
    }
}
```

One method, two completely different element types in two calls. The class `NullFallback` is not generic; it has no `<T>` after its name. The `<T>` belongs to `firstNonNull` alone. Each call gets its own `T`, inferred from the arguments.

The placement of `<T>` is what makes this a generic method. It sits between the modifiers (`public static`) and the return type (`T`). The compiler reads that as: from here until the end of the method's signature, the name `T` is a stand-in for a type the caller will fix.

If the `<T>` is missing, the compiler doesn't know what `T` means in the parameters or return type:

**What's wrong with this code?**

```java
public static T firstNonNull(T a, T b) {
    return (a != null) ? a : b;
}
```

The compiler reports `cannot find symbol: class T` because `T` was never declared. Without the `<T>` declaration before the return type, `T` is just an unknown name, not a type parameter.

**Fix:**

```java
public static <T> T firstNonNull(T a, T b) {
    return (a != null) ? a : b;
}
```

The declaration `<T>` introduces the name; the rest of the signature can then use it as a type. Read it like this: "for any type `T`, this method takes two `T`s and returns a `T`."

<h1 id="the-syntax-in-one-diagram">The Syntax in One Diagram</h1>

The four parts of a generic method signature sit in a fixed order:

Modifiers come first, then the type parameter list `<T>`, then the return type, then the method name and parameter list. The order matters: `public static T <T> firstNonNull(...)` doesn't compile, because the compiler would try to read `T` as the return type before it had been declared.

A method can declare more than one type parameter. They go inside the same angle brackets, separated by commas. A method that pairs a key and a value into a `Map.Entry`:

```java
import java.util.Map;

public class PairBuilder {
    public static <K, V> Map.Entry<K, V> pair(K key, V value) {
        return Map.entry(key, value);
    }

    public static void main(String[] args) {
        Map.Entry<String, Integer> stockEntry = pair("Notebook", 25);
        Map.Entry<String, String> labelEntry = pair("status", "shipped");

        System.out.println("Stock: " + stockEntry);
        System.out.println("Label: " + labelEntry);
    }
}
```

Two independent type parameters, `K` and `V`, fixed separately at each call. The first call binds `K` to `String` and `V` to `Integer`. The second binds both to `String`. The method body never has to know the concrete types; it hands them to `Map.entry`, which is itself a generic method on the `Map` interface.

<h1 id="generic-methods-inside-a-non-generic-class">
  Generic Methods Inside a Non-Generic Class
</h1>

The host class doesn't need to be generic for its methods to be. Utility classes are the most common example: a holder for static helpers that operate on whatever types the caller passes.

A small utility class for cart operations:

```java
import java.util.ArrayList;
import java.util.List;

public class CartUtils {
    public static <T> List<T> firstN(List<T> items, int n) {
        int limit = Math.min(n, items.size());
        List<T> result = new ArrayList<>(limit);
        for (int i = 0; i < limit; i++) {
            result.add(items.get(i));
        }
        return result;
    }

    public static <T> void addIfNotPresent(List<T> items, T item) {
        if (!items.contains(item)) {
            items.add(item);
        }
    }

    public static void main(String[] args) {
        List<String> catalog = List.of("Notebook", "Pen", "Eraser", "Highlighter", "Ruler");
        List<String> topThree = firstN(catalog, 3);
        System.out.println("Top three: " + topThree);

        List<Integer> orderIds = new ArrayList<>(List.of(101, 102, 103));
        addIfNotPresent(orderIds, 102);
        addIfNotPresent(orderIds, 104);
        System.out.println("Orders: " + orderIds);
    }
}
```

`CartUtils` is a plain class with no type parameter of its own. Each method carries its own `<T>` and works on whatever element type the caller passes. `firstN` is called once with `List<String>` and could also be called with `List<Order>`; same code, different `T`. `addIfNotPresent` is called twice with `List<Integer>` and `Integer`; the compiler ensures the item type matches the list's element type at each call.

This is the most common shape of a generic method. Most static helpers in `java.util.Collections` and `java.util.Arrays` follow this pattern: a non-generic class hosting many independent generic methods.

`firstN` allocates a new list sized to `limit` up front, which avoids the resizing growth that an empty `ArrayList` would go through during the loop. Without the capacity hint, a few small reallocations happen on the way to the final size.

<h1 id="generic-methods-inside-a-generic-class">
  Generic Methods Inside a Generic Class
</h1>

A generic class can host a method whose type parameter is different from the class's. Take care here: the class's `T` and the method's `T` are not the same `T`, even if you write the same letter.

A small container that supports converting its contents through a caller-supplied mapping function demonstrates this. (The class is generic in `T`; the method introduces a new type parameter `R` for the result.)

```java
import java.util.function.Function;

public class Box<T> {
    private final T value;

    public Box(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }

    public <R> Box<R> map(Function<T, R> mapper) {
        return new Box<>(mapper.apply(value));
    }

    public static void main(String[] args) {
        Box<String> nameBox = new Box<>("Notebook");
        Box<Integer> lengthBox = nameBox.map(String::length);

        System.out.println("Name: " + nameBox.get());
        System.out.println("Length: " + lengthBox.get());
    }
}
```

The class fixes `T` to `String` when you build `nameBox`. The `map` method introduces a fresh `R`, which is bound to `Integer` at the call site because `String::length` returns an `int` (autoboxed to `Integer`). The method returns a new `Box<R>`, which is `Box<Integer>` in this call.

Reusing the class's name `T` for the method makes the compiler treat the method's `T` as **shadowing** the class's `T`, which is almost never the intent. Each name is a label, but reusing a label invites confusion.

**What's wrong with this code?**

```java
public class Box<T> {
    private final T value;

    public Box(T value) { this.value = value; }

    // The <T> here shadows the class's T.
    public <T> Box<T> map(Function<Object, T> mapper) {
        return new Box<>(mapper.apply(value));
    }
}
```

The class declares `T` and the method declares another, unrelated `T` inside the same scope. Inside `map`, the name `T` refers to the method's type parameter, not the class's. Reading `value` as a `T` of the class no longer works, because `value`'s static type is the outer (shadowed) `T`. Some compilers raise a warning; either way, it hurts readability.

**Fix:** Use a different letter for the method's type parameter, like `R` for "result". That signals that the two parameters are independent.

```java
public <R> Box<R> map(Function<T, R> mapper) {
    return new Box<>(mapper.apply(value));
}
```

Conventional letters help: `T` for "type" on the class, `R` for "result", `K` and `V` for "key" and "value", `E` for "element". They're not enforced by the language; they're a contract for the next reader of the code.

<h1 id="type-inference-at-the-call-site">Type Inference at the Call Site</h1>

In every example so far, the call to a generic method has been short: `firstNonNull(null, "WELCOME10")`, not `NullFallback.<String>firstNonNull(null, "WELCOME10")`. The compiler infers the type parameter from the arguments, so most of the time the type doesn't need to be written explicitly.

Inference looks at three sources:

1. The types of the arguments passed to the method.
2. The expected type of the return value (the **target type**).
3. The type of any explicit type parameter at the call site.

For `firstNonNull(null, "WELCOME10")`, the first argument is `null` (which doesn't constrain `T`), but the second is a `String`, so the compiler infers `T = String`. For `pair("Notebook", 25)`, the first argument fixes `K = String` and the second fixes `V = Integer`.

The target type kicks in when arguments alone aren't enough. A generic factory for empty lists:

```java
import java.util.ArrayList;
import java.util.List;

public class EmptyLists {
    public static <T> List<T> emptyList() {
        return new ArrayList<>();
    }

    public static void main(String[] args) {
        List<String> wishlist = emptyList();
        List<Integer> stockLevels = emptyList();

        wishlist.add("Notebook");
        stockLevels.add(10);

        System.out.println("Wishlist: " + wishlist);
        System.out.println("Stock: " + stockLevels);
    }
}
```

`emptyList` has no arguments, so the compiler can't look at parameters to infer `T`. It looks at the target type instead. On the line `List<String> wishlist = emptyList();`, the target is `List<String>`, which fixes `T = String`. On the next line, the target is `List<Integer>`, so `T = Integer`. Two calls to the same generic method produce two differently typed empty lists.

When the compiler can't infer the type and there's no target type to fall back on, the diamond goes empty and `T` defaults to `Object`. That's almost never the intended behaviour.

**What's wrong with this code?**

```java
System.out.println(EmptyLists.emptyList());
```

Inside `println(Object)`, the target type for `emptyList()` is `Object`, which the compiler accepts. `T` becomes `Object`, and the call returns a `List<Object>`. No compile error, but probably not the intended outcome; assigning the result to a `List<String>` would fail.

**Fix:** Assign to a typed variable first, or use the explicit-type syntax to pin `T` at the call site.

```java
List<String> wishlist = EmptyLists.emptyList();
System.out.println(wishlist);
```

Or:

```java
System.out.println(EmptyLists.<String>emptyList());
```

The second form is the **explicit type witness**. The angle brackets sit between the dot and the method name. It's rare in practice (the compiler usually handles inference well), but recognizing it is useful.

Inference for the most common case:

The compiler combines what it sees in the arguments with what it knows about the target type, intersects the constraints, and picks the narrowest `T` that satisfies both. When the inputs disagree, it walks up the type hierarchy until they meet. `firstNonNull("WELCOME10", 25)` infers `T = Object` (or more precisely, an upper bound of `Object & Serializable & Comparable<?>`) because `String` and `Integer` have no closer common parent in Java's type system.

```java
public class MixedTypes {
    public static <T> T firstNonNull(T a, T b) {
        return (a != null) ? a : b;
    }

    public static void main(String[] args) {
        Object result = firstNonNull("WELCOME10", 25);
        System.out.println("Result: " + result + " (" + result.getClass().getSimpleName() + ")");
    }
}
```

`T` is inferred as something like `Object & Serializable & Comparable<?>`, which is why the call site has to assign the result to an `Object`. The runtime value is still a `String`; it's the static type that widens.

<h1 id="when-you-have-to-use-an-explicit-type-witness">
  When You Have to Use an Explicit Type Witness
</h1>

Inference handles almost every call. Three situations still need an explicit witness:

**The call has no arguments and no target type.** Calling `EmptyLists.emptyList()` directly inside a varargs argument list, or passing it to a method that accepts `Object`, gives the compiler no constraints to work with.

**A `T` wider than the arguments suggest is needed.** Passing a `String` while the inferred type should be `CharSequence` requires the witness to force it.

**Method chaining where inference can't see far enough.** Older Java versions had trouble inferring through chained calls; the witness short-circuits the lookup.

```java
import java.util.List;

public class WitnessExamples {
    public static <T> T firstNonNull(T a, T b) {
        return (a != null) ? a : b;
    }

    public static <T> List<T> singleton(T value) {
        return List.of(value);
    }

    public static void main(String[] args) {
        // Inference from arguments alone, T = String.
        System.out.println(firstNonNull("A", "B"));

        // Explicit witness, T forced to CharSequence.
        CharSequence cs = WitnessExamples.<CharSequence>firstNonNull("A", "B");
        System.out.println("CharSequence: " + cs);

        // No arguments, no target type; without the witness, T would be Object.
        System.out.println(WitnessExamples.<String>singleton("Notebook"));
    }
}
```

Three calls, one without a witness and two with. The second call forces `T = CharSequence` even though the arguments are `String`s, which the compiler accepts because `String` implements `CharSequence`. The third call uses the witness because passing the result straight to `println(Object)` would otherwise erase the element type.

The witness goes between the receiver (or the class name, for static calls) and the method name, separated by a dot. For static method calls on the current class, the form is `WitnessExamples.<T>method(...)` or, on an instance, `this.<T>method(...)`. The dot is part of the syntax; without it the compiler reads `<` as a less-than operator.

<h1 id="static-generic-methods-are-the-most-common-shape">
  Static Generic Methods Are the Most Common Shape
</h1>

Most generic methods are static. Instance methods on a generic class usually rely on the class's `T`, so they don't need their own. The methods that need their own are usually utilities that don't depend on instance state.

A pattern that comes up often in e-commerce code is picking something at random:

```java
import java.util.List;
import java.util.Random;

public class RandomPick {
    private static final Random RANDOM = new Random();

    public static <T> T pickRandom(List<T> options) {
        if (options.isEmpty()) {
            throw new IllegalArgumentException("options is empty");
        }
        int index = RANDOM.nextInt(options.size());
        return options.get(index);
    }

    public static void main(String[] args) {
        List<String> categories = List.of("Books", "Stationery", "Office");
        String promoted = pickRandom(categories);
        System.out.println("Promoted: " + promoted);
    }
}
```

**Output (varies between runs):**

```text
Promoted: Stationery
```

The method works on any element type, because the body never touches anything specific to `String` (or `Integer`, or whatever the caller passes). The compiler's type-checking guarantees that the returned `T` matches the list's `T`, so the caller never needs a cast.

Put one of these together with a `Map`:

```java
import java.util.HashMap;
import java.util.Map;

public class MapUtils {
    public static <K, V> void putIfAbsent(Map<K, V> map, K key, V value) {
        if (!map.containsKey(key)) {
            map.put(key, value);
        }
    }

    public static void main(String[] args) {
        Map<String, Integer> stock = new HashMap<>();
        stock.put("Notebook", 10);

        putIfAbsent(stock, "Notebook", 50);  // already present, value stays at 10
        putIfAbsent(stock, "Pen", 25);        // new entry

        System.out.println(stock);
    }
}
```

Two type parameters, fixed independently from `map`'s declared types. The compiler checks that `key` matches `map`'s key type and `value` matches `map`'s value type. The actual `java.util.Map` interface ships a richer `putIfAbsent` that also returns the existing value, but the shape is the same: a generic method whose type parameters mirror the map's.

`containsKey` followed by `put` walks the hash table twice. `Map.putIfAbsent` (the built-in instance method) is one lookup. The version above is fine for teaching the syntax, but production code should use the built-in.

<h1 id="a-realistic-mix-of-generic-methods">
  A Realistic Mix of Generic Methods
</h1>

Putting several of these patterns into one class shows how generic methods compose in real code. The class is non-generic; each method declares its own type parameter (or parameters):

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Random;

public class StoreUtils {
    private static final Random RANDOM = new Random();

    public static <T> T firstNonNull(T a, T b) {
        return (a != null) ? a : b;
    }

    public static <T> List<T> firstN(List<T> items, int n) {
        int limit = Math.min(n, items.size());
        List<T> result = new ArrayList<>(limit);
        for (int i = 0; i < limit; i++) {
            result.add(items.get(i));
        }
        return result;
    }

    public static <T> T pickRandom(List<T> options) {
        return options.get(RANDOM.nextInt(options.size()));
    }

    public static <K, V> Map.Entry<K, V> pair(K key, V value) {
        return Map.entry(key, value);
    }

    public static <K, V> Map<V, K> invert(Map<K, V> map) {
        Map<V, K> inverted = new HashMap<>(map.size());
        for (Map.Entry<K, V> entry : map.entrySet()) {
            inverted.put(entry.getValue(), entry.getKey());
        }
        return inverted;
    }

    public static void main(String[] args) {
        String coupon = firstNonNull(null, "WELCOME10");

        List<String> catalog = List.of("Notebook", "Pen", "Eraser", "Highlighter");
        List<String> topTwo = firstN(catalog, 2);
        String pick = pickRandom(catalog);

        Map.Entry<String, Integer> stockEntry = pair("Notebook", 25);

        Map<String, Integer> stock = new HashMap<>();
        stock.put("Notebook", 25);
        stock.put("Pen", 100);
        Map<Integer, String> byCount = invert(stock);

        System.out.println("Coupon: " + coupon);
        System.out.println("Top two: " + topTwo);
        System.out.println("Pick: " + pick);
        System.out.println("Entry: " + stockEntry);
        System.out.println("By count: " + byCount);
    }
}
```

**Output (pick varies between runs):**

```text
Coupon: WELCOME10
Top two: [Notebook, Pen]
Pick: Eraser
Entry: Notebook=25
By count: {25=Notebook, 100=Pen}
```

Five generic methods, five different shapes:

- `firstNonNull` takes two values of the same type and returns one.
- `firstN` takes a list of one type and returns a list of that same type.
- `pickRandom` takes a list and returns one element.
- `pair` takes two values of two different types and returns a structured combination.
- `invert` takes a map and swaps its key and value types.

Each one declares the type parameters it needs in its own header. The class doesn't carry any of them, because it doesn't need to. This is the pattern that fits utility code: data-free classes with generic methods that operate on whatever the caller has.

<h1 id="comparing-generic-classes-and-generic-methods">
  Comparing Generic Classes and Generic Methods
</h1>

The two tools solve different problems:

| Question                                         | Generic class                  | Generic method                                  |
| ------------------------------------------------ | ------------------------------ | ----------------------------------------------- |
| Where is the type parameter declared?            | After the class name           | Before the return type                          |
| How long does the type stay fixed?               | Lifetime of the instance       | Single method call                              |
| Does every method on the host see the same type? | Yes                            | Only this one method                            |
| Best fit for                                     | Containers and data structures | Utilities and helpers                           |
| Example from `java.util`                         | `ArrayList<E>`, `HashMap<K,V>` | `Collections.<T>emptyList()`, `Map.entry(k, v)` |

A class is generic when an instance holds something whose type the caller chose. A method is generic when an operation works on arguments whose types the caller chose, but no instance is needed to carry that type forward.

Both can coexist in one class. `ArrayList<E>` has a class-level `E`, but the static generic method `Collections.<T>emptyList()` (declared on `Collections`, not on `ArrayList`) follows the generic method pattern. Inside `ArrayList`, methods like `toArray(T[] a)` declare their own `T`, separate from the class's `E`.

```java
import java.util.ArrayList;
import java.util.List;

public class ToArrayDemo {
    public static void main(String[] args) {
        // The list's element type E is String.
        List<String> cart = new ArrayList<>(List.of("Notebook", "Pen", "Eraser"));

        // toArray declares its own <T>; T is fixed to String[] by the argument.
        String[] arr = cart.toArray(new String[0]);

        System.out.println("First: " + arr[0]);
        System.out.println("Length: " + arr.length);
    }
}
```

`List<E>` has `E = String`, and `toArray` is `<T> T[] toArray(T[] a)`. The `<T>` is declared on the method, fixed to `String` by the array argument. The compiler enforces that `T` is compatible with `E` (in a real library this is enforced at runtime by checking the array's component type), so an `Integer[]` cannot accidentally be passed to a `List<String>` and produce a typed `Integer[]` back. That signature shows why a method inside a generic class might still want its own type parameter: the array type isn't necessarily the same as the element type, but it has to be a supertype of it.
