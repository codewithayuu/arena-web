<h1 id="write-and-writelines">write() and writelines()</h1>

A text file opened in write mode (`"w"`, `"a"`, or any mode with `+`) gives you a file object with two methods for putting data in: `write` and `writelines`. They're both straightforward, and they differ in one way.

```python
with open("products.txt", "w", encoding="utf-8") as f:
    f.write("mug,12.99\n")
    f.write("notebook,7.49\n")
    f.write("pen,1.99\n")

with open("products.txt", "r", encoding="utf-8") as f:
    print(f.read())
```

Three calls, three lines on disk. `write` takes a string and writes it. That's the entire interface. It returns the number of characters written, which most code ignores.

```python
with open("scratch.txt", "w", encoding="utf-8") as f:
    n = f.write("Welcome\n")
    print("wrote", n, "characters")
```

The return value is sometimes useful for diagnostics on partial writes, but in everyday text-file code you can ignore it.

`writelines` is the second method, and the name is misleading. It takes an iterable of strings and writes each one. It does **not** add newlines between them. You're responsible for putting `\n` at the end of each string yourself.

```python
lines = [
    "mug,12.99\n",
    "notebook,7.49\n",
    "pen,1.99\n",
]

with open("products.txt", "w", encoding="utf-8") as f:
    f.writelines(lines)

with open("products.txt", "r", encoding="utf-8") as f:
    print(f.read())
```

The output is identical to three separate `write` calls. That's by design: `writelines(lines)` is equivalent to `for line in lines: f.write(line)`. The performance difference is tiny because of buffering; both forms end up in the same in-memory buffer before going to disk.

The trap is forgetting that `writelines` doesn't add newlines. The following code looks correct but produces one long line:

```python
lines = ["mug,12.99", "notebook,7.49", "pen,1.99"]
with open("oops.txt", "w", encoding="utf-8") as f:
    f.writelines(lines)

with open("oops.txt", "r", encoding="utf-8") as f:
    print(f.read())
```

That's the cost of the "writelines doesn't add newlines" rule. Two clean fixes: either include `"\n"` in each string when you build the list, or write a helper:

```python
def write_lines(file, lines):
    for line in lines:
        file.write(line + "\n")

lines = ["mug,12.99", "notebook,7.49", "pen,1.99"]
with open("clean.txt", "w", encoding="utf-8") as f:
    write_lines(f, lines)
```

Either approach works. A common style is to build the strings with newlines included, so the data structure mirrors what hits the disk.

Both `write` and `writelines` go through Python's buffered I/O layer. Writing one byte at a time in a loop is fine; the buffer absorbs the calls and flushes to disk in larger chunks. Don't waste time concatenating into a large string to reduce write calls.

<h1 id="write-vs-print-two-tools-that-look-similar">
  write vs print: Two Tools That Look Similar
</h1>

The `print` function writes to standard output by default, but it accepts a `file` keyword argument and can write to any file object. So you can produce the same output with either method:

```python
with open("greeting.txt", "w", encoding="utf-8") as f:
    f.write("Welcome to the store\n")

with open("greeting.txt", "w", encoding="utf-8") as f:
    print("Welcome to the store", file=f)

with open("greeting.txt", "r", encoding="utf-8") as f:
    print(f.read().rstrip())
```

The two approaches differ in a few specific ways that come up in practice.

| Behavior                     | `write`                  | `print`                                 |
| ---------------------------- | ------------------------ | --------------------------------------- |
| Adds a newline               | No. You write it.        | Yes (controlled by `end=`).             |
| Accepts multiple arguments   | No. One string per call. | Yes. Joins with `sep=` (default space). |
| Calls `str()` on non-strings | No. Raises `TypeError`.  | Yes. Converts everything via `str`.     |
| Flushes after each call      | No. Buffered.            | No, unless you pass `flush=True`.       |

The "calls `str()` on non-strings" difference is the practical one. `print(total, file=f)` works even when `total` is a float, while `f.write(total)` raises:

```python
total = 124.95
with open("total.txt", "w", encoding="utf-8") as f:
    f.write(total)
```

The fix is `f.write(str(total))` or `f.write(f"{total}\n")` or `print(total, file=f)`. Any of them work. For occasional logging or quick one-off output, `print(..., file=f)` is often cleaner because it handles the conversion and the newline for you. For structured output where the exact bytes matter (writing CSV rows, generating a specific format), `write` with explicit formatting gives you more control.

`print` calls `str()` on every argument. That's a few extra function calls per line. For occasional output it's invisible. For tight loops writing millions of lines, `write(f"{...}\n")` is slightly faster.

A practical pattern: use `print(file=f)` for human-readable output where the default formatting fits, and `write` for formats where you control every byte.

```python
# Human-readable summary with print.
with open("summary.txt", "w", encoding="utf-8") as f:
    print("Order summary", file=f)
    print("=" * 30, file=f)
    for product, price in [("mug", 12.99), ("notebook", 7.49)]:
        print(f"{product:.<20} ${price:.2f}", file=f)
```

```python
# Strict CSV format with write.
with open("export.csv", "w", encoding="utf-8") as f:
    f.write("product,price\n")
    for product, price in [("mug", 12.99), ("notebook", 7.49)]:
        f.write(f"{product},{price:.2f}\n")
```

Both work. Pick whichever reads more clearly for the task at hand.

<h1 id="newlines-in-cross-platform-writes">
  Newlines in Cross-Platform Writes
</h1>

Text mode does newline translation on the way out. When you call `f.write("hello\n")`, Python translates that `\n` into the platform's preferred line separator before the bytes hit disk. On Unix-like systems (macOS, Linux) that's `\n`. On Windows it's `\r\n`. The translation is hidden by default, which is usually convenient and occasionally a problem.

```python
with open("orders.txt", "w", encoding="utf-8") as f:
    f.write("order-1\norder-2\norder-3\n")

with open("orders.txt", "rb") as f:
    print(f.read())
```

Same string written, different bytes on disk. Python does this so a file written on Windows opens cleanly in Notepad (which historically expected `\r\n`) and a file written on Linux opens cleanly in `cat`. Most of the time you don't care, because reading the file in text mode reverses the translation: any of `\n`, `\r\n`, or `\r` in the file is read back as `\n`.

The translation only matters when:

- You're comparing files byte-for-byte across platforms (a hash check, a diff, a checksum).
- You're writing a format where the exact bytes matter (a custom binary protocol, a CSV with embedded newlines inside quoted fields).
- You're writing to a pipe or socket and the other side expects specific line endings.

For those cases, control the translation explicitly with the `newline` argument to `open`. Passing `newline=""` disables translation entirely on write while still handling all line-ending styles cleanly on read.

```python
with open("orders.csv", "w", encoding="utf-8", newline="") as f:
    f.write("product,price\n")
    f.write("mug,12.99\n")

with open("orders.csv", "rb") as f:
    print(f.read())
```

The bytes match exactly across operating systems. This is the recommended setting whenever you use the `csv` module, because CSV fields can legally contain embedded `\r\n` sequences and you don't want Python rewriting them.

For everyday log files and config files, the default translation is fine. For format-sensitive output (CSV, custom binary, network protocols), pass `newline=""` and control the bytes yourself.

<h1 id="buffering-and-flush">Buffering and flush()</h1>

When you call `f.write("hello")`, the bytes don't necessarily reach the disk right away. Python keeps an in-memory buffer and only flushes it when the buffer fills up, when you explicitly call `flush`, or when the file is closed. Buffering is what makes file I/O fast: a single 8 KB write to the OS is far cheaper than 8,000 separate one-byte writes.

Three buffering modes exist, controlled by the `buffering` keyword argument to `open`.

| `buffering=` value | Mode                                | When data goes to disk                        |
| ------------------ | ----------------------------------- | --------------------------------------------- |
| `0`                | Unbuffered (binary mode only)       | Every `write` is a system call.               |
| `1`                | Line-buffered (text mode only)      | Every newline triggers a flush.               |
| `> 1`              | Block-buffered with this many bytes | When the buffer fills, or on `flush`/`close`. |
| `-1` (default)     | Use the OS default                  | Typically 8 KB block buffering.               |

For most code, the default fits. Two cases call for changing it.

<h3 id="line-buffering-for-real-time-logs">
  Line Buffering for Real-Time Logs
</h3>

A log file you want to monitor with `tail -f` should flush after every line. Without line buffering, an 8 KB buffer might hold an hour of low-volume log lines before flushing, which makes the log appear "stuck."

```python
import time

with open("activity.log", "w", encoding="utf-8", buffering=1) as f:
    f.write("user opened cart\n")
    # at this point the line is already on disk
    time.sleep(2)
    f.write("user added mug\n")
```

Without `buffering=1`, those two writes might sit in memory for several seconds (or until the program exits). With it, each newline forces a flush, so a tail of the file shows lines as they happen.

<h3 id="explicit-flush-for-critical-points">
  Explicit flush() for Critical Points
</h3>

Sometimes you want to flush at a specific moment, not after every line. The `flush` method does exactly that.

```python
with open("checkout.log", "w", encoding="utf-8") as f:
    f.write("step 1: cart loaded\n")
    f.write("step 2: payment validated\n")
    f.flush()  # everything above is now durable
    f.write("step 3: order created\n")
    # step 3 might be in the buffer when an exception happens here
```

`flush` pushes the Python buffer down to the OS. That's enough to survive a Python crash, because the OS keeps its own page cache and the bytes will still get to disk eventually.

For durability against a power loss or OS crash, you need to push the OS to flush its own cache too. That's what `os.fsync` is for.

```python
import os

with open("orders.log", "w", encoding="utf-8") as f:
    f.write("order-1: mug\n")
    f.flush()
    os.fsync(f.fileno())  # OS flush: bytes are now on physical disk
```

`fsync` is slow (it waits for the disk to commit), and most application code doesn't need it. Databases and financial systems do. For ordinary file work, `flush` is enough; for crash-safe writes, use the rename pattern below.

The diagram shows the two-stage path a write takes. Bytes leave your code, sit in Python's buffer, then move to the OS page cache when the buffer flushes, then to physical disk when the OS flushes (or you call `fsync`). A Python crash loses anything still in the Python buffer. An OS crash or power loss loses anything still in the OS page cache. Most code only cares about the first stage.

<h1 id="atomic-writes-the-write-then-rename-pattern">
  Atomic Writes: The Write-Then-Rename Pattern
</h1>

A problem with writing files: if your program crashes mid-write, the file on disk is half-written. Anyone reading it gets corrupt data. This matters because "the program crashed" doesn't have to mean "I wrote buggy code." A user might Ctrl-C the process. The OS might kill the process. The machine might lose power.

```python
# Risky: corrupts orders.txt if the program dies between line 1 and line 3.
with open("orders.txt", "w", encoding="utf-8") as f:
    f.write("order-1: mug\n")
    f.write("order-2: notebook\n")
    f.write("order-3: pen\n")
```

The `"w"` mode truncates the file the moment `open` runs. If the program crashes after that point but before all the writes finish, `orders.txt` exists but contains only part of the new data. Reopen the program and there's no reliable way to tell whether what's on disk is complete or partial.

The standard fix is to write to a temporary file in the same directory, then atomically rename it to the target name. On every major operating system, rename is an atomic operation: either the new name points to the new file, or it points to the old file, with no in-between state. A reader sees either the old version or the complete new version, never a partial state.

```python
import os
from pathlib import Path

def atomic_write(filename, content):
    target = Path(filename)
    tmp = target.with_suffix(target.suffix + ".tmp")
    with open(tmp, "w", encoding="utf-8") as f:
        f.write(content)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, target)

atomic_write("orders.txt", "order-1: mug\norder-2: notebook\norder-3: pen\n")

with open("orders.txt", "r", encoding="utf-8") as f:
    print(f.read())
```

The function does four things:

1. Write all the content to a temp file (`orders.txt.tmp`).
2. Flush the Python buffer and call `fsync` so the temp file is fully durable on disk.
3. Use `os.replace` to atomically swap the temp file into the target name.
4. The previous `orders.txt`, if any, is now gone, replaced in a single OS operation.

If the program crashes during step 1, you end up with an incomplete `.tmp` file and an intact original. Recovery is "delete the .tmp file." If the program crashes during step 3, the rename either happened or it didn't; there's no half-rename.

`os.replace` (added in Python 3.3) is the function to use for the rename. It works on both Windows and Unix, and it overwrites the destination if it already exists. Older code used `os.rename`, which fails on Windows if the destination exists.

The same pattern works for binary writes; use `"wb"` instead of `"w"`. For most application code, this is the recommended way to write any file whose corruption would be a real problem: configuration files, generated reports, snapshots of state, anything that another part of the system might read while you're writing.

A few practical notes:

- The temp file must be on the same filesystem as the target. `os.replace` is atomic across filenames in the same directory; across filesystems it falls back to a copy-and-delete which isn't atomic.
- The `tempfile` module in the standard library has helpers (`tempfile.NamedTemporaryFile`) that handle the temp-file creation for you.
- For very large writes, the `fsync` call costs real time. Skip it if your data isn't critical; the rename itself is still atomic regardless.

<h1 id="appending-vs-overwriting">Appending vs Overwriting</h1>

The other half of writing files is choosing between overwriting and appending. Here's the practical summary.

```python
# Overwrites: every call wipes the file and writes fresh.
with open("log.txt", "w", encoding="utf-8") as f:
    f.write("new content\n")

# Appends: every call adds to whatever was already there.
with open("log.txt", "a", encoding="utf-8") as f:
    f.write("more content\n")
```

`"w"` is for "I want this file to contain exactly what I write." `"a"` is for "I want to extend what's already there." A common bug in this section is using `"w"` inside a function that's called repeatedly, where the intent was to accumulate but the actual behavior wipes the file each time.

```python
def log_event(filename, event):
    with open(filename, "w", encoding="utf-8") as f:  # bug: should be "a"
        f.write(event + "\n")

log_event("events.log", "cart opened")
log_event("events.log", "item added")
log_event("events.log", "checkout started")

with open("events.log", "r", encoding="utf-8") as f:
    print(f.read())
```

Only the last event survives. Each call truncated the file. The fix is one character: change `"w"` to `"a"`. `"w"` truncates and `"a"` appends.

<h1 id="generating-structured-output">Generating Structured Output</h1>

Writing CSV, JSON, and other structured formats has dedicated modules (`csv`, `json`) in the standard library. But you can build simple structured output by hand with `write` and string formatting, which is sometimes the appropriate choice for one-off scripts or for formats that the standard library doesn't cover.

<h3 id="writing-a-csv-file-by-hand">Writing a CSV File by Hand</h3>

For tightly controlled data (no commas in field values, no embedded newlines, no quotes), produce a CSV file with `write`:

```python
products = [
    ("mug", 12.99, 40),
    ("notebook", 7.49, 150),
    ("pen", 1.99, 500),
    ("water bottle", 14.99, 80),
]

with open("products.csv", "w", encoding="utf-8") as f:
    f.write("name,price,stock\n")
    for name, price, stock in products:
        f.write(f"{name},{price:.2f},{stock}\n")

with open("products.csv", "r", encoding="utf-8") as f:
    print(f.read())
```

This works for clean data. The moment a product name contains a comma (`"mug, large"`), the hand-rolled writer produces invalid CSV. That's the case the `csv` module is for. Use this pattern only when you control the data shape and know it's safe.

<h3 id="writing-a-json-file-by-hand">Writing a JSON File by Hand</h3>

For JSON, hand-rolling is even riskier (escaping rules are subtle), so always use the `json` module. This pattern still shows up in older codebases:

```python
# Don't do this in real code. Use json.dump.
products = [{"name": "mug", "price": 12.99}, {"name": "notebook", "price": 7.49}]

with open("products.json", "w", encoding="utf-8") as f:
    f.write("[\n")
    for i, p in enumerate(products):
        comma = "," if i < len(products) - 1 else ""
        f.write(f'  {{"name": "{p["name"]}", "price": {p["price"]}}}{comma}\n')
    f.write("]\n")
```

This produces valid JSON for this data, but it breaks the moment a product name contains a quote, a backslash, or a control character. Use the `json` module that handles all of this correctly.

The takeaway: for one-off scripts or quick exports, hand-rolling structured output is fine if the data shape is fully under your control. For anything ingesting data that might surprise you, use the standard library modules.

<h1 id="common-pitfalls">Common Pitfalls</h1>

A few mistakes that come up repeatedly.

<h3 id="forgetting-with-and-losing-buffered-writes">
  Forgetting with and Losing Buffered Writes
</h3>

```python
f = open("orders.txt", "w", encoding="utf-8")
f.write("order-1: mug\n")
# program exits abnormally here, or you forgot f.close()
```

Without `close` (or the `with` block that calls it for you), the buffered write might sit in Python's memory until garbage collection happens. On a normal exit that's fine, but on an abnormal exit (Ctrl-C, OS kill, segfault) the write is lost. The fix is `with`.

<h3 id="mixing-encoding-on-write-and-read">
  Mixing Encoding on Write and Read
</h3>

```python
with open("customer.txt", "w", encoding="utf-8") as f:
    f.write("RenÃ©e MÃ¼ller\n")

with open("customer.txt", "r", encoding="latin-1") as f:
    print(f.read())
```

The write encodes `Ã©` as the UTF-8 bytes `\xc3\xa9`. The read decodes those bytes as Latin-1, which interprets each one as a separate character, producing `ÃÂ©` instead of `Ã©`. The output looks like text, which is the worst failure mode: no error, only wrong data. Use the same encoding on both sides, and prefer UTF-8 everywhere.

<h3 id="writing-bytes-in-text-mode">Writing Bytes in Text Mode</h3>

```python
with open("note.txt", "w", encoding="utf-8") as f:
    f.write(b"hello")
```

Text mode requires `str`. Either drop the `b` prefix or open the file in binary mode (`"wb"`). The `bytes`-vs-`str` split is enforced strictly; mixing them always raises.

<h3 id="forgetting-newlines-in-writelines">
  Forgetting Newlines in writelines
</h3>

The most common `writelines` bug, discussed earlier: the method doesn't add newlines. Build them into the strings or use a `for` loop with `f.write(line + "\n")`.

<h3 id="truncating-with-w-when-you-wanted-to-append">
  Truncating With "w" When You Wanted to Append
</h3>

`"w"` wipes the file; `"a"` extends it. If your function is supposed to add to a log over time, use `"a"`.

<h3 id="writing-to-a-file-that-another-process-is-reading">
  Writing to a File That Another Process Is Reading
</h3>

If a reader and a writer both have the same file open, the reader can see partial writes: a line missing its newline because the writer flushed mid-line, or even garbled bytes because the OS doesn't synchronize between processes. The fix is the atomic-write pattern: write to a temp file, then rename. The reader either sees the old version or the new one, never anything in between.

<h1 id="common-mistakes-recap">Common Mistakes (Recap)</h1>

- Forgetting `with`. The fix is always the same: use a `with` block.
- Forgetting `encoding="utf-8"`. The default is platform-dependent; pass it explicitly.
- Calling `writelines` without newlines in the strings. Either build them in or write a small `for` loop.
- Using `"w"` when you meant `"a"`. `"w"` truncates; `"a"` appends.
- Writing bytes in text mode (or strings in binary mode). The error is clear; the fix is to match the mode to the data.
- Reading mid-write from another process. Use the atomic-write pattern.
