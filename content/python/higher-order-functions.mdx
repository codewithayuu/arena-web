<h1 id="what-counts-as-higher-order">What Counts as Higher-Order</h1>

The definition is straightforward but easy to underrate. A function is higher-order if either of the following is true:

1. It takes at least one function as an argument.
2. It returns a function.

That's the rule. Both conditions are common in Python, and many higher-order functions do both at once. The classic example: `sorted` takes a `key` function (it accepts a function), and decorators take a function and return a wrapped function (they accept and return).

A small demonstration:

```python
def apply_twice(func, value):
    return func(func(value))

def add_five(n):
    return n + 5

print(apply_twice(add_five, 10))
print(apply_twice(lambda p: p * 2, 7))
```

`apply_twice` takes a function and an argument, calls the function on the argument, then calls the function on the result. It works with any callable: a `def`-defined function, a lambda, a built-in, a method. That's the freedom higher-order functions provide. Write the structure ("do this twice") once and let the caller plug in the behavior.

The reverse direction is just as easy. A function that returns a function:

```python
def make_multiplier(factor):
    def multiply(value):
        return value * factor
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)

print(double(7))
print(triple(7))
```

`make_multiplier` is higher-order because it returns a function. Each call produces a small, pre-configured multiplier that remembers its `factor`. The returned function is a closure; it carries the `factor` along even after `make_multiplier` has returned.

The diagram shows the two shapes side by side. On the left, a function flows into the higher-order function as a regular argument. On the right, the higher-order function can produce either a plain result or another function. Both directions involve treating functions as first-class values.

Why does this matter in practice? Because most of the time the goal is to vary **what is done**, not **how it's iterated, validated, retried, logged, or sorted**. A higher-order function lets the structure be written once with the behavior parameterized. That's the engineering win.

<h1 id="higher-order-built-ins">Higher-Order Built-ins</h1>

Python's standard library is full of higher-order functions.

**`sorted`, `min`, `max`, `list.sort`** all accept a `key` argument. The `key` is a function called once per element to produce the value used for comparison.

```python
cart = [
    {"name": "Wireless Mouse", "price": 29.99},
    {"name": "USB Cable", "price": 4.99},
    {"name": "HDMI Cable", "price": 14.99},
]

by_price = sorted(cart, key=lambda item: item["price"])
print([item["name"] for item in by_price])
```

`sorted` is the canonical higher-order built-in. The structure ("walk the list and compare items") is fixed. The behavior ("how to turn an item into something comparable") is what the caller plugs in.

**`map(func, iterable)`** calls `func` on every item.

```python
prices = [29.99, 14.99, 9.99]
in_cents = list(map(lambda p: int(p * 100), prices))
print(in_cents)
```

**`filter(func, iterable)`** keeps items where `func` returns truthy.

```python
prices = [29.99, 4.99, 14.99, 49.99]
expensive = list(filter(lambda p: p > 10, prices))
print(expensive)
```

**`functools.reduce(func, iterable, initial)`** collapses an iterable into a single value by repeatedly applying a two-argument function.

```python
from functools import reduce

prices = [29.99, 14.99, 4.99]
total = reduce(lambda acc, p: acc + p, prices, 0)
print(round(total, 2))
```

**`any(iterable)` and `all(iterable)`** are higher-order in spirit; they consume iterables that the caller often builds from a generator expression that filters or projects with a small function. They short-circuit, so `any` stops on the first truthy result and `all` stops on the first falsy one.

```python
cart = [
    {"name": "Mouse", "in_stock": True},
    {"name": "Cable", "in_stock": False},
    {"name": "Webcam", "in_stock": True},
]

print(any(item["in_stock"] for item in cart))
print(all(item["in_stock"] for item in cart))
```

**`functools.partial(func, \*args, **kwargs)`\*\* returns a new function with some arguments already filled in. The new function is higher-order's output: a callable derived from another callable.

```python
from functools import partial

def shipping_cost(weight, rate):
    return weight * rate

domestic = partial(shipping_cost, rate=2.50)
print(domestic(3))
print(domestic(7))
```

**Decorators**, which are everywhere in modern Python, are higher-order functions. A decorator takes a function and returns a (usually wrapped) function. The `@decorator` syntax is just sugar for `func = decorator(func)`.

```python
def log_calls(func):
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__} with {args} {kwargs}")
        return func(*args, **kwargs)
    return wrapper

@log_calls
def add_to_cart(item, qty=1):
    return f"{qty}x {item}"

print(add_to_cart("Wireless Mouse", qty=2))
```

`log_calls` is higher-order on both sides: it takes a function (the one being decorated) and returns a function (the wrapper). Every `@something` above a function definition is a higher-order function being applied.

Each layer of decorator adds one function call to every invocation of the underlying function. For a tight inner loop, that overhead can matter; for the application code most decorators sit on (request handlers, business logic, command handlers), it's invisible.

The takeaway: higher-order functions are already used all over Python. Naming the pattern makes it easier to spot when one fits the problem, and easier to read code that's built on the technique.

<h1 id="functions-that-return-functions-factories">
  Functions That Return Functions: Factories
</h1>

A function factory is a higher-order function whose return value is another function, configured by the factory's arguments. It's a clean way to build small, specialized callables from a shared template.

The pattern shows up often. Building a tax calculator for different jurisdictions:

```python
def make_tax_calculator(rate):
    def calculate(price):
        return round(price * (1 + rate), 2)
    return calculate

with_us_tax = make_tax_calculator(0.08)
with_eu_tax = make_tax_calculator(0.20)
with_in_tax = make_tax_calculator(0.18)

print(with_us_tax(29.99))
print(with_eu_tax(29.99))
print(with_in_tax(29.99))
```

`make_tax_calculator` is called once per jurisdiction, and each call produces a separate function with its own captured rate. The returned functions are closures (the topic of the closures lesson), but closure mechanics don't have to be in mind every time the pattern is used. The model is "give me a calculator configured for this rate."

Another common shape: building a validator from a rule.

```python
def at_least(minimum):
    def check(value):
        return value >= minimum
    return check

over_zero = at_least(0)
over_one_hundred = at_least(100)

print(over_zero(5))
print(over_one_hundred(50))
print(over_one_hundred(150))
```

`at_least` is a factory that produces a one-arg predicate function. Each predicate carries its threshold. These predicates can be passed to `filter`, `all`, or `any`:

```python
prices = [4.99, 29.99, 14.99, 89.99, 49.99]
high_value = list(filter(at_least(50), prices))
print(high_value)
```

The call shape: `at_least(50)` is invoked first to produce the predicate, then `filter` uses it. That's a higher-order call chain: a factory produces a function that gets handed to another higher-order function.

Factories also fit when a library expects a callback with a specific signature and extra context needs to be bound into it:

```python
def make_logger(prefix):
    def log(message):
        print(f"[{prefix}] {message}")
    return log

cart_log = make_logger("cart")
order_log = make_logger("order")

cart_log("added Wireless Mouse")
order_log("placed order #1001")
```

Each logger captures its own prefix. `cart_log` can be handed to any code that wants a one-argument logging function, and the prefix follows along automatically. (`print` is used here for clarity; real code would use the `logging` module.)

The factory pattern is one of the most common reasons to write a function that returns a function. The rule of thumb: when nearly the same function gets written over and over with one parameter changing, extract the varying part as a factory argument and have the factory return the specialized function.

<h1 id="function-composition">Function Composition</h1>

Function composition is the act of stitching two functions together so that the output of one becomes the input of the next. Mathematically, the composition of `f` and `g` is the function `x -> f(g(x))`. In Python, there's no built-in `compose`, but one can be written in two lines:

```python
def compose(f, g):
    def composed(x):
        return f(g(x))
    return composed
```

`compose` is higher-order in both directions: it takes two functions and returns a function. The returned function does whatever `g` does, then feeds the result into `f`.

A concrete example: format a product name for display by stripping whitespace first, then title-casing it.

```python
def compose(f, g):
    def composed(x):
        return f(g(x))
    return composed

clean = compose(str.title, str.strip)

print(clean("  wireless MOUSE  "))
print(clean(" usb cable "))
```

Read `compose(str.title, str.strip)` as "title-case the result of stripping". The right-hand function runs first, the left-hand function runs second. That's the same order as mathematical composition (the rightmost function is the innermost), which sometimes confuses readers new to the idea. A mnemonic: the function closest to the input runs first.

For three or more functions, manual `compose(f, compose(g, h))` calls get clunky. A more general version handles any number:

```python
from functools import reduce

def pipe(*functions):
    """Pipe x through each function in order, left to right."""
    def piped(x):
        return reduce(lambda value, func: func(value), functions, x)
    return piped

clean_and_tag = pipe(str.strip, str.title, lambda s: f"[product] {s}")

print(clean_and_tag("  wireless MOUSE  "))
```

This `pipe` reads in the natural order: first strip, then title-case, then add the tag. The argument flows through the functions left to right, which matches how the pipeline would be described out loud. Many Python codebases prefer a `pipe`-shaped helper over a math-style `compose` because the reading order is friendlier.

Each composed function adds one level of call indirection. For a pipeline of three or four functions, that's negligible. For a pipeline of fifty applied inside a hot loop, benchmark before optimizing; usually the function bodies dominate the call overhead anyway.

The diagram shows the data flow through a three-stage pipeline. Each orange box is one function. The input enters on the left, gets reshaped at each stage, and emerges as the final output on the right. This is what `pipe(str.strip, str.title, add_tag)` does internally: chaining the functions so each one operates on the output of the previous.

<h1 id="building-pipelines">Building Pipelines</h1>

A pipeline is a chain of transformations applied to a piece of data. In Python, pipelines can be built with composition, but more often they're built with comprehensions, generators, and chains of method calls. The model is the same either way: a value flows through a series of named or anonymous transforms.

A simple data-processing pipeline. Take a raw catalog, normalize the names, filter to in-stock items, sort by price, and pull the top three.

```python
catalog = [
    {"name": "  wireless MOUSE  ", "price": 29.99, "in_stock": True},
    {"name": " usb cable ", "price": 4.99, "in_stock": False},
    {"name": "MECHANICAL keyboard", "price": 89.99, "in_stock": True},
    {"name": "HDMI cable", "price": 14.99, "in_stock": True},
    {"name": " webcam ", "price": 49.99, "in_stock": True},
]

def normalize(item):
    return {**item, "name": item["name"].strip().title()}

normalized = [normalize(item) for item in catalog]
available = [item for item in normalized if item["in_stock"]]
cheapest = sorted(available, key=lambda item: item["price"])
top_three = cheapest[:3]

for item in top_three:
    print(f"{item['name']}: ${item['price']}")
```

Each line is one stage. The data flows top to bottom: normalize, filter, sort, slice. The same pipeline can be rewritten using `pipe`:

```python
from functools import reduce

def pipe(*functions):
    def piped(x):
        return reduce(lambda value, func: func(value), functions, x)
    return piped

process = pipe(
    lambda items: [normalize(i) for i in items],
    lambda items: [i for i in items if i["in_stock"]],
    lambda items: sorted(items, key=lambda i: i["price"]),
    lambda items: items[:3],
)

for item in process(catalog):
    print(f"{item['name']}: ${item['price']}")
```

The `pipe` version is more "functional-looking" but not necessarily more readable. For a small number of stages, the step-by-step version with named intermediates is usually clearer because each line carries a meaningful name (`normalized`, `available`, `cheapest`). The `pipe` version is more interesting when each stage is already a named function that can be handed in directly:

```python
def normalize_all(items):
    return [normalize(i) for i in items]

def keep_in_stock(items):
    return [i for i in items if i["in_stock"]]

def by_price(items):
    return sorted(items, key=lambda i: i["price"])

def top_n(n):
    return lambda items: items[:n]

process = pipe(normalize_all, keep_in_stock, by_price, top_n(3))
for item in process(catalog):
    print(f"{item['name']}: ${item['price']}")
```

Now each stage is a named function that does one thing. Reading the `pipe(...)` line tells the whole story. And because each stage is a pure function, each can be tested in isolation, swapped out, or reordered without worrying about hidden coupling.

Two style notes worth taking seriously:

- **Don't force pipelines.** If a four-line block of regular code reads better than a four-line pipeline, write the regular code. Pipelines fit when each stage is a real, reusable transformation, not when one-line operations are squeezed into a chain to look clever.
- **Generators are pipelines too.** A chain of generator expressions is the classic Python pipeline: lazy, memory-friendly, and easy to reason about. The `itertools` module covers many of the same shapes (`itertools.chain`, `itertools.islice`, `itertools.takewhile`) without needing a custom `pipe`.

<h1 id="type-hints-with-callable">Type Hints With Callable</h1>

Passing functions around as values calls for a way to type them. Python's `typing` module provides `Callable` for this.

The shape is `Callable[[ArgType1, ArgType2, ...], ReturnType]`. The bracketed list is the argument types, and the type after the closing bracket is the return type.

```python
from typing import Callable

def apply_to_all(items: list[float], func: Callable[[float], float]) -> list[float]:
    return [func(item) for item in items]

def with_tax(price: float) -> float:
    return round(price * 1.08, 2)

prices = [29.99, 14.99, 4.99]
print(apply_to_all(prices, with_tax))
```

The annotation `Callable[[float], float]` says: "a function that takes one float and returns a float". A type checker like `mypy` will warn if the caller passes a function whose signature doesn't match.

A function with two arguments is the same idea:

```python
from typing import Callable

def reduce_pair(values: list[float], combine: Callable[[float, float], float]) -> float:
    result = values[0]
    for value in values[1:]:
        result = combine(result, value)
    return result

prices = [10.0, 20.0, 30.0]
total = reduce_pair(prices, lambda a, b: a + b)
biggest = reduce_pair(prices, max)
print(total)
print(biggest)
```

`Callable[[float, float], float]` is a function of two floats returning a float. Both `lambda a, b: a + b` and the built-in `max` (when called on two values) fit that signature, so both pass the type check.

For more complex signatures (keyword arguments, optional arguments, `*args`/`**kwargs`), the `typing.Protocol` class or the `typing.Callable` form has limits. For everyday use, the simple `Callable[[arg_types], return_type]` form covers most cases.

Type hints have no runtime cost. They're metadata: Python stores them but doesn't enforce them. The benefit is in static analysis (catching bugs before runtime) and IDE help (autocomplete, parameter info), not in execution speed.

A `Callable` annotation makes the intent of a higher-order function much clearer to readers. Compare:

```python
def filter_items(items, predicate):
    return [i for i in items if predicate(i)]
```

with:

```python
from typing import Callable

def filter_items(items: list[dict], predicate: Callable[[dict], bool]) -> list[dict]:
    return [i for i in items if predicate(i)]
```

The second version says, without requiring the reader to look at the body, that `predicate` should be a function taking a dict and returning a bool. That's the kind of contract higher-order functions benefit from documenting.

<h1 id="common-higher-order-patterns">Common Higher-Order Patterns</h1>

A handful of patterns come up often. Naming them helps to spot which one fits a given problem.

**1. Callback.** A function handed to another function to be called later, often after some asynchronous or deferred event.

```python
def process_order(order, on_success, on_failure):
    if order["total"] > 0:
        on_success(order)
    else:
        on_failure(order, reason="zero total")

def confirm(order):
    print(f"Order {order['id']} confirmed: ${order['total']}")

def reject(order, reason):
    print(f"Order {order['id']} rejected: {reason}")

process_order({"id": 1001, "total": 49.99}, confirm, reject)
process_order({"id": 1002, "total": 0}, confirm, reject)
```

The "what happens on success/failure" behavior is plugged in by the caller. The function processing the order doesn't have to know what success or failure looks like in this part of the system.

**2. Strategy.** Pass in a function that decides how something should be done. This is what `sorted(key=...)` is doing: the strategy for turning an item into a comparison value is the caller's business, not `sorted`'s.

```python
def total_cart(cart, pricing_strategy):
    return sum(pricing_strategy(item) for item in cart)

def regular(item):
    return item["price"] * item["qty"]

def member(item):
    return item["price"] * item["qty"] * 0.9

cart = [
    {"name": "Wireless Mouse", "price": 29.99, "qty": 1},
    {"name": "USB Cable", "price": 4.99, "qty": 3},
]

print(round(total_cart(cart, regular), 2))
print(round(total_cart(cart, member), 2))
```

`total_cart` doesn't care whether the strategy applies a discount, adds tax, or rounds in a particular way. It calls the strategy on each item.

**3. Transformation.** Apply a function to each element of a collection. This is `map` or a comprehension.

```python
def transform_all(items, transform):
    return [transform(item) for item in items]

upper_names = transform_all(["mouse", "cable", "webcam"], str.upper)
print(upper_names)
```

**4. Retry/Wrap.** A higher-order function that wraps a target function with extra behavior (retry on failure, log inputs/outputs, time the call). This is exactly the decorator pattern.

```python
def with_retries(func, retries=3):
    def wrapped(*args, **kwargs):
        last_error = None
        for attempt in range(retries):
            try:
                return func(*args, **kwargs)
            except Exception as exc:
                last_error = exc
        raise last_error
    return wrapped

import random

def flaky_lookup(item_id):
    if random.random() < 0.7:
        raise RuntimeError("network glitch")
    return {"id": item_id, "name": "Wireless Mouse"}

robust_lookup = with_retries(flaky_lookup, retries=10)
```

`with_retries` takes a function and returns a new function that calls it up to `retries` times before giving up. The original `flaky_lookup` doesn't have to know anything about retrying.

**5. Function factory.** Return a configured function. Covered earlier in the chapter; this is the "make_multiplier", "make_tax_calculator", "at_least" pattern.

These five patterns cover a large fraction of higher-order code in real Python projects. Naming them makes them easier to recognize and apply without inventing the shape from scratch.

<h1 id="higher-order-functions-vs-oop-polymorphism">
  Higher-Order Functions vs OOP Polymorphism
</h1>

There's an interesting overlap between higher-order functions and object-oriented polymorphism. Both are ways to parameterize behavior. The difference is what gets passed: a function or an object.

Consider a discount system where different kinds of discounts (percentage off, fixed amount off, buy-one-get-one) need to be pluggable.

**Object-oriented style: pass an object that has a `apply` method.**

```python
class PercentageDiscount:
    def __init__(self, rate):
        self.rate = rate

    def apply(self, price):
        return price * (1 - self.rate)

class FixedDiscount:
    def __init__(self, amount):
        self.amount = amount

    def apply(self, price):
        return max(price - self.amount, 0)

def checkout(price, discount):
    return round(discount.apply(price), 2)

print(checkout(100, PercentageDiscount(0.10)))
print(checkout(100, FixedDiscount(15)))
```

`checkout` doesn't know which kind of discount it received; it calls `.apply` on it. That's polymorphism: different objects respond to the same message in different ways.

**Functional style: pass a function.**

```python
def percentage_discount(rate):
    return lambda price: price * (1 - rate)

def fixed_discount(amount):
    return lambda price: max(price - amount, 0)

def checkout(price, discount):
    return round(discount(price), 2)

print(checkout(100, percentage_discount(0.10)))
print(checkout(100, fixed_discount(15)))
```

Same behavior, less ceremony. `checkout` takes a callable; the callable is built by a factory that captures the discount's configuration.

Which is better depends on what else the "discount" needs to do. If a discount is just a function from price to discounted price, the functional version is shorter and clearer. If a discount also needs to know its name, its expiration date, whether it stacks with other discounts, and how to format itself for display, an object that bundles all that state and behavior in one place is the better fit.

| Aspect              | Higher-order function      | OOP polymorphism                                       |
| ------------------- | -------------------------- | ------------------------------------------------------ |
| What gets passed    | A function                 | An object with methods                                 |
| State               | Captured in a closure      | Held as object attributes                              |
| Multiple operations | One function per operation | Multiple methods on one object                         |
| Extending           | Add a new function         | Add a new class (or method)                            |
| When to prefer      | Behavior is one operation  | Behavior is several related operations on shared state |

The pragmatic answer is "use the lighter tool when it fits". A class with one method and nothing else is usually a sign that a function would be better. A closure that captures three different pieces of behavior across multiple returned functions is usually a sign that a class would be better.

The diagram is the quick decision sketch. Parameterizing one operation, or several? One operation usually fits a function; several related operations usually fit a class. Either way, the goal is the same: write the structure once and let the caller plug in the variable behavior.
