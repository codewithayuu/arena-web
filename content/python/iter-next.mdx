<h1 id="the-two-methods-that-define-the-protocol">
  The Two Methods That Define the Protocol
</h1>

Two roles matter here: an **iterable** is something you can loop over, and an **iterator** is the thing that actually walks through the items one at a time. The iterator protocol is what makes those roles concrete.

An object plays the protocol by implementing dunder methods:

| Role     | Required Method  | What It Returns                                     |
| -------- | ---------------- | --------------------------------------------------- |
| Iterable | `__iter__(self)` | A fresh iterator over the iterable's items.         |
| Iterator | `__next__(self)` | The next item, or raises `StopIteration` when done. |
| Iterator | `__iter__(self)` | `self`. Iterators are also iterables.               |

That's the whole protocol. Three slots, one exception. Everything in Python that loops, comprehends, unpacks, or otherwise consumes a sequence ultimately calls these methods.

A short demo with a built-in iterable makes the slots visible:

```python
cart = ["mug", "notebook", "pen"]

it = cart.__iter__()
print(type(it))

print(it.__next__())
print(it.__next__())
print(it.__next__())
print(it.__next__())
```

The list itself doesn't have `__next__`. Calling `cart.__iter__()` produced a separate `list_iterator` object, and that's the object that knows how to walk the list. Each `__next__()` call returned the next item until there were none left. The fourth call raised `StopIteration` to signal the end.

The built-in functions `iter()` and `next()` are friendlier names for the dunders. You almost never call `__iter__` or `__next__` directly in real code:

```python
cart = ["mug", "notebook", "pen"]

it = iter(cart)
print(next(it))
print(next(it))
print(next(it))
```

`iter(obj)` calls `obj.__iter__()`. `next(it)` calls `it.__next__()`. Same operation, cleaner syntax.

<h1 id="iterable-vs-iterator-at-the-protocol-level">
  Iterable vs Iterator at the Protocol Level
</h1>

The cleanest way to describe the difference between an iterable and an iterator is by which methods each one has.

| Object                                 | Has `__iter__`?    | Has `__next__`? | Calling `iter()` returns      |
| -------------------------------------- | ------------------ | --------------- | ----------------------------- |
| Iterable (list, tuple, dict, str, set) | yes                | no              | A new iterator over its items |
| Iterator (returned by `iter()`)        | yes (returns self) | yes             | The same object               |

A list is iterable. It has `__iter__` but not `__next__`. Try to call `next()` on a list directly and Python tells you off:

```python
cart = ["mug", "notebook", "pen"]
next(cart)
```

The list doesn't track a position. It can't tell you what the "next" item is because it has no notion of "current." That state has to live somewhere, and that somewhere is the iterator object that `iter(cart)` creates.

Calling `iter()` on the same iterable twice gives you two independent iterators, each with its own position:

```python
cart = ["mug", "notebook", "pen"]

it1 = iter(cart)
it2 = iter(cart)

print(next(it1))
print(next(it1))
print(next(it2))
print(next(it1))
```

`it1` and `it2` walk the same list but keep separate cursors. This is exactly what makes nested loops over the same list work without surprises.

The diagram shows the relationship. One iterable. Many iterators, each with private state. When you call `iter()` on the iterable, you ask it to manufacture a fresh walker.

<h1 id="why-an-iterator-is-also-an-iterable">
  Why an Iterator Is Also an Iterable
</h1>

The protocol requires iterators to implement `__iter__` and return `self`. At first this sounds odd, since an iterator is the thing doing the walking, not the thing being walked. Why does it need to advertise itself as iterable too?

The reason is so iterators can be used directly in `for` loops, comprehensions, and any function that expects an iterable. The `for` statement always starts by calling `iter()` on its target. If iterators didn't return themselves from `__iter__`, you'd get an error every time you tried to loop over a raw iterator.

Here's the rule in action. Take an iterator, pass it back through `iter()`, and you get the same object:

```python
cart = ["mug", "notebook", "pen"]
it = iter(cart)

print(it is iter(it))
```

`iter(it)` doesn't make a new iterator. It returns the same one. That's what "iterators are iterables" means at the implementation level.

The practical effect is that this works:

```python
cart = ["mug", "notebook", "pen"]
it = iter(cart)

for item in it:
    print(item)
```

The `for` loop internally calls `iter(it)`, which gives back `it` itself, and then calls `next()` on it until `StopIteration`.

The catch: an iterator is single-use. Once exhausted, it stays exhausted. Looping over the same iterator twice does nothing the second time:

```python
cart = ["mug", "notebook", "pen"]
it = iter(cart)

for item in it:
    print(item)

print("second pass:")
for item in it:
    print(item)
```

The second `for` immediately gets `StopIteration` on the first `next()` call and exits without printing anything. The iterator's internal cursor is sitting past the end, and nothing in the protocol resets it. If you want to walk the data again, ask the iterable for a new iterator.

> **Cost:** Manufacturing a new iterator from a built-in iterable like `list` is O(1). It allocates one small object and stores a reference to the list and an index. The work happens later as you call `next()`.

<h1 id="how-for-x-in-obj-desugars">How for x in obj: Desugars</h1>

The `for` loop is the most common consumer of the iterator protocol, and it's worth seeing exactly what it does behind the scenes. This loop:

```python
cart = ["mug", "notebook", "pen"]
for item in cart:
    print(item)
```

is roughly equivalent to this `while` loop:

```python
cart = ["mug", "notebook", "pen"]
it = iter(cart)
while True:
    try:
        item = next(it)
    except StopIteration:
        break
    print(item)
```

Three steps. First, call `iter()` on the target once, at the start. Second, repeatedly call `next()` to pull items, binding each one to the loop variable. Third, catch `StopIteration` and break out of the loop. The `for` statement isn't magic. It's a tight wrapper around these three operations.

This desugaring explains several things that otherwise feel arbitrary:

- **Why `for` works on anything iterable.** Lists, tuples, dicts, sets, strings, files, ranges, and any class with `__iter__` all pass step one.
- **Why a `for` loop on the same iterator twice does nothing the second time.** The iterator returned by step one is already exhausted, so step two raises `StopIteration` immediately.
- **Why dicts loop over keys by default.** A dict's `__iter__` returns a key iterator, so the desugared `next()` calls yield keys.
- **Why iterating a file reads one line at a time.** Files implement `__next__` to read the next line and raise `StopIteration` at end of file.

Other constructs use the same desugaring. List comprehensions, generator expressions, tuple unpacking, `sum`, `min`, `max`, `any`, `all`, `sorted`, and the `in` operator on most types all start with `iter()` and consume with `next()`.

The flow shows one full pass of a `for` loop. `iter()` runs once. `next()` runs in a tight loop until `StopIteration` is raised, at which point the exception is swallowed and control moves past the loop.

<h1 id="stopiteration-is-how-an-iterator-says-im-done">
  StopIteration Is How an Iterator Says "I'm Done"
</h1>

The protocol has no "is there a next item?" method. There's no `has_next`, no boolean check. Instead, an iterator says "I'm done" by raising `StopIteration` from `__next__`. The caller is expected to catch that exception or use a construct (like `for`) that catches it automatically.

This makes `__next__` strictly two-state: either return a value, or raise `StopIteration`. Nothing else is a valid "end" signal.

```python
nums = iter([1, 2])
print(next(nums))
print(next(nums))

try:
    print(next(nums))
except StopIteration:
    print("iterator exhausted")
```

Once an iterator raises `StopIteration`, it stays exhausted. Calling `next()` again raises `StopIteration` again. The iterator never magically resets.

```python
nums = iter([1, 2])
list(nums)
list(nums)
```

```python
>>> nums = iter([1, 2])
>>> list(nums)
[1, 2]
>>> list(nums)
[]
```

The first `list(nums)` drained the iterator. The second got nothing because the iterator was already done.

`next()` also accepts an optional **default** argument. If you pass one, `StopIteration` is converted into a return of that default value instead of being raised:

```python
prices = iter([29.99, 14.99])

print(next(prices, None))
print(next(prices, None))
print(next(prices, None))
print(next(prices, "no more prices"))
```

This is occasionally cleaner than a `try`/`except` when you just want to peek at the next item with a fallback.

<h1 id="a-minimal-custom-iterator">A Minimal Custom Iterator</h1>

The protocol becomes concrete the moment you implement it on your own class. Here's the smallest example that exercises both methods, just to make the contract tangible.

```python
class CartCounter:
    """Yields integers 1, 2, ..., n for counting items in a cart."""

    def __init__(self, total_items):
        self.total_items = total_items
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.current >= self.total_items:
            raise StopIteration
        self.current += 1
        return self.current

counter = CartCounter(3)
for n in counter:
    print(f"item {n}")
```

Three things to notice. First, `__iter__` returns `self` because this class is its own iterator. Second, `__next__` checks the end condition first and raises `StopIteration` before doing anything else. Third, the state (`self.current`) lives on the instance, which is why the iterator can pause and resume between `next()` calls.

This class works in any context that consumes an iterable:

```python
print(list(CartCounter(4)))
print(sum(CartCounter(5)))
print(", ".join(str(n) for n in CartCounter(3)))
```

`list()`, `sum()`, and the generator expression all call `iter()` on the `CartCounter` instance (which returns the instance itself), then `next()` until `StopIteration`. The class needed no extra code to be compatible with these built-ins because it spoke the protocol.

Most non-trivial custom iterators are easier to write as full classes or as generator functions. The hand-rolled class above is the lowest-level form, but it's rarely the cleanest.

> **Cost:** Each `next()` call is a method call plus whatever work `__next__` does. Generator functions often produce identical iteration with less code and slightly less per-call overhead because their state machine is implemented in C.

<h1 id="the-two-argument-itercallable-sentinel-form">
  The Two-Argument iter(callable, sentinel) Form
</h1>

`iter()` has a less-known second form that takes two arguments: a zero-argument callable and a sentinel value. It builds an iterator that calls the callable each time `next()` is called and stops as soon as the callable returns the sentinel.

The shape:

```python
it = iter(callable_with_no_args, sentinel)
```

Each call to `next(it)` calls `callable_with_no_args()`. If the result equals `sentinel`, `StopIteration` is raised. Otherwise the result is the next item.

A small e-commerce example: ask the customer to enter products to add to their cart, one per line, until they type `done`:

```python
def prompt_for_item():
    return input("Add item (or 'done'): ").strip()

cart = list(iter(prompt_for_item, "done"))
print("cart:", cart)
```

**Sample run:**

```text
Add item (or 'done'): mug
Add item (or 'done'): notebook
Add item (or 'done'): pen
Add item (or 'done'): done
cart: ['mug', 'notebook', 'pen']
```

Without the two-argument form, you'd write a `while` loop with an explicit break:

```python
cart = []
while True:
    item = prompt_for_item()
    if item == "done":
        break
    cart.append(item)
```

Both versions do the same thing. The `iter(callable, sentinel)` form turns the loop into an iterator that any consumer (a `for` loop, a comprehension, `list()`, `sum()`) can use.

A useful pattern this enables: reading a file in fixed-size chunks until the end of the file. `file.read(n)` returns an empty bytes/string when the file is exhausted, which makes `b""` (or `""`) a natural sentinel:

```python
with open("orders.log", "wb") as f:
    f.write(b"order-1\norder-2\norder-3\norder-4\n")

with open("orders.log", "rb") as f:
    for chunk in iter(lambda: f.read(8), b""):
        print(chunk)
```

The lambda is a zero-argument callable that returns the next 8-byte chunk. The sentinel `b""` marks end of file. The result is a clean `for` loop over fixed-size blocks, without a hand-written `while True` and `break`.

The callable must take no arguments. If yours does, wrap it in a `lambda` or `functools.partial`:

```python
import functools

def read_n(f, n):
    return f.read(n)

with open("orders.log", "rb") as f:
    reader = functools.partial(read_n, f, 16)
    for chunk in iter(reader, b""):
        print(chunk)
```

The two-argument form is one of those features that's easy to overlook but pays off the moment you have a "call this thing repeatedly until it signals done" pattern.

<h1 id="the-full-protocol-contract-in-one-picture">
  The Full Protocol Contract in One Picture
</h1>

Reading the diagram in plain language:

1. Any object that wants to be iterable defines `__iter__`. That method returns an iterator.
2. The iterator also defines `__iter__`, but it returns itself. This is what lets iterators stand in for iterables in any consumer.
3. The iterator defines `__next__`. Each call returns the next item, or raises `StopIteration` if there are none left.
4. `StopIteration` is the only way to signal end-of-iteration.

Every loop, comprehension, unpacking, and iteration-consuming built-in in Python is built on these four facts.

<h1 id="common-mistake-patterns">Common Mistake Patterns</h1>

A few patterns trip up beginners more than others. Each one is easy to spot once you know what to look for.

<h3 id="forgetting-to-raise-stopiteration">
  Forgetting to Raise StopIteration
</h3>

The single most common iterator bug: `__next__` returns a sentinel value (like `None`) instead of raising `StopIteration`. The `for` loop never sees the end-of-iteration signal and either yields the sentinel as a normal value or loops forever.

**What's wrong with this code?**

```python
class Countdown:
    def __init__(self, start):
        self.value = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.value <= 0:
            return None
        self.value -= 1
        return self.value + 1

for n in Countdown(3):
    print(n)
    if n is None:
        break
```

The author meant `Countdown(3)` to yield `3, 2, 1` and stop. But because `__next__` returns `None` instead of raising `StopIteration`, the loop keeps going and `None` shows up as a regular value. The `if n is None: break` is a workaround, not a fix.

**Fix:**

```python
class Countdown:
    def __init__(self, start):
        self.value = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.value <= 0:
            raise StopIteration
        self.value -= 1
        return self.value + 1

for n in Countdown(3):
    print(n)
```

`StopIteration` is the only legitimate "I'm done" signal. Returning `None` is just returning `None`.
