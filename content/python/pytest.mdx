<h1 id="why-pytest">Why pytest</h1>

`unittest`, the test framework that ships with the standard library, works, but the API is heavy. Every check goes through a method (`assertEqual`, `assertTrue`, `assertIn`, `assertRaises`, and a couple dozen more), every test lives inside a `TestCase` subclass, and setup happens through `setUp`/`tearDown` boilerplate. That style was familiar to anyone coming from JUnit in the early 2000s. It's also a lot of typing for what should be simple checks.

pytest takes a different stance. A test is a plain function whose name starts with `test_`. A check is a plain `assert`. There's no class to inherit, no method to look up, no special imports for most cases. The framework handles the rest: collecting tests from your files, running them, and producing a readable failure report when something breaks.

The result is shorter tests, less ceremony, and (this matters more than it sounds) failure messages that actually show you what went wrong. Where `unittest` shows `AssertionError: 99.95 != 99.96`, pytest shows the full expression, the values of every sub-expression, and the diff. You'll see this in action in a moment.

pytest is not in the standard library. It's a community project, but it's the de facto standard. The big open-source Python projects, the major web frameworks, the data and ML libraries, all use it. If you're writing tests in 2026, this is the framework to learn.

<h1 id="installing-pytest">Installing pytest</h1>

A single pip install gets you the framework and the `pytest` command:

```text
pip install pytest
```

Confirm the install:

```text
pytest --version
```

Versions move forward, so your number may differ. Anything in the 8.x range behaves the same for what's in this chapter. From here on, every `pytest` command in the chapter assumes the binary is on your `PATH`. If it isn't, run `python -m pytest` instead, which calls the same entry point through the interpreter.

A typical project keeps tests in a `tests/` folder next to the application code:

```text
shop/
    __init__.py
    cart.py
    pricing.py
    orders.py
tests/
    test_cart.py
    test_pricing.py
    test_orders.py
pyproject.toml
```

The `tests/` directory doesn't need an `__init__.py` in most setups. pytest collects from it directly. Some larger projects do add one to control import paths, but you don't need to start there.

<h1 id="your-first-pytest-test">Your First pytest Test</h1>

Here's a minimum working example. The application code:

```python
# shop/pricing.py
def calculate_total(prices):
    return sum(prices)
```

The test:

```python
# tests/test_pricing.py
from shop.pricing import calculate_total

def test_calculate_total_sums_prices():
    assert calculate_total([29.99, 14.99, 9.99]) == 54.97
```

Run it from the project root:

```text
pytest
```

The dot after the file name is the test result. One dot per test: `.` for pass, `F` for fail, `E` for error during setup, `s` for skipped, `x` for expected-fail. The summary line at the bottom totals everything up.

That's the whole loop. Write a function whose name starts with `test_`, put an `assert` inside, run `pytest`. There's nothing else to import, nothing to inherit from.

<h1 id="test-discovery-rules">Test Discovery Rules</h1>

pytest finds tests by following a small set of conventions. The rules are simple enough to memorize, and they're how the framework gets away with so little ceremony.

| Item                               | Rule                                          |
| ---------------------------------- | --------------------------------------------- |
| Test files                         | Named `test_*.py` or `*_test.py`              |
| Test functions                     | Names start with `test_`                      |
| Test classes                       | Names start with `Test`, no `__init__` method |
| Test methods (inside Test classes) | Names start with `test_`                      |

Anything not matching these patterns is ignored. A helper file called `helpers.py` in your `tests/` folder won't be collected, even if it contains functions whose names start with `test_`. A function called `check_total` inside `test_pricing.py` won't be collected, because its name doesn't start with `test_`. A class called `OrderTests` won't be collected, because its name doesn't start with `Test`.

The "no `__init__` method" rule on test classes catches a few people off guard. pytest can't instantiate a class with constructor arguments, so if you write `def __init__(self, ...)` on a `Test*` class, pytest skips it with a warning. Use fixtures for setup instead.

Here's a quick demonstration of all three forms in one file:

```python
# tests/test_cart.py
from shop.pricing import calculate_total

# A standalone function
def test_empty_cart_totals_zero():
    assert calculate_total([]) == 0

# A class grouping related tests
class TestCartTotals:
    def test_single_item(self):
        assert calculate_total([19.99]) == 19.99

    def test_multiple_items(self):
        assert calculate_total([10.00, 20.00, 30.00]) == 60.00
```

Run pytest and all three are picked up:

```text
pytest -v
```

The `::` notation is pytest's way of pointing at a specific test. You can copy any of those identifiers and pass it back to pytest to run just that one:

```text
pytest tests/test_cart.py::TestCartTotals::test_single_item
```

This shows up everywhere: in CI failure output, in editor integrations, in the `--lf` "rerun last failed" feature. Knowing how to read the `::` path is useful.

The diagram shows the two-stage pipeline: **collection** walks the directory tree and finds matching files, functions, and classes; **execution** runs everything collection found. Collection happens up front, before any test runs. If you have a syntax error in `test_cart.py`, you'll see it as a collection error, not a test failure.

<h1 id="plain-assert-and-why-its-better">Plain assert and Why It's Better</h1>

This is pytest's headline feature. You write a normal Python `assert`, and when it fails, pytest unpacks the expression and shows you what each side evaluated to. The technical term for this is **assertion rewriting**: pytest rewrites the bytecode of your test functions at import time so that a failing `assert` produces a rich diff instead of a bare `AssertionError`.

Compare. Here's an equivalent test in `unittest` and pytest:

```python
# unittest style
import unittest
from shop.pricing import calculate_total

class TestPricing(unittest.TestCase):
    def test_total(self):
        self.assertEqual(calculate_total([29.99, 14.99, 9.99]), 99.99)
```

```python
# pytest style
from shop.pricing import calculate_total

def test_total():
    assert calculate_total([29.99, 14.99, 9.99]) == 99.99
```

Both fail (the actual total is `54.97`, not `99.99`). Look at the failure output side by side.

**unittest output:**

```text
======================================================================
FAIL: test_total (__main__.TestPricing.test_total)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "test.py", line 6, in test_total
    self.assertEqual(calculate_total([29.99, 14.99, 9.99]), 99.99)
AssertionError: 54.97 != 99.99
```

**pytest output:**

```text
=================================== FAILURES ===================================
__________________________________ test_total __________________________________

    def test_total():
>       assert calculate_total([29.99, 14.99, 9.99]) == 99.99
E       assert 54.97 == 99.99
E        +  where 54.97 = calculate_total([29.99, 14.99, 9.99])

tests/test_pricing.py:4: AssertionError
```

The pytest version shows the failing line, breaks it into its sub-expressions, and tells you which call produced which value. For a small case the difference is minor. For anything more involved, the difference is enormous.

Here's a more interesting failure. Suppose you have a function that builds an order summary dict:

```python
# shop/orders.py
def order_summary(items):
    return {
        "count": len(items),
        "total": sum(item["price"] for item in items),
        "names": [item["name"] for item in items],
    }
```

A test with the wrong expected value:

```python
def test_order_summary():
    items = [
        {"name": "Mouse", "price": 29.99},
        {"name": "Cable", "price": 9.99},
    ]
    assert order_summary(items) == {
        "count": 2,
        "total": 39.98,
        "names": ["Mouse", "Keyboard"],
    }
```

pytest shows a structured diff:

```text
def test_order_summary():
        items = [...]
>       assert order_summary(items) == {
E           AssertionError: assert {'count': 2, '...uffix...} == {'count': 2, '...uffix...}
E
E             Common items:
E             {'count': 2, 'total': 39.98}
E             Differing items:
E             {'names': ['Mouse', 'Cable']} != {'names': ['Mouse', 'Keyboard']}
E             Use -v to get more diff
```

For lists and strings, pytest shows element-level diffs. For nested structures, it points at which key differs. For long sequences, `-v` (verbose) gives the full side-by-side diff.

That richness is the whole reason people switch off `assertEqual` and friends. You don't have to remember which assertion method to use for which type. `assert` works for everything, and the failure output gives you enough information to fix the test (or find the bug) without rerunning under a debugger.

> **Cost:** Assertion rewriting only works inside test files that pytest imports (the ones matching `test_*.py` or `*_test.py`). If you write a helper function in a module that lives outside the test tree and `assert` from there, you'll get the plain `AssertionError` without the rich output. Move the helper to a test file or to `conftest.py` to keep the nice errors.

<h1 id="expecting-exceptions-with-pytestraises">
  Expecting Exceptions with pytest.raises
</h1>

Some code is supposed to raise. A discount above 100% should reject. A negative quantity should reject. Pulling stock for an out-of-stock item should reject. You don't want to write `try/except` boilerplate for every one of those tests; pytest gives you `pytest.raises` as a context manager.

The pattern is straightforward:

```python
import pytest

def apply_discount(total, percent):
    if not 0 <= percent <= 100:
        raise ValueError(f"discount must be 0-100, got {percent}")
    return total * (1 - percent / 100)

def test_negative_discount_raises():
    with pytest.raises(ValueError):
        apply_discount(100, -5)

def test_oversized_discount_raises():
    with pytest.raises(ValueError):
        apply_discount(100, 150)
```

Inside the `with` block, the code under test must raise the named exception (or a subclass) for the test to pass. If it raises a different exception, that exception propagates and the test errors out. If it raises nothing at all, the test fails with `DID NOT RAISE`.

You can also check the exception message using `match=`, which takes a regex:

```python
def test_negative_discount_message():
    with pytest.raises(ValueError, match=r"discount must be 0-100"):
        apply_discount(100, -5)
```

`match=` is a `re.search`, not a full-string match, so you only need a fragment of the message. Useful for asserting that the error is for the right reason without pinning the test to the exact wording.

If you need to inspect the exception (assert on its attributes, for example), the context manager captures it as the `as` target:

```python
def test_discount_error_value():
    with pytest.raises(ValueError) as exc_info:
        apply_discount(100, -5)
    assert "-5" in str(exc_info.value)
    assert exc_info.type is ValueError
```

`exc_info.value` is the exception instance. `exc_info.type` is the exception class. `exc_info.traceback` is the traceback object if you ever need it.

One thing to watch for: only the code that needs to raise should be inside the `with` block. Setting up data or asserting on side effects should be outside.

**What's wrong with this code?**

```python
def test_oversized_discount_raises():
    with pytest.raises(ValueError):
        total = 100
        percent = 150
        result = apply_discount(total, percent)
        assert result < 0
```

The `assert result < 0` will never run; the call before it raises. But more importantly, if the setup of `total` or `percent` were to raise something unrelated, the test would still pass (`pytest.raises` would accept the wrong-reason exception). Keep the block tight:

**Fix:**

```python
def test_oversized_discount_raises():
    total = 100
    percent = 150
    with pytest.raises(ValueError):
        apply_discount(total, percent)
```

Now the only thing the `with` block guards is the one call you expect to raise.

<h1 id="comparing-floats-with-pytestapprox">
  Comparing Floats with pytest.approx
</h1>

Floating point math is approximate, and equality checks on floats are a common source of false failures. The classic example:

```python
>>> 0.1 + 0.2 == 0.3
False
>>> 0.1 + 0.2
0.30000000000000004
```

This bites tests all the time. Sum a list of prices, apply a discount, compare the result to a hand-calculated total, watch the assertion fail by a millionth of a cent.

pytest's answer is `pytest.approx`, a helper that compares floats with a tolerance:

```python
import pytest

def test_cart_total_with_floats():
    prices = [0.1, 0.2]
    assert sum(prices) == pytest.approx(0.3)
```

This passes. `pytest.approx` defaults to a relative tolerance of `1e-6` (one part in a million), which is loose enough to absorb the usual IEEE 754 noise but tight enough that real bugs still surface.

You can tune the tolerance when you need to:

```python
# Absolute tolerance: difference must be within 0.01
assert apply_discount(100, 33) == pytest.approx(67.00, abs=0.01)

# Relative tolerance: difference within 0.1% of the expected value
assert apply_discount(99.95, 10) == pytest.approx(89.955, rel=0.001)
```

`abs` is good when you want "within a cent" or "within a millisecond" semantics. `rel` is good when the expected value can vary in magnitude (a $5 cart and a $5,000 cart should both pass a "within 0.1%" check).

`approx` works on collections, too. Comparing two lists of floats element-by-element is one line:

```python
def test_apply_discount_to_each_price():
    prices = [10.00, 20.00, 30.00]
    discounted = [p * 0.9 for p in prices]
    assert discounted == pytest.approx([9.00, 18.00, 27.00])
```

It also works on dict values:

```python
def test_order_totals():
    actual = {"subtotal": 99.99, "tax": 8.25, "total": 108.24}
    expected = {"subtotal": 99.99, "tax": 8.25, "total": 108.24}
    assert actual == pytest.approx(expected)
```

If you're testing anything that involves arithmetic on floats (totals, taxes, discounts, percentages, scientific computation, ML metrics), make `approx` your default. Plain `==` on floats is a footgun.

> **Cost:** `pytest.approx` is fine for the sizes of cart and order data you'll typically see, but on very large numeric arrays (10,000+ elements) the comparison runs element-by-element in Python. For heavy numerical work, `numpy.testing.assert_allclose` is faster.

<h1 id="skips-and-expected-failures">Skips and Expected Failures</h1>

Tests aren't always supposed to run. Some depend on an environment that isn't available (a database, a specific OS, a feature flag). Some are for code that's known to be broken right now, where you want to mark the failure as "expected" so it doesn't break the build, but still flip back to a pass once it's fixed.

pytest gives you three tools for this: `pytest.skip`, `pytest.xfail`, and `pytest.fail`. All three can be called as functions inside a test, and they have decorator equivalents (`@pytest.mark.skip`, `@pytest.mark.skipif`, `@pytest.mark.xfail`) for cases where you can decide before the test runs.

<h3 id="pytestskip-and-pytestmarkskip">pytest.skip and @pytest.mark.skip</h3>

Use `skip` when a test shouldn't run at all under the current conditions:

```python
import sys
import pytest

def test_uses_walrus_operator():
    if sys.version_info < (3, 8):
        pytest.skip("walrus operator requires Python 3.8+")
    # ... rest of test
```

The decorator form is cleaner when the condition is static:

```python
@pytest.mark.skip(reason="needs database; run with --db")
def test_orders_persisted_to_db():
    ...
```

`@pytest.mark.skipif` takes a condition:

```python
@pytest.mark.skipif(sys.platform == "win32", reason="POSIX file paths only")
def test_export_path_format():
    ...
```

In the output, skipped tests show as `s` in the dot summary, and `pytest -rs` (or `-ra` for all non-pass reasons) prints the skip reasons:

```text
tests/test_orders.py s                                                   [100%]

============================ short test summary info ===========================
SKIPPED [1] tests/test_orders.py:5: needs database; run with --db
=========================== 1 skipped in 0.01s ================================
```

<h3 id="pytestmarkxfail">@pytest.mark.xfail</h3>

Expected failure. The test runs, but its result is inverted: if it fails, the suite still passes (recorded as `xfail`); if it unexpectedly passes, that shows up as `xpass`, which you can configure to fail the build (`strict=True`).

```python
@pytest.mark.xfail(reason="bug #1234: cart rounds half-up instead of banker's")
def test_cart_uses_banker_rounding():
    cart_total = sum([0.005, 0.005, 0.005])
    assert round(cart_total, 2) == 0.02  # banker's rounding would give 0.02
```

`xfail` is the right tool when you know about a bug and you've written the test that proves the fix, but the fix isn't merged yet. It documents the failure in the test suite without breaking CI. Once the fix lands, the test starts passing, and you remove the marker.

<h3 id="pytestfail">pytest.fail</h3>

Force a failure with a message. Useful inside branches where the test should never reach (a defensive "this shouldn't happen" check):

```python
def test_order_status_transitions():
    order = place_order()
    if order.status == "cancelled":
        pytest.fail(f"order should not be cancelled at this point; got {order!r}")
    assert order.status == "placed"
```

You'd reach for this in tests with multiple branches or post-hoc inspection logic. Most of the time, a plain `assert` does the job.

<h1 id="markers-basics">Markers Basics</h1>

A **marker** is a tag you attach to a test (or a class, or a whole module) with `@pytest.mark.something`. pytest treats certain markers as built-in (`skip`, `skipif`, `xfail`, `parametrize`), and you can define your own for filtering and grouping.

You've already seen `skip`, `skipif`, and `xfail`. `parametrize` runs the same test against multiple inputs.

Custom markers let you tag tests by category and then run subsets:

```python
import pytest

@pytest.mark.slow
def test_full_order_pipeline():
    # takes a few seconds to run
    ...

@pytest.mark.smoke
def test_create_cart():
    ...
```

Run only the smoke tests:

```text
pytest -m smoke
```

Run everything except the slow ones:

```text
pytest -m "not slow"
```

Combine markers:

```text
pytest -m "smoke and not slow"
```

There's one gotcha: by default, pytest warns about unknown markers. To register your custom markers properly, add them to `pytest.ini` (or the `[tool.pytest.ini_options]` section in `pyproject.toml`):

```text
# pytest.ini
[pytest]
markers =
    slow: tests that take more than a second
    smoke: minimal smoke tests run on every commit
    db: tests that require a database connection
```

With that in place, `pytest --markers` lists all registered markers along with their descriptions, and the warnings stop. Skipping this step works, but you'll see noise like:

```text
PytestUnknownMarkWarning: Unknown pytest.mark.smoke - is this a typo?  You can register custom marks to avoid this warning - for details, see https://docs.pytest.org/en/stable/how-to/mark.html
```

Register your markers. It's a one-line entry per marker, and it gives the next person on the team a place to look for the conventions you're using.

<h1 id="useful-command-line-flags">Useful Command-Line Flags</h1>

pytest has more flags than you'll ever memorize, but a small set comes up daily. These are worth committing to muscle memory.

| Flag                      | What it does                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| `-v`                      | Verbose. Show each test name and pass/fail status, instead of dots.                       |
| `-q`                      | Quiet. Even less output than the default. Good for CI.                                    |
| `-x`                      | Stop on the first failure. Don't continue with the rest of the suite.                     |
| `--maxfail=N`             | Stop after N failures. Like `-x` but with a budget.                                       |
| `-k EXPR`                 | Run only tests whose name matches the expression.                                         |
| `-m EXPR`                 | Run only tests whose markers match the expression.                                        |
| `--lf` / `--last-failed`  | Re-run only the tests that failed last time.                                              |
| `--ff` / `--failed-first` | Run failed tests first, then the rest.                                                    |
| `-s`                      | Don't capture stdout. Let `print()` show through to the terminal.                         |
| `--tb=short`              | Compact tracebacks. `--tb=long` for full, `--tb=line` for one-liners, `--tb=no` for none. |
| `--collect-only`          | Show what would run, don't actually run anything.                                         |

<h3 id="-x-stop-on-first-failure">-x: Stop on First Failure</h3>

When you're debugging a regression, the first failure is usually the most useful. The next ten failures might be downstream effects of the same broken state. `-x` halts the suite at the first red, which gets you to the relevant traceback immediately.

```text
pytest -x
```

> **Cost:** On a 5,000-test suite that takes 8 minutes, the difference between "run to completion" and "stop on first fail" can be 7 minutes and 50 seconds. Pair `-x` with `--lf` after you fix the bug to re-run just the previously-failing tests, and you avoid the full suite cost entirely.

<h3 id="-k-expr-filter-by-test-name">-k EXPR: Filter by Test Name</h3>

Run only tests whose names contain a substring:

```text
pytest -k discount
```

This matches every test whose qualified name (file, class, function) contains "discount" (case-insensitive). The expression supports `and`, `or`, and `not`:

```text
pytest -k "discount and not negative"
```

That runs every discount test except the ones whose name contains "negative".

<h3 id="-lf-and-ff-re-run-failed-tests">--lf and --ff: Re-Run Failed Tests</h3>

After a failure, the tightest feedback loop is to fix the code and re-run only the test that broke. `--lf` does exactly that:

```text
pytest --lf
```

If everything is fixed, `--lf` reports "no tests ran" and skips the work. If some failures remain, only those run.

`--ff` is the cousin: run the failed tests first, then everything else. Useful when you want fast feedback on the known-broken tests but also want to make sure you didn't break anything else.

<h3 id="-s-let-print-through">-s: Let print() Through</h3>

pytest captures stdout during test runs, so `print()` calls don't show up unless a test fails. When you're debugging by sprinkling prints, that's frustrating. `-s` disables the capture:

```text
pytest -s
```

Use it sparingly. The default capture is there because hundreds of `print` lines from passing tests would drown the actual report.

<h3 id="-tbshort-compact-tracebacks">--tb=short: Compact Tracebacks</h3>

The default traceback is helpful but verbose. For a suite with a hundred failures (think: a refactor that breaks an import), the screens of traceback get unmanageable. `--tb=short` trims each to just the failure location and one line of context:

```text
pytest --tb=short
```

`--tb=line` is even more compact (one line per failure). `--tb=no` suppresses tracebacks entirely, leaving just the summary. All three are good for skimming a large failure set before diving in.

<h1 id="project-layout-and-conftestpy">Project Layout and conftest.py</h1>

A typical pytest project keeps tests in their own folder, mirroring the application structure:

```text
shop/
    __init__.py
    cart.py
    pricing.py
    orders.py
    inventory.py
tests/
    test_cart.py
    test_pricing.py
    test_orders.py
    test_inventory.py
    conftest.py
pyproject.toml
```

`conftest.py` is a special file pytest knows about. It's where you put fixtures and hooks that should be shared across multiple test files in the same directory (and its subdirectories). You don't import it; pytest finds it automatically.

The name `conftest.py` is reserved, and you'll see it in every real-world pytest project. If you're poking around an open-source codebase and see a `conftest.py`, that's where the shared test setup lives.

You don't have to put `__init__.py` in the `tests/` folder. pytest can collect from a flat directory without it. Some projects do add it (often to fix import conflicts when two files in different folders have the same name), but it's not the default.

For a one-file project, you can also just drop your tests at the top level:

```text
shop.py
test_shop.py
```

Running `pytest` from that directory works the same. The folder layout is convention, not requirement.

<h1 id="a-worked-example">A Worked Example</h1>

Here's everything together. A small e-commerce module and a test file that exercises the pieces covered in this chapter.

The application code:

```python
# shop/cart.py
class CartError(ValueError):
    """Raised for invalid cart operations."""

def calculate_total(items):
    return sum(item["price"] * item["quantity"] for item in items)

def apply_discount(total, percent):
    if not 0 <= percent <= 100:
        raise CartError(f"discount must be 0-100, got {percent}")
    return total * (1 - percent / 100)

def cart_summary(items, discount_percent=0):
    subtotal = calculate_total(items)
    total = apply_discount(subtotal, discount_percent)
    return {
        "item_count": sum(item["quantity"] for item in items),
        "subtotal": subtotal,
        "discount_percent": discount_percent,
        "total": total,
    }
```

The tests:

```python
# tests/test_cart.py
import pytest
from shop.cart import CartError, calculate_total, apply_discount, cart_summary

# Basic equality with plain assert
def test_calculate_total_for_empty_cart():
    assert calculate_total([]) == 0

def test_calculate_total_multiplies_price_by_quantity():
    items = [{"price": 9.99, "quantity": 3}]
    assert calculate_total(items) == pytest.approx(29.97)

# Class grouping
class TestApplyDiscount:
    def test_no_discount_returns_full_total(self):
        assert apply_discount(100, 0) == 100

    def test_50_percent_halves_the_total(self):
        assert apply_discount(99.98, 50) == pytest.approx(49.99)

    def test_negative_discount_raises(self):
        with pytest.raises(CartError, match="must be 0-100"):
            apply_discount(100, -5)

    def test_oversized_discount_raises(self):
        with pytest.raises(CartError):
            apply_discount(100, 150)

def test_cart_summary_structure():
```

Running this with the default flags:

```text
pytest -v
```

To skip the slow test for a quick check during development:

```text
pytest -v -m "not slow"
```

To run only the discount tests:

```text
pytest -v -k discount
```

To re-run anything that failed last time, stopping on the first one:

```text
pytest --lf -x
```

That's the daily flow. Most of pytest's power comes from combining these few flags, and you'll use them dozens of times a day once it's in your fingers.

A couple of pieces are conspicuously missing from this example: there's no `@pytest.fixture` for setting up the cart, and there's no `@pytest.mark.parametrize` for the four `TestApplyDiscount` cases that all look similar. Fixtures let you share setup code across tests without duplication. `parametrize` would turn those four discount tests into one parametrized test with four input rows. `monkeypatch` is a built-in fixture for replacing dependencies during a test.
