<h1 id="what-pickle-does">What Pickle Does</h1>

Pickle takes a Python object and produces a byte stream that can rebuild an equivalent object later. The conversion goes both ways with two pairs of functions: `dumps`/`loads` for in-memory bytes, and `dump`/`load` for files.

```python
import pickle

order = {
    "order_id": 5001,
    "customer": "ria",
    "items": [
        {"id": 101, "name": "wireless mouse", "price": 29.99, "qty": 1},
        {"id": 103, "name": "hdmi cable", "price": 9.99, "qty": 2},
    ],
    "total": 49.97,
    "status": "placed",
}

blob = pickle.dumps(order)
print(type(blob))
print(blob[:32])
print(len(blob), "bytes")

restored = pickle.loads(blob)
print(restored["items"][0]["name"])
print(restored == order)
```

The output is binary, not text. The first byte (`\x80`) is the pickle protocol marker, followed by opcodes that the decoder interprets to rebuild the object. The bytes aren't meant to be read by eye; pass them back to `pickle.loads`. The restored object is structurally equal to the original, including the nested list of dicts.

The encoder walks the object graph, emitting opcodes that describe types, attributes, and references. The decoder reads those opcodes back and runs them to reconstruct the graph. The decode side is what makes pickle dangerous; the security section covers that.

<h1 id="the-four-core-functions">The Four Core Functions</h1>

| Function                 | Input                              | Output                      | Use when                      |
| ------------------------ | ---------------------------------- | --------------------------- | ----------------------------- |
| `pickle.dumps(obj)`      | A Python object                    | A `bytes` object            | You want the result in memory |
| `pickle.loads(blob)`     | A `bytes` (or `bytes-like`) object | The reconstructed object    | You have the bytes already    |
| `pickle.dump(obj, file)` | Object + binary file               | `None` (writes to the file) | You're writing to disk        |
| `pickle.load(file)`      | A binary file                      | The reconstructed object    | You're reading from disk      |

The convention matches `json`: `s` at the end means "string" (well, bytes here), no `s` means "file". The file-based versions always take a file opened in binary mode (`"rb"` or `"wb"`), because pickle data is binary.

```python
import pickle

products = [
    {"id": 101, "name": "wireless mouse", "price": 29.99},
    {"id": 102, "name": "hdmi cable", "price": 9.99},
]

with open("products.pkl", "wb") as f:
    pickle.dump(products, f)

with open("products.pkl", "rb") as f:
    restored = pickle.load(f)

print(restored[0]["name"])
print(restored == products)
```

`dump` is more efficient than `dumps` followed by `f.write`, because it doesn't build the full byte string in memory before writing. For small objects the difference is invisible; for large ones it matters.

`pickle.load` and `pickle.loads` allocate the full object graph in memory at once. A pickle representing a 2 GB dataframe needs at least 2 GB of memory to load, plus overhead. For pickling large datasets, look at `pickle.HIGHEST_PROTOCOL` (smaller output) or formats designed for the job, like Parquet or HDF5.

<h1 id="what-pickle-can-serialize">What Pickle Can Serialize</h1>

Pickle handles most things in the Python standard library, plus most user-defined classes, with no special effort on your part.

**Pickles cleanly without setup:**

- All built-in types: `int`, `float`, `bool`, `str`, `bytes`, `None`, `complex`.
- Containers: `list`, `tuple`, `dict`, `set`, `frozenset`. Tuples come back as tuples (unlike JSON).
- Common stdlib types: `datetime`, `date`, `time`, `timedelta`, `Decimal`, `Fraction`, `Path` from `pathlib`.
- Most user-defined classes whose state lives in `__dict__` or `__slots__`$La9

```python
import pickle
from datetime import datetime
from decimal import Decimal

class Order:
    def __init__(self, order_id, customer, total, placed_at):
        self.order_id = order_id
        self.customer = customer
        self.total = total
        self.placed_at = placed_at

    def __repr__(self):
        return f"Order({self.order_id}, {self.customer}, {self.total}, {self.placed_at})"

order = Order(
    order_id=5001,
    customer="ria",
    total=Decimal("89.97"),
    placed_at=datetime(2024, 11, 12, 14, 30, 0),
)

blob = pickle.dumps(order)
restored = pickle.loads(blob)
print(restored)
print(type(restored.total))
print(restored.placed_at.isoformat())
```

`Decimal` and `datetime` round-trip with full precision. No custom encoder, no string conversion, no type tags. The `Order` instance comes back as the same class, with the same attributes, ready to use.

Tuples and sets round-trip exactly, which is one of the main advantages over JSON:

```python
import pickle

data = {
    "coordinates": (37.7749, -122.4194),
    "tags": {"wireless", "ergonomic"},
}

restored = pickle.loads(pickle.dumps(data))
print(type(restored["coordinates"]))
print(type(restored["tags"]))
```

JSON would turn both into lists. Pickle preserves the distinction because it has the type information natively.

<h1 id="what-pickle-cant-serialize">What Pickle Can't Serialize</h1>

Pickle can't capture an object whose state depends on resources outside the running process. Common examples:

- **Open file objects.** They wrap an OS file descriptor; the descriptor number is meaningless in another process.
- **Open sockets and database connections.** Same reason.
- **Threads and locks.** They're tied to the current process.
- **Lambdas and inner functions.** Pickle stores functions by import path (module + qualified name). A lambda has neither; an inner function is defined inside another function and isn't importable.
- **Classes defined inside functions or interactively.** Same reason: pickle stores classes by reference, and a class inside a function has no stable import path.
- **Generators, iterators with internal state, and coroutines.** Their suspension state is not capturable.

```python
import pickle

f = open("orders.txt", "w", encoding="utf-8")

try:
    pickle.dumps(f)
except TypeError as e:
    print(f"file: {e}")

try:
    pickle.dumps(lambda x: x + 1)
except (AttributeError, pickle.PicklingError) as e:
    print(f"lambda: {e}")

def outer():
    class Inner:
        pass
    try:
        pickle.dumps(Inner())
    except (AttributeError, pickle.PicklingError) as e:
        print(f"inner class: {e}")

outer()
f.close()
```

The fix is to redesign so the unpicklable thing isn't part of the state you're trying to save. For an object that holds a connection, store the connection parameters, not the connection. For a callback, store its name or use a registry; don't pickle a lambda.

For more control over what gets pickled, classes can define `__getstate__` (returns the state dict to pickle) and `__setstate__` (rebuilds from that state). That lets you exclude unpicklable attributes during dump and recreate them on load:

```python
import pickle

class CachedClient:
    def __init__(self, url):
        self.url = url
        self.connection = self._connect()

    def _connect(self):
        return f"<live connection to {self.url}>"

    def __getstate__(self):
        # Drop the live connection; keep enough to rebuild it.
        return {"url": self.url}

    def __setstate__(self, state):
        self.url = state["url"]
        self.connection = self._connect()

client = CachedClient("https://store.example.com/api")
print(client.connection)
restored = pickle.loads(pickle.dumps(client))
print(restored.connection)
```

`__getstate__` and `__setstate__` are the standard extension points. The same hooks are useful for a compact representation, migrating old pickles into a new schema, or scrubbing credentials before serialization.

<h1 id="pickle-protocols">Pickle Protocols</h1>

A pickle starts with a one-byte protocol marker that tells the decoder which set of opcodes to expect. Python ships with six protocol versions, numbered 0 through 5. Each one is a strict superset of the previous, with smaller and faster encodings.

| Protocol | Python version | Notes                                                        |
| -------- | -------------- | ------------------------------------------------------------ |
| 0        | All            | ASCII text, human-readable, slowest, largest output          |
| 1        | All            | Older binary format, mostly historical                       |
| 2        | 2.3+           | Efficient binary for new-style classes                       |
| 3        | 3.0+           | Adds support for `bytes`                                     |
| 4        | 3.4+           | Adds large object support and frame markers; default in 3.8+ |
| 5        | 3.8+           | Adds out-of-band buffers for zero-copy of large arrays       |

`pickle.dumps` accepts an optional `protocol` argument. The two relevant defaults are `pickle.DEFAULT_PROTOCOL` (a sensible balance for the current Python version) and `pickle.HIGHEST_PROTOCOL` (the newest format the interpreter supports).

```python
import pickle

data = {"name": "wireless mouse", "stock": 25, "tags": ("usb", "compact")}

for protocol in range(pickle.HIGHEST_PROTOCOL + 1):
    blob = pickle.dumps(data, protocol=protocol)
    print(f"protocol {protocol}: {len(blob)} bytes")
```

The numbers shift around depending on the object, but the trend is consistent: protocol 0 is much larger than the binary protocols. For interoperability between Python versions, use the lowest protocol both sides understand. For storage and speed, use the highest one the writer supports and accept that older readers can't decode it.

For pickles meant to be read by a different Python version, pin the protocol explicitly:

```python
import pickle

data = {"order_id": 5001}
# Pin to protocol 4 so Python 3.4+ can read it
with open("compat.pkl", "wb") as f:
    pickle.dump(data, f, protocol=4)
```

For most code, the default `protocol` is fine. Pin it only when there's a known compatibility constraint.

<h1 id="the-security-problem">The Security Problem</h1>

`pickle.load` is not a parser, it's an interpreter. It runs opcodes from the byte stream, and those opcodes can call almost any Python function, including `os.system`, `subprocess.Popen`, `eval`, `exec`, or anything else importable. A malicious pickle is essentially a script that runs on import.

A concrete example: a pickle that runs a shell command when loaded.

```python
import pickle
import os

class Evil:
    def __reduce__(self):
        # __reduce__ tells pickle how to reconstruct the object.
        # Pickle calls the first item with the second as arguments.
        return (os.system, ("echo PWNED",))

blob = pickle.dumps(Evil())
print(f"blob length: {len(blob)} bytes")
print("loading...")
pickle.loads(blob)
```

The `__reduce__` method is the official extension point for telling pickle "to rebuild me, call this function with these arguments". The same mechanism that lets a class control its own serialization is what makes loading untrusted pickles dangerous. The payload doesn't have to be `os.system`; it can be anything reachable through the import system.

This isn't theoretical. Pickle has been used in attacks against ML model registries (where downloaded models are pickled `.pt` or `.pkl` files), task queue messages, and cache stores.

**The rule, with no exceptions:**

- Only load pickles from sources you fully control.
- Never load a pickle from user input, an HTTP request, a public registry, or any storage where an attacker could have written.
- If you need to send Python-like data across a trust boundary, use JSON, msgpack, protocol buffers, or another format whose decoder is a pure parser.

If you must accept pickles from a partially trusted source (an internal service, a colleague's data export), the safest approach is to load in a sandboxed subprocess and validate the result before using it. Even then, treat pickle as a last resort.

The standard library ships a `pickle.Unpickler` subclass mechanism (`find_class`) that lets you restrict which classes can be reconstructed. It's not a security boundary to rely on; it raises the attack cost slightly but doesn't eliminate it. Treat it as a hardening measure, not a fix.

```python
import pickle
import io

class SafeUnpickler(pickle.Unpickler):
    """Only allows specific safe types to be reconstructed."""
    ALLOWED = {
        ("builtins", "dict"),
        ("builtins", "list"),
        ("builtins", "tuple"),
        ("builtins", "str"),
        ("builtins", "int"),
        ("builtins", "float"),
        ("builtins", "bool"),
        ("builtins", "NoneType"),
    }

    def find_class(self, module, name):
        if (module, name) not in self.ALLOWED:
            raise pickle.UnpicklingError(f"forbidden: {module}.{name}")
        return super().find_class(module, name)

safe_data = pickle.dumps({"order_id": 5001, "items": [1, 2, 3]})
print(SafeUnpickler(io.BytesIO(safe_data)).load())

class Evil:
    def __reduce__(self):
        import os
        return (os.system, ("echo PWNED",))

evil_data = pickle.dumps(Evil())
try:
    SafeUnpickler(io.BytesIO(evil_data)).load()
except pickle.UnpicklingError as e:
    print(f"blocked: {e}")
```

The custom unpickler refuses to resolve `os.system`, so the malicious pickle fails. This is a whitelist, and getting whitelists right against a determined attacker is hard. The right default is "don't load untrusted pickles".

<h1 id="pickle-vs-json">Pickle vs JSON</h1>

The two formats look comparable on the surface; both serialize Python data structures and read them back. The differences are large and shape when you should use each.

| Aspect                 | Pickle                                             | JSON                                                       |
| ---------------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| Language support       | Python-only                                        | Universal (every language)                                 |
| Output format          | Binary opcodes                                     | Text (UTF-8)                                               |
| Type coverage          | Almost any Python object, custom classes           | Six fixed types: object, array, string, number, bool, null |
| Tuples and sets        | Round-trip exactly                                 | Tuples become arrays; sets need explicit conversion        |
| Custom classes         | Native support via `__reduce__` and `__getstate__` | Requires `default` callback or encoder subclass            |
| Security on load       | Arbitrary code execution risk                      | Pure parser, safe by design                                |
| Human-readable         | No                                                 | Yes                                                        |
| File size              | Smaller for binary-heavy data                      | Often comparable; can be larger for nested structures      |
| Stable across versions | No formal guarantee; protocol matters              | Yes; the format is standardized                            |

The decision rule:

- **JSON when:** the data crosses a trust boundary, the consumer is in another language, the format will live for years, the data fits within JSON's type model with a small amount of conversion, or a human will read or hand-edit the file.
- **Pickle when:** all sides are Python, you control both ends, you need to capture complex types (custom classes, datetimes, decimals) without writing converters, and the data is internal (caches, multiprocessing IPC, snapshots during development).

When in doubt, start with JSON. Move to pickle only when the type mismatch becomes a real problem and you can guarantee the data won't cross a trust boundary.

<h1 id="real-use-cases">Real Use Cases</h1>

Situations where pickle is the appropriate tool:

<h3 id="caching-computed-objects">Caching Computed Objects</h3>

A function that does expensive computation can cache its result on disk and reload it on subsequent runs. Pickle handles whatever object the function returns without requiring the cache layer to understand its shape.

```python
import pickle
import os

def expensive_catalog_query():
    print("running expensive query...")
    return [
        {"id": 101, "name": "wireless mouse", "price": 29.99},
        {"id": 102, "name": "hdmi cable", "price": 9.99},
    ]

def cached_catalog(cache_path):
    if os.path.exists(cache_path):
        with open(cache_path, "rb") as f:
            return pickle.load(f)
    catalog = expensive_catalog_query()
    with open(cache_path, "wb") as f:
        pickle.dump(catalog, f)
    return catalog

print(cached_catalog("catalog.pkl"))
print(cached_catalog("catalog.pkl"))
```

The second call hits the cache and skips the expensive computation. The cache path is fully under the program's control, so the security concern doesn't apply.

<h3 id="multiprocessing-ipc">Multiprocessing IPC</h3>

The `multiprocessing` module uses pickle to send objects between processes. When you call `Pool.map(fn, items)`, Python pickles each item, sends the bytes to a worker, unpickles them there, runs the function, and pickles the result back. The pickle calls are implicit in the API.

```python
from multiprocessing import Pool

def total_for_order(order):
    return order["order_id"], sum(item["price"] * item["qty"] for item in order["items"])

if __name__ == "__main__":
    orders = [
        {"order_id": 5001, "items": [{"price": 29.99, "qty": 1}, {"price": 9.99, "qty": 2}]},
        {"order_id": 5002, "items": [{"price": 14.99, "qty": 1}]},
    ]

    with Pool(2) as pool:
        for order_id, total in pool.map(total_for_order, orders):
            print(f"order {order_id}: total {total}")
```

`Pool.map` works on the items because each `dict` of primitives pickles cleanly. The function `total_for_order` works because it's defined at module level (and so is importable by name on the worker side). A lambda passed in its place would fail with a pickling error. That's the most common multiprocessing trap.

<h3 id="snapshots-for-debugging">Snapshots for Debugging</h3>

When a bug appears intermittently in production data, pickling the relevant in-memory state before the crash gives you something to reload in a debugger later. The state captures everything, custom classes and all, so the failing logic can be re-run in isolation.

```python
import pickle

def process_orders(orders):
    try:
        for order in orders:
            if order["status"] not in {"placed", "shipped"}:
                raise ValueError(f"unknown status: {order['status']}")
            # ... real processing here
    except Exception:
        with open("crash-state.pkl", "wb") as f:
            pickle.dump({"orders": orders}, f)
        raise
```

Loading `crash-state.pkl` later in a REPL provides the exact dict that triggered the failure, with full type fidelity. JSON would lose the distinction between sets, tuples, and custom classes that may matter for reproducing the bug.

<h1 id="alternatives-worth-knowing">Alternatives Worth Knowing</h1>

Pickle isn't the only serializer in town. Each alternative trades a feature in exchange for a different property.

| Format                          | Strength                                               | When to choose                                                               |
| ------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| **JSON**                        | Universal, safe, readable                              | Web APIs, configs, human-edited files, anything crossing language boundaries |
| **msgpack**                     | Binary, compact, fast, multi-language                  | Caches and queues that need to be fast and small but cross-language          |
| **Protocol Buffers (protobuf)** | Strongly-typed schemas, code generation, very fast     | RPC, long-lived stored data with versioning needs                            |
| **Apache Arrow / Parquet**      | Columnar, efficient for large tabular data             | Data engineering, analytics workloads                                        |
| **Pickle**                      | Native Python types, custom classes without converters | Caches, multiprocessing, snapshots, trusted-only data                        |

The trade-off: pickle is the most convenient and the least safe. JSON is the safest and the most limited. msgpack and protobuf sit between them, trading some convenience for portability and (in protobuf's case) a schema you can evolve.

For new code that doesn't have a strong reason to be Python-only, prefer one of the cross-language formats. Use pickle when the data is Python-shaped and the trust model is "I wrote both sides".

<h1 id="putting-it-together">Putting It Together</h1>

A small caching helper that handles the common cases: it pickles a value, writes it to disk through a temporary file (so a crash mid-write doesn't corrupt the cache), and reloads it on demand.

```python
import pickle
import os

def write_cache(value, path, protocol=pickle.HIGHEST_PROTOCOL):
    tmp = path + ".tmp"
    with open(tmp, "wb") as f:
        pickle.dump(value, f, protocol=protocol)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)

def read_cache(path):
    with open(path, "rb") as f:
        return pickle.load(f)

computed = {
    "generated_at": "2024-11-12T14:30:00",
    "products": [
        {"id": 101, "name": "wireless mouse", "price": 29.99},
        {"id": 102, "name": "hdmi cable", "price": 9.99},
    ],
}

write_cache(computed, "catalog.pkl")
restored = read_cache("catalog.pkl")
print(restored["products"][0]["name"])
print(restored == computed)
```

`HIGHEST_PROTOCOL` keeps the output compact. Writing through `.tmp` and `os.replace` means a reader either sees the old file or the new one, never a half-written file. `os.fsync` is the extra step that forces the data to physical disk before the rename; for caches it can be dropped, for anything that has to survive a power loss, keep it.

This is roughly the shape of a production-grade pickle write: atomic, with an explicit protocol, and confined to a path the program controls.
