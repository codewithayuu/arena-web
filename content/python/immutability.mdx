<h1 id="why-immutability-matters">Why Immutability Matters</h1>

A mutable value can be changed by anyone who holds a reference to it. That sounds harmless, but it's the source of a lot of bug-hunting in production code. Once a list, dict, or custom object is shared, any code path that touches it can change the state for every other code path.

Three concrete benefits come from making values immutable:

**Referential transparency.** This is the formal name for the property that the value of an expression doesn't depend on when or where you evaluate it. If `cart.total` is a method on a mutable cart, calling it twice in a row might give different answers, because something between the two calls might have added an item. If `cart` is immutable, `cart.total` is the same answer every time. Referentially transparent code is easier to test, easier to cache, and easier to refactor.

**No action at a distance.** When a function takes a mutable list and modifies it, the caller's list changes too, often unexpectedly. Immutable values can't be modified by called code, so the caller's value stays stable. Bugs caused by a function mutating its inputs can't happen.

**Safe sharing across threads.** Two threads reading the same immutable value never need to coordinate; nobody's writing. Two threads sharing a mutable value need locks, atomics, or careful queue-based coordination. The relevant fact here is that immutability removes most of the sharing problem.

A small e-commerce example shows the difference. The mutable version:

```python
def apply_discount(cart, percent):
    for item in cart:
        item["price"] = round(item["price"] * (1 - percent / 100), 2)
    return cart

original_cart = [
    {"name": "Wireless Mouse", "price": 29.99},
    {"name": "USB Cable", "price": 4.99},
]

discounted = apply_discount(original_cart, 10)
print("discounted:", discounted)
print("original:", original_cart)
```

The original cart was mutated. The caller still has a reference to the same list, and that list now holds discounted prices. Any code elsewhere holding a reference to `original_cart` and expecting the original prices would get incorrect data.

The immutable version returns a new cart instead:

```python
def apply_discount(cart, percent):
    return [
        {"name": item["name"], "price": round(item["price"] * (1 - percent / 100), 2)}
        for item in cart
    ]

original_cart = [
    {"name": "Wireless Mouse", "price": 29.99},
    {"name": "USB Cable", "price": 4.99},
]

discounted = apply_discount(original_cart, 10)
print("discounted:", discounted)
print("original:", original_cart)
```

Same discounted result, but the original cart is untouched. Any caller holding the original reference still has the original prices.

The cost of the immutable version is one extra list of dicts allocated. In return, the function is safe to call from anywhere, in any order, without worrying about what other code is doing with the inputs.

Returning new values instead of mutating doubles the memory pressure for that operation (the old value plus the new one). For small data, this is invisible. For million-element collections, it can matter; the persistent-data-structures section below covers what to do then.

<h1 id="pythons-built-in-immutable-types">Python's Built-in Immutable Types</h1>

Python has a handful of immutable types built in. They're the foundation of any immutability-based design, and the type itself enforces the rule.

| Type                      | Mutable? | Hashable? | Notes                                  |
| ------------------------- | -------- | --------- | -------------------------------------- |
| `int`, `float`, `complex` | No       | Yes       | Arithmetic returns new numbers         |
| `bool`                    | No       | Yes       | `True` and `False` are singletons      |
| `str`                     | No       | Yes       | All string methods return new strings  |
| `bytes`                   | No       | Yes       | Like `str` but for raw bytes           |
| `tuple`                   | No       | Sometimes | Immutable, but contents can be mutable |
| `frozenset`               | No       | Yes       | The immutable cousin of `set`          |
| `range`                   | No       | Yes       | Immutable lazy integer sequence        |
| `None`                    | No       | Yes       | A singleton                            |

The "sometimes" on `tuple` deserves a note. The tuple itself is immutable: you can't add, remove, or reassign elements. But if one of the elements is mutable (a list, say), that element can still be changed in place. The container is frozen; the contents may not be.

```python
prices = (29.99, 14.99, 9.99)

# This raises TypeError; tuples don't support item assignment.
try:
    prices[0] = 99.99
except TypeError as exc:
    print(f"TypeError: {exc}")

# But if a tuple holds mutable elements, those elements are still mutable.
mixed = ("Wireless Mouse", [29.99, 26.99])
mixed[1].append(24.99)
print(mixed)
```

The tuple holds a reference to the list. The reference can't be replaced, but the list it points at can still be modified. Immutability in Python is about the type of the container plus the types of its contents, not just the outermost type.

The same rule means a tuple with a mutable element isn't hashable, because hashing requires that the value (transitively) never changes. A tuple of fully immutable values is hashable; a tuple containing a list is not.
