<h1 id="the-four-clauses-at-a-glance">The Four Clauses at a Glance</h1>

A full exception-handling block in Python can have up to four clauses. You write `try` once, then any combination of `except`, `else`, and `finally`. Each one runs at a specific point in the flow, and each one answers a different question.

| Clause    | When it runs                                    | What it's for                               |
| --------- | ----------------------------------------------- | ------------------------------------------- |
| `try`     | First, always                                   | The risky operation you want to guard       |
| `except`  | Only if a matching exception is raised in `try` | Recovering from a specific failure          |
| `else`    | Only if `try` finished with no exception        | Code that should run only on the happy path |
| `finally` | Always, exception or not                        | Cleanup that has to happen no matter what   |

The minimum is `try` plus at least one `except` or `finally`. A `try` on its own is a syntax error, and so is `else` without an `except`. Beyond that, you mix and match. The most common shapes are `try/except`, `try/except/finally`, and the full `try/except/else/finally` when you want all four jobs handled cleanly.

Here's a small example that uses all four clauses on a product price lookup:

```python
prices = {"mug": 12.99, "notebook": 7.49, "pen": 1.99}

def get_price(product):
    try:
        price = prices[product]
    except KeyError:
        print(f"'{product}' not in catalog")
        return None
    else:
        print(f"Found '{product}'")
        return price
    finally:
        print("Lookup attempt complete")

print(get_price("mug"))
print("---")
print(get_price("phone"))
```

Notice that `"Lookup attempt complete"` prints on both runs, but `"Found 'mug'"` only prints on the successful one, and `"'phone' not in catalog"` only prints on the failing one. That's the whole pattern in miniature. The rest of the lesson is just details on each clause and the rules that connect them.

<h1 id="try-and-except-the-basics">try and except: The Basics</h1>

A `try` block marks the code you want to guard. An `except` block says "if this specific kind of exception happens in the `try`, here's how to handle it." If the `try` runs cleanly, the `except` block is skipped. If an exception is raised and it matches the type listed on the `except`, control jumps to the handler.

```python
quantities = {"mug": 5, "notebook": 12}

try:
    in_stock = quantities["pen"]
    print(f"Pen in stock: {in_stock}")
except KeyError:
    print("Pen isn't in the inventory yet")
```

The dict lookup raises `KeyError`. Python checks the `except` clauses in order, finds one that names `KeyError`, and runs that handler. The program keeps going from after the whole `try/except` block.

Catching an exception also catches its subclasses. `KeyError` is itself a subclass of `LookupError`, and `LookupError` is a subclass of `Exception`. Any of these three would catch the same dict-lookup error:

```python
prices = {"mug": 12.99}

for handler in ("KeyError", "LookupError", "Exception"):
    try:
        prices["notebook"]
    except KeyError:
        print(f"Caught by {handler}")
        break
```

The rule to remember is: `except SomeException` catches `SomeException` and every class that inherits from it.

> **Cost:** Setting up a `try` block is essentially free in CPython. The hit only comes when an exception actually fires, because Python has to build the traceback. On the happy path, `try/except` costs no more than the code it wraps.

<h1 id="catching-specific-exceptions">Catching Specific Exceptions</h1>

Catching a specific exception type is the version you should reach for most of the time. It says "I know this exact failure can happen here, and here's what to do about it." Anything else falls through and becomes a real crash, which is usually what you want.

```python
def parse_price(raw):
    try:
        return float(raw)
    except ValueError:
        return None

print(parse_price("19.99"))
print(parse_price("nineteen"))
print(parse_price(""))
```

The function only catches `ValueError`, which is what `float()` raises for strings that don't look like numbers. If a caller passed something weirder, like a list, `float([])` would raise `TypeError`. That wouldn't match the `except` clause, so it would propagate up and crash. That's fine. The function never claimed to handle `TypeError`; it claimed to handle "this string doesn't look like a number," and that's exactly the failure it catches.

The opposite approach, catching everything, looks like this:

```python
def parse_price_loose(raw):
    try:
        return float(raw)
    except:
        return None
```

This catches `ValueError`, `TypeError`, `MemoryError`, `KeyboardInterrupt`, and every other exception in Python. It also catches typos in your own code. If you misspell a variable name inside the `try`, that's a `NameError`, and this handler would silently turn it into `None`. Bare `except` is almost always wrong.

The takeaway for now: catch the smallest exception type that covers the failure you actually want to handle. Everything else should be allowed to crash so you can find out about it.

<h1 id="catching-multiple-exceptions">Catching Multiple Exceptions</h1>

Sometimes one piece of risky code can fail in several distinct ways, and you want the same recovery for each. Python gives you two ways to handle that: list the types in a tuple after one `except`, or write multiple `except` blocks with different handlers.

The tuple form groups types that share a handler:

```python
def get_first_item(cart):
    try:
        return cart[0]["name"]
    except (IndexError, KeyError, TypeError):
        return "Empty or malformed cart"

print(get_first_item([{"name": "mug"}]))
print(get_first_item([]))
print(get_first_item([{"price": 9.99}]))
print(get_first_item("not a cart"))
```

Each call fails in a different way. The empty list raises `IndexError`. The dict without a `"name"` key raises `KeyError`. The string can be indexed, but `"not a cart"[0]` is `"n"`, and `"n"["name"]` raises `TypeError` because strings don't index by string. All three failures land in the same handler.

Use the tuple form when the response is the same for every type in the group. If the response differs, write separate `except` blocks:

```python
def add_to_cart(cart, product, quantity):
    try:
        cart[product] += quantity
    except KeyError:
        cart[product] = quantity
        print(f"Added new product '{product}'")
    except TypeError:
        print(f"Cart should be a dict, got {type(cart).__name__}")

cart = {"mug": 1}
add_to_cart(cart, "mug", 2)
add_to_cart(cart, "pen", 5)
add_to_cart("not a cart", "pen", 5)
print(cart)
```

Two different failures, two different reactions. The first call works normally and the print line never fires. The second hits `KeyError` and adds the product. The third hits `TypeError` because you can't do `"not a cart"["pen"] += 5`, and the second handler reports it.

<h1 id="order-matters-specific-before-general">
  Order Matters: Specific Before General
</h1>

When you stack multiple `except` blocks, Python checks them in source order and takes the first one that matches. Because catching an exception also catches its subclasses, putting a general handler before a specific one means the specific handler can never fire.

Here's the trap:

```python
prices = {"mug": 12.99}

try:
    prices["notebook"]
except Exception:
    print("General handler")
except KeyError:
    print("Specific handler")
```

`KeyError` is a subclass of `Exception`, so the first `except` matches and Python never even looks at the second. The second handler is dead code. CPython doesn't warn you about this by default, although some linters will.

Swap the order and both handlers become reachable:

```python
prices = {"mug": 12.99}

try:
    prices["notebook"]
except KeyError:
    print("Specific handler")
except Exception:
    print("General handler")
```

Now `KeyError` matches the first clause and runs the specific handler. A different exception type, say a `TypeError`, would skip the first clause and fall through to the second.

The rule is simple: **most specific first, most general last**. If you're catching three or four related exception types, write them in the order from narrowest to widest. A general `except Exception:` at the bottom is occasionally useful as a last-resort net, but most of the time you should list the specific types you actually expect and let anything else crash.

The diagram traces what Python does at runtime. After the `try` block, if no exception was raised, the whole `try/except` is done and control moves on. If something was raised, Python walks the `except` clauses in source order. The first match wins. If nothing matches, the exception propagates upward and either gets caught higher up or eventually crashes the program.

<h1 id="capturing-the-exception-with-as">Capturing the Exception with as</h1>

Catching an exception by type tells you _what_ went wrong, but often you also want to know the details: which key was missing, which value failed to parse, what the original message said. The `as` clause binds the exception object to a name so you can use it inside the handler.

```python
def parse_quantity(raw):
    try:
        return int(raw)
    except ValueError as e:
        print(f"Couldn't parse quantity: {e}")
        return 0

parse_quantity("12")
parse_quantity("abc")
parse_quantity("3.5")
```

Printing the exception object gives you the message Python would have shown in the traceback. The `as e` part isn't required. You can write `except ValueError:` with no name if you don't need the details. But once you do need them, `as` is how you get them.

The exception object carries more than just its message. It has an `args` attribute (the arguments it was constructed with) and a `__traceback__` attribute (the call stack at the time it was raised). For most logging, `str(e)` or just `print(e)` is enough.

```python
cart = {"mug": 12.99}

try:
    price = cart["notebook"]
except KeyError as e:
    print(f"Message: {e}")
    print(f"Args: {e.args}")
    print(f"Missing key: {e.args[0]}")
```

`KeyError` is one of the few exception types where `str(e)` adds quotes around the value, because that's how `KeyError.__str__` is implemented. The raw missing key sits in `e.args[0]`, which is sometimes easier to use programmatically.

One gotcha worth knowing: the name you bind with `as` is only visible inside the `except` block. After the block ends, Python deletes the name. This is intentional, because the exception holds a reference to the traceback, which holds references to every local variable in the frames where it was raised. Letting that linger would keep large amounts of memory alive.

```python
try:
    int("nope")
except ValueError as e:
    captured = e
    print(e)

print(captured)
print(e)
```

`captured` survives because you bound it to a separate name. `e` is gone the moment the `except` block ends.

<h1 id="the-else-clause-code-that-runs-only-on-success">
  The else Clause: Code That Runs Only on Success
</h1>

The `else` clause is the one most newcomers skip. It runs only if the `try` block finished without raising an exception, and it runs after the `try` but before any `finally`. The point is to separate "this can fail" code from "this only makes sense if the above succeeded" code.

Without `else`, you tend to write this:

```python
def show_price(product, catalog):
    try:
        price = catalog[product]
        print(f"{product}: ${price:.2f}")
    except KeyError:
        print(f"{product} not in catalog")

show_price("mug", {"mug": 12.99})
show_price("phone", {"mug": 12.99})
```

That works, but now the `print` line lives inside the `try`. If `print` itself raised an exception for some reason (it can, if the stream is closed), the `except KeyError:` wouldn't catch it, which is fine, but the `print` would still be "guarded" by a clause that wasn't meant to guard it. More importantly, you've blurred the line between "the operation we're guarding" and "what we do with the result."

With `else`, the two paths are cleanly separated:

```python
def show_price(product, catalog):
    try:
        price = catalog[product]
    except KeyError:
        print(f"{product} not in catalog")
    else:
        print(f"{product}: ${price:.2f}")

show_price("mug", {"mug": 12.99})
show_price("phone", {"mug": 12.99})
```

The `try` block contains exactly one risky line. The `except` handles the failure. The `else` runs only when the lookup succeeded, and `price` is guaranteed to be bound when it runs.

The other reason `else` matters: it makes the scope of your `except` honest. If you put everything in the `try`, a bug five lines down might get swallowed by the same `except` that was only supposed to catch the lookup. Keeping the `try` short and pushing the rest into `else` prevents that.

```python
def confirm_order(cart, prices):
    try:
        total = sum(prices[item] for item in cart)
    except KeyError as e:
        print(f"Missing price for {e}, can't confirm order")
        return
    else:
        # If we get here, the sum succeeded and total is valid.
        # A KeyError below would be a different bug, not a price issue.
        save_order_record(cart, total)
        print(f"Order confirmed: ${total:.2f}")

def save_order_record(cart, total):
    print(f"Saved {len(cart)} items, total ${total:.2f}")

confirm_order(["mug", "notebook"], {"mug": 12.99, "notebook": 7.49})
confirm_order(["mug", "phone"], {"mug": 12.99, "notebook": 7.49})
```

If `save_order_record` itself raised a `KeyError` for unrelated reasons, the handler above wouldn't catch it. That's correct behavior. The `try` was about the price lookup, not about saving. `else` made that boundary explicit.

<h1 id="the-finally-clause-always-runs">The finally Clause: Always Runs</h1>

The `finally` clause runs no matter what happened in the `try`. Exception or not, caught or uncaught, return statement or normal flow, the `finally` block fires before control leaves the `try/except/else/finally` structure. That makes it the natural home for cleanup: closing a file, releasing a lock, restoring some setting, logging that an attempt finished.

```python
def load_catalog(filename):
    file = open(filename)
    try:
        contents = file.read()
        print(f"Loaded {len(contents)} chars")
    finally:
        file.close()
        print("File closed")
```

If `file.read()` raises, the `finally` still runs and closes the file, then the exception propagates. If `file.read()` succeeds, the `finally` still runs. Either way, the file isn't left open. In real Python code you'd use a `with` statement here, but `finally` is the lower-level mechanism that `with` is built on.

A practical e-commerce example: imagine a counter that tracks how many lookups your catalog has handled, regardless of whether they succeeded:

```python
lookups_attempted = 0

def get_product(catalog, product):
    global lookups_attempted
    try:
        return catalog[product]
    except KeyError:
        return None
    finally:
        lookups_attempted += 1

catalog = {"mug": 12.99, "pen": 1.99}
get_product(catalog, "mug")
get_product(catalog, "phone")
get_product(catalog, "pen")
print(f"Attempted lookups: {lookups_attempted}")
```

The counter goes up on every call, hit or miss. If the function had ten different return paths and three exception handlers, `finally` would still fire exactly once per call.

`finally` runs even when there's no matching `except`. If a `try` raises a type that no handler catches, Python runs the `finally` block first, then propagates the exception:

```python
def risky():
    try:
        int("nope")
    finally:
        print("cleanup")

risky()
```

`cleanup` prints first, then the exception bubbles up to the top of the program.

> **Cost:** `finally` runs even when you press Ctrl+C, because `KeyboardInterrupt` is an exception too. Keep `finally` blocks short, and don't put anything in them that could itself fail in a hard-to-recover way.

<h1 id="when-finally-eats-your-exception">When finally Eats Your Exception</h1>

`finally` always runs, and that "always" has a sharp edge. If the `finally` block returns a value, or raises its own exception, the original exception or return value from the `try`/`except`/`else` part disappears. This is a real gotcha. Code that should crash quietly succeeds, and you spend an afternoon wondering where your error went.

The classic example, a `return` inside `finally`:

```python
def get_stock(inventory, product):
    try:
        return inventory[product]
    except KeyError:
        raise
    finally:
        return -1

stock = {"mug": 5}
print(get_stock(stock, "mug"))
print(get_stock(stock, "phone"))
```

The first call should return `5`. The second should propagate the `KeyError` from the explicit `raise`. Neither happens. The `return -1` in `finally` wins over both. Python evaluates the `try`/`except` to figure out the answer, then `finally` runs and replaces that answer with its own `return`.

The fix is to not return from `finally`. Use it for cleanup, not for results.

The same effect happens if `finally` raises:

```python
def get_stock(inventory, product):
    try:
        return inventory[product]
    finally:
        raise RuntimeError("cleanup failed")

stock = {"mug": 5}
get_stock(stock, "mug")
```

The lookup succeeded, but the new exception from `finally` replaces the return value. If the `try` had raised its own exception, that one would be lost too, although Python at least chains them so the original shows in the traceback as the context.

Two rules to live by:

- Never `return` from a `finally` block. If you need to change the return value based on whether the `try` succeeded, do it in `else` or after the whole block.
- Don't raise new exceptions from `finally` unless you really mean to. Treat `finally` as a place where things should not fail.

<h1 id="bare-except-except-exception-and-except-baseexception">
  Bare except, except Exception, and except BaseException
</h1>

You can write `except` with no exception type at all. This is called a **bare except** and it catches literally everything that can be raised in Python.

```python
def fragile():
    try:
        risky_operation()
    except:
        print("something went wrong")

def risky_operation():
    raise KeyboardInterrupt
```

A bare `except` catches `KeyboardInterrupt` (Ctrl+C), `SystemExit` (calls to `sys.exit()`), and `MemoryError`. None of these are usually things you want to swallow. If a user presses Ctrl+C to kill your program, they expect it to actually stop. A bare `except` can quietly turn that into "something went wrong" and keep running.

The standard recommendation is to write `except Exception` instead. `Exception` is the base class for almost every exception you actually want to catch (`ValueError`, `KeyError`, `TypeError`, custom application errors, and so on), but it does _not_ include `KeyboardInterrupt`, `SystemExit`, or `GeneratorExit`.

```python
def safer():
    try:
        risky_operation()
    except Exception as e:
        print(f"something went wrong: {e}")
```

Now Ctrl+C still stops the program, but every "ordinary" exception is caught.

| Pattern                 | Catches                                         | When to use                                      |
| ----------------------- | ----------------------------------------------- | ------------------------------------------------ |
| `except SomeType:`      | `SomeType` and its subclasses                   | The default. Catch what you can actually handle. |
| `except Exception:`     | Most exceptions, but not Ctrl+C or `SystemExit` | A last-resort catch-all at a top-level boundary. |
| `except BaseException:` | Everything, including Ctrl+C and `SystemExit`   | Almost never. Usually a mistake.                 |
| `except:` (bare)        | Same as `except BaseException:`                 | Almost never. Usually a mistake.                 |

Even `except Exception` should be rare. Use it at the outer edge of a program, where you want to log unexpected failures and keep a long-running service alive, not in the middle of business logic where it would mask bugs.

```python
def main():
    try:
        run_checkout()
    except Exception as e:
        log(f"unhandled error: {e}")
        notify_ops(e)

def run_checkout():
    pass

def log(msg):
    print(msg)

def notify_ops(e):
    print(f"alerted on-call about {type(e).__name__}")

main()
```

That's a reasonable outer boundary. Inside `run_checkout`, you should catch specific exceptions, not all of them.

<h1 id="how-python-evaluates-the-whole-block">
  How Python Evaluates the Whole Block
</h1>

When you stack all four clauses, the order Python uses is fixed. It's worth seeing it laid out once so the rest of the lesson clicks together.

Reading this top to bottom: the `try` runs first. If nothing is raised, `else` runs, then `finally`, then we move on. If something is raised, Python checks the `except` clauses. A match runs the handler, then `finally`, then we move on. No match runs `finally` and then propagates the exception up the call stack. `finally` is always on the path; `else` is only on the no-exception path; the handler is only on the matched-exception path.

Here's a script that demonstrates each branch by printing what runs:

```python
def trace(scenario):
    print(f"\n--- {scenario} ---")
    try:
        print("try start")
        if scenario == "raise-caught":
            raise ValueError("bad price")
        if scenario == "raise-uncaught":
            raise RuntimeError("system down")
        print("try end")
    except ValueError as e:
        print(f"except: {e}")
    else:
        print("else")
    finally:
        print("finally")

trace("clean")
trace("raise-caught")
try:
    trace("raise-uncaught")
except RuntimeError:
    print("outer caught RuntimeError")
```

Three scenarios, three paths. Clean run hits try, else, finally. Caught exception hits try, except, finally (no else, because an exception fired). Uncaught exception hits try, finally, and then propagates to the outer handler. The `else` branch never runs on a path where the `try` raised. That's the single rule that ties all this together.

<h1 id="exception-groups-except-python-311">
  Exception Groups: except* (Python 3.11+)
</h1>

Python 3.11 added a new flavor of exception called an **exception group**, plus a new `except*` syntax for handling them. The motivating use case is concurrent code: when you run several tasks in parallel and more than one of them fails, you want to receive all the failures together rather than just the first one. PEP 654 has the full design rationale.

A regular `except` clause can't unpack a group. It either catches the whole group or none of it. `except*` is the version that knows how to split a group, handle the parts that match a given type, and let the rest re-raise.

```python
def validate_cart(cart):
    errors = []
    for product, qty in cart.items():
        if not isinstance(product, str):
            errors.append(TypeError(f"product key not a string: {product}"))
        if qty <= 0:
            errors.append(ValueError(f"non-positive quantity for {product}: {qty}"))
    if errors:
        raise ExceptionGroup("cart validation failed", errors)

cart = {"mug": 2, "pen": -1, 42: 3}

try:
    validate_cart(cart)
except* ValueError as group:
    print(f"value errors: {[str(e) for e in group.exceptions]}")
except* TypeError as group:
    print(f"type errors: {[str(e) for e in group.exceptions]}")
```

`ExceptionGroup` collects related exceptions into one object. `except* ValueError` catches every `ValueError` inside the group (no matter how deeply nested), bundles them into a sub-group, and runs the handler. The `TypeError` in the same group falls through to the second `except*` clause. If neither clause caught everything, the remaining exceptions would propagate as a smaller group.

This syntax is most useful inside `asyncio.TaskGroup` and similar APIs, where many tasks run together and any subset of them can fail. For straight-line code, plain `try/except` is still the right tool. The full rules are in PEP 654.

<h1 id="putting-it-all-together">Putting It All Together</h1>

A realistic e-commerce example: a function that loads a single product from a price file, parses a quantity, and reports the line total. It uses every clause and shows them working in concert.

```python
def load_prices(filename):
    try:
        file = open(filename)
    except FileNotFoundError:
        print(f"price file '{filename}' is missing, using empty catalog")
        return {}
    try:
        prices = {}
        for line in file:
            name, raw_price = line.strip().split(",")
            prices[name] = float(raw_price)
    except ValueError as e:
        print(f"price file is malformed: {e}")
        return {}
    else:
        print(f"loaded {len(prices)} prices")
        return prices
    finally:
        file.close()
        print(f"closed '{filename}'")

prices = load_prices("does-not-exist.csv")
print(prices)
```

If the file is missing, the first `try/except` catches the `FileNotFoundError` and returns early. The second block never runs. If the file opens but a line is malformed, the second `try` raises `ValueError` from the `split` or the `float` call, the `except` handles it, and the `finally` still closes the file. On a clean run, `else` prints the count and returns the dict, and again `finally` closes the file. Three different paths, one set of clauses, and the file is closed every time.

This is the shape exception handling takes once you're comfortable with the four clauses: small, focused `try` blocks; specific `except` types; an `else` for the "everything worked" path; and a `finally` that handles cleanup without caring about which path you took.
