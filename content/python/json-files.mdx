<h1 id="why-json-shows-up-everywhere">Why JSON Shows Up Everywhere</h1>

When an online store fetches a product catalog from a backend, the response is almost always JSON. When a mobile app posts a new order, the body is JSON. When a config file ships with a service, it's probably JSON. The format is human-readable, language-neutral, and maps cleanly onto the data structures every language already has: lists, dicts/maps, strings, numbers, booleans, and null. Python's `json` module is the official translator between JSON text and Python objects.

```python
import json

product_json = '{"id": 101, "name": "wireless mouse", "price": 29.99, "in_stock": true}'
product = json.loads(product_json)

print(product["name"])
print(product["price"] * 2)
```

The JSON `true` became Python `True`, the JSON object became a dict, and the price is a real float you can do arithmetic on. That's the whole appeal: parse once, work in Python.

<h1 id="json-types-vs-python-types">JSON Types vs Python Types</h1>

JSON has six value types. Python has more, but the `json` module only knows how to translate between this fixed set. Anything outside the table needs custom handling, which we'll get to later.

| JSON             | Python           | Notes                                               |
| ---------------- | ---------------- | --------------------------------------------------- |
| `object`         | `dict`           | Keys are always strings in JSON.                    |
| `array`          | `list`           | Always a list, never a tuple, on decode.            |
| `string`         | `str`            | Unicode by default.                                 |
| `number` (int)   | `int`            | No size limit on the Python side.                   |
| `number` (float) | `float`          | IEEE 754 double precision.                          |
| `true` / `false` | `True` / `False` | Lowercase in JSON, capitalized in Python.           |
| `null`           | `None`           | One direction is obvious, the other catches people. |

Going the other way, Python `tuple` becomes a JSON array, so a round trip turns tuples into lists. Sets, `datetime` objects, `Decimal`, and your own classes are not in the table at all and will raise `TypeError` unless you teach the encoder how to handle them.

```python
import json

>>> json.dumps([1, 2, 3])
'[1, 2, 3]'
>>> json.dumps((1, 2, 3))
'[1, 2, 3]'
>>> json.loads('[1, 2, 3]')
[1, 2, 3]
>>> type(json.loads('[1, 2, 3]'))
<class 'list'>
```

Notice the asymmetry: tuples encode as arrays, but arrays always decode as lists. If you need a tuple back, convert after decoding.

<h1 id="parsing-json-loads-and-load">Parsing JSON: loads and load</h1>

There are two parsing functions, and the only difference is where the JSON comes from. Use `loads` (load string) when you already have the JSON as a `str`. Use `load` (load file) when you have a file object opened in text mode.

```python
import json

# from a string
order_json = '{"order_id": 5001, "customer": "ria", "total": 89.97, "status": "placed"}'
order = json.loads(order_json)
print(order["status"])
```

For files, open the file and pass the file object directly. The function reads and parses in one step.

```python
import json

# orders.json on disk contains:
# {"order_id": 5001, "customer": "ria", "total": 89.97, "status": "placed"}

with open("orders.json", "r", encoding="utf-8") as f:
    order = json.load(f)

print(order["customer"])
```

The `encoding="utf-8"` matters. JSON is officially UTF-8 by default, and product names, customer names, or address fields may contain characters outside ASCII. Opening without an explicit encoding falls back to the platform default, which on Windows can be `cp1252` and silently mangle non-Latin text.

A file containing a JSON array of records (a catalog of products, a list of orders) reads exactly the same way; the whole file is still one JSON value. `json.load` returns the list and you iterate over it normally.

> **Cost:** `json.load` reads the entire file into memory and parses it as one value. A 1 GB catalog file will need at least 1 GB of memory for the raw bytes, plus more for the parsed Python objects. For huge files, look at JSON Lines (one record per line) or the `ijson` third-party package for streaming parsing.

You can read with `pathlib` too, which lets you skip the `open` boilerplate when you just need the text:

```python
import json
from pathlib import Path

text = Path("catalog.json").read_text(encoding="utf-8")
catalog = json.loads(text)
```

We'll stick with `open` for the rest of the examples.

<h1 id="writing-json-dumps-and-dump">Writing JSON: dumps and dump</h1>

The output side mirrors the input side. `dumps` returns a JSON string. `dump` writes JSON directly to an open file.

```python
import json

wishlist = {
    "customer_id": 42,
    "items": [
        {"id": 201, "name": "ergonomic chair", "price": 249.0},
        {"id": 202, "name": "monitor stand", "price": 39.99},
    ],
    "shared": False,
}

text = json.dumps(wishlist)
print(text)
```

Two things to notice. First, JSON booleans are lowercase (`false`, not `False`). Second, the output is one long line with no whitespace beyond the separators. That's the most compact form, which is what you want when shipping data over a network. It's also unreadable for humans.

To write to a file:

```python
import json

wishlist = {
    "customer_id": 42,
    "items": [
        {"id": 201, "name": "ergonomic chair", "price": 249.0},
        {"id": 202, "name": "monitor stand", "price": 39.99},
    ],
    "shared": False,
}

with open("wishlist.json", "w", encoding="utf-8") as f:
    json.dump(wishlist, f)
```

The file ends up with the same single-line output you saw from `dumps`. The choice between `dump` and `dumps` is just "do I have a file or a string?". `dump` is slightly more efficient because it doesn't build the full string in memory before writing, though for normal payload sizes you won't notice.

<h1 id="pretty-printing-indent-sort_keys-separators">
  Pretty Printing: indent, sort_keys, separators
</h1>

The default output is compact. For anything a human will read, like a config file, a sample fixture, or a snapshot in a test, pass `indent` to get a readable layout.

```python
import json

order = {
    "order_id": 5001,
    "customer": "ria",
    "items": [
        {"id": 101, "name": "wireless mouse", "qty": 1, "price": 29.99},
        {"id": 103, "name": "hdmi cable", "qty": 2, "price": 9.99},
    ],
    "total": 49.97,
    "status": "placed",
}

print(json.dumps(order, indent=2))
```

`indent=2` means two spaces per level. `indent=4` is also common. You can pass any non-negative integer, or even a string (`indent="\t"` for tabs).

By default, the output preserves dict insertion order. That's fine until you want a stable diff between two versions of the same file. `sort_keys=True` orders keys alphabetically at every level, which makes JSON output deterministic regardless of how the dict was built.

```python
import json

order = {"status": "placed", "order_id": 5001, "customer": "ria"}
print(json.dumps(order, indent=2, sort_keys=True))
```

The third formatting knob is `separators`. By default, it's `(", ", ": ")`: comma-space between items, colon-space between key and value. For the most compact output (no spaces at all), pass `(",", ":")`.

```python
import json

product = {"id": 101, "name": "wireless mouse", "price": 29.99}
print(json.dumps(product, separators=(",", ":")))
```

That extra trimming matters when you're sending millions of small records over a network or storing them in a column that has a size limit. It also produces canonical output that's stable byte-for-byte across writes.

> **Cost:** `indent` and the default `separators` add roughly 20-30% to output size on typical payloads. For data you write to disk and read back programmatically, leave them off. For data a human will read or diff, turn `indent` on. Don't optimize this by hand; just pick the form that fits the use.

A practical pattern: wrap the two modes in helpers and call the one that fits the job.

```python
import json

def to_compact_json(data):
    return json.dumps(data, separators=(",", ":"), sort_keys=True)

def to_pretty_json(data):
    return json.dumps(data, indent=2, sort_keys=True)
```

<h1 id="ensure_ascii-and-non-ascii-text">ensure_ascii and Non-ASCII Text</h1>

By default, `json.dumps` escapes any non-ASCII character as a Unicode escape sequence. That keeps the output strictly 7-bit ASCII, which used to matter for systems that couldn't handle UTF-8 cleanly.

```python
import json

product = {"name": "cafÃ© latte mug", "country": "EspaÃ±a"}

print(json.dumps(product))
print(json.dumps(product, ensure_ascii=False))
```

The `Ã©` becomes `Ã©` by default. Technically correct (the JSON parser will decode it back to `Ã©`), but ugly, larger, and unhelpful when you're reading the file. Almost every modern system handles UTF-8, so `ensure_ascii=False` is usually what you want.

When writing to a file, pair this with `encoding="utf-8"` on the `open` call:

```python
import json

products = [
    {"id": 301, "name": "cafÃ© latte mug", "price": 14.99},
    {"id": 302, "name": "naÃ¯ve gift box", "price": 24.99},
    {"id": 303, "name": "äº¬é½ tea set", "price": 39.99},
]

with open("products.json", "w", encoding="utf-8") as f:
    json.dump(products, f, indent=2, ensure_ascii=False)
```

The file ends up containing the actual characters, encoded as UTF-8 bytes. Readers using the same encoding (which is the default for most tools today) see the original text.

<h1 id="handling-errors-jsondecodeerror">Handling Errors: JSONDecodeError</h1>

Parsing user-supplied or network-fetched JSON fails sometimes. The data might be truncated, malformed, or just not JSON. The `json` module raises `json.JSONDecodeError`, a subclass of `ValueError`, with helpful attributes for diagnostics.

```python
import json

bad_json = '{"id": 101, "name": "wireless mouse", "price": 29.99'  # missing closing brace

try:
    json.loads(bad_json)
except json.JSONDecodeError as e:
    print(f"parse failed: {e.msg}")
    print(f"at line {e.lineno}, column {e.colno} (char {e.pos})")
```

`JSONDecodeError` carries the message, the line and column where parsing failed, and the absolute character position. That's enough to point a user at the broken spot in their file. The error message itself (`Expecting ',' delimiter`) is the parser's best guess at what it wanted to see next.

A typical catch in production code distinguishes between "the file isn't there" (`FileNotFoundError`), "the file has bad JSON" (`json.JSONDecodeError`), and "the JSON is valid but missing fields you need" (`KeyError`). Each one deserves a different response.

```python
import json

def load_catalog(path):
    try:
        with open(path, "r", encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        print(f"catalog file {path!r} not found, using empty catalog")
        return []
    except json.JSONDecodeError as e:
        print(f"catalog file {path!r} is malformed: line {e.lineno}, col {e.colno}")
        return []

catalog = load_catalog("catalog.json")
print(f"loaded {len(catalog)} products")
```

A subtler failure: the JSON parses fine, but the structure isn't what you expected. The parser doesn't know your data shape; it just turns text into Python objects. Validating that the result has the keys you need is your code's job. Libraries like `pydantic` and `jsonschema` exist for this; we'll skip them and stick to plain checks.

```python
import json

raw = '{"order_id": 5001, "customer": "ria"}'  # missing "total"
order = json.loads(raw)

if "total" not in order:
    raise KeyError("order is missing required field 'total'")
```

<h1 id="types-json-cant-handle-by-default">
  Types JSON Can't Handle by Default
</h1>

JSON only knows about the seven types in the mapping table. If you try to encode anything else, the encoder raises `TypeError`.

**What's wrong with this code?**

```python
import json

product = {
    "id": 101,
    "name": "wireless mouse",
    "tags": {"wireless", "ergonomic", "rgb"},
}

print(json.dumps(product))
```

A `set` has no native JSON form. JSON arrays are ordered; sets are not. The encoder doesn't guess, it errors.

**Fix:** convert the set to a list before encoding. Sorting gives stable output too.

```python
product = {
    "id": 101,
    "name": "wireless mouse",
    "tags": sorted({"wireless", "ergonomic", "rgb"}),
}
print(json.dumps(product))
```

The same problem applies to `datetime`, `Decimal` (which is common in money calculations because `float` can't represent `0.1` exactly), and any custom class.

```python
import json
from datetime import datetime
from decimal import Decimal

class Product:
    def __init__(self, product_id, name):
        self.product_id = product_id
        self.name = name

json.dumps(datetime(2024, 11, 12))          # TypeError: Object of type datetime is not JSON serializable
json.dumps(Decimal("29.99"))                # TypeError: Object of type Decimal is not JSON serializable
json.dumps(Product(101, "wireless mouse"))  # TypeError: Object of type Product is not JSON serializable
```

The `json` module isn't being lazy. JSON is a strict format with a closed set of types, and the standard library refuses to invent a convention for everything else. That's where custom encoders come in.

<h1 id="custom-encoders-the-default-function">
  Custom Encoders: The default Function
</h1>

The simplest extension point is the `default` argument to `json.dumps` and `json.dump`. When the encoder hits an object it doesn't know how to serialize, it calls `default(obj)` and uses whatever JSON-serializable value you return.

```python
import json
from datetime import datetime
from decimal import Decimal

def serialize_unknown(obj):
    if isinstance(obj, datetime):
        return obj.isoformat()
    if isinstance(obj, Decimal):
        return str(obj)
    if isinstance(obj, set):
        return sorted(obj)
    raise TypeError(f"Object of type {type(obj).__name__} is not JSON serializable")

order = {
    "order_id": 5001,
    "placed_at": datetime(2024, 11, 12, 14, 30, 0),
    "total": Decimal("89.97"),
    "tags": {"priority", "gift"},
}

print(json.dumps(order, default=serialize_unknown, indent=2))
```

`default` is called once per unknown object. It must either return a JSON-serializable value or raise `TypeError`. Re-raising is important: if you silently return `None`, you'll produce JSON that looks fine but has missing data, which is harder to debug than a clean failure.

`Decimal` becomes a string here, not a float. That preserves precision: `Decimal("29.99")` is an exact value, but `float(Decimal("29.99"))` would round it to the nearest IEEE 754 double. For money fields, strings are the safe choice. The downside is that the receiving end has to know to parse those strings back as `Decimal`.

<h1 id="custom-encoders-subclassing-jsonencoder">
  Custom Encoders: Subclassing JSONEncoder
</h1>

For more structured handling, subclass `json.JSONEncoder` and override `default`. The behavior is the same, but the encoder is reusable, configurable, and easy to plug into multiple call sites.

```python
import json
from datetime import datetime
from decimal import Decimal

class ShopEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, datetime):
            return obj.isoformat()
        if isinstance(obj, Decimal):
            return str(obj)
        if isinstance(obj, set):
            return sorted(obj)
        return super().default(obj)  # raises TypeError with the standard message

order = {
    "order_id": 5001,
    "placed_at": datetime(2024, 11, 12, 14, 30, 0),
    "total": Decimal("89.97"),
    "tags": {"priority", "gift"},
}

print(json.dumps(order, cls=ShopEncoder, indent=2))
```

The `cls=` argument tells `json.dumps` to use your subclass. Calling `super().default(obj)` for anything you don't recognize delegates back to the parent, which raises the standard `TypeError`. That's better than raising your own, because users can catch `TypeError` and get the same message they'd see from plain `json.dumps`.

For application-defined classes, the convention is to define a `to_dict` method on the class and have the encoder call it. That keeps each class responsible for its own JSON shape, and the encoder stays a thin dispatcher that says "if you can describe yourself, do so". `dataclasses.asdict` offers a terser way to do this for data classes. For now, the explicit `to_dict` pattern is fine and works on any class.

<h1 id="custom-decoders-object_hook">Custom Decoders: object_hook</h1>

Parsing has its own extension point. The `object_hook` parameter is a function that gets called for every JSON object (Python dict) the parser produces. Whatever it returns replaces the dict in the result.

```python
import json
from datetime import datetime

def parse_dates(obj):
    if "placed_at" in obj and isinstance(obj["placed_at"], str):
        obj["placed_at"] = datetime.fromisoformat(obj["placed_at"])
    return obj

raw = '{"order_id": 5001, "customer": "ria", "placed_at": "2024-11-12T14:30:00"}'
order = json.loads(raw, object_hook=parse_dates)

print(type(order["placed_at"]).__name__)
print(order["placed_at"])
```

The hook runs bottom-up: inner objects are passed before outer ones. That means by the time `object_hook` sees the outer order, the inner items (if any) have already been transformed. Useful for nested structures.

A common application is turning a JSON object back into a domain class. If the JSON has a "type tag" field that says which class it is, the hook can look at it and dispatch:

```python
import json

class Product:
    def __init__(self, product_id, name, price):
        self.product_id = product_id
        self.name = name
        self.price = price

    def __repr__(self):
        return f"Product(id={self.product_id}, name={self.name!r}, price={self.price})"

def from_json(obj):
    if obj.get("_type") == "product":
        return Product(obj["id"], obj["name"], obj["price"])
    return obj

raw = '{"_type": "product", "id": 101, "name": "wireless mouse", "price": 29.99}'
product = json.loads(raw, object_hook=from_json)
print(product)
print(type(product).__name__)
```

The `_type` field is a convention you choose, not a JSON feature. The encoder side has to include it when writing, and the decoder side knows to look for it. If you don't control both sides, the type tag won't be there and you'll fall back to plain dicts.

For projects that need decimal precision back on the way in, there's `parse_float`:

```python
import json
from decimal import Decimal

raw = '{"id": 101, "name": "wireless mouse", "price": 29.99}'
product = json.loads(raw, parse_float=Decimal)
print(type(product["price"]).__name__, product["price"])
```

`parse_float` is called for every JSON number that has a decimal point or exponent. There's also `parse_int` for integers and `parse_constant` for `Infinity`, `-Infinity`, and `NaN`.

<h1 id="json-lines-one-record-per-line">JSON Lines: One Record Per Line</h1>

Standard JSON forces you to load the whole file before you can use any of it. For logs, exports, or streaming data, that's wasteful. The JSON Lines format (sometimes called NDJSON, for newline-delimited) puts one JSON value on each line, with no enclosing array. Each line is independently parseable.

A `orders.jsonl` file might look like:

```text
{"order_id": 5001, "customer": "ria", "total": 89.97}
{"order_id": 5002, "customer": "alex", "total": 14.99}
{"order_id": 5003, "customer": "mei", "total": 249.0}
```

You read it line by line and parse each line on its own:

```python
import json

orders = []
with open("orders.jsonl", "r", encoding="utf-8") as f:
    for line in f:
        line = line.strip()
        if not line:
            continue
        orders.append(json.loads(line))

print(f"loaded {len(orders)} orders")
print(orders[0])
```

Writing follows the same pattern: open a file, loop through your records, and write each one as `json.dumps(record) + "\n"`.

> **Cost:** JSON Lines lets you process a 100 GB file in constant memory because you only ever hold one record at a time. A regular JSON file holding the same data would need 100 GB of RAM just to load. The format is also resilient: one corrupted line doesn't break the whole file.

When to use JSON Lines: log records, append-only data, exports from databases, anything where records arrive over time. When to stick with regular JSON: small configuration files, structured objects that need to be one whole tree, anything a human will hand-edit.

<h1 id="putting-it-together-round-tripping-a-wishlist">
  Putting It Together: Round-Tripping a Wishlist
</h1>

Here's a compact example that ties the pieces together: a `Product` class with a `to_dict` method, a custom encoder, and a decoder hook that rebuilds the class from the JSON.

```python
import json
from datetime import datetime
from decimal import Decimal

class Product:
    def __init__(self, product_id, name, price):
        self.product_id = product_id
        self.name = name
        self.price = price

    def to_dict(self):
        return {
            "_type": "product",
            "id": self.product_id,
            "name": self.name,
            "price": str(self.price),
        }

    def __repr__(self):
        return f"Product({self.product_id}, {self.name!r}, {self.price})"

class ShopEncoder(json.JSONEncoder):
    def default(self, obj):
        if hasattr(obj, "to_dict"):
            return obj.to_dict()
        if isinstance(obj, datetime):
            return obj.isoformat()
        return super().default(obj)

def shop_decoder(obj):
    if obj.get("_type") == "product":
        return Product(obj["id"], obj["name"], Decimal(obj["price"]))
    return obj

wishlist = {
    "customer_id": 42,
    "created_at": datetime(2024, 11, 12, 14, 30, 0),
    "items": [
        Product(201, "cafÃ© espresso machine", Decimal("349.00")),
        Product(202, "ergonomic chair", Decimal("249.00")),
    ],
}

text = json.dumps(wishlist, cls=ShopEncoder, indent=2, ensure_ascii=False)
restored = json.loads(text, object_hook=shop_decoder)

print(restored["customer_id"])
for item in restored["items"]:
    print(" ", item, type(item.price).__name__)
```

The `_type` tag is the bridge between JSON shape and Python class. The encoder stamps it on the way out; the decoder reads it on the way in. `Decimal` stays exact because we encode it as a string. The diagram below traces a single record through the full pipeline.

The encoder flattens Python-only types into JSON-friendly ones, and the decoder rebuilds them on the way back. The JSON text in the middle is the source of truth that any other tool, in any language, can read.
