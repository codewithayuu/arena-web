<h1 id="why-call-c-from-python">Why Call C from Python</h1>

Most of the time you don't need to. NumPy, Pandas, `re`, `json`, `hashlib`, and `sqlite3` are already C under the hood, and a well-written Python loop using them is fast enough for almost any e-commerce workload. There are three situations where dropping to C is the right call:

1. **A hot loop in pure Python is the bottleneck.** A function that totals a million cart line items in pure Python may run 50x slower than the same loop in C.
2. **You need to wrap an existing C library.** A vendor ships `libpricing.so` for inventory pricing or fraud scoring, and there's no Python wrapper.
3. **You need OS-level features the stdlib doesn't expose.** Low-level file system calls, hardware interfaces, or a kernel feature too new for Python.

For everything else, profile first. The slowest function in your checkout pipeline is almost never the place you think.

> **Cost:** Crossing the Python-C boundary isn't free. Each call has fixed overhead (argument marshalling, type checks, the GIL dance). Calling C a million times in a tight loop can be slower than one Python loop. Push the loop into C, don't call C inside a Python loop.

<h1 id="the-four-common-options">The Four Common Options</h1>

Python has a family of tools for calling C, each with different trade-offs. The chapter focuses on `ctypes` and `cffi` because they need no compilation on the Python side, but it helps to know the full landscape first.

| Tool        | Compile Step Needed                      | Type Safety                    | Performance   | Best For                                                        |
| ----------- | ---------------------------------------- | ------------------------------ | ------------- | --------------------------------------------------------------- |
| `ctypes`    | None (stdlib)                            | Manual (you declare types)     | Good          | Quick wrapping of an existing `.so`/`.dll`/`.dylib`             |
| `cffi`      | Optional (ABI mode = no, API mode = yes) | Better (parses real C headers) | Good to great | Robust bindings, especially when C headers are available        |
| Cython      | Yes (compiles `.pyx` to C)               | Strong (typed)                 | Excellent     | Speeding up pure-Python hot loops, mixed Python/C code          |
| PyO3 (Rust) | Yes (cargo build)                        | Strong (Rust types)            | Excellent     | New native extensions written in Rust, memory safety guarantees |

`ctypes` ships with Python, so there's nothing to install. `cffi` is `pip install cffi` away and is what cryptography, psycopg, and many other libraries use under the hood. Cython is a separate language that looks like Python with type hints and compiles to C. PyO3 is the modern Rust ecosystem's answer to the C API.

The boundary diagram below shows where Python and C meet for the two tools this lesson focuses on.

The binding layer in the middle is the only thing you write on the Python side. It tells Python what's in the shared library, what each function expects, and what each function returns. The shared library itself is already compiled, sitting on disk as `.so` (Linux), `.dylib` (macOS), or `.dll` (Windows).

<h1 id="ctypes-calling-a-c-function-in-30-seconds">
  ctypes: Calling a C Function in 30 Seconds
</h1>

`ctypes` loads a shared library at runtime and lets you call functions inside it. The library is found by name, the function is looked up by name, and you call it like any Python function.

Every Unix system has `libm`, the C math library. It contains `sqrt`, `pow`, `sin`, `cos`, and friends. A first call looks like this:

```python
import ctypes

# Load libm. On Linux it's libm.so.6, on macOS libSystem.dylib has it.
# CDLL searches the standard library path.
import sys
libm_name = "libm.so.6" if sys.platform.startswith("linux") else "libSystem.dylib"
libm = ctypes.CDLL(libm_name)

# Tell ctypes the types of the arguments and return value.
libm.sqrt.argtypes = [ctypes.c_double]
libm.sqrt.restype = ctypes.c_double

# Now call it like any Python function.
result = libm.sqrt(2.0)
print(f"sqrt(2) = {result}")
```

Four things happened. `CDLL(...)` opened the shared library. `libm.sqrt` looked up the symbol `sqrt` inside it. Setting `argtypes` and `restype` told `ctypes` how to marshal a Python `float` into a C `double` and how to interpret the return value. Then the call itself works like any function call.

The `argtypes`/`restype` declaration looks optional, but it isn't. Skip it and `ctypes` defaults to `int` for both argument and return type, which silently corrupts a `double` result.

**What's wrong with this code?**

```python
import ctypes, sys
libm_name = "libm.so.6" if sys.platform.startswith("linux") else "libSystem.dylib"
libm = ctypes.CDLL(libm_name)

# argtypes and restype not declared
print(libm.sqrt(2.0))
```

The C function `sqrt` takes a `double` and returns a `double`. Without `argtypes`, `ctypes` tries to pass `2.0` as an `int`, which gets converted to `2`. Without `restype`, the 8-byte return value is interpreted as a 4-byte `int`. The "result" is garbage. Always declare types before the first call.

**Fix:**

```python
libm.sqrt.argtypes = [ctypes.c_double]
libm.sqrt.restype = ctypes.c_double
```

<h1 id="c-type-mappings">C Type Mappings</h1>

`ctypes` exposes a Python type for every C primitive. The names follow the obvious pattern: `c_int`, `c_double`, `c_char`, `c_void_p`, and so on.

| C type            | ctypes type  | Python type for input        |
| ----------------- | ------------ | ---------------------------- |
| `int`             | `c_int`      | `int`                        |
| `unsigned int`    | `c_uint`     | `int`                        |
| `long`            | `c_long`     | `int`                        |
| `float`           | `c_float`    | `float`                      |
| `double`          | `c_double`   | `float`                      |
| `char *` (string) | `c_char_p`   | `bytes`                      |
| `wchar_t *`       | `c_wchar_p`  | `str`                        |
| `void *`          | `c_void_p`   | `int` (address) or `None`    |
| `T *` (pointer)   | `POINTER(T)` | array or `ctypes.byref(obj)` |

Strings are the easy place to trip up. C strings are bytes, not Unicode text. To pass a Python `str` you encode it first; to read a returned `char *` you decode it.

```python
import ctypes

libc = ctypes.CDLL("libc.so.6" if __import__("sys").platform.startswith("linux") else "libSystem.dylib")

# size_t strlen(const char *s)
libc.strlen.argtypes = [ctypes.c_char_p]
libc.strlen.restype = ctypes.c_size_t

product_name = "wireless headphones"
length = libc.strlen(product_name.encode("utf-8"))
print(f"'{product_name}' has {length} bytes")
```

Encoding to bytes is mandatory. Passing a Python `str` to a `c_char_p` argument without `.encode(...)` raises `TypeError: bytes or integer address expected`.

<h1 id="ctypes-with-structs">ctypes With Structs</h1>

C programs pass complex data as structs. To talk to them, you mirror the struct on the Python side by subclassing `ctypes.Structure` and declaring `_fields_` in the same order and types as the C definition.

Suppose the inventory system ships a C function that computes the discounted price of a product:

```text
// pricing.h
typedef struct {
    int id;
    double price;
    int stock;
} Product;

double discounted_price(Product *p, double percent_off);
```

The implementation is one line in C:

```text
// pricing.c
#include "pricing.h"

double discounted_price(Product *p, double percent_off) {
    return p->price * (1.0 - percent_off / 100.0);
}
```

You'd compile it once with `gcc -shared -fPIC -o libpricing.so pricing.c` (or the macOS/Windows equivalent) to produce a shared library. From Python, the binding looks like this:

```python
import ctypes

class Product(ctypes.Structure):
    _fields_ = [
        ("id", ctypes.c_int),
        ("price", ctypes.c_double),
        ("stock", ctypes.c_int),
    ]

libpricing = ctypes.CDLL("./libpricing.so")
libpricing.discounted_price.argtypes = [ctypes.POINTER(Product), ctypes.c_double]
libpricing.discounted_price.restype = ctypes.c_double

headphones = Product(id=101, price=59.99, stock=12)
final = libpricing.discounted_price(ctypes.byref(headphones), 20.0)
print(f"Discounted price: ${final:.2f}")
```

A few things to call out. `_fields_` must match the C struct's field order and types exactly. Mismatched offsets cause silent corruption (the function reads a different field than you think it's reading). `ctypes.POINTER(Product)` is the type for a pointer to a `Product`, used in `argtypes`. `ctypes.byref(headphones)` passes the address of `headphones` without making a copy.

You can also read and write fields back from C-modified structs. If `discounted_price` wrote to `p->price` (it doesn't here, but it could), the change would be visible in Python through `headphones.price` after the call.

<h1 id="ctypes-pitfalls">ctypes Pitfalls</h1>

A short list of things that cause real bugs:

- **Forgetting `argtypes` and `restype`.** As shown earlier, the defaults (`int` for both) are wrong for most functions. Always declare them before the first call.
- **Wrong field order or types in `Structure`.** No compile-time check exists. Mismatches produce silent corruption.
- **Ownership of returned pointers.** If a C function returns `char *` and Python wraps it with `c_char_p`, who frees the memory? `ctypes` doesn't know. If the library `malloc`'d it and expects you to `free` it, you have to call `free` explicitly. If the library returned a pointer to a static buffer, calling `free` is a crash.
- **The GIL is held by default.** Calling a long-running C function (say, a 5-second crypto computation) blocks every other Python thread. To release the GIL during the call, use `ctypes.CDLL(libname, use_errno=True)` and the function attribute `_flags_ |= ctypes._FUNCFLAG_USE_ERRNO` patterns, or wrap the function with `ctypes.PYFUNCTYPE` configured to release. The common shortcut is to load via `cdll` for "hold the GIL" semantics and `WinDLL`/manual settings for the alternative on Windows. For long calls, consider running the C work in a separate thread.
- $La5

> **Cost:** Releasing the GIL has overhead per call. For functions that take microseconds, holding the GIL is fine. Release it for calls that take milliseconds or more, where blocking other threads becomes a real problem.

<h1 id="cffi-the-friendlier-option">cffi: The Friendlier Option</h1>

`cffi` is a third-party library (`pip install cffi`) that solves several `ctypes` pain points. The biggest difference is that you declare types using actual C syntax, not Python objects. You paste the relevant header into a string, and `cffi` parses it.

`cffi` has two modes: **ABI mode** (no compiler needed, like `ctypes`) and **API mode** (a small C compiler step at install time, faster and safer). The chapter sticks to ABI mode for examples since it works without any build infrastructure.

The same `libm.sqrt` example using `cffi` in ABI mode:

```python
from cffi import FFI

ffi = FFI()
ffi.cdef("double sqrt(double x);")

import sys
libm_name = "libm.so.6" if sys.platform.startswith("linux") else "libSystem.dylib"
libm = ffi.dlopen(libm_name)

print(f"sqrt(2) = {libm.sqrt(2.0)}")
```

Two things to notice. `ffi.cdef("double sqrt(double x);")` is real C syntax, the kind you'd see in a header file. `cffi` parses this and figures out the argument and return types itself, no `c_double` declarations needed. `ffi.dlopen(...)` opens the library, like `ctypes.CDLL`.

The same `Product` struct example in `cffi`:

```python
from cffi import FFI

ffi = FFI()
ffi.cdef("""
typedef struct {
    int id;
    double price;
    int stock;
} Product;

double discounted_price(Product *p, double percent_off);
""")

libpricing = ffi.dlopen("./libpricing.so")

headphones = ffi.new("Product *", {"id": 101, "price": 59.99, "stock": 12})
final = libpricing.discounted_price(headphones, 20.0)
print(f"Discounted price: ${final:.2f}")
```

`ffi.new("Product *", {...})` allocates a `Product` and returns a pointer to it, with the fields populated from the dict. You pass that pointer directly to the C function. There's no `byref` or `POINTER` ceremony, the binding reads more like C and less like glue code.

When `cffi` shines is wrapping a real library. You take the project's header file, paste the relevant declarations into `ffi.cdef`, and the binding is done. The C compiler isn't needed for ABI mode, and types are checked against the declarations rather than left to you to get right by hand.

<h1 id="ctypes-vs-cffi-when-to-pick-which">
  ctypes vs cffi: When to Pick Which
</h1>

Both tools cover the same ground. The choice comes down to taste and the size of the binding.

| Aspect               | ctypes                                    | cffi                                    |
| -------------------- | ----------------------------------------- | --------------------------------------- |
| Install              | Stdlib                                    | `pip install cffi`                      |
| Type declarations    | Python objects (`c_int`, `c_double`, ...) | C syntax in `ffi.cdef(...)` strings     |
| Struct definitions   | `class P(Structure): _fields_ = [...]`    | Pasted C `typedef struct {...}`         |
| Compile step         | Never                                     | Optional (API mode for speed/safety)    |
| Reading headers      | Manual translation                        | Mostly copy-paste                       |
| Safer error messages | Generic                                   | Better, since `cffi` knows the C types  |
| Best for             | Quick scripts, small bindings             | Larger projects, code from real headers |

For a one-off script that calls two or three functions out of `libc`, `ctypes` is fine and saves an install. For a full binding to a real C library with dozens of functions and structs, `cffi` is less painful, especially because you can keep the `cdef` block in sync with the upstream header.

The cryptography library, psycopg (PostgreSQL driver), and many native database drivers ship `cffi` bindings in API mode. That's the same machinery you'd use for production work.

<h1 id="callbacks-calling-python-back-from-c">
  Callbacks: Calling Python Back from C
</h1>

Some C libraries take callbacks: a function pointer you pass in, and the library calls back into your code. Both `ctypes` and `cffi` support this.

A typical use case: a C library that processes a list of products and lets you supply a custom pricing rule.

```text
// process.c
#include <stddef.h>

double process_cart(int *ids, double *prices, size_t n,
                    double (*rule)(int id, double price)) {
    double total = 0.0;
    for (size_t i = 0; i < n; i++) {
        total += rule(ids[i], prices[i]);
    }
    return total;
}
```

The Python side with `ctypes`:

```python
import ctypes

libprocess = ctypes.CDLL("./libprocess.so")

# Define the callback type: takes int and double, returns double.
RuleType = ctypes.CFUNCTYPE(ctypes.c_double, ctypes.c_int, ctypes.c_double)

libprocess.process_cart.argtypes = [
    ctypes.POINTER(ctypes.c_int),
    ctypes.POINTER(ctypes.c_double),
    ctypes.c_size_t,
    RuleType,
]
libprocess.process_cart.restype = ctypes.c_double

# Python function used as the callback.
def loyalty_rule(product_id: int, price: float) -> float:
    # 10% off products with even IDs.
    return price * 0.9 if product_id % 2 == 0 else price

# Build C arrays from Python lists.
ids = (ctypes.c_int * 3)(101, 102, 103)
prices = (ctypes.c_double * 3)(59.99, 9.99, 29.99)

total = libprocess.process_cart(ids, prices, 3, RuleType(loyalty_rule))
print(f"Cart total: ${total:.2f}")
```

`CFUNCTYPE` describes the signature of a C function pointer. Wrapping a Python function in that type produces a callable C function pointer that the library can call. The Python function runs on whatever thread the C code is on, so it needs the GIL.

The big pitfall: don't let the wrapped callback get garbage-collected while C still holds a pointer to it. Keep a reference in Python (e.g., assign it to a module-level variable) for as long as the C library might call it. Forgetting this causes a crash that's hard to diagnose because it looks like memory corruption in C, not a Python bug.

> **Cost:** A callback into Python pays the full Python-C round-trip on every invocation. Calling a Python callback a million times from a C loop is much slower than a million-iteration pure-Python loop. If the callback is hot, write it in C.

<h1 id="when-not-to-reach-for-c">When NOT to Reach for C</h1>

The most common mistake is reaching for `ctypes` or `cffi` before profiling. The order of operations matters:

1. **Measure first.** `cProfile`, `time.perf_counter`, `py-spy`. Don't guess.
2. **Try the obvious Python fixes.** Vectorize with NumPy. Cache results. Use a `set` instead of a list lookup. Pick a better algorithm.
3. **Try a faster Python.** PyPy or the free-threaded build can be a drop-in win for pure-Python code.
4. **Then consider C.** Only after the above hasn't moved the needle.

A real example. Suppose your checkout pipeline spends 200ms summing line items for orders with 1,000 products. The naive C extension might shave that to 5ms, but a NumPy `np.sum` gets you to 8ms with no compilation, no new dependency, and no foreign-function-interface headaches. The Python solution wins almost every time.

The other reason to avoid C extensions is operational pain. A pure-Python package installs anywhere with `pip install`. A C extension needs the right compiler, the right header files, and the right shared library on every machine that uses it. Wheels (precompiled binaries on PyPI) help a lot, but only if you remember to build them for every platform and Python version your users have.

C extensions are the right call for genuine, measured, hot loops or for wrapping libraries that have no Python equivalent. They're the wrong call for "Python feels slow." Almost always, the bottleneck is something else.

The decision tree puts C extensions at the very bottom, after every cheaper option fails. That ordering matches how experienced engineers think about performance.
