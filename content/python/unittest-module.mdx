<h1 id="when-to-reach-for-unittest">When to Reach for unittest</h1>

Three situations make `unittest` the right tool. The first is that it's already there. If you're working in an environment where installing third-party packages is a hassle (a locked-down CI runner, an embedded interpreter, a constrained Docker image), `unittest` works out of the box.

The second is that the Python standard library itself uses `unittest` for its own tests, so reading CPython's test suite, or any project that grew up alongside it, means reading `unittest` code. Being able to follow `TestCase` subclasses is a small but real skill.

The third is interoperability. `pytest` can run `unittest`-style tests without changes, which means a project can start with `unittest` and migrate piece by piece. Going the other way doesn't work as cleanly, so understanding the baseline is useful even if you eventually move on.

Where `unittest` falls short is in its style. Every test goes inside a class. Every assertion is a method call. Setup and teardown are class methods with fixed names. Compared to `pytest`'s plain functions and bare `assert` statements, `unittest` feels heavier. The framework's mechanics are worth understanding on their own.

<h1 id="your-first-testcase">Your First TestCase</h1>

A test class is any class that inherits from `unittest.TestCase`. Each test is a method on that class whose name starts with `test_`. The framework scans for that prefix and treats every matching method as a separate test. Methods that don't start with `test_` are ignored by the runner, which is how you write helper methods on the same class without confusing the discovery process.

Here's a minimal class that tests a small `Cart` object:

```python
import unittest

class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price):
        self.items.append({"name": name, "price": price})

    def total(self):
        return sum(item["price"] for item in self.items)

class CartTests(unittest.TestCase):
    def test_empty_cart_total_is_zero(self):
        cart = Cart()
        self.assertEqual(cart.total(), 0)

    def test_single_item_total(self):
        cart = Cart()
        cart.add("Wireless Mouse", 29.99)
        self.assertEqual(cart.total(), 29.99)

    def test_two_items_total(self):
        cart = Cart()
        cart.add("Wireless Mouse", 29.99)
        cart.add("USB Cable", 9.99)
        self.assertEqual(cart.total(), 39.98)

if __name__ == "__main__":
    unittest.main()
```

Three dots, one per passing test. The line `unittest.main()` at the bottom is what kicks off the runner when you execute the file directly. It scans the current module for `TestCase` subclasses, collects every `test_`-prefixed method, and runs them.

Each test method is its own world. The framework creates a fresh instance of the test class for every test method, so anything you set on `self` in one test doesn't leak into the next. That isolation is the most important property of any test framework: a test's outcome depends only on the code under test and what the test itself sets up, not on the order tests happen to run in.

Method names matter. Renaming `test_empty_cart_total_is_zero` to `check_empty_cart` would make the framework skip it silently, because the `test_` prefix is the only thing telling `unittest` "this is a test". The convention is `test_<what_it_checks>`, and the longer and more descriptive the better. The name is what shows up in failure reports, so future-you (or a teammate at 2am) reading "test_two_items_total failed" learns more than "test_5 failed".

<h1 id="the-assertion-api">The Assertion API</h1>

`unittest` doesn't use the plain `assert` statement. Instead, `TestCase` provides a long list of assertion methods, each one tailored to a specific comparison. They all do the same fundamental thing (raise an `AssertionError` if the check fails), but the dedicated methods produce better failure messages than a bare `assert` would. When `assertEqual(a, b)` fails, you see both values; when `assert a == b` fails with `unittest`, you'd see "AssertionError" and nothing useful.

Here's the full set you'll actually reach for:

| Method                                     | What it checks                     | Example                                                |
| ------------------------------------------ | ---------------------------------- | ------------------------------------------------------ |
| `assertEqual(a, b)`                        | `a == b`                           | `self.assertEqual(cart.total(), 39.98)`                |
| `assertNotEqual(a, b)`                     | `a != b`                           | `self.assertNotEqual(cart.total(), 0)`                 |
| `assertTrue(x)`                            | `bool(x) is True`                  | `self.assertTrue(cart.has_discount)`                   |
| `assertFalse(x)`                           | `bool(x) is False`                 | `self.assertFalse(cart.is_empty())`                    |
| `assertIs(a, b)`                           | `a is b`                           | `self.assertIs(found, original)`                       |
| `assertIsNot(a, b)`                        | `a is not b`                       | `self.assertIsNot(copy, original)`                     |
| `assertIsNone(x)`                          | `x is None`                        | `self.assertIsNone(cart.coupon)`                       |
| `assertIsNotNone(x)`                       | `x is not None`                    | `self.assertIsNotNone(order.id)`                       |
| `assertIn(item, container)`                | `item in container`                | `self.assertIn("Mouse", names)`                        |
| `assertNotIn(item, container)`             | `item not in container`            | `self.assertNotIn("Keyboard", names)`                  |
| `assertIsInstance(obj, cls)`               | `isinstance(obj, cls)`             | `self.assertIsInstance(cart.total(), float)`           |
| `assertNotIsInstance(obj, cls)`            | `not isinstance(obj, cls)`         | `self.assertNotIsInstance(cart, list)`                 |
| `assertAlmostEqual(a, b)`                  | rounds to 7 decimal places         | `self.assertAlmostEqual(0.1 + 0.2, 0.3)`               |
| `assertGreater(a, b)`                      | `a > b`                            | `self.assertGreater(cart.total(), 0)`                  |
| `assertGreaterEqual(a, b)`                 | `a >= b`                           | `self.assertGreaterEqual(stock, 1)`                    |
| `assertLess(a, b)`                         | `a < b`                            | `self.assertLess(discount, 1.0)`                       |
| `assertLessEqual(a, b)`                    | `a <= b`                           | `self.assertLessEqual(weight, max_weight)`             |
| `assertRaises(exc, fn, *args)`             | calling `fn(*args)` raises `exc`   | `self.assertRaises(KeyError, dict.pop, {}, "k")`       |
| `assertRaisesRegex(exc, regex, fn, *args)` | raises `exc` with message matching | `self.assertRaisesRegex(ValueError, r"negative", ...)` |
| `assertCountEqual(a, b)`                   | same elements, order-independent   | `self.assertCountEqual([1, 2, 2], [2, 1, 2])`          |
| `assertListEqual(a, b)`                    | list-specific equality + diff      | `self.assertListEqual(got, expected)`                  |
| `assertDictEqual(a, b)`                    | dict-specific equality + diff      | `self.assertDictEqual(got, expected)`                  |
| `assertSetEqual(a, b)`                     | set-specific equality + diff       | `self.assertSetEqual(got, expected)`                   |

The vast majority of tests you'll write use `assertEqual`, `assertTrue`, `assertIn`, `assertIsNone`, and `assertRaises`. The rest exist because they produce specialized failure messages. `assertListEqual` knows how to print a side-by-side diff of two lists. `assertAlmostEqual` knows to compare floats with a tolerance. `assertIs` distinguishes "same object" from "equal value", which matters for sentinel values like `None` or `True`.

A small worked example showing the most useful five:

```python
import unittest

class Order:
    def __init__(self, items, customer_email=None):
        if not items:
            raise ValueError("order must have at least one item")
        self.items = items
        self.customer_email = customer_email
        self.status = "placed"

    def total(self):
        return sum(item["price"] for item in self.items)

    def product_names(self):
        return [item["name"] for item in self.items]

class OrderTests(unittest.TestCase):
    def test_total_sums_prices(self):
        order = Order([
            {"name": "Wireless Mouse", "price": 29.99},
            {"name": "USB Cable", "price": 9.99},
        ])
        self.assertEqual(order.total(), 39.98)

    def test_status_is_placed_when_created(self):
        order = Order([{"name": "USB Cable", "price": 9.99}])
        self.assertEqual(order.status, "placed")
        self.assertTrue(order.status)

    def test_email_is_none_by_default(self):
        order = Order([{"name": "USB Cable", "price": 9.99}])
        self.assertIsNone(order.customer_email)

    def test_product_name_in_order(self):
        order = Order([
            {"name": "Wireless Mouse", "price": 29.99},
            {"name": "USB Cable", "price": 9.99},
        ])
        self.assertIn("Wireless Mouse", order.product_names())

    def test_empty_items_raises(self):
        with self.assertRaises(ValueError):
            Order([])

if __name__ == "__main__":
    unittest.main()
```

Notice the last test. `assertRaises` is special: it can be used as a context manager (the recommended form) or as a function call (`self.assertRaises(ValueError, Order, [])`). The context manager form reads naturally: "this block of code should raise `ValueError`". If the block runs without raising, the test fails. If it raises a different exception, the test errors out (which is treated as a failure but reported differently).

`assertRaises` also exposes the caught exception, which is useful when you want to check the message:

```python
import unittest

class DiscountCalculator:
    def apply(self, price, percent):
        if percent < 0 or percent > 100:
            raise ValueError(f"percent must be between 0 and 100, got {percent}")
        return price * (100 - percent) / 100

class DiscountTests(unittest.TestCase):
    def test_negative_percent_raises(self):
        calc = DiscountCalculator()
        with self.assertRaises(ValueError) as cm:
            calc.apply(29.99, -5)
        self.assertIn("between 0 and 100", str(cm.exception))

    def test_negative_percent_raises_regex(self):
        calc = DiscountCalculator()
        with self.assertRaisesRegex(ValueError, r"got -5"):
            calc.apply(29.99, -5)

if __name__ == "__main__":
    unittest.main()
```

`cm.exception` holds the actual `ValueError` instance after the block. You can inspect its message, its arguments, anything you'd inspect in an `except` clause. `assertRaisesRegex` skips the manual `assertIn` step by letting you check the message against a regular expression in one call.

A small but important note about `assertEqual` on floats. Floating-point arithmetic is approximate, so direct equality comparisons trip you up:

```python
import unittest

class PriceMathTests(unittest.TestCase):
    def test_exact_equality_fails(self):
        # This test FAILS, on purpose, to show the trap
        self.assertEqual(0.1 + 0.2, 0.3)

    def test_almost_equal_works(self):
        self.assertAlmostEqual(0.1 + 0.2, 0.3)

if __name__ == "__main__":
    unittest.main()
```

`0.1 + 0.2` is not exactly `0.3` in binary floating point; it's `0.30000000000000004`. `assertEqual` checks exact equality and fails. `assertAlmostEqual` rounds both numbers to 7 decimal places by default and compares those, which is what you want for any price math involving fractional amounts. You can pass `places=` for more or fewer digits, or `delta=` for a custom tolerance.

> **Cost:** `assertAlmostEqual` defaults to comparing the rounded difference. For very small numbers (below 1e-7), the default tolerance is too coarse and may pass tests that shouldn't. Use `delta=` explicitly when comparing values near zero or at any unusual scale.

The collection-specific assertions (`assertListEqual`, `assertDictEqual`, `assertSetEqual`) are worth using when you care about a clear failure message. `assertEqual([1, 2, 3], [1, 2, 4])` works fine, but the failure message is a wall of text. `assertListEqual` produces a diff:

```python
import unittest

class CartItemsTests(unittest.TestCase):
    def test_list_diff_shown_clearly(self):
        expected = ["Wireless Mouse", "USB Cable", "Keyboard", "Monitor"]
        actual = ["Wireless Mouse", "USB Cable", "Keyboard", "Webcam"]
        self.assertListEqual(actual, expected)

if __name__ == "__main__":
    unittest.main()
```

The "First differing element 3" line pinpoints where the lists diverged. For longer or nested lists, that's the difference between "spend 20 seconds debugging" and "spend 5 minutes scrolling".

`assertCountEqual` is the one most people forget. It checks that two sequences contain the same elements, ignoring order. The name is misleading; it doesn't count anything. It's useful when you have a function that returns items in an unpredictable order (a `set`-backed result, a dict iteration before guaranteed ordering, a parallel result) and you only care that the contents match.

```python
import unittest

def discount_eligible_products(cart):
    return [item["name"] for item in cart if item["price"] >= 20]

class DiscountEligibilityTests(unittest.TestCase):
    def test_eligible_products(self):
        cart = [
            {"name": "Wireless Mouse", "price": 29.99},
            {"name": "USB Cable", "price": 9.99},
            {"name": "Keyboard", "price": 49.99},
        ]
        expected = ["Keyboard", "Wireless Mouse"]
        self.assertCountEqual(discount_eligible_products(cart), expected)

if __name__ == "__main__":
    unittest.main()
```

The function returned `["Wireless Mouse", "Keyboard"]`. The test expected `["Keyboard", "Wireless Mouse"]`. `assertCountEqual` doesn't care about order; both lists contain the same elements, so the test passes.

<h1 id="setup-and-teardown-per-test-hooks">
  setUp and tearDown: Per-Test Hooks
</h1>

Most test classes contain several tests that all need similar setup. Three tests of a `Cart` class might all start with "create a cart and add a few items". Repeating that boilerplate in every test method gets old fast, and copy-pasted setup tends to drift apart over time.

`TestCase` provides two hooks for this: `setUp` runs before every test method, `tearDown` runs after every test method. Both are instance methods, both take only `self`, and the framework calls them automatically. You don't invoke them from your test code; you just override them in your subclass.

```python
import unittest

class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price):
        self.items.append({"name": name, "price": price})

    def remove(self, name):
        self.items = [i for i in self.items if i["name"] != name]

    def total(self):
        return sum(item["price"] for item in self.items)

    def count(self):
        return len(self.items)

class CartTests(unittest.TestCase):
    def setUp(self):
        print(f"  setUp for {self._testMethodName}")
        self.cart = Cart()
        self.cart.add("Wireless Mouse", 29.99)
        self.cart.add("USB Cable", 9.99)

    def tearDown(self):
        print(f"  tearDown for {self._testMethodName}")

    def test_count_after_setup(self):
        self.assertEqual(self.cart.count(), 2)

    def test_total_after_setup(self):
        self.assertAlmostEqual(self.cart.total(), 39.98)

    def test_remove_decreases_count(self):
        self.cart.remove("USB Cable")
        self.assertEqual(self.cart.count(), 1)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

`setUp` fired three times, once before each test. `tearDown` fired three times, once after each. Even though `test_remove_decreases_count` removed an item from the cart, the next test got a fresh cart with both items, because `setUp` created a new one. This is the isolation property again: every test starts from the same known state.

`tearDown` is the place for cleanup that has to happen no matter what. Closing files, deleting temp directories, restoring environment variables, resetting global state. It runs even if the test method raised an exception, which is the key reason you'd put cleanup there instead of at the end of the test method itself.

```python
import os
import tempfile
import unittest

class CatalogExporter:
    def export(self, products, path):
        with open(path, "w") as f:
            for product in products:
                f.write(f"{product['name']},{product['price']}\n")

class ExporterTests(unittest.TestCase):
    def setUp(self):
        fd, self.path = tempfile.mkstemp(prefix="catalog_", suffix=".csv")
        os.close(fd)
        self.exporter = CatalogExporter()

    def tearDown(self):
        if os.path.exists(self.path):
            os.remove(self.path)

    def test_export_writes_one_line_per_product(self):
        products = [
            {"name": "Wireless Mouse", "price": 29.99},
            {"name": "USB Cable", "price": 9.99},
        ]
        self.exporter.export(products, self.path)
        with open(self.path) as f:
            lines = f.readlines()
        self.assertEqual(len(lines), 2)

    def test_export_writes_name_and_price(self):
        products = [{"name": "Wireless Mouse", "price": 29.99}]
        self.exporter.export(products, self.path)
        with open(self.path) as f:
            content = f.read()
        self.assertIn("Wireless Mouse,29.99", content)

if __name__ == "__main__":
    unittest.main()
```

Each test gets a fresh temp file from `setUp` and that file is deleted in `tearDown`. If the test method raised partway through, `tearDown` would still run and the file would still be deleted. That guarantee is the whole reason for the hook.

> **Cost:** `setUp` runs before every test method. If your setup is expensive (opening a database connection, building a large fixture, doing network I/O), you pay that cost N times for N tests. `setUpClass`, covered next, runs once per class instead. Use it when the setup can be safely shared.

<h1 id="setupclass-and-teardownclass-per-class-hooks">
  setUpClass and tearDownClass: Per-Class Hooks
</h1>

Some setup is too expensive to repeat for every test. Opening a database connection, building a large in-memory dataset, starting a subprocess. For those cases, `setUpClass` and `tearDownClass` run once per class: once before any test method runs, once after all of them finish.

The catch is that these hooks are `@classmethod`s, not instance methods. They receive `cls` (the class itself), not `self`. You store the setup result as a class attribute. Every test then reads the same shared object.

```python
import unittest

class ProductCatalog:
    def __init__(self, products):
        self.products = products

    def find(self, name):
        for product in self.products:
            if product["name"] == name:
                return product
        return None

    def cheapest(self):
        return min(self.products, key=lambda p: p["price"])

    def most_expensive(self):
        return max(self.products, key=lambda p: p["price"])

class CatalogTests(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        print("  setUpClass: building catalog")
        cls.catalog = ProductCatalog([
            {"name": "Wireless Mouse", "price": 29.99},
            {"name": "USB Cable", "price": 9.99},
            {"name": "Keyboard", "price": 49.99},
            {"name": "Monitor", "price": 199.99},
        ])

    @classmethod
    def tearDownClass(cls):
        print("  tearDownClass: catalog discarded")

    def test_find_existing_product(self):
        product = self.catalog.find("Keyboard")
        self.assertIsNotNone(product)
        self.assertEqual(product["price"], 49.99)

    def test_find_missing_product(self):
        self.assertIsNone(self.catalog.find("Tablet"))

    def test_cheapest_is_usb_cable(self):
        self.assertEqual(self.catalog.cheapest()["name"], "USB Cable")

    def test_most_expensive_is_monitor(self):
        self.assertEqual(self.catalog.most_expensive()["name"], "Monitor")

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

`setUpClass` ran once, before any test. Four tests ran, each accessing `self.catalog` (which works because instance attribute lookup falls back to class attributes). `tearDownClass` ran once, after the last test.

The trade-off is sharing. Because every test sees the same `catalog` object, a test that mutates it can leak state into the next test. The four tests above only read from the catalog, so they're safe. If `test_find_existing_product` had called `self.catalog.products.append(...)`, the appended item would be visible to every later test. That's the whole reason `setUp` (per-test) exists as a separate hook: when state can be mutated, you want a fresh instance for each test.

The diagram below shows the full lifecycle Python walks through when running a test class:

The outer hooks (`setUpClass`, `tearDownClass`) fire once. The inner hooks (`setUp`, `tearDown`) fire once per test. If a test class has 50 tests, `setUpClass` runs once and `setUp` runs 50 times. The asymmetry is what makes the per-class hooks worthwhile for expensive setup, and what makes the per-test hooks essential when isolation matters.

`tearDownClass` runs even if a test failed, but it does **not** run if `setUpClass` itself raised. If your `setUpClass` allocates two resources and the second allocation fails, the first one leaks unless `setUpClass` catches its own error and cleans up before re-raising. This mirrors the same rule from the context manager chapter: setup methods own their own partial-failure cleanup.

<h1 id="module-level-hooks-setupmodule-and-teardownmodule">
  Module-Level Hooks: setUpModule and tearDownModule
</h1>

One level above the class are module-level hooks. `setUpModule` and `tearDownModule` are plain functions (not methods) defined at the top level of the test file. They run once for the whole module, before any class in the module is touched, and once after every class is done.

```python
import unittest

def setUpModule():
    print("setUpModule: loading shared catalog data")

def tearDownModule():
    print("tearDownModule: releasing shared catalog data")

class CartTests(unittest.TestCase):
    def test_one(self):
        pass

class OrderTests(unittest.TestCase):
    def test_two(self):
        pass

if __name__ == "__main__":
    unittest.main()
```

Use module-level hooks for setup that genuinely spans multiple classes in the same file: loading a large fixture file, starting a test database, mocking an environment variable. In practice they're rare; most projects keep their setup at the class level because that's where the scoping is most predictable. If you find yourself reaching for module-level hooks, it's worth asking whether the classes should share a base class with `setUpClass` instead.

The four-level hierarchy (module, class, instance, method) is summarized below:

| Hook             | Scope    | Type        | Called                               |
| ---------------- | -------- | ----------- | ------------------------------------ |
| `setUpModule`    | module   | function    | once before any class in the module  |
| `setUpClass`     | class    | classmethod | once before any test in the class    |
| `setUp`          | instance | method      | before every test method             |
| test method      | one test | method      | itself                               |
| `tearDown`       | instance | method      | after every test method              |
| `tearDownClass`  | class    | classmethod | once after all tests in the class    |
| `tearDownModule` | module   | function    | once after all classes in the module |

The pattern is symmetric: setup goes outside-in (module, then class, then instance), teardown goes inside-out (instance, then class, then module). It's the same structure as nested `with` statements from the context manager chapter.

<h1 id="running-tests">Running Tests</h1>

There are three ways to run `unittest` tests from the command line, and you'll use all three at different times.

The first runs a single file directly, assuming the file ends with `unittest.main()`:

```text
python test_cart.py
```

This works for ad-hoc development. You run the file, the `unittest.main()` call picks up the `TestCase` classes in the module, and the results print. Add `-v` for verbose output:

```text
python test_cart.py -v
```

The verbose flag prints one line per test name plus the result, instead of one dot per pass. Useful when something's going wrong and you want to see which test even ran.

The second invokes `unittest` as a module against a specific file or test:

```text
python -m unittest test_cart
python -m unittest test_cart.CartTests
python -m unittest test_cart.CartTests.test_total_after_setup
```

The dotted form lets you target a module, a class, or a single test method. This is what you reach for when one test is failing and you want to iterate on it without running the rest. Single-test runs are a few hundred milliseconds; full suites can be minutes.

The third is **test discovery**, which scans a directory tree for test files automatically:

```text
python -m unittest discover
python -m unittest discover -s tests -p "test_*.py"
```

`discover` without arguments looks in the current directory for files matching `test*.py`. The `-s` flag (start directory) and `-p` flag (pattern) override the defaults. Run from your project root, this finds every test file in the tree, every `TestCase` subclass in those files, every `test_`-prefixed method in those classes, and runs them all.

Discovery has one rule that surprises people: it walks into subdirectories only if they contain an `__init__.py` file (so they're proper packages). A `tests/` folder without an `__init__.py` won't be descended into. The fix is to add an empty `__init__.py` to every test folder, or pass `--top-level-directory` explicitly. Modern projects on Python 3.3+ get implicit namespace packages, so an empty folder works too, but the explicit `__init__.py` is safer.

> **Cost:** Discovery imports every matching file. If your test files have heavy module-level imports (loading a large dataset, opening a connection, starting a server), every discovery run pays that cost up front. Push expensive setup into `setUpClass` or `setUpModule` so it only runs when tests in that file actually execute.

A failure looks like this:

```text
.F.
======================================================================
FAIL: test_total_after_remove (__main__.CartTests.test_total_after_remove)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "test_cart.py", line 23, in test_total_after_remove
    self.assertEqual(self.cart.total(), 29.99)
AssertionError: 39.98 != 29.99

----------------------------------------------------------------------
Ran 3 tests in 0.001s

FAILED (failures=1)
```

The dots show pass/fail status per test. `.` is a pass, `F` is a failure (an assertion didn't hold), `E` is an error (an unexpected exception, not from an assertion), `s` is a skip, `x` is an expected failure, `u` is an unexpected pass (a test marked `expectedFailure` that surprisingly passed). The summary at the end shows totals. Anything other than "OK" at the end means at least one test didn't pass cleanly.

<h1 id="skipping-tests">Skipping Tests</h1>

Some tests shouldn't run in every environment. A test that hits the network shouldn't run when offline. A test that uses a Linux-only feature shouldn't run on Windows. A test for a feature you haven't built yet shouldn't fail and pollute the results; it should announce "not implemented" cleanly.

`unittest` provides decorators for each case.

`@unittest.skip(reason)` skips the test unconditionally. Use it when a test is broken and you're tracking the fix in another commit:

```python
import unittest

class FeatureTests(unittest.TestCase):
    @unittest.skip("waiting on stock API rewrite (ticket 4421)")
    def test_stock_check_with_new_api(self):
        self.fail("not implemented yet")

    def test_other_thing(self):
        self.assertEqual(1, 1)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

`@unittest.skipIf(condition, reason)` skips when the condition is truthy:

```python
import sys
import unittest

class PlatformTests(unittest.TestCase):
    @unittest.skipIf(sys.platform == "win32", "uses Unix file permissions")
    def test_file_mode_is_644(self):
        self.assertEqual(0o644, 0o644)

    @unittest.skipIf(sys.version_info < (3, 10), "requires structural pattern matching")
    def test_match_statement(self):
        self.assertEqual(1, 1)

if __name__ == "__main__":
    unittest.main()
```

`@unittest.skipUnless(condition, reason)` is the inverse: skip unless the condition is truthy. It reads naturally for "only run when":

```python
import unittest

HAS_REDIS = False

class CacheTests(unittest.TestCase):
    @unittest.skipUnless(HAS_REDIS, "redis not available")
    def test_with_redis(self):
        self.assertEqual(1, 1)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

`@unittest.expectedFailure` is the odd one. It marks a test that's currently broken in a known way. If the test fails, the framework reports it as "expected failure" and the overall run still passes. If the test unexpectedly **passes**, the framework reports it as "unexpected success" and the run fails. The point is to track known bugs without breaking the build, and to find out immediately when the bug gets fixed (so you can remove the decorator).

```python
import unittest

class WIPTests(unittest.TestCase):
    @unittest.expectedFailure
    def test_discount_handles_zero_correctly(self):
        # known bug: returns NaN instead of 0
        self.assertEqual(0, float("nan"))

    @unittest.expectedFailure
    def test_this_actually_passes(self):
        self.assertEqual(1, 1)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

The first test failed (as expected). The second test passed (unexpectedly), which fails the run. The signal is "you marked this test as broken, but it works now; go remove the decorator".

You can also skip from inside a test by calling `self.skipTest(reason)`:

```python
import unittest

class ConditionalTests(unittest.TestCase):
    def test_premium_feature(self):
        is_premium = False
        if not is_premium:
            self.skipTest("premium account required")
        self.assertEqual(1, 1)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

`self.skipTest` is useful when the skip condition depends on state that's only known at runtime (a config flag, a database query, an environment probe). The decorator form is preferable when the condition is known statically.

<h1 id="subtest-many-assertions-in-one-test">
  subTest: Many Assertions in One Test
</h1>

Sometimes you want to test the same logic against several inputs without writing one method per case. `unittest` provides `self.subTest()` as a context manager: each block inside is reported separately if it fails, but the whole thing counts as one test method.

```python
import unittest

def apply_discount(price, percent):
    return price * (100 - percent) / 100

class DiscountTests(unittest.TestCase):
    def test_various_discounts(self):
        cases = [
            # (price, percent, expected)
            (100.0, 0, 100.0),
            (100.0, 10, 90.0),
            (100.0, 50, 50.0),
            (29.99, 10, 26.991),
            (49.99, 25, 37.4925),
        ]
        for price, percent, expected in cases:
            with self.subTest(price=price, percent=percent):
                self.assertAlmostEqual(apply_discount(price, percent), expected)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

If one case fails, you still see which one. Say the discount function had a bug for `percent=50`:

```text
test_various_discounts (__main__.DiscountTests.test_various_discounts) ...
======================================================================
FAIL: test_various_discounts (__main__.DiscountTests.test_various_discounts) (price=100.0, percent=50)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "test_discount.py", line 17, in test_various_discounts
    self.assertAlmostEqual(apply_discount(price, percent), expected)
AssertionError: 49.0 != 50.0 within 7 places (1.0 difference)

----------------------------------------------------------------------
Ran 1 test in 0.000s

FAILED (failures=1)
```

The `subTest(price=..., percent=...)` parameters are printed in the failure header, so you know exactly which row of the table broke. Without `subTest`, the first failed assertion would abort the loop and you'd never know about cases 4 and 5.

`subTest` is the closest `unittest` gets to "parametrized" tests. It works, but it's clumsy compared to `pytest.mark.parametrize`. The pytest version generates one test ID per row in the test report, runs each row as a separate test, and integrates with all the other pytest tools (filtering by ID, re-running just one row, and so on). If you're starting a new project and you need parametrization, pytest's approach is worth the switch on its own.

For an existing `unittest` codebase, `subTest` is fine. Just remember that within a single `subTest` block, an assertion failure does abort the rest of that block (not the whole test); execution then moves to the next iteration of the loop.
