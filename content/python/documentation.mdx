<h1 id="types-of-documentation">Types of Documentation</h1>

A single Python project usually has four kinds of documentation, each with a different audience and purpose. Confusing one for another is a common mistake.

| Type                 | Audience                          | Question it answers                                    | Where it lives                  |
| -------------------- | --------------------------------- | ------------------------------------------------------ | ------------------------------- |
| README               | First-time visitor                | What is this, why would I use it, how do I install it? | Root of the repository          |
| Docstrings           | Developer reading the code        | What does this function do, what are its arguments?    | Inside the source files         |
| Tutorials and guides | New user learning the project     | How do I accomplish task X step by step?               | A `docs/` folder, hosted online |
| API reference        | Existing user looking up a detail | What's the exact signature of `cart.add_item`?         | Auto-generated from docstrings  |

Each one builds on the others. The README is the front door. Docstrings are the source of truth that everything else derives from. Tutorials show real workflows. The API reference catalogs every public function and class.

The arrows match the order a typical user walks through the docs. They land on the README, follow a tutorial to get something running, consult how-to guides when they hit a specific task, and dip into the API reference when they need precise details. The docstrings inside your source files feed the API reference automatically, so the same prose appears in two places: in the source for developers, and on the docs site for users.

<h1 id="the-readme">The README</h1>

The README is the first thing anyone sees on GitHub, PyPI, or your project's homepage. If it's bad, visitors often leave. If it's good, it tells them in 30 seconds whether the project is worth their time and how to get started.

A solid README has roughly this shape:

1. **Project name and one-line description.** What this is, in a single sentence.
2. **Badges (optional).** Build status, version, license, coverage. Use sparingly.
3. **Why this exists.** The problem it solves, in two or three sentences.
4. **Installation.** The exact command, copy-pasteable.
5. **Quick start.** A 10 to 20 line example that does something real.
6. **Links to longer docs.** Tutorials, API reference, contributing guide.
7. **License and contributing info.** A line each, with a link.

A minimal example for a fictional shopping cart library:

```text
# cartkit

A small library for building shopping carts in Python.

## Why cartkit

Most Python e-commerce code reinvents the same shopping cart logic: adding
items, applying discounts, computing totals with tax and shipping. cartkit
gives you those primitives in a few hundred lines of code with no
dependencies.

## Install

    pip install cartkit

## Quick start

    from cartkit import Cart

    cart = Cart()
    cart.add("headphones", price=59.99)
    cart.add("cable", price=9.99, quantity=2)

    print(cart.total())
    # 79.97

## Learn more

- Full docs: https://cartkit.readthedocs.io
- Source: https://github.com/example/cartkit
- License: MIT
```

The structure is deliberate. The first paragraph answers "what is this." The "Why" section answers "should I care." Install and Quick Start let the reader run something within a minute. Everything else is a link, not a wall of text.

What to leave out of the README: the entire API reference, long architecture discussions, every configuration option. Those belong in dedicated docs. The README is for the first impression, not completeness.

<h1 id="project-documentation-tutorials-guides-and-api-reference">
  Project Documentation: Tutorials, Guides, and API Reference
</h1>

When a project grows past a single README, you need a docs site. There's a well-known model for organizing it, called the Diataxis framework, that splits docs into four categories based on what the reader is trying to do.

| Category     | Reader's goal            | Example title                                 |
| ------------ | ------------------------ | --------------------------------------------- |
| Tutorial     | Learn by doing           | "Build your first shopping cart with cartkit" |
| How-to guide | Solve a specific problem | "How to apply percentage discounts to a cart" |
| Reference    | Look up a fact           | "`Cart.add_item(name, price, quantity=1)`"    |
| Explanation  | Understand the why       | "How cartkit handles tax rounding"            |

Most small projects don't need all four. A useful starting point is a README, a single tutorial, and an auto-generated API reference. As the project grows, you add how-to guides for the questions users keep asking, and you add explanations for the design decisions that need context.

A common mistake is mixing categories in the same page. A tutorial that veers into how-to material loses its narrative. An API reference that includes a long explanation forces the reader to scroll past prose to find a method signature. Pick one category per page.

<h3 id="the-quick-start-tutorial">The Quick-Start Tutorial</h3>

A quick-start tutorial walks a new user through a complete, end-to-end example in 15 to 30 minutes. It assumes nothing except "you have Python installed." It builds up to one finished piece of working code by the end.

A pattern that works:

1. **Set the goal.** State the deliverable in one sentence ("a working shopping cart that computes totals with tax and discount").
2. **Install.** One command. Don't make them debug their environment.
3. **First runnable snippet.** Eight to ten lines. Print something.
4. **One concept at a time.** Each step adds one new idea. Don't introduce three at once.
5. **Show the output after every step.** The reader should see the same output you describe.
6. **End with the complete program.** Everything they built, in one block they can copy.

The tutorial is the project's onboarding. If a new user can't follow it without getting stuck, they often leave. Teams that care about adoption put more effort into the tutorial than into anything else, because it's the page that converts visitors into users.

<h3 id="how-to-guides">How-To Guides</h3>

A how-to guide answers a specific question. "How do I apply a discount that only kicks in above a minimum order value?" "How do I export a cart to JSON?" Each guide is short (a screenful or two), focused on one task, and assumes the reader already knows the basics.

How-to guides accumulate over time. You write them when users ask the same question more than twice. A useful pattern:

1. State the problem in the title.
2. Give the shortest solution that works.
3. Explain the parts that aren't obvious.
4. Link to deeper material if the reader wants more.

What a how-to is not: a tutorial. Tutorials teach concepts in order. How-tos assume the concepts and skip to the solution.

<h3 id="the-api-reference">The API Reference</h3>

The API reference is the long, exhaustive list of every public function, class, and method, with their signatures and descriptions. It's the page users go to when they know what they want and need a detail.

You don't write the API reference by hand. You write docstrings inside your source code, and a tool generates the reference from them.

<h1 id="documentation-tools">Documentation Tools</h1>

Three tools cover almost every Python project: Sphinx, MkDocs, and pdoc. Each has a different philosophy.

<h3 id="sphinx">Sphinx</h3>

Sphinx is the original Python documentation generator, written in Python itself and used by the standard library, NumPy, Django, and most of the older big projects. It was built around reStructuredText (ReST), a markup language that's more powerful than Markdown but less familiar.

```text
pip install sphinx
sphinx-quickstart docs/
```

After running the quick-start, you have a `docs/` directory with a `conf.py`, an `index.rst`, and a `Makefile`. You write pages in `.rst` files, run `make html`, and Sphinx builds a static HTML site.

Sphinx's strengths:

- **Cross-references.** You can link to any function, class, or section by name, and Sphinx checks that the link target exists.
- **Extensions.** A large ecosystem of plugins for diagrams, math, automatic API generation, multi-language support.
- **Auto-generated API docs.** The `autodoc` extension reads your source code, finds the docstrings, and turns them into reference pages.
- **Multi-format output.** HTML, PDF, ePub, man pages.

Sphinx's weaknesses:

- **ReST is harder to learn than Markdown.** The syntax for links, code blocks, and cross-references is its own thing.
- **The default theme is dated.** Most projects use `furo` or `sphinx-rtd-theme` instead.
- **The configuration is verbose.** `conf.py` has dozens of settings and the docs are dense.

Sphinx is the right pick when you need its capabilities: cross-references that survive refactors, math rendering, multi-version docs, or PDF output for a book-style project. It's overkill for a small library with one tutorial and an API reference.

<h3 id="mkdocs">MkDocs</h3>

MkDocs is younger and Markdown-based. You write pages in Markdown, configure a single YAML file, and run `mkdocs serve` to preview locally. The output is a clean static site.

```text
pip install mkdocs mkdocs-material
mkdocs new my-project
cd my-project
mkdocs serve
```

The default theme is plain, but the Material theme (from `mkdocs-material`) gives you a clean, modern look out of the box. Most new Python projects in the last few years that picked MkDocs picked it with Material.

MkDocs's strengths:

- **Markdown.** Widely known, low learning curve.
- **Fast preview.** `mkdocs serve` watches files and reloads in milliseconds.
- **Simple config.** One YAML file with a clear structure.
- **Modern themes.** Material is among the most readable.

MkDocs's weaknesses:

- **Weaker cross-references.** Linking to a function by name across pages takes plugin help.
- **API generation needs a plugin.** `mkdocstrings` does the job, but it's a separate install.

A rough decision rule: pick MkDocs (with Material) for new small-to-medium projects that prioritize ease of writing. Pick Sphinx when the docs need to grow into something more involved.

<h3 id="pdoc">pdoc</h3>

`pdoc` is the simplest option. It takes a Python module, reads its docstrings, and generates an HTML API reference. That's it. No tutorials, no how-to guides, only the reference pages.

```text
pip install pdoc
pdoc src/cartkit/ -o docs/
```

For a small library where the README is the tutorial and the API reference is all the user docs you need, `pdoc` is the fastest path from "I have docstrings" to "I have a docs site." It's a poor fit for a project with extensive tutorials or how-to material.

<h3 id="comparison">Comparison</h3>

| Tool   | Format                                 | Best for                              | Default theme                          | API generation          |
| ------ | -------------------------------------- | ------------------------------------- | -------------------------------------- | ----------------------- |
| Sphinx | reStructuredText (Markdown via plugin) | Large projects, multi-format output   | `alabaster` (most use `furo` or `rtd`) | Built-in (`autodoc`)    |
| MkDocs | Markdown                               | Small to medium projects, modern look | Plain (Material recommended)           | Plugin (`mkdocstrings`) |
| pdoc   | (none, reads docstrings)               | API reference only, tiny projects     | Minimal HTML                           | Built-in                |

For a fresh project today, the common starting point is MkDocs with the Material theme and the `mkdocstrings` plugin. It gives you Markdown for prose, auto-generated API reference from docstrings, and a clean output, all in about 50 lines of YAML config.

<h1 id="rest-vs-markdown">ReST vs Markdown</h1>

The format question matters because it affects who can contribute to your docs and how much friction that contribution carries. Most non-Python developers know Markdown. ReST is mostly known to people who already work on Python projects.

A side-by-side of the same content:

**Markdown:**

```text
# Cart

A `Cart` holds shopping items and computes totals.

## Methods

- `add(name, price, quantity=1)` - add an item
- `total()` - return the cart total

See [Discounts](discounts.md) for applying discounts.
```

**reStructuredText:**

```text
Cart
====

A :class:`Cart` holds shopping items and computes totals.

Methods
-------

* :meth:`Cart.add` - add an item
* :meth:`Cart.total` - return the cart total

See :doc:`discounts` for applying discounts.
```

Both produce the same visible result. The ReST version uses **roles** (`:class:`, `:meth:`, `:doc:`) that Sphinx understands. The roles let Sphinx check that the linked target exists, jump straight to it, and update the link automatically if the target moves. Markdown doesn't have that out of the box; you can get most of it back with plugins, but the default is a plain link.

The trade-off is reach versus capability. Markdown is universal, easy to teach, and good enough for almost everything. ReST is more capable when the docs site gets large, but the entry cost is higher.

MyST is a Markdown extension that adds ReST's features back. Sphinx supports it as a first-class input format, so a modern Sphinx project can use Markdown for prose and ReST roles for the cross-references. That setup gives you both, at the cost of two formats living in the same repo.

<h1 id="hosting-documentation">Hosting Documentation</h1>

Once you've built the site locally, you need somewhere to host it.

**Read the Docs** is the standard Python doc host. It's free for open-source projects, automatically rebuilds the docs on every push to your git repo, supports multi-version docs (one URL per release), and works with Sphinx and MkDocs. Most well-known Python libraries host their docs there: Django, Flask, requests, pytest, hundreds more.

The setup is a config file in your repo:

```yaml
# .readthedocs.yaml
version: 2

build:
  os: ubuntu-22.04
  tools:
    python: "3.11"

sphinx:
  configuration: docs/conf.py

python:
  install:
    - requirements: docs/requirements.txt
```

Push, and Read the Docs builds your site. Future pushes trigger automatic rebuilds. The free plan covers public projects with reasonable limits; the paid plan supports private repos and larger build minutes.

**GitHub Pages** is the simpler alternative. You publish a built HTML directory to a `gh-pages` branch (or a `docs/` folder on `main`), and GitHub serves it. MkDocs has a built-in command for this:

```text
mkdocs gh-deploy
```

The command builds the site, commits the output to `gh-pages`, and pushes. GitHub serves the result at `https://yourname.github.io/project-name/`. No external service needed.

**Other hosts.** Cloudflare Pages, Netlify, and Vercel all support static sites. For a docs site, any of them works the same way: build the HTML locally or in CI, push it to the host, and the host serves it. They're useful when you want a custom domain or when GitHub Pages and Read the Docs don't fit.

A common pattern for established projects: Read the Docs hosts the long-form docs (tutorials, guides, reference), GitHub Pages hosts the project's homepage (a single landing page), and the README on GitHub does the rest. Together they cover every audience.

<h1 id="what-to-document">What to Document</h1>

A practical checklist of what a Python project should document. Not every project needs all of these. Start small and add as users ask questions.

- **Purpose.** One paragraph at the top of the README that explains why the project exists.
- **Install.** The exact command and any prerequisites.
- **Quick start.** Ten to twenty lines of code that produces visible output.
- **Tutorial.** A 15 to 30 minute walkthrough of building something real.
- **API reference.** Auto-generated from docstrings. Every public function and class.
- **How-to guides.** One per common task. Grows over time.
- **Configuration.** Every option, with defaults and examples.
- **Changelog.** A `CHANGELOG.md` listing what changed in each release.
- **Contributing.** A `CONTRIBUTING.md` explaining how to set up the dev environment, run tests, and submit changes.
- **License.** A `LICENSE` file at the repo root. Choose one of the standard open-source licenses (MIT, Apache 2.0, BSD) unless you have a specific reason not to.

What you don't need to document: every internal helper function, every private method, every detail of the implementation. Internal code is documented by the source itself. Documentation effort should go to the public surface.

The flow matches how documentation gets used in practice. A user starts at the README, runs the tutorial, builds something, and then dips into how-to guides or the API reference when they hit specific questions. Each layer of documentation handles one stage. Skip a layer and the user can get stuck.

<h1 id="versioning-documentation">Versioning Documentation</h1>

When a project has multiple releases, the docs need to track which version they describe. A function that exists in 2.0 might not exist in 1.5, and a user on the old version needs the old docs.

Read the Docs handles this automatically. Each git tag becomes a documentation version, and the site shows a version picker so users can switch between them. The URL pattern is `cartkit.readthedocs.io/en/v1.5/` for version 1.5, `cartkit.readthedocs.io/en/latest/` for the current main branch.

Inside the docs, mark version-specific information explicitly. Sphinx has `.. versionadded::` and `.. versionchanged::` directives:

```text
.. function:: cart.add(name, price, quantity=1, tags=None)

   Add an item to the cart.

   .. versionadded:: 1.0

   .. versionchanged:: 2.0
      The ``tags`` parameter was added.
```

Markdown projects do the same thing manually:

```text
### `cart.add(name, price, quantity=1, tags=None)`

Add an item to the cart.

*Added in 1.0. `tags` parameter added in 2.0.*
```

Either form gives the reader context without forcing them to dig through a changelog.

<h1 id="living-documentation">Living Documentation</h1>

Documentation rots when it's separated from the code. You change a function signature, you forget to update the docstring, and three months later a user files a bug because the docs are wrong.

Practices that keep docs honest:

- **Docstrings live in the source code**, so a code change and a doc change happen in the same commit.
- **API reference is auto-generated**, so the signatures in the docs are always the actual signatures.
- **Code examples in docs are tested.** Sphinx's `doctest` extension and MkDocs's `pytest-markdown-docs` plugin both run the example code and fail the build if it doesn't produce the documented output.
- **Type hints catch drift.** If a docstring claims a function returns a `Cart` but the signature says `Order`, the type checker flags the mismatch before users do.

A useful rule: if the docs and the code disagree, the code is the source of truth. The fix is to update the docs, not the code. The auto-generation patterns above make this rule easier to follow, because much of the doc content comes straight from the source.

<h1 id="type-hints-as-documentation">Type Hints as Documentation</h1>

Python 3 brought type hints, and they changed what you have to write down. Before type hints, a function signature like `def add(name, price, quantity=1):` told you nothing about what types were expected. The docstring had to say "name is a string, price is a float, quantity is an int." After type hints:

```python
def add(name: str, price: float, quantity: int = 1) -> None:
    """Add an item to the cart."""
```

The signature itself tells you that `name` is a `str`, `price` is a `float`, `quantity` is an `int` (with a default of 1), and the function returns `None`. The docstring no longer needs to repeat that information; it can focus on what the function does and any non-obvious behavior.

Modern Python documentation is shorter than it used to be because of this. Type information lives in the signature, where it's checked by tools like `mypy` and `pyright`. The docstring covers what's left: the purpose, edge cases, raised exceptions, and usage notes.

A practical comparison. Before type hints, a docstring might look like:

```python
def apply_discount(price, percent):
    """Apply a percentage discount to a price.

    Args:
        price (float): The original price in dollars.
        percent (float): The discount as a decimal (0.10 for 10% off).

    Returns:
        float: The discounted price, rounded to two decimal places.
    """
    return round(price * (1 - percent), 2)
```

With type hints, the same function:

```python
def apply_discount(price: float, percent: float) -> float:
    """Apply a percentage discount to a price.

    `percent` is a decimal: pass 0.10 for 10% off, not 10.
    """
    return round(price * (1 - percent), 2)
```

The types moved into the signature, so the docstring describes only the non-obvious behavior (the decimal-not-percentage convention). The docstring got shorter, the signature got more informative, and the type checker can now catch a mistake at the call site if someone passes 10 instead of 0.10.

<h1 id="when-docs-arent-needed">When Docs Aren't Needed</h1>

Not every Python file needs documentation. The cases where less is more:

- **Private internal scripts.** A one-off script you'll throw away next week doesn't need a README. Add comments where the logic is non-obvious; skip the rest.
- **Throwaway experiments.** Jupyter notebooks for exploration, scratch files, prototypes. Don't spend time documenting code you're about to delete.
- **Tightly scoped internal tooling.** A 50-line script that converts CSVs for one specific report doesn't need a tutorial. A README with three lines is enough.
- **Implementation details of a library.** The public API gets full documentation. The private helper functions inside it get docstrings only when they're non-obvious.

The rule is to document the parts other people interact with. If a file or function is only called by code in the same repo, a docstring is enough. If something is called by other developers, other teams, or external users, it needs proper docs.

Over-documenting has a real cost. Every paragraph you write is something that has to be maintained, and an out-of-date paragraph is worse than no paragraph. Aim for the minimum that lets your users succeed, then add more when they ask for it.

**Exercise 4:** A function signature changes from `def add(name, price)` to `def add(name, price, quantity=1)`. List two ways to make sure the docs reflect the change.

<details>
<summary>Solution</summary>

**Option 1: Auto-generated API reference.** If the project uses Sphinx's `autodoc` or MkDocs's `mkdocstrings`, the reference page rebuilds on every doc build and pulls the new signature from the source automatically. No manual update needed for the signature itself.

**Option 2: Doc tests.** If the docs include example code (in a tutorial or how-to guide), tools like Sphinx's `doctest` extension or MkDocs's `pytest-markdown-docs` plugin run the examples as part of the build. If the old example used `add("headphones", 59.99)` and the new signature now expects three arguments, the example fails the build and you catch it before users do.

Both should be set up together. Auto-generation keeps the reference correct; doc tests catch broken examples in the prose.

</details>

**Exercise 7:** A project has these four docstring conventions across its files. Which one is most useful for users in 2024?

```python
def add(name, price):
    """Add an item.

    @param name: the item name (string)
    @param price: the item price (float)
    @return: None
    """
```

```python
def add(name: str, price: float) -> None:
    """Add an item to the cart."""
```

```python
def add(name, price):
    """Add an item."""
```

```python
def add(name, price):
    # Adds an item.
    pass
```

<details>
<summary>Solution</summary>

The second one. Type hints (`name: str, price: float, -> None`) carry the type information that the first version puts in `@param` tags. The docstring is short because the signature already says everything the user needs to know about types, so it can focus on the human-readable purpose. The first version duplicates information; the third leaves out the types; the fourth uses a comment where a docstring should be (a `#` comment doesn't show up in `help()` or in auto-generated docs).

The modern pattern: type hints in the signature, prose in the docstring, no overlap between them.

</details>

**Exercise 8:** A teammate proposes putting the full API reference inside the README so users don't have to leave GitHub. What's the problem with this, and what's the alternative?

<details>
<summary>Solution</summary>

The problem: the API reference for a non-trivial library can be thousands of lines, and the README is meant to be scanned in 30 seconds. Putting the reference in the README pushes the install instructions and quick-start example below the fold, so visitors leave without trying the project. It also means every signature change requires a manual README update.

The alternative: keep the README focused on the first impression (what, why, install, quick start, links) and put the API reference on the docs site, auto-generated from docstrings. GitHub doesn't render an auto-generated reference inline, so the natural home is a separate docs site (Read the Docs, GitHub Pages, etc.) linked from the README.

</details>

**Exercise 9:** A small internal script that one person on the team uses occasionally has no README and no docstrings. The script is 80 lines. Is this a problem?

<details>
<summary>Solution</summary>

Probably not. A small internal script used by one person doesn't need formal documentation. The author can read the code; nobody else is going to call it. Adding a README and docstrings for the sake of "documenting everything" is busy work that produces material no one will read.

What's worth adding even for a small script:

1. A short comment at the top explaining what the script does and how to run it (one or two lines).
2. Comments inside the script where the logic is non-obvious.

The full documentation pattern (tutorial, reference, etc.) only pays off when there are users beyond the author. The judgment call is whether a second person would ever need to understand this. If yes, document it. If no, comments are enough.

</details>

**Exercise 10:** Your library is at version 2.0. A function `cart.set_discount(percent)` existed in 1.x and was removed. A user on 1.5 reads the latest docs and is confused that `set_discount` is gone. What docs practices would prevent this?

<details>
<summary>Solution</summary>

Two practices, both common in well-maintained Python projects:

**1. Versioned documentation.** Read the Docs builds a separate docs site per git tag and shows a version picker. A user on 1.5 can switch to the 1.5 docs and see `set_discount` documented as it existed. The 2.0 docs don't show it because it's gone. The user picks their version and gets the matching docs.

**2. Deprecation notes in the docs.** Before removing `set_discount` in 2.0, the 1.x docs should have marked it as deprecated with a pointer to the replacement:

```text
### `cart.set_discount(percent)`

**Deprecated since 1.6, removed in 2.0.** Use `cart.apply_discount(percent)` instead.
```

A 2.0 changelog entry that says "Removed `set_discount`, use `apply_discount`" gives users a migration path. Combining the two helps: versioned docs let old users find their version, and deprecation notes warn current users before the breaking change lands.

</details>
