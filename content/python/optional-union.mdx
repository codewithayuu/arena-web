<h1 id="optional-means-x-or-none">Optional Means "X or None"</h1>

`Optional[X]` says a value is either an `X` or `None`. The "missing value" case shows up everywhere in Python code: dict lookups, database queries, parsed user input, function parameters that default to `None`.

```python
from typing import Optional

def find_product_name(product_id: int) -> Optional[str]:
    catalog = {1: "Wireless Mouse", 2: "USB Cable", 3: "HDMI Cable"}
    return catalog.get(product_id)

found = find_product_name(2)
missing = find_product_name(999)

print(found)
print(missing)
```

`dict.get()` returns the value for a key or `None` if the key isn't present, so `Optional[str]` captures the two possible return shapes exactly. A caller who reads the annotation knows the `None` case must be handled before assuming the return is a string.

`Optional[X]` is equivalent to `Union[X, None]`. It's a shorthand, nothing more. The two forms compile to the same internal type and the type checker treats them identically:

```python
from typing import Optional, Union

def a(x: Optional[int]) -> None: ...
def b(x: Union[int, None]) -> None: ...

print(a.__annotations__["x"])
print(b.__annotations__["x"])
print(a.__annotations__["x"] == b.__annotations__["x"])
```

Python normalizes `Union[int, None]` to `Optional[int]` because they're the same type. The name `Optional` exists purely for readability: it signals "this thing, or missing".

<h1 id="optional-doesnt-mean-optional-argument">
  Optional Doesn't Mean Optional Argument
</h1>

A common source of confusion with `Optional`. `Optional[X]` describes the value's type. It says nothing about whether the parameter has a default. A required parameter can be `Optional`, and an optional parameter (one with a default) doesn't have to be `Optional`.

```python
from typing import Optional

# Required parameter, value can be None
def log_event(event_type: str, customer_id: Optional[int]) -> None:
    suffix = "anonymous" if customer_id is None else f"customer {customer_id}"
    print(f"Event: {event_type} ({suffix})")

# Caller MUST pass something, but None is acceptable
log_event("page_view", None)
log_event("page_view", 42)
```

The caller cannot omit `customer_id` because there's no default. But the value passed is allowed to be `None`. That's a different question from "is this parameter required."

The two ideas combine in the most common pattern: a parameter that defaults to `None` and is also typed as accepting `None`.

```python
from typing import Optional

def add_to_cart(
    product: str,
    quantity: int = 1,
    note: Optional[str] = None,
) -> dict[str, int | str]:
    item: dict[str, int | str] = {"product": product, "quantity": quantity}
    if note is not None:
        item["note"] = note
    return item

print(add_to_cart("Wireless Mouse"))
print(add_to_cart("Webcam", quantity=2, note="Gift wrap, please"))
```

Here `note` is both optional (has a default) and `Optional` (allows `None`). That combination is so common that some style guides discourage `Optional[X] = something_other_than_None`. When the default isn't `None`, the type usually shouldn't include `None` either.

<h1 id="union-for-multiple-allowed-types">Union for Multiple Allowed Types</h1>

`Union[A, B]` describes a value that can be one of several types. Where `Optional[X]` is the special case of "X or None", `Union` is the general form for "any one of these".

```python
from typing import Union

def format_id(value: Union[int, str]) -> str:
    if isinstance(value, int):
        return f"ORDER-{value:05d}"
    return f"ORDER-{value.upper()}"

print(format_id(42))
print(format_id("abc"))
```

A `Union` can hold any number of types. `Union[int, str, float]` says "int or str or float". Order doesn't matter; `Union[int, str]` and `Union[str, int]` are the same type to the checker.

A common use case is a function that accepts different but related input shapes. A search function that lets the caller pass either a product name or a numeric ID is a natural fit:

```python
from typing import Union, Optional

CATALOG: dict[int, str] = {1: "Wireless Mouse", 2: "USB Cable", 3: "HDMI Cable"}

def find_product(query: Union[int, str]) -> Optional[str]:
    if isinstance(query, int):
        return CATALOG.get(query)
    for name in CATALOG.values():
        if name.lower() == query.lower():
            return name
    return None

print(find_product(2))
print(find_product("Wireless Mouse"))
print(find_product("not-real"))
```

The `Union[int, str]` parameter and `Optional[str]` return together describe the function's contract in a single signature.

<h1 id="the-pipe-operator-python-310">The Pipe Operator (Python 3.10+)</h1>

Since Python 3.10 (PEP 604), the `|` operator works on types directly, replacing both `Optional` and `Union` in most idiomatic code:

| Old form                    | New form (3.10+)      |
| --------------------------- | --------------------- |
| `Optional[str]`             | `str \| None`         |
| `Union[int, str]`           | `int \| str`          |
| `Union[int, str, float]`    | `int \| str \| float` |
| `Optional[Union[int, str]]` | `int \| str \| None`  |

The same `find_product` function in modern style:

```python
CATALOG: dict[int, str] = {1: "Wireless Mouse", 2: "USB Cable", 3: "HDMI Cable"}

def find_product(query: int | str) -> str | None:
    if isinstance(query, int):
        return CATALOG.get(query)
    for name in CATALOG.values():
        if name.lower() == query.lower():
            return name
    return None

print(find_product(2))
print(find_product("HDMI Cable"))
```

No imports. The annotation reads left to right and matches the spoken description of the type: "int or string or none".

The `|` operator works in `isinstance()` checks too, also from Python 3.10:

```python
def coerce_to_int(value: int | str | bool) -> int:
    if isinstance(value, bool):
        return 1 if value else 0
    if isinstance(value, int | str):
        return int(value)
    raise TypeError(f"Cannot coerce {type(value).__name__} to int")

print(coerce_to_int(42))
print(coerce_to_int("17"))
print(coerce_to_int(True))
```

`isinstance(value, int | str)` is shorthand for `isinstance(value, (int, str))`. Both work, but the pipe form lines up nicely with the annotation above.

For new code targeting 3.10+, prefer `|`. Libraries that still support 3.9 or older need to keep using `Optional` and `Union`, or add `from __future__ import annotations` to defer evaluation.

`from __future__ import annotations` makes all annotations strings at parse time, which means `int | None` works as a hint even on Python 3.9. The constraint: any runtime code that reads the annotation (like Pydantic) needs to use `typing.get_type_hints()` to resolve it. The same applies to forward references and any other deferred annotation.

The diagram captures the relationship. The two annotation styles produce different runtime objects (`typing.Union` for the old form, `types.UnionType` for the pipe form), but type checkers normalize them to the same logical type. Either form works; in new code, the pipe is the shorter and clearer choice.

<h1 id="when-to-use-union-and-when-not-to">
  When to Use Union and When Not To
</h1>

`Union` is not always appropriate. A type checker can only help when the types describe what the function actually accepts. Three valid cases for `Union` (or `|`):

1. **The function accepts different shapes and branches internally.** The `find_product(query: int | str)` example earlier is the canonical case. There's no single shared type, and the function does different things for each branch.
2. **A return value is one of a small set of distinct outcomes.** A parser that returns `int | float | str` depending on what it matched, for example.
3. **Modeling a result/error pattern.** `Result | Error` where each side is a structured object.

Three cases where `Union` is the wrong tool:

1. **Papering over an unclear API.** A signature like `Union[int, str, bytes, list, dict]` means the function is doing too much. Split it into separate functions, one per input shape.
2. **The "types" are actually a state machine.** When a value is "either pending or processed", a dataclass with a status field is clearer than `Pending | Processed` (though discriminated unions, covered below, are sometimes the right answer here).
3. **`Any` was the intent.** `Union[X, Y, Z]` and `Any` look similar, but `Union` keeps the checker working: narrowing is required before calling type-specific methods. `Any` turns the checker off entirely. A `Union` written because the type was unclear usually signals `Any` was the intent, and something deeper is wrong.

The general rule: keep unions narrow. Two or three types is fine. A union of six types is a signature smell.

<h1 id="handling-optional-values-safely">Handling Optional Values Safely</h1>

A value typed `X | None` cannot be used as if it were just `X`. The type checker will reject any operation that would fail on `None`. The type must be narrowed first.

The standard approach is an explicit check. After the check, the checker knows the value can't be `None` in the relevant branch:

```python
def greet_customer(customer: str | None) -> str:
    if customer is None:
        return "Hello, guest"
    return f"Hello, {customer.upper()}"

print(greet_customer("Alice"))
print(greet_customer(None))
```

Inside the `if customer is None:` branch, the checker knows `customer` is `None`. After the early return, the checker knows it's a `str`, which is why `.upper()` is allowed without complaint.

For the common case of "use the value if it exists, otherwise fall back", the `or` operator and the conditional expression work well:

```python
def display_name(customer: str | None) -> str:
    return customer or "Guest"

def total_with_default(value: float | None, default: float) -> float:
    return value if value is not None else default

print(display_name("Alice"))
print(display_name(None))
print(display_name(""))  # empty string is falsy
print(total_with_default(99.99, 0.0))
print(total_with_default(None, 0.0))
```

`customer or "Guest"` works because `None` is falsy. The constraint: empty strings and `0` are also falsy, so `display_name("")` returns `"Guest"`, which may not be the intended behavior. When the type allows `None` and also a "real" falsy value like `""` or `0`, use the explicit `is None` check instead of `or`.

The walrus operator (`:=`, Python 3.8+) is useful for looking up a value and using it only if found, without naming it twice:

```python
CATALOG: dict[int, str] = {1: "Wireless Mouse", 2: "USB Cable"}

def announce_product(product_id: int) -> str:
    if (name := CATALOG.get(product_id)) is not None:
        return f"Found: {name}"
    return f"Product {product_id} not in catalog"

print(announce_product(1))
print(announce_product(99))
```

`CATALOG.get(product_id)` is called once. The walrus binds the result to `name`, and the `is not None` check narrows the type inside the body. Without the walrus, the alternative is either calling `.get()` twice or assigning on a separate line.

For deeply nested optional access, the pattern can get noisy. Five `if x is not None` checks in a row suggests the data model could be flatter, or that a tool like `dataclasses` with non-optional fields could replace the chain of optional lookups.

<h1 id="type-narrowing-with-isinstance">Type Narrowing with isinstance</h1>

A union of unrelated types needs `isinstance` checks to tell the checker which branch applies. Inside an `isinstance(value, T)` block, the checker narrows the type to `T`:

```python
def render_price(price: int | float | str) -> str:
    if isinstance(price, int):
        return f"${price}.00"
    if isinstance(price, float):
        return f"${price:.2f}"
    return f"${price}"

print(render_price(20))
print(render_price(19.99))
print(render_price("free"))
```

After `if isinstance(price, int):`, the checker treats `price` as `int` inside that branch. After the early return, the checker knows `price` is `float | str`. After the second `isinstance`, it's narrowed to `float`. The final `return` line is reached only when `price` is a `str`, and the checker tracks that automatically.

The same narrowing happens with `is None` checks (as shown above) and with comparisons against literal values (covered next). The general name for this is "type narrowing", and it's what makes unions usable: the checker watches the control flow and removes types from the union as they are eliminated.

<h1 id="discriminated-unions-with-literal">
  Discriminated Unions with Literal
</h1>

`Literal` (from `typing`, Python 3.8+) restricts a value to one of a set of exact constants. Combined with `Union`, it produces what's called a discriminated union: a union of types that each carry a tag field, where the tag tells the checker which variant the value holds.

```python
from typing import Literal

OrderStatus = Literal["placed", "shipped", "delivered", "cancelled"]

def status_message(status: OrderStatus) -> str:
    if status == "placed":
        return "Your order is being prepared."
    if status == "shipped":
        return "Your order is on the way."
    if status == "delivered":
        return "Your order has arrived."
    return "Your order was cancelled."

print(status_message("shipped"))
print(status_message("placed"))
```

`Literal["placed", "shipped", "delivered", "cancelled"]` is the type of any one of those four exact strings. A caller passing `"in_transit"` gets a type-checker error, because that string isn't in the literal set. At runtime nothing is enforced, but the static check catches typos before they ship.

The "discriminated" part comes in when each variant carries a tag plus extra fields:

```python
from typing import Literal
from dataclasses import dataclass

@dataclass
class CardPayment:
    kind: Literal["card"]
    last_four: str

@dataclass
class CashPayment:
    kind: Literal["cash"]
    received: float

Payment = CardPayment | CashPayment

def confirmation(payment: Payment) -> str:
    if payment.kind == "card":
        return f"Charged card ending in {payment.last_four}"
    return f"Received ${payment.received:.2f} cash"

print(confirmation(CardPayment(kind="card", last_four="4242")))
print(confirmation(CashPayment(kind="cash", received=50.0)))
```

Inside `if payment.kind == "card":`, the checker narrows `payment` from `CardPayment | CashPayment` to just `CardPayment`. This is why `payment.last_four` is allowed: the narrowed type has that attribute. Without the discriminator, the checker would only allow access to fields that both types share.

This pattern is the bedrock of modeling state machines, event types, and parser results. Each variant has its own structured fields, and the tag tells the type checker which one is held.

<h1 id="common-mypy-errors-with-optional">Common mypy Errors with Optional</h1>

When running a type checker over Optional-heavy code, certain errors come up over and over.

**Error 1: calling a method on a value that might be None.**

```python
def first_word(text: str | None) -> str:
    return text.split()[0]
```

mypy reports:

```text
error: Item "None" of "str | None" has no attribute "split"  [union-attr]
```

The fix is to narrow first, either by checking `is None` and handling it, or by raising an exception:

```python
def first_word(text: str | None) -> str:
    if text is None:
        raise ValueError("text must not be None")
    return text.split()[0]
```

**Error 2: assigning `None` where the type doesn't allow it.**

```python
def reset_total() -> float:
    total: float = 0.0
    total = None  # error
    return total
```

mypy reports:

```text
error: Incompatible types in assignment (expression has type "None", variable has type "float")  [assignment]
```

The fix is to widen the type when `None` is genuinely valid, or to use a different sentinel (like `-1.0` or `float("nan")`) otherwise:

```python
def reset_total() -> float | None:
    total: float | None = 0.0
    total = None
    return total
```

**Error 3: implicit Optional from a `None` default.**

```python
def add_note(note: str = None) -> None:
    if note:
        print(note)
```

In older versions of mypy this was accepted without warning; modern versions (and `strict` mode) reject it because the annotation says `str` but the default is `None`. The fix is to make the type honest:

```python
def add_note(note: str | None = None) -> None:
    if note:
        print(note)
```

The general lesson: when `None` is a possible value, say so in the type. The checker will then require handling it everywhere the value is used.

<h1 id="alternatives-typeddict-and-dataclasses">
  Alternatives: TypedDict and Dataclasses
</h1>

A union of dictionaries is a code smell, even when each variant has a Literal discriminator. The reason: dictionaries can be misspelled. `payment["last_four"]` versus `payment["last4"]` is a runtime error in waiting. Two structured-data alternatives keep the same shape but get more help from the type checker.

`TypedDict` describes a dict's exact keys and value types:

```python
from typing import TypedDict, Literal

class CardPayment(TypedDict):
    kind: Literal["card"]
    last_four: str

class CashPayment(TypedDict):
    kind: Literal["cash"]
    received: float

Payment = CardPayment | CashPayment

def confirmation(payment: Payment) -> str:
    if payment["kind"] == "card":
        return f"Card ending in {payment['last_four']}"
    return f"Cash: ${payment['received']:.2f}"

print(confirmation({"kind": "card", "last_four": "4242"}))
print(confirmation({"kind": "cash", "received": 50.0}))
```

`TypedDict` is suited to JSON, database rows, or other dict-shaped data that can't be replaced with proper classes. The type checker validates keys and value types, like it would for a class.

Dataclasses are the alternative when the shape is under control and a class can be introduced. They provide attribute access, proper equality, and a constructor without extra code. The discriminated-union example earlier in this lesson used dataclasses for this reason.

The shorthand version of the trade-off: `TypedDict` for dict-shaped data received from outside (JSON, DB rows, third-party APIs), dataclasses for shaped data created in code under control. Both work with `|` unions for variants.
