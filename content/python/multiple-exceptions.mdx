<h1 id="multiple-except-clauses-on-one-try">
  Multiple except Clauses on One try
</h1>

A single `try` block can be followed by as many `except` clauses as needed. Python checks them top to bottom and runs the first one whose type matches the raised exception. Anything that doesn't match propagates out as if no `try` were there.

```python
def get_price(catalog, product, quantity_str):
    try:
        price = catalog[product]
        quantity = int(quantity_str)
        return price * quantity
    except KeyError:
        print(f"'{product}' is not in the catalog")
        return 0.0
    except ValueError:
        print(f"'{quantity_str}' is not a valid quantity")
        return 0.0

catalog = {"Wireless Mouse": 29.99, "HDMI Cable": 14.99}
print(get_price(catalog, "Wireless Mouse", "2"))
print(get_price(catalog, "USB Hub", "1"))
print(get_price(catalog, "Wireless Mouse", "two"))
```

Three calls, three different paths through the same block. The first one finds the product, parses the quantity, and returns the line total. The second one hits the dict lookup first, so the `KeyError` handler runs and the rest of the `try` body never executes. The third one passes the lookup but fails on `int("two")`, which raises `ValueError` and lands in the second handler.

Each `except` handles exactly one kind of failure. Splitting them like this keeps the function readable: a reader can scan the handlers and see which problems the function knows how to recover from, and what it does in each case. A single combined handler would force the reader to dig through conditional logic to figure out the same thing.

Adding more `except` clauses costs nothing on the happy path. Python only walks the list when something is actually raised, and the search is fast.

<h1 id="grouping-types-in-a-tuple">Grouping Types in a Tuple</h1>

If two or more exception types should be handled the same way, write them as a tuple inside one `except`. This avoids copy-pasted handler bodies.

```python
def get_first_review(reviews):
    try:
        return reviews[0]["text"]
    except (IndexError, KeyError, TypeError):
        return "No review available"

print(get_first_review([{"text": "Great mouse"}]))
print(get_first_review([]))
print(get_first_review([{"rating": 5}]))
print(get_first_review(None))
```

Four different inputs, four different outcomes. The full review object returns its text. The empty list raises `IndexError`. The review without a `"text"` key raises `KeyError`. The `None` raises `TypeError` because `NoneType` is not subscriptable. All three failures fall into the same `except` and produce the same fallback string.

The parentheses around the types are required. `except IndexError, KeyError:` was old Python 2 syntax for `except IndexError as KeyError:`, and it doesn't work in Python 3 at all. The modern form is always `except (Type1, Type2):` with a tuple.

Use the tuple form when the response is the same for every type. If the handler body contains an `isinstance` check on the exception to branch on its type, separate clauses are a better fit.

<h1 id="why-order-matters-specific-before-parent">
  Why Order Matters: Specific Before Parent
</h1>

When multiple `except` clauses are stacked, Python walks them in source order and stops at the first match. Because catching a class also catches its subclasses, putting a broad parent class above a narrower child class makes the child handler unreachable.

The relevant corner of the exception hierarchy looks like this:

`KeyError` and `IndexError` are both subclasses of `LookupError`, which is a subclass of `Exception`. So `except LookupError:` catches both, and `except Exception:` catches every class in this diagram.

The trap that follows from this:

```python
catalog = {"Wireless Mouse": 29.99}

try:
    price = catalog["USB Hub"]
except Exception:
    print("General handler ran")
except KeyError:
    print("Specific handler ran")
```

The second handler is dead code. `KeyError` inherits from `Exception`, so the broad clause matches first and Python never checks the narrower one. CPython doesn't raise an error or a warning for this. Static checkers like ruff and pylint flag it, but only when those tools are run.

Flipping the order makes both handlers reachable:

```python
catalog = {"Wireless Mouse": 29.99}

try:
    price = catalog["USB Hub"]
except KeyError:
    print("Specific handler ran")
except Exception:
    print("General handler ran")
```

Now `KeyError` matches the first clause. A different exception type, say a `TypeError` from a bad operation later in the `try`, would skip the first clause and fall through to the second.

The rule is short: **most specific first, most general last.** When stacking three or four handlers, sort them from narrowest type to widest. A final `except Exception:` safety net belongs at the bottom.

A more realistic version with three layers, each stricter than the one below it:

```python
def update_stock(inventory, product, delta):
    try:
        inventory[product] += delta
    except KeyError:
        print(f"'{product}' not in inventory, adding it")
        inventory[product] = delta
    except TypeError:
        print(f"inventory must be a dict, got {type(inventory).__name__}")
    except Exception as e:
        print(f"unexpected failure: {type(e).__name__}: {e}")

stock = {"Wireless Mouse": 5}
update_stock(stock, "Wireless Mouse", 2)
update_stock(stock, "HDMI Cable", 3)
update_stock("not a dict", "Wireless Mouse", 1)
print(stock)
```

The first call updates an existing product cleanly. The second misses on the lookup, lands in `KeyError`, and adds the new product. The third hits `TypeError` because strings don't support item assignment. If any fourth scenario raised something not listed (say a `MemoryError`), the final `except Exception` would catch it as a safety net. That last clause isn't strictly necessary; one alternative is to leave unexpected errors uncaught so they surface as real bugs. Either way, the ordering rule still holds.

<h1 id="catch-all-handlers-except-exception-and-bare-except">
  Catch-All Handlers: except Exception and Bare except
</h1>

Two patterns look similar but behave very differently. One is a reasonable last-resort net. The other is almost always a bug.

`except Exception:` catches every exception class that inherits from `Exception`, which covers the vast majority of errors in normal code: `ValueError`, `KeyError`, `TypeError`, `RuntimeError`, custom application exceptions, and so on. It does **not** catch `KeyboardInterrupt` (raised when the user presses Ctrl+C), `SystemExit` (raised by `sys.exit()`), or `GeneratorExit` (used internally for generator cleanup). Those three inherit from `BaseException` directly, on a separate branch of the tree, and they're meant to flow through normal handlers without being absorbed.
