<h1 id="the-four-ways-to-read-a-text-file">
  The Four Ways to Read a Text File
</h1>

A text file opened with `open(path, "r", encoding="utf-8")` gives you a file object with several read-flavored methods. They differ in how much they read at once and what they return.

| Method          | Reads                   | Returns           | Memory cost                    |
| --------------- | ----------------------- | ----------------- | ------------------------------ |
| `f.read()`      | The whole file          | One `str`         | Entire file in memory          |
| `f.read(size)`  | Up to `size` characters | `str`             | One chunk in memory            |
| `f.readline()`  | One line                | `str` (with `\n`) | One line in memory             |
| `f.readlines()` | The whole file          | `list[str]`       | Entire file plus list overhead |
| `for line in f` | One line per iteration  | `str` (with `\n`) | One line in memory             |

Five rows, four ideas. The last two (iterating the file object and calling `readline` in a loop) do the same thing internally, but iteration is the idiomatic Python form.

The same product file read four different ways:

```python
with open("products.txt", "w", encoding="utf-8") as f:
    f.write("mug,12.99\nnotebook,7.49\npen,1.99\n")

with open("products.txt", "r", encoding="utf-8") as f:
    print("read():", repr(f.read()))

with open("products.txt", "r", encoding="utf-8") as f:
    print("readline():", repr(f.readline()))

with open("products.txt", "r", encoding="utf-8") as f:
    print("readlines():", f.readlines())

with open("products.txt", "r", encoding="utf-8") as f:
    for line in f:
        print("iterate:", repr(line))
```

Every read includes the trailing `\n` from each line. You strip those yourself, usually with `rstrip()` or `splitlines()`. `readlines()` returns a list of strings, which means every line lives in memory at once, the same as `read()`. Iterating the file object yields one line at a time and never holds the whole file in memory.

That last property is what makes the iteration form the default. Use it unless there's a specific reason to do otherwise.

<h1 id="read-slurp-the-whole-file">read(): Slurp the Whole File</h1>

`f.read()` with no argument returns the entire contents of the file as a single `str`. It's the simplest method and fits when the file is small enough that "all of it in memory" is fine.

```python
with open("greeting.txt", "w", encoding="utf-8") as f:
    f.write("Welcome to the store\nOpen 9 to 9 every day\n")

with open("greeting.txt", "r", encoding="utf-8") as f:
    content = f.read()

print(type(content))
print(content)
```

For a 200-byte file like this one, slurping is fine. For a 200 MB log file, it allocates 200 MB of `str` and pegs your memory. For a 20 GB file, it crashes.

`f.read()` allocates a `str` the size of the file. A 1 GB log file means roughly 1 GB of Python memory while you process it. For files larger than a few hundred megabytes, iterate the file object instead.

Two practical use cases for `read()`:

- **Config and small data files.** A 5 KB JSON config, a CSV with 50 rows, a small Markdown file. The simplicity wins.
- **One-pass transformations.** When you need to feed the entire content to a parser at once (like `json.loads` or `xml.etree.ElementTree.fromstring`), you have to slurp anyway. Read it, parse it, throw it away.

For everything else, prefer the streaming forms.

`read()` has a positional argument too: `read(size)` returns up to `size` characters in text mode (or up to `size` bytes in binary mode). It's how you do chunked reads when you want bounded memory but don't want to deal with line boundaries:

```python
with open("greeting.txt", "r", encoding="utf-8") as f:
    chunk = f.read(10)
    print(repr(chunk))
    chunk = f.read(10)
    print(repr(chunk))
```

Each call advances the cursor. When you hit the end of the file, `read(size)` returns an empty string, which is the signal to stop. Chunked reads come up again later in this lesson with binary files and large file processing.

<h1 id="readline-one-line-at-a-time">readline(): One Line at a Time</h1>

`f.readline()` reads up to and including the next `\n` (or to the end of the file, whichever comes first) and returns it as a `str`. The newline character is kept in the result. When there's nothing left to read, it returns an empty string.

```python
with open("orders.txt", "w", encoding="utf-8") as f:
    f.write("order-1: mug\norder-2: notebook\norder-3: pen\n")

with open("orders.txt", "r", encoding="utf-8") as f:
    print(repr(f.readline()))
    print(repr(f.readline()))
    print(repr(f.readline()))
    print(repr(f.readline()))  # past end of file
```

The empty string after the last line is the end-of-file signal. This is the loop pattern you'd use if you wanted explicit control over reading:

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    while True:
        line = f.readline()
        if not line:
            break
        print(line.rstrip())
```

That works, but it's clunky. Python already gives you iteration over file objects, which does the same thing in one line. `readline()` directly fits two niche cases: reading the header from a file without consuming the body, or implementing a custom parser that needs to peek ahead and back off.

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    header = f.readline()
    print("header:", header.rstrip())
    body = f.read()
    print("body bytes:", len(body))
```

The first `readline` consumes only the first line. The `read` after it picks up from wherever the cursor sits, which is right after the first newline. Mixing reads on a single file object is allowed; the cursor moves with each call.

<h1 id="readlines-the-one-you-probably-shouldnt-use">
  readlines(): The One You Probably Shouldn't Use
</h1>

`f.readlines()` reads the entire file and returns a list of strings, one per line. Newlines are kept in each string, same as `readline()`.

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    lines = f.readlines()

print(type(lines))
print(lines)
print(lines[1].rstrip())
```

This looks convenient, and for small files it is. The problem is memory. `readlines()` keeps every line in a list, so a 1 GB log file becomes a 1 GB string buffer plus the per-string overhead of millions of small `str` objects. The per-object cost adds up: each `str` carries a header of around 50 bytes on CPython, so a file of 10 million short lines may use more memory as a list of strings than the file's size on disk.

The motivation for `readlines()` is usually "I want to iterate the lines." But iterating the file object already does that, line by line, without building the list. Compare:

```python
# Materializes all lines in memory.
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f.readlines():
        print(line.rstrip())

# Yields one line at a time, never holds the full file in memory.
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f:
        print(line.rstrip())
```

Both produce the same output. The second form is strictly better for any file larger than "small". Use `readlines()` only when you need the list, like when you need random access to lines by index or want to process the file twice without reopening it.

`readlines()` reads the entire file and constructs a list of `str` objects. Memory usage is roughly the file size plus 50 bytes of overhead per line. For a 10 GB log, that's 10 GB plus the list overhead.

<h1 id="iterating-the-file-object-the-idiomatic-pattern">
  Iterating the File Object: The Idiomatic Pattern
</h1>

A file object opened in text mode is iterable, and iterating it yields one line per step. This is the idiomatic Python form and the one to use first.

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f:
        order_id, item = line.rstrip().split(": ")
        print(f"{order_id} ordered {item}")
```

Three properties make this the default:

- It uses constant memory regardless of file size. Only one line lives in memory at a time.
- It's the shortest form. No method call, no `while True`, no end-of-file check.
- It composes with the rest of the iteration tooling in Python: `enumerate(f)`, `zip(f1, f2)`, generator expressions, `itertools` functions.

`enumerate` is handy when you want the line number along with the content:

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    for line_number, line in enumerate(f, start=1):
        print(f"{line_number}: {line.rstrip()}")
```

And for many real tasks, the parsing fits in a generator expression or a comprehension:

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    totals = [int(line.split(": item-")[1]) for line in f if "item-" in line]

# (Example with a different file that has "order-N: item-K" format.)
```

The file object behaves like any other iterable. Once that's clear, file processing is another form of "iterate and transform."

The diagram traces what happens when you iterate a file object. Python keeps a buffer in memory (typically 8 KB) and reads from disk in chunks. Each step of the loop scans the buffer for the next `\n`, yields the line up to and including that newline, and refills the buffer when needed. The full file never sits in memory at once. End-of-file raises `StopIteration` internally, which is how `for` loops know to stop.

<h1 id="stripping-newlines">Stripping Newlines</h1>

Every line returned by `readline`, `readlines`, or file iteration includes the trailing `\n` (or `\r\n` on Windows files read in binary mode). Usually you want it gone before processing the content.

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f:
        print(repr(line))           # with newline
        print(repr(line.rstrip()))  # without
        break
```

Three string methods come up here:

| Method              | What it strips                               | When to use                                                  |
| ------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| `line.rstrip()`     | Trailing whitespace (newlines, spaces, tabs) | Default. Handles `\n`, `\r\n`, and stray trailing spaces.    |
| `line.rstrip("\n")` | Trailing `\n` only                           | When trailing spaces are meaningful data.                    |
| `line.strip()`      | Leading and trailing whitespace              | When the format allows leading indentation you want to drop. |

For most product data and log lines, `line.rstrip()` fits. It handles all three line-ending styles (`\n`, `\r\n`, `\r`) and also strips trailing spaces.

If you want all the lines as a list of clean strings (without writing a comprehension), the `splitlines()` method on the whole-file string is a one-liner:

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    lines = f.read().splitlines()

print(lines)
```

`splitlines()` is smart about line endings: it handles `\n`, `\r\n`, and `\r` all the same way, and it doesn't keep the separator. The trade-off is that you've slurped the whole file, which is fine for small files and wrong for huge ones.

<h1 id="reading-by-chunks-readsize">Reading by Chunks: read(size)</h1>

When you don't want to load the whole file at once but you also don't care about line boundaries, `read(size)` reads up to `size` characters in text mode (or bytes in binary mode). It fits binary files, files that aren't line-oriented (like a long XML document), and streaming-style processing.

```python
with open("greeting.txt", "w", encoding="utf-8") as f:
    f.write("Welcome to the store, open 9 to 9 every day, free shipping on orders over $50.\n")

with open("greeting.txt", "r", encoding="utf-8") as f:
    while True:
        chunk = f.read(20)
        if not chunk:
            break
        print(repr(chunk))
```

Each call reads up to 20 characters and advances the cursor. The last call returns a short chunk because the file didn't have a full 20 characters left. The call after that returns an empty string, which is the end-of-file signal.

In text mode, the `size` is a character count, not a byte count, and Python takes care of not splitting a multi-byte UTF-8 character across two chunks. In binary mode, `size` is a byte count and there's no character awareness; you can split anything, anywhere.

```python
with open("greeting.txt", "rb") as f:
    chunk = f.read(20)
    print(chunk)
    print(len(chunk))
```

Binary chunked reads are how you process large media files, network downloads, or anything where you want to push data through in fixed-size pieces.

<h1 id="binary-reads">Binary Reads</h1>

For non-text files (images, PDFs, compiled archives), open the file with `"rb"` and read `bytes` instead of `str`.

```python
with open("logo.png", "wb") as f:
    f.write(b"\x89PNG\r\n\x1a\n" + b"\x00" * 100)

with open("logo.png", "rb") as f:
    header = f.read(8)

print(header)
print(header == b"\x89PNG\r\n\x1a\n")
```

The first 8 bytes of every PNG file are the same. Reading them gives you a fast way to verify the file type without parsing the rest. That kind of header check is what binary chunked reads are designed for.

Binary reads have a few practical differences from text reads:

- The size argument is bytes, not characters.
- There's no encoding, no decoding, no `UnicodeDecodeError`. Bytes go in, bytes come out.
- There's no line-ending translation. A `\r\n` in the file stays `b'\r\n'` in memory.
- Iteration still works, splitting on `\n` bytes, but binary files often aren't line-oriented in a useful way, so iteration is less common.

The takeaway: text mode for human-readable formats, binary mode for everything else.

<h1 id="reading-large-files-efficiently">Reading Large Files Efficiently</h1>

A common mistake with file reading is calling `read()` or `readlines()` on a file too big to fit in memory. The fix is almost always the same: iterate.

Consider a 4 GB log file with around 50 million lines. Three ways to count lines that contain the word `"error"`:

```python
# Wrong: tries to load 4 GB into memory.
with open("server.log", "r", encoding="utf-8") as f:
    text = f.read()
    print(text.count("\nerror"))

# Wrong-but-slightly-better: still loads all 50 million strings.
with open("server.log", "r", encoding="utf-8") as f:
    print(sum(1 for line in f.readlines() if "error" in line))

# Right: constant memory.
with open("server.log", "r", encoding="utf-8") as f:
    print(sum(1 for line in f if "error" in line))
```

The first form allocates a 4 GB string. The second form materializes a list of 50 million strings (which costs more memory than the file itself, because each `str` carries object overhead). The third form keeps one line in memory at a time.

The same principle applies to binary files. To hash a large file, read in fixed-size chunks:

```python
import hashlib

def file_hash(path, chunk_size=1024 * 1024):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while True:
            chunk = f.read(chunk_size)
            if not chunk:
                break
            h.update(chunk)
    return h.hexdigest()

print(file_hash("logo.png"))
```

The function never holds more than `chunk_size` bytes in memory regardless of the file's total size. 1 MB chunks are a reasonable default for large-file work; smaller chunks waste time on extra system calls, larger ones use more memory than necessary.

<h3 id="memory-benchmark-slurp-vs-iterate">
  Memory Benchmark: Slurp vs Iterate
</h3>

To make the cost concrete, run this benchmark. Generate a 100 MB text file, then process it two ways and watch resident memory.

```python
import os
import resource  # POSIX only; use psutil on Windows.

# 1. Generate the file.
with open("big.txt", "w", encoding="utf-8") as f:
    for i in range(1_000_000):
        f.write(f"order-{i}: mug\n")

print("file size:", os.path.getsize("big.txt"), "bytes")

# 2. Slurp.
with open("big.txt", "r", encoding="utf-8") as f:
    data = f.read()
    peak = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    print("after slurp, peak memory:", peak, "kb")

# 3. Iterate.
with open("big.txt", "r", encoding="utf-8") as f:
    for line in f:
        pass
    peak = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    print("after iterate, peak memory:", peak, "kb")
```

The "after iterate" memory is barely higher than the baseline because nothing accumulated. The "after slurp" memory includes the entire file as a `str`. On a 20 MB file that's not catastrophic; on a 2 GB file you'd see the difference between "runs fine" and "out of memory."

Iterating a file object reads from an 8 KB buffer in memory. Slurping reads the entire file. The wall-clock difference is small for small files and large for large ones. When in doubt, iterate.

<h1 id="encoding-errors-and-the-errors-parameter">
  Encoding Errors and the errors Parameter
</h1>

Text mode decodes bytes into `str` using the encoding you specified. When the bytes don't match the encoding, you get `UnicodeDecodeError`.

```python
# Write some UTF-8 bytes that include a French accent.
with open("french.txt", "wb") as f:
    f.write("Customer: RenÃ©e MÃ¼ller\n".encode("utf-8"))

# Try to read it as ASCII.
with open("french.txt", "r", encoding="ascii") as f:
    print(f.read())
```

ASCII only knows the first 128 code points. The byte `0xc3` (the first byte of UTF-8's encoding of `Ã©`) is outside that range, so the decoder gives up.

The ideal fix is to use the correct encoding. Pass `encoding="utf-8"` to the read and the file decodes cleanly. But sometimes you don't control the input: a partner system sends a CSV in mixed encoding, a log file has occasional binary garbage, a user uploaded a file labeled wrong. For those cases, the `errors` argument to `open` tells Python what to do when a byte can't be decoded.

| `errors=` value      | What happens on a bad byte                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| `"strict"` (default) | Raise `UnicodeDecodeError`.                                                                                |
| `"replace"`          | Substitute a Unicode replacement character (`U+FFFD`, displayed as `?` in many fonts).                     |
| `"ignore"`           | Drop the byte silently.                                                                                    |
| `"backslashreplace"` | Replace with the `\xNN` escape, preserving the byte value as text.                                         |
| `"surrogateescape"`  | Map each bad byte to a private-use code point that round-trips back to the original byte if you re-encode. |

The first three are the most commonly used.

```python
with open("french.txt", "r", encoding="ascii", errors="replace") as f:
    print(f.read())

with open("french.txt", "r", encoding="ascii", errors="ignore") as f:
    print(f.read())

with open("french.txt", "r", encoding="ascii", errors="backslashreplace") as f:
    print(f.read())
```

`"replace"` substitutes a placeholder, which makes the bad data visible without crashing. `"ignore"` drops the bad bytes and merges the surrounding characters, which can produce text that looks normal but has lost information. `"backslashreplace"` keeps every byte in some form, which is the safest choice for logs and diagnostics.

None of these substitutes for picking the correct encoding. They're escape hatches for processing messy input where crashing isn't acceptable, like log analysis pipelines that have to handle gigabytes of mixed-encoding data without stopping.

<h1 id="common-patterns">Common Patterns</h1>

A few real-world reading patterns that come up often.

<h3 id="line-by-line-processing">Line-by-Line Processing</h3>

The most common case: read a text file one line at a time, transform each line, accumulate results.

```python
with open("orders.txt", "w", encoding="utf-8") as f:
    f.write("mug,12.99\nnotebook,7.49\npen,1.99\n")

totals = {}
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f:
        name, price = line.rstrip().split(",")
        totals[name] = float(price)

print(totals)
```

The pattern is always the same: open in a `with` block, iterate the file, `rstrip` the newline, split or parse the line, store the result. For CSV files specifically, the `csv` module is better than `split`.

<h3 id="parsing-csv-like-text-by-hand">Parsing CSV-Like Text by Hand</h3>

Before the `csv` module, this is what you'd write for simple files where every row has the same shape and no commas inside fields:

```python
with open("products.csv", "w", encoding="utf-8") as f:
    f.write("name,price,stock\n")
    f.write("mug,12.99,40\n")
    f.write("notebook,7.49,150\n")

with open("products.csv", "r", encoding="utf-8") as f:
    header = f.readline().rstrip().split(",")
    for line in f:
        values = line.rstrip().split(",")
        row = dict(zip(header, values))
        print(row)
```

This works for clean inputs. The moment a product name has a comma in it (`"mug, large"`), the hand-rolled split breaks. That's what the `csv` module is for. Use this pattern only when you control the data format and know it's simple.

<h3 id="reading-config-files">Reading Config Files</h3>

Small text-based config files (the old `.ini` or simple `key=value` style) follow the same pattern as line-by-line processing, with a bit of structure.

```python
with open("store.conf", "w", encoding="utf-8") as f:
    f.write("# Store config\n")
    f.write("currency=USD\n")
    f.write("tax_rate=0.08\n")
    f.write("free_shipping_threshold=50\n")

config = {}
with open("store.conf", "r", encoding="utf-8") as f:
    for line in f:
        line = line.rstrip()
        if not line or line.startswith("#"):
            continue
        key, _, value = line.partition("=")
        config[key.strip()] = value.strip()

print(config)
```

`partition` is a useful alternative to `split` here: it splits on the first occurrence of the separator, so `"key=value=with=equals"` becomes `("key", "=", "value=with=equals")` instead of being mangled. For anything more complex than a flat key-value file, use the `configparser` standard library module instead.

<h1 id="common-mistakes">Common Mistakes</h1>

A few recurring mistakes worth listing.

<h3 id="forgetting-to-strip-the-newline">Forgetting to Strip the Newline</h3>

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    for line in f:
        if line == "mug":  # never matches!
            print("found")
```

The lines read from a file end in `\n`. `"mug\n" == "mug"` is `False`. Always `rstrip` (or `splitlines` on a slurped string) before comparing.

<h3 id="calling-read-twice-on-the-same-file">
  Calling read() Twice on the Same File
</h3>

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    first = f.read()
    second = f.read()

print(repr(first))
print(repr(second))
```

The first `read` consumed the file. The cursor is at the end, so the second `read` returns nothing. The same issue applies when iterating a file and then trying to iterate it again in the same `with` block:

```python
with open("orders.txt", "r", encoding="utf-8") as f:
    print(sum(1 for _ in f))   # 3
    print(sum(1 for _ in f))   # 0
```

If you need to re-read, either reopen the file or call `f.seek(0)` to move the cursor back to the start.

<h3 id="using-readlines-for-counting">Using readlines() for Counting</h3>

```python
with open("server.log", "r", encoding="utf-8") as f:
    print(len(f.readlines()))
```

This works, but it loads the whole file into a list to take the list's length. `sum(1 for _ in f)` does the same thing in constant memory.

<h3 id="reading-a-binary-file-in-text-mode">
  Reading a Binary File in Text Mode
</h3>

```python
with open("logo.png", "r", encoding="utf-8") as f:
    f.read()
```

PNG, JPEG, PDF, and most other binary formats start with bytes that aren't valid in any text encoding. Open them with `"rb"`.
