<h1 id="why-pathlib-exists">Why pathlib Exists</h1>

The classic way to build a path looks innocent until you actually try to use it across platforms.

```python
import os

base = "exports"
customer_id = "C-4821"
filename = "orders.csv"

path = base + "/" + customer_id + "/" + filename
print(path)
```

That works on macOS and Linux. On Windows, the path separator is `\`, and the same code produces something the operating system might still accept, but mixing styles is fragile. The `os.path.join` function fixes the separator issue, but you still get a string back, which means everything you want to do next, including checking whether the path exists, reading its contents, or pulling out the file extension, lives in a different module and a different function.

`pathlib`, added in Python 3.4, replaces that scattered toolkit with one type. A `Path` is an object that represents a filesystem path; it has methods for inspection, methods for I/O, and an overloaded `/` operator for joining. Everything you used to call `os.path.something(path_string)` to do, you now call as `path.something()`.

```python
from pathlib import Path

base = Path("exports")
customer_id = "C-4821"
filename = "orders.csv"

path = base / customer_id / filename
print(path)
print(type(path))
```

The output type is `PosixPath` on macOS and Linux and `WindowsPath` on Windows. You don't pick the concrete subclass yourself; `Path()` returns the right one for the OS you're running on. The string form of the path uses the platform's native separator, so the same code prints `exports\C-4821\orders.csv` on Windows without any conditional logic.

<h1 id="constructing-paths">Constructing Paths</h1>

`Path()` accepts a string, multiple strings, another `Path`, or any object that implements `__fspath__`. When you pass multiple arguments, it joins them using the platform separator.

```python
from pathlib import Path

p1 = Path("exports/orders.csv")
p2 = Path("exports", "orders.csv")
p3 = Path(Path("exports"), "orders.csv")

print(p1)
print(p2)
print(p3)
print(p1 == p2 == p3)
```

All three constructions produce equal paths. The multi-argument form is convenient when the parts are already separate variables; the slash operator (covered in the next section) is the most readable form when you want to compose a path inline.

Two helpers give you well-known anchor points without hardcoding strings:

```python
from pathlib import Path

print(Path.cwd())
print(Path.home())
```

`Path.cwd()` returns the current working directory the program was launched from. `Path.home()` returns the current user's home directory. Both return `Path` objects, so you can immediately compose further with `/`.

```python
from pathlib import Path

uploads = Path.home() / "Pictures" / "product-uploads"
print(uploads)
```

> **Cost:** `Path.cwd()` calls `os.getcwd()` under the hood, which is a system call. It's cheap, but don't call it in a tight loop; capture the result in a variable and reuse it.

<h1 id="joining-paths-with-the-operator">Joining Paths with the / Operator</h1>

`pathlib` overloads `/` so you can join paths the same way you'd write them on a command line.

```python
from pathlib import Path

product_id = "P-9217"
images_dir = Path("storefront") / "products" / product_id / "images"
print(images_dir)
```

The left operand must be a `Path`. The right operand can be a `Path` or a string. The result is always a new `Path`. The operator handles separators correctly even when components have leading or trailing slashes:

```python
from pathlib import Path

print(Path("storefront") / "products/")
print(Path("storefront") / "/products")
```

The first case strips the trailing slash. The second case is more interesting: when the right operand is absolute (starts with `/`), it replaces the left operand entirely. This matches how `os.path.join` and shell path-joining work, but it does surprise people the first time they hit it. Treat absolute-looking strings carefully when you're building paths from user input or config.

**What's wrong with this code?**

```python
from pathlib import Path

base = Path("exports")
customer = "C-4821"
filename = "orders.csv"

path = base + "/" + customer + "/" + filename
print(path)
```

`Path` objects don't support `+`. The whole point of the type is to push you away from string concatenation. The fix is to use `/`:

```python
from pathlib import Path

base = Path("exports")
customer = "C-4821"
filename = "orders.csv"

path = base / customer / filename
print(path)
```

The slash operator is shorter, cross-platform, and harder to get wrong. If you find yourself reaching for `+` or f-strings to glue path parts together, you're doing it the old way.

<h1 id="anatomy-of-a-path">Anatomy of a Path</h1>

A path has parts: a parent directory, a file name, a stem (name without extension), an extension. `pathlib` exposes each one as a property. The diagram below labels each property for the path `exports/2024-Q4/customer-C4821/orders.csv`:

The properties are read-only views into the path; they don't touch the disk. Here's each one in code:

```python
from pathlib import Path

p = Path("exports/2024-Q4/customer-C4821/orders.csv")

print("name:    ", p.name)
print("stem:    ", p.stem)
print("suffix:  ", p.suffix)
print("suffixes:", p.suffixes)
print("parent:  ", p.parent)
print("parts:   ", p.parts)
print("anchor:  ", repr(p.anchor))
```

A few things worth pointing out. `name` is just the last component as a string; `parent` is a `Path`, not a string, so you can keep chaining methods. `parts` is a tuple of every component as strings, which is handy when you want to slice or filter by position. `anchor` is the root portion, which is empty for a relative path and something like `/` on macOS or `C:\` on Windows for an absolute path.

`suffixes` (plural) returns every extension when a file has more than one, which is common with compressed exports:

```python
from pathlib import Path

archive = Path("exports/orders-2024-Q4.csv.gz")
print(archive.suffix)
print(archive.suffixes)
print(archive.stem)
```

`suffix` only returns the last extension, which is usually what you want. `suffixes` gives you the full chain. `stem` strips just the last extension off the name, not all of them, so `orders-2024-Q4.csv.gz` has the stem `orders-2024-Q4.csv`. If you need the bare name without any suffix, strip them one at a time or use a manual split.

The `parents` property (plural) is a sequence of every ancestor directory, walked outward from the current path:

```python
from pathlib import Path

p = Path("exports/2024-Q4/customer-C4821/orders.csv")
for ancestor in p.parents:
    print(ancestor)
```

This is useful when you want to find the nearest containing directory that satisfies some condition, like searching upward for a config file.

<h1 id="checking-whats-on-disk">Checking What's on Disk</h1>

So far the path operations have been purely textual; no filesystem access happens until you ask. A handful of predicate methods tell you whether the path corresponds to something real and what kind of something it is.

```python
from pathlib import Path

uploads = Path("storefront/uploads")
uploads.mkdir(parents=True, exist_ok=True)
(uploads / "banner.png").touch()
(uploads / "links").symlink_to("banner.png") if not (uploads / "links").exists() else None

print((uploads / "banner.png").exists())
print((uploads / "banner.png").is_file())
print((uploads / "banner.png").is_dir())
print(uploads.is_dir())
print((uploads / "missing.png").exists())
```

`exists()` returns `True` for anything: file, directory, symlink, FIFO, anything else the OS exposes as a path. `is_file()` and `is_dir()` are narrower; they each return `True` only for that specific kind. All three follow symlinks by default, so a symlink pointing to a file makes `is_file()` return `True`. To check the symlink itself rather than its target, use `is_symlink()`:

```python
from pathlib import Path

link = Path("storefront/uploads/links")
print(link.is_symlink())
print(link.is_file())
print(link.resolve())
```

The `is_*` predicates return `False` (not an error) when the path doesn't exist. That makes them safe to call before doing anything destructive.

> **Cost:** Each predicate does a `stat` system call. For a single check, it's negligible. If you're scanning thousands of paths and need multiple predicates per path, call `path.stat()` once and inspect the resulting object yourself, instead of paying for `exists()`, then `is_file()`, then `is_dir()` separately.

<h1 id="absolute-resolved-and-relative-paths">
  Absolute, Resolved, and Relative Paths
</h1>

Paths come in two flavors: absolute (starting from the filesystem root) and relative (interpreted from the current working directory). `pathlib` gives you methods to move between them.

```python
from pathlib import Path

p = Path("exports/orders.csv")
print(p.is_absolute())
print(p.absolute())
print(p.resolve())
```

`absolute()` returns an absolute path without touching the disk; it just prepends the current working directory. `resolve()` goes further: it makes the path absolute, follows symbolic links, and collapses `..` and `.` segments. The result is the canonical location on disk. The difference shows up when the path contains a `..`:

```python
from pathlib import Path

p = Path("exports/2024-Q4/../orders.csv")
print(p.absolute())
print(p.resolve())
```

`absolute()` leaves the `..` segment in place; `resolve()` simplifies it. Prefer `resolve()` when you want to compare paths for equality, because two textually different paths can point to the same file.

`relative_to(other)` is the inverse direction: given two paths, compute the relative path from one to the other.

```python
from pathlib import Path

product_path = Path("/Users/maya/projects/storefront/exports/2024-Q4/orders.csv")
base = Path("/Users/maya/projects/storefront")

print(product_path.relative_to(base))
```

This is handy when you're building a list of files relative to a project root, for example when generating a manifest or building a list of upload keys. If `product_path` isn't actually inside `base`, `relative_to` raises `ValueError`; it's not a "best effort" function.

<h1 id="reading-and-writing-through-path">Reading and Writing Through Path</h1>

Paths can do the file I/O themselves. For small files where you want everything in memory at once, `read_text` and `write_text` replace the `open` and `read`/`write` ceremony.

```python
from pathlib import Path

orders = Path("exports/orders.csv")
orders.parent.mkdir(parents=True, exist_ok=True)

orders.write_text("order_id,customer,total\n1001,C-4821,124.95\n1002,C-7733,49.50\n")
print(orders.read_text())
```

`write_text` opens the file in text-write mode, writes the string, and closes it. It returns the number of characters written. `read_text` reads the entire file as a string. Both accept an optional `encoding` argument (default `utf-8` on most platforms, but it follows the locale; pass `encoding="utf-8"` explicitly when portability matters).

For binary data (product images, PDFs, downloaded archives), use `read_bytes` and `write_bytes`:

```python
from pathlib import Path

logo = Path("storefront/assets/logo.png")
logo.parent.mkdir(parents=True, exist_ok=True)
logo.write_bytes(b"\x89PNG\r\n\x1a\n")  # truncated PNG header for illustration
print(logo.read_bytes()[:4])
```

These are convenience wrappers. They open, transfer all the data, and close in one call. For files that don't fit in memory, or when you need to read line by line, fall back to `path.open()`, which behaves identically to the built-in `open`:

```python
from pathlib import Path

orders = Path("exports/orders.csv")
with orders.open("r", encoding="utf-8") as f:
    for line in f:
        print(line.rstrip())
```

`path.open(mode, encoding=...)` returns the same file object you'd get from the built-in `open(path, ...)`. The advantage is that the path object is the entry point; you don't have to convert it to a string first.

> **Cost:** `read_text()` reads the entire file into memory. For multi-gigabyte logs it's the wrong tool. Use `path.open()` with a `for line in f:` loop or read in chunks.

A few other in-place operations:

```python
from pathlib import Path

placeholder = Path("storefront/uploads/pending.txt")
placeholder.parent.mkdir(parents=True, exist_ok=True)
placeholder.touch()       # creates empty file, or updates mtime if it exists
placeholder.write_text("waiting for moderator review\n")
placeholder.rename(placeholder.with_name("approved.txt"))
print(list(placeholder.parent.iterdir()))
```

`touch()` creates an empty file (or updates the modification time of an existing one). `rename()` moves a file to a new path within the same filesystem and returns the new `Path`. `unlink()` deletes a file (use `missing_ok=True` if you don't want an error when the file is already gone).

<h1 id="creating-and-removing-directories">
  Creating and Removing Directories
</h1>

`mkdir()` creates a directory at the path. Two keyword arguments matter:

| Argument   | Default | Effect                                                          |
| ---------- | ------- | --------------------------------------------------------------- |
| `parents`  | `False` | Create missing parent directories along the way                 |
| `exist_ok` | `False` | Don't raise `FileExistsError` when the directory already exists |

You almost always want `parents=True, exist_ok=True`:

```python
from pathlib import Path

target = Path("exports/2024-Q4/customer-C4821")
target.mkdir(parents=True, exist_ok=True)
print(target.is_dir())
```

Without `parents=True`, the call fails if `exports/2024-Q4` doesn't already exist. Without `exist_ok=True`, the call fails if the leaf directory already exists, which makes the operation non-idempotent and forces you to wrap it in `try/except`. The combined form is the idiomatic "make sure this directory exists" line.

To remove an empty directory, use `rmdir()`. To remove a file, use `unlink()`. Removing a directory tree (a directory with files inside it) needs `shutil.rmtree`.

<h1 id="iterating-a-directory">Iterating a Directory</h1>

`iterdir()` yields the entries (files and subdirectories) inside a directory, one `Path` per item. It does not recurse.

```python
from pathlib import Path

uploads = Path("storefront/product-images")
uploads.mkdir(parents=True, exist_ok=True)
for name in ["mouse.png", "keyboard.jpg", "notes.txt"]:
    (uploads / name).touch()

for entry in uploads.iterdir():
    print(entry)
```

The order isn't guaranteed; it depends on the filesystem. If you need a stable order, sort the result yourself.

`iterdir()` returns an iterator, not a list. For huge directories that's a feature: you can start processing the first entries while the rest of the listing is still being walked. If you want a list, wrap it: `list(uploads.iterdir())`.

To filter, combine with a comprehension or with the `glob` method below.

<h1 id="globbing-pattern-based-file-listings">
  Globbing: Pattern-Based File Listings
</h1>

`glob(pattern)` matches the pattern against the directory's contents and yields matching paths. It supports the usual shell wildcards: `*` (anything except a separator), `?` (one character), and `[abc]` (character class).

```python
from pathlib import Path

images = Path("storefront/product-images")
for img in images.glob("*.png"):
    print(img)
```

`glob` only looks at the immediate directory; it doesn't descend into subdirectories. To recurse, use `rglob` (recursive glob) or use the `**` pattern:

```python
from pathlib import Path

storefront = Path("storefront")
for path in storefront.rglob("*.png"):
    print(path)
```

`rglob("*.png")` is equivalent to `glob("**/*.png")`. The `**` segment means "this directory and all its subdirectories", recursively. Use whichever reads better to you; the behavior is the same.

> **Cost:** `rglob('*')` walks the entire subtree. On a directory with millions of files (a node_modules folder, a checked-out monorepo, a customer upload bucket), it can take minutes and consume a lot of memory if you wrap the result in `list()`. Iterate lazily, filter early, and consider whether `os.walk` with manual pruning fits better.

You can combine globs with predicates for finer filters:

```python
from pathlib import Path

exports = Path("exports")
exports.mkdir(exist_ok=True)
(exports / "orders-2024-Q3.csv").touch()
(exports / "orders-2024-Q4.csv").touch()
(exports / "summary.txt").touch()

recent_exports = [p for p in exports.glob("orders-2024-*.csv") if p.is_file()]
for p in recent_exports:
    print(p)
```

The pattern narrows the candidates by name; the `is_file()` check rejects directories that happen to match the pattern. For most product use cases, that combination handles "find me all the files of type X under directory Y".

`match(pattern)` checks a single path against a glob pattern without listing the filesystem:

```python
from pathlib import Path

p = Path("exports/2024-Q4/orders.csv")
print(p.match("*.csv"))
print(p.match("2024-*/orders.csv"))
print(p.match("logs/*.csv"))
```

`match` is right-anchored: `"*.csv"` matches any path whose last component ends in `.csv`. To anchor at the start, include the full structure (`"exports/**/*.csv"`).

<h1 id="modifying-path-components">Modifying Path Components</h1>

Sometimes you have a path and want a sibling: same directory, slightly different name or extension. `with_name`, `with_stem`, and `with_suffix` give you these.

```python
from pathlib import Path

original = Path("exports/2024-Q4/orders.csv")

print(original.with_name("refunds.csv"))
print(original.with_stem("orders-final"))
print(original.with_suffix(".json"))
print(original.with_suffix(""))
```

`with_name` replaces the entire last component (name plus extension). `with_stem` replaces just the part before the last extension. `with_suffix` replaces the last extension; passing `""` strips it entirely. None of these methods change the original path; each returns a new `Path`.

A common pattern is "write the result next to the input, with a different extension":

```python
from pathlib import Path

source = Path("exports/orders.csv")
source.parent.mkdir(parents=True, exist_ok=True)
source.write_text("order_id,total\n1001,124.95\n")

archive = source.with_suffix(".json")
archive.write_text('[{"order_id": 1001, "total": 124.95}]\n')

print(list(source.parent.iterdir()))
```

`with_stem` was added in Python 3.9. If you're targeting older interpreters, build the equivalent with `with_name(f"{p.stem}-final{p.suffix}")`.

<h1 id="purepath-vs-path">PurePath vs Path</h1>

`Path` is the type you've been using. Internally it has a sibling called `PurePath` (and concrete `PurePosixPath` and `PureWindowsPath` variants). The split matters when you want to manipulate path strings without ever touching the filesystem.

| Type       | What it does                                                                          |
| ---------- | ------------------------------------------------------------------------------------- |
| `Path`     | Full path object with I/O methods (`read_text`, `mkdir`, etc.) and inspection methods |
| `PurePath` | Path manipulation only; no methods that touch the disk                                |

You use `PurePath` when:

- You're parsing or building paths for a different operating system than the one running the code. For example, generating Windows paths from a Linux server.
- You're writing tests that should work without creating real files.
- You want to make it explicit at the type level that a function never reads or writes the disk.

```python
from pathlib import PureWindowsPath, PurePosixPath

windows = PureWindowsPath("C:/Users/maya/exports/orders.csv")
posix = PurePosixPath("/home/maya/exports/orders.csv")

print(windows)
print(windows.parent)
print(posix)
print(posix.parent)
```

`PureWindowsPath` displays with backslashes even when you're running on macOS or Linux. `PurePosixPath` always uses forward slashes. Neither type has methods like `exists()` or `read_text()`, because both might run on a machine that doesn't actually have a `C:\Users\maya` directory.

For day-to-day code, stick with `Path`. Reach for `PurePath` only when you specifically need cross-platform path generation without filesystem access.

<h1 id="a-quick-mental-model-path-methods-by-category">
  A Quick Mental Model: Path Methods by Category
</h1>

The full `Path` interface is large, but it groups cleanly. Keep this map in your head:

| Category                | Examples                                                                            | Notes                           |
| ----------------------- | ----------------------------------------------------------------------------------- | ------------------------------- |
| Construction            | `Path()`, `Path.cwd()`, `Path.home()`, `/` operator                                 | No disk access                  |
| Inspection (textual)    | `name`, `stem`, `suffix`, `parts`, `parent`, `parents`, `anchor`                    | No disk access                  |
| Inspection (filesystem) | `exists()`, `is_file()`, `is_dir()`, `is_symlink()`, `stat()`                       | One system call each            |
| Resolution              | `absolute()`, `resolve()`, `relative_to()`                                          | Only `resolve` touches the disk |
| Modification (textual)  | `with_name()`, `with_stem()`, `with_suffix()`                                       | Returns a new `Path`            |
| I/O                     | `read_text()`, `write_text()`, `read_bytes()`, `write_bytes()`, `open()`, `touch()` | Reads or writes data            |
| Directory ops           | `mkdir()`, `rmdir()`, `unlink()`, `rename()`, `iterdir()`, `glob()`, `rglob()`      | Filesystem changes or listings  |
| Pattern matching        | `match()`                                                                           | Purely textual                  |

When you're picking a method, ask first whether the operation needs disk access. If it doesn't (renaming a path string, checking the extension), prefer the textual operations; they're cheap and they don't fail if the file isn't there yet.

<h1 id="putting-it-together">Putting It Together</h1>

A realistic snippet that uses most of what we've covered: scan an upload directory, sort images by extension into per-format subfolders, and write a manifest.

```python
from pathlib import Path

uploads = Path("storefront/uploads")
uploads.mkdir(parents=True, exist_ok=True)
for name in ["banner.png", "thumbnail.png", "promo.jpg", "discount.jpg", "tag.svg"]:
    (uploads / name).touch()

manifest_lines = []

for image in uploads.iterdir():
    if not image.is_file():
        continue
    target_dir = uploads / image.suffix.lstrip(".")
    target_dir.mkdir(exist_ok=True)
    destination = target_dir / image.name
    image.rename(destination)
    manifest_lines.append(f"{destination.relative_to(uploads)}")

(uploads / "manifest.txt").write_text("\n".join(sorted(manifest_lines)) + "\n")
print((uploads / "manifest.txt").read_text())
```

Every operation here is a `Path` method or property. There's no `os.path`, no string concatenation, no manual separator handling. The code reads top to bottom as a description of what's happening: list the uploads, filter to files, derive a target directory from the extension, make sure it exists, move the file, record the new location, write a manifest.
