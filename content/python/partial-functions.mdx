<h1 id="what-partial-does">What partial Does</h1>

`functools.partial(func, *args, **kwargs)` returns a new callable. Calling that new thing is like calling `func` with the saved arguments plus whatever the caller adds. The original function is untouched; nothing global changes. You just get back a second callable that has been pre-loaded with some inputs.

```python
from functools import partial

def shipping_cost(weight_kg, zone, express=False):
    base = 5.00 + weight_kg * 0.50 + zone * 1.25
    if express:
        base += 10.00
    return round(base, 2)

zone_1_shipping = partial(shipping_cost, zone=1)

print(zone_1_shipping(2.5))
print(zone_1_shipping(weight_kg=4.0))
print(zone_1_shipping(1.0))
```

`partial(shipping_cost, zone=1)` produces a new callable. Calling `zone_1_shipping(2.5)` is the same as calling `shipping_cost(2.5, zone=1)`. The `zone=1` is baked in once; every caller after that only supplies the remaining arguments. The original `shipping_cost` is still around and works exactly as before. The partial is an additional callable, not a replacement.

You can bind positional arguments too. They fill in from the left.

```python
from functools import partial

def price_with_tax(price, tax_rate, discount=0.0):
    return round(price * (1 - discount) * (1 + tax_rate), 2)

# Bind the price positionally. Now we only need tax_rate (and optionally discount).
flat_99 = partial(price_with_tax, 99.00)

print(flat_99(0.0725))
print(flat_99(0.04, discount=0.10))
print(flat_99(0.0))
```

`partial(price_with_tax, 99.00)` fills in `price` with `99.00`. The new callable accepts the rest in order: first `tax_rate`, then `discount`. Each call to `flat_99` reuses the bound price without you having to type it again.

Positional and keyword binding can be mixed. Whatever you save in the `partial` call is saved; whatever you supply at call time is added on.

```python
from functools import partial

def make_order(customer, item, quantity, status="placed"):
    return f"{customer} ordered {quantity}x {item} (status: {status})"

# Bind one positional plus one keyword.
alice_order = partial(make_order, "Alice", status="placed")

print(alice_order("Wireless Mouse", 2))
print(alice_order("USB Cable", 5))
print(alice_order("HDMI Cable", 1, status="shipped"))
```

`alice_order` has `customer="Alice"` (positional) and `status="placed"` (keyword) baked in. The caller adds `item` and `quantity`, and may override `status` if they want. The third call passes `status="shipped"` at call time, which overrides the saved keyword default.

A `partial` is a regular callable. It can be passed anywhere a function is expected, stored in a variable or a list, returned from another function, or used as an argument to another `partial`. The thing it returns is callable just like the original.

Each call through a `partial` does a small amount of extra work: building the merged argument tuple and dict, then calling the underlying function. The overhead is a few microseconds at most, which is invisible for functions that do any real work and only worth thinking about in tight loops over trivial calls.

<h1 id="why-use-partial-instead-of-just-calling-the-function">
  Why Use partial Instead of Just Calling the Function
</h1>

You could always write `shipping_cost(weight, zone=1)` at every call site. `partial` is useful when you want to **save** that decision, not repeat it. Three common cases:

**Callbacks and higher-order functions.** When you hand a function to `sorted`, `map`, `filter`, or any framework that calls it back later, the receiver decides what arguments to pass. If your function needs an extra argument the receiver doesn't know about, pre-bind that argument before handing the function over. `partial` does this in one line.

```python
from functools import partial

products = [
    {"name": "Wireless Mouse", "price": 29.99, "rating": 4.5},
    {"name": "USB Cable", "price": 4.99, "rating": 4.8},
    {"name": "HDMI Cable", "price": 14.99, "rating": 4.6},
    {"name": "Webcam", "price": 89.99, "rating": 4.2},
]

def sort_key(product, by):
    return product[by]

by_price = sorted(products, key=partial(sort_key, by="price"))
by_rating = sorted(products, key=partial(sort_key, by="rating"), reverse=True)

for p in by_price:
    print(f"{p['name']}: ${p['price']}")
print()
for p in by_rating:
    print(f"{p['name']}: {p['rating']}")
```

`sorted` expects `key` to be a one-argument function that takes a product and returns the sort value. `sort_key` takes two arguments. `partial(sort_key, by="price")` produces a one-argument function with `by="price"` already supplied, which is exactly what `sorted` wants. The same `sort_key` is reused with a different binding for ratings.

**Simplified signatures for repeat callers.** Long-signature functions are fine when each call uses different arguments. When every call in a module uses the same value for one parameter, repeating it on every line adds noise. Bind it once.

```python
from functools import partial

def log_event(timestamp, customer_id, event_type, detail, severity="info"):
    return f"[{timestamp}] {severity.upper()} customer={customer_id} {event_type}: {detail}"

# Within one request handler, the timestamp and customer don't change. Bind them once.
log = partial(log_event, "2024-06-01T10:30:00", "C-4421")

print(log("login", "from web"))
print(log("add_to_cart", "Wireless Mouse"))
print(log("checkout_failed", "card declined", severity="warning"))
```

The timestamp and customer ID are constant for the duration of one request, so binding them once with `partial` keeps the call sites focused on what's actually changing. The result reads better and there's one place to fix if the bound value needs to change.

**Pre-configured versions of general helpers.** A general-purpose function with several knobs is more reusable, but you often want specific named versions for common cases. `partial` builds those named versions without copying code.

```python
from functools import partial

def format_money(amount, currency, decimals):
    return f"{currency}{amount:.{decimals}f}"

usd = partial(format_money, currency="$", decimals=2)
eur = partial(format_money, currency="â¬", decimals=2)
jpy = partial(format_money, currency="Â¥", decimals=0)

print(usd(29.99))
print(eur(29.99))
print(jpy(3000))
```

One general formatter, three specific ones built from it. No duplication of the formatting logic; each currency version is one line.

<h1 id="partial-vs-lambda">Partial vs Lambda</h1>

Both `partial` and `lambda` can solve the same problem: turn a multi-argument function into a callable that has some arguments pre-filled. The difference is in style and a few small features.

```python
from functools import partial

def price_with_tax(price, tax_rate):
    return round(price * (1 + tax_rate), 2)

# These are equivalent.
ca_partial = partial(price_with_tax, tax_rate=0.0725)
ca_lambda = lambda price: price_with_tax(price, tax_rate=0.0725)

print(ca_partial(100))
print(ca_lambda(100))
```

Both produce a one-argument callable that applies a California sales tax. The behavior is identical; the choice is mostly about style and a couple of practical concerns.

The case for `partial`:

- The name `partial` says "this is a function with some arguments pre-filled". A lambda hides that intent inside its body.
- `partial` objects are introspectable. You can read `.func`, `.args`, and `.keywords` to see what's bound. That's useful for debugging and for code that needs to inspect callbacks.
- A `partial` is **picklable** if the underlying function is picklable. A lambda is not picklable. This matters for multiprocessing, joblib, and other tools that serialize callables across processes.

The case for `lambda`:

- A lambda can do more than pre-bind arguments. It can also rearrange, transform, or add logic around the call. `partial` only binds.
- For a one-off use right at the call site, `lambda x: f(x, 0.08)` is shorter than importing `partial` and writing two lines.
- Lambdas don't require an import. `partial` lives in `functools`.

A rule of thumb: if all you're doing is fixing some arguments of a function you've already named, use `partial`. If you're also computing or rearranging, use a lambda. If you'll serialize the result for multiprocessing or save it to disk, use `partial` (or a regular `def`).

```python
from functools import partial

def make_order(customer, item, quantity, status="placed"):
    return f"{customer} ordered {quantity}x {item} (status: {status})"

alice_order = partial(make_order, "Alice")

# Introspect the partial.
print(alice_order.func.__name__)
print(alice_order.args)
print(alice_order.keywords)
print(alice_order("Wireless Mouse", 2))
```

`alice_order.func` is the original `make_order`. `alice_order.args` is the tuple of bound positional arguments. `alice_order.keywords` is the dict of bound keyword arguments. A lambda has none of these; it's just a callable with no record of what it captured.

<h1 id="composing-with-map-filter-and-sorted">
  Composing with map, filter, and sorted
</h1>

`partial` fits naturally in code that passes functions around. `map`, `filter`, and `sorted` all take a callable and call it for each element of an iterable. When the function you want needs an extra argument they don't supply, `partial` bridges the gap.

```python
from functools import partial

prices = [29.99, 14.99, 9.99, 49.99, 19.99]

def add_tax(price, rate):
    return round(price * (1 + rate), 2)

with_8_pct = partial(add_tax, rate=0.08)
taxed = list(map(with_8_pct, prices))

print(taxed)
```

`map` calls `with_8_pct` once per price. The `rate=0.08` is already bound, so each call only needs the one price. The result is the same as `[add_tax(p, 0.08) for p in prices]`, and which one reads better depends on the codebase's conventions. The `partial` plus `map` version reuses `with_8_pct` elsewhere if needed; the comprehension repeats the rate inline.

`filter` works the same way. The predicate needs to be a one-argument function returning a boolean. If your predicate needs a threshold (or any other configuration), bind it with `partial`.

```python
from functools import partial

products = [
    {"name": "Wireless Mouse", "price": 29.99},
    {"name": "USB Cable", "price": 4.99},
    {"name": "HDMI Cable", "price": 14.99},
    {"name": "Webcam", "price": 89.99},
    {"name": "Power Strip", "price": 12.49},
]

def under_budget(product, max_price):
    return product["price"] <= max_price

cheap = list(filter(partial(under_budget, max_price=15.00), products))
for p in cheap:
    print(f"{p['name']}: ${p['price']}")
```

`filter` calls `partial(under_budget, max_price=15.00)` once per product. Each call passes the product as the first argument; `max_price=15.00` is already bound. Products with prices over 15 are filtered out.

The same pattern works for `sorted`'s `key` argument, as shown earlier. Anywhere a one-argument callable is required and your function needs more, `partial` is the standard fix.

<h1 id="partial-vs-currying">Partial vs Currying</h1>

Currying and partial application are related but not the same. Both let you "supply arguments later", but they're shaped differently and they come from different traditions.

**Currying** transforms a function `f(a, b, c)` into a chain of one-argument calls: `f(a)(b)(c)`. Each call returns a function that expects the next argument. You can't supply two arguments at the same time; you supply one at a time, and the function eats them one at a time.

**Partial application** lets you supply **any number** of arguments now and get back a callable that needs the rest. You can pre-bind one, two, or all of them in a single step, and you can choose positional or keyword bindings.

Python's `functools.partial` is partial application, not currying. The short version: partial is more flexible (bind whatever you want, in any order) but doesn't compose as cleanly in functional-style pipelines. Curried functions compose naturally because every intermediate step is itself a function expecting one argument, which fits patterns like `f >> g >> h`.

In day-to-day Python code, partial is far more common than true currying. The language doesn't encourage one-argument-at-a-time chains, and `partial` provides the practical benefit (specializing a function) without the FP-language style.

<h1 id="partialmethod-partial-application-on-methods">
  partialmethod: Partial Application on Methods
</h1>

`functools.partialmethod` is the cousin of `partial` for use inside class bodies. It binds arguments to a method instead of a free function, so the bound arguments come after `self` rather than before.

```python
from functools import partialmethod

class Order:
    def __init__(self, customer):
        self.customer = customer
        self.status = "placed"

    def set_status(self, status):
        self.status = status
        return self

    # Specialized methods, each pre-binding a status value.
    mark_shipped = partialmethod(set_status, "shipped")
    mark_delivered = partialmethod(set_status, "delivered")
    cancel = partialmethod(set_status, "cancelled")

order = Order("Alice")
print(order.status)

order.mark_shipped()
print(order.status)

order.mark_delivered()
print(order.status)
```

`partialmethod(set_status, "shipped")` produces a method that, when called as `order.mark_shipped()`, calls `set_status(order, "shipped")`. The `self` binding still works the normal way (it's filled in when you access the method on an instance), and the extra argument is bound by `partialmethod`. This pattern fits when you want named methods that are thin wrappers around one general-purpose method.

Using a plain `partial` here would not work, because `partial` doesn't know about the descriptor protocol that classes use to bind `self`. `partialmethod` is the version that does.

A `partialmethod` call is one extra function call over the plain method call, which is negligible. The benefit is fewer lines of repetitive method definitions for cases like state-machine transitions or fixed-argument variants.

<h1 id="pitfalls">Pitfalls</h1>

A few details are worth knowing before using `partial` heavily. None are deep, but knowing them in advance saves time.

**`partial` of a `partial` works, and the bindings compose.** You can wrap a `partial` in another `partial`. The bindings accumulate from the outside in.

```python
from functools import partial

def shipping_cost(weight_kg, zone, express):
    base = 5.00 + weight_kg * 0.50 + zone * 1.25
    if express:
        base += 10.00
    return round(base, 2)

zone_3 = partial(shipping_cost, zone=3)
zone_3_express = partial(zone_3, express=True)

print(zone_3(2.5, express=False))
print(zone_3_express(2.5))
print(zone_3_express(1.0))
```

`zone_3` binds `zone=3`. `zone_3_express` is built from `zone_3` and binds `express=True` on top of it. The result is a callable that needs only the weight. The technique is occasionally useful, but stacking three or four `partial`s is usually clearer as a small wrapper function.

**Positional binding fills from the left only.** To bind a later positional argument without binding the earlier ones, use a keyword. `partial(f, x=10)` works for any function whose parameter list lets `x` be supplied by keyword. `partial(f, 10)` always binds the first positional argument, not whichever argument you meant.

```python
from functools import partial

def fn(a, b, c):
    return f"a={a} b={b} c={c}"

# Bind only 'b' by keyword.
b_bound = partial(fn, b=99)
print(b_bound(1, c=3))

# Trying to bind only 'b' positionally doesn't work.
# This binds 'a' to 99, not 'b'.
wrong = partial(fn, 99)
print(wrong(2, 3))
```

There's no syntax for "skip the first positional and bind the second". Use a keyword when the parameter you want to bind isn't the leftmost one.

**Don't confuse the variable name `partial` with `functools.partial`.** It's easy to shadow `partial` with a local variable by accident. If a function called `partial` is suddenly raising `TypeError`, check whether something else has been assigned to that name in scope. The convention in most codebases is to import `partial` directly and avoid reusing the name.

```python
# Bad: shadowing partial breaks later imports.
from functools import partial

partial = 0.5  # don't do this
# Now you can't use partial as a function.
```

The fix is to use a different name (`partial_total`, `discount_partial`, etc.) for any variable that would otherwise collide.

**Picklability follows the wrapped function.** A `partial` is picklable if and only if its `func`, `args`, and `keywords` are all picklable. Named module-level functions are picklable. Lambdas, nested functions, and methods bound to dynamically-created instances are usually not. When using `partial` with `multiprocessing.Pool.map` and seeing a "PicklingError", check what's being wrapped.

```python
from functools import partial

def add_tax(price, rate):
    return price * (1 + rate)

# This partial is picklable because add_tax is a module-level function.
with_8_pct = partial(add_tax, rate=0.08)

# This is not picklable because the inner function is local.
def make_pricer():
    def add_local(price, rate):
        return price * (1 + rate)
    return partial(add_local, rate=0.08)
```

The second `partial` wraps a function defined inside `make_pricer`. That inner function isn't reachable by name from the top level, so pickle can't serialize it. `partial` doesn't change this; whatever rules apply to the underlying function apply to the partial too.
