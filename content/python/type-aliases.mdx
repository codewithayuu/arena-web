<h1 id="why-name-your-types">Why Name Your Types</h1>

Look at this function signature for an inventory system that groups products by category, with each product carrying a stock count and a price:

```python
def restock(inventory: dict[str, list[tuple[int, float]]], category: str) -> None:
    ...
```

The annotation is technically correct, but a reader has to parse it like an algebra problem. What's the `str` key? What does the tuple represent? You have to read the function body or the docstring to find out. Now compare it with named pieces:

```python
ProductId = int
Price = float
Stock = tuple[ProductId, Price]
Inventory = dict[str, list[Stock]]

def restock(inventory: Inventory, category: str) -> None:
    ...
```

The signature reads like English. `Inventory` is what goes in, `category` picks one out. The reader doesn't need to remember the underlying shape unless they're actually modifying it.

Naming a type does three things at once:

1. **It documents intent.** `Cents` is more informative than `int` everywhere it shows up.
2. **It centralizes change.** If you decide `Price` should be a `Decimal` instead of a `float`, you update one alias, not forty function signatures.
3. **It enables stronger checking.** With `NewType`, you can get the checker to flag `add_to_cart(customer_id)` when the function actually wanted a `ProductId`.

The first two points work with plain aliases. The third needs `NewType`, which is the more interesting half of this lesson.

<h1 id="simple-aliases">Simple Aliases</h1>

A type alias in its simplest form is just a variable assignment at module scope:

```python
ProductId = int
Cents = int
Cart = dict[ProductId, int]

def add_item(cart: Cart, product_id: ProductId, quantity: int) -> None:
    cart[product_id] = cart.get(product_id, 0) + quantity

shopping_cart: Cart = {}
add_item(shopping_cart, 42, 2)
add_item(shopping_cart, 17, 1)
print(shopping_cart)
```

The checker treats `ProductId` and `int` as the same type. You can pass an `int` literal where a `ProductId` is expected, and vice versa, without complaint. The alias is a documentation tool here, nothing more.

This form has worked since type hints landed in Python 3.5. It uses no special syntax: the right-hand side is any valid type expression, and the left-hand side is the name you want to use. The interpreter at runtime sees a normal variable assignment. The type checker recognizes it as an alias because the value on the right is a type.

A few common shapes in an e-commerce codebase:

```python
CustomerId = int
OrderId = int
Email = str
Cents = int
ProductCategory = str

CategoryListing = dict[ProductCategory, list[ProductId]]
ItemLine = tuple[ProductId, int, Cents]  # product, quantity, unit price
Receipt = list[ItemLine]
```

Every one of those is interchangeable with its underlying type from the checker's perspective. The win is purely readability.

<h1 id="the-typealias-annotation-python-310">
  The TypeAlias Annotation (Python 3.10)
</h1>

Plain assignments work, but they have an ambiguity problem. Look at this:

```python
ProductId = int
DEFAULT_LIMIT = 100
```

Both lines are assignments. The first is meant as a type alias; the second is a module-level constant. A type checker has to use heuristics to decide which is which. Most of the time it gets it right, but edge cases exist. What about this?

```python
Price = float  # alias?
EMPTY_PRICE = float  # also alias? or a reference to the float class?
```

The two lines look almost identical, and yet the intent is different. PEP 613, shipped in Python 3.10, gave us a way to be explicit:

```python
from typing import TypeAlias

ProductId: TypeAlias = int
Price: TypeAlias = float
Cart: TypeAlias = dict[ProductId, int]
```

The `: TypeAlias` annotation tells the checker, "this is an alias, no guessing required." It has no runtime effect; the variable still holds the same value it would have without the annotation. But to a checker, the intent is unambiguous, and tooling can flag mistakes like later reassigning `ProductId` to a non-type value.

There's a subtler benefit: forward references. A plain assignment can't easily refer to a name defined later in the same module without using string quotes. With `TypeAlias`, both string forms and direct references behave predictably:

```python
from typing import TypeAlias

# Forward reference using a string
Tree: TypeAlias = "list[Tree | int]"
```

Without the annotation, a checker might not be sure whether the string is a type or just a string. With `TypeAlias`, the meaning is fixed.

You don't need `TypeAlias` everywhere. If your aliases are simple and live in a module of pure type definitions, plain assignments are fine. Reach for `TypeAlias` when:

- The right-hand side could plausibly be a runtime value (a class, a function reference) and you want to mark it as a type.
- You're working in a codebase that has adopted strict checking and your tools need the hint.
- You're using forward references that the checker might otherwise misread.

In a Python 3.12 codebase, you'll skip `TypeAlias` entirely and use the `type` statement instead, which we'll get to next.

<h1 id="the-type-statement-python-312">The type Statement (Python 3.12+)</h1>

Python 3.12 introduced a new syntax specifically for declaring type aliases, via PEP 695. It looks like this:

```python
type ProductId = int
type Price = float
type Cart = dict[ProductId, int]
type Inventory = dict[str, list[tuple[ProductId, Price]]]

def total(cart: Cart) -> Price:
    return sum(cart.values())  # simplified

shopping_cart: Cart = {42: 2999, 17: 1499}
print(f"Items: {len(shopping_cart)}")
```

The `type` keyword is now an actual statement. Three things are different from plain assignments and `TypeAlias`:

1. **No import needed.** `type` is a built-in keyword, not a `typing` import.
2. **Lazy evaluation.** The right-hand side isn't evaluated until something asks for it. This means you can reference names defined later in the file without quote tricks.
3. **Its own scope.** The alias creates a `TypeAliasType` object at runtime, similar to how a class creates a `type` object.

The lazy evaluation point is the most practical. Consider mutually recursive types, which used to be awkward:

```python
# Python 3.12+
type NestedCategory = dict[str, list[NestedCategory] | list[int]]

catalog: NestedCategory = {
    "Electronics": [
        {"Phones": [101, 102, 103]},
        {"Laptops": [201, 202]},
    ],
}
```

The right-hand side references `NestedCategory` itself, but Python doesn't try to resolve it until the type is actually inspected. With plain assignments or `TypeAlias`, this would require quoting the name.

The `type` statement is the recommended form going forward. If your codebase is on 3.12 or newer, use it by default and fall back to the older forms only when supporting older versions matters. Here's a visual summary of how the three alias forms map to Python versions and what they buy you:

All three are aliases from the checker's perspective: the named type is identical to whatever it points at. None of them creates a distinct type. For that, you need `NewType`.

<h1 id="newtype-for-distinct-subtypes">NewType for Distinct Subtypes</h1>

Here's where things get interesting. An alias makes `UserId` mean `int` to both the reader and the checker. A `NewType` makes `UserId` mean `int` at runtime but a distinct subtype at check time:

```python
from typing import NewType

UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)

def cancel_order(order_id: OrderId) -> None:
    print(f"Cancelling order {order_id}")

user: UserId = UserId(42)
order: OrderId = OrderId(1001)

cancel_order(order)   # OK
cancel_order(user)    # type checker error: argument of type "UserId" cannot be assigned to parameter of type "OrderId"
```

The checker now treats `UserId` and `OrderId` as different types, even though both are `int` at runtime. Passing a `UserId` to a function expecting `OrderId` becomes a static error. The bug that's almost impossible to spot in a plain-`int` codebase, accidentally swapping two integer IDs, becomes a one-line complaint from your type checker.

The pattern for using a `NewType` is simple:

1. **Declare it once at module scope:** `UserId = NewType("UserId", int)`.
2. **Construct values by calling it:** `user = UserId(42)`.
3. **Use the name in annotations:** `def lookup(user: UserId) -> Customer: ...`.

The constructor call at runtime is a thin wrapper. It returns the argument unchanged. There's no allocation, no wrapper object, no overhead beyond a function call. From the interpreter's perspective, `UserId(42)` is `42`. From the checker's perspective, it's a value of type `UserId`, which is a subtype of `int`.

The subtype direction is important. Because `UserId` is a subtype of `int`, you can pass a `UserId` to any function that takes a plain `int`:

```python
from typing import NewType

UserId = NewType("UserId", int)

def double(n: int) -> int:
    return n * 2

user_id: UserId = UserId(42)
result = double(user_id)  # OK: UserId is a subtype of int
print(result)
```

You can't go the other way. A plain `int` is not a `UserId`. Functions that demand a `UserId` reject raw ints:

```python
from typing import NewType

UserId = NewType("UserId", int)

def deactivate(user: UserId) -> None:
    print(f"Deactivating user {user}")

deactivate(UserId(42))  # OK
deactivate(42)          # type checker error: argument of type "int" cannot be assigned to parameter of type "UserId"
```

At runtime, both calls succeed; the checker is the one keeping you honest. The pattern forces every call site to be explicit about which kind of integer it's handing over.

A diagram makes the runtime-vs-checker split easier to remember:

The left side, runtime, sees an integer. The right side, the type checker, sees a distinct type. Both views coexist without conflict because the checker never runs your code and the runtime never looks at your annotations.

> **Cost:** `NewType` calls are O(1) and don't allocate. The constructor is implemented as a function that returns its argument unchanged. Wrapping every ID assignment in `UserId(...)` costs essentially nothing at runtime.

<h1 id="aliases-vs-newtype-a-comparison">Aliases vs NewType: A Comparison</h1>

This is the table to remember. The decision between the two forms turns on whether you want the checker to enforce a distinction or just provide a readable label:

| Feature              | Type Alias                              | NewType                                       |
| -------------------- | --------------------------------------- | --------------------------------------------- |
| Declaration          | `Price = float` or `type Price = float` | `Price = NewType("Price", float)`             |
| Runtime cost         | Zero (no object)                        | Tiny function call (returns argument)         |
| Checker view         | Same as the original type               | Distinct subtype                              |
| Mixing with original | Free, interchangeable                   | One-way: subtype to base allowed, not reverse |
| Catches ID swaps?    | No                                      | Yes                                           |
| Can add methods?     | No                                      | No                                            |
| Generic support      | Yes (`type Cart[T] = dict[int, T]`)     | Limited; not a real class                     |
| Construction         | None required                           | Explicit: `Price(29.99)`                      |
| Best for             | Readable shorthand for complex types    | Distinguishing same-shaped primitives         |

The two tools solve different problems. An alias makes a long type expression short. A `NewType` makes a primitive type more specific. You can use both in the same codebase, and a single domain concept might pick either depending on whether mix-ups are likely.

Concrete examples of the decision:

```python
from typing import NewType

# Aliases: just shorthand, mix-up isn't possible
type ProductMap = dict[int, str]
type PriceList = list[float]

# NewType: distinct identities matter
UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)
ProductId = NewType("ProductId", int)
Cents = NewType("Cents", int)
Email = NewType("Email", str)
```

`ProductMap` is just a shape. Nothing's going to confuse a `ProductMap` with another `dict[int, str]` because there's no other `dict[int, str]` floating around in the same scope. `UserId` and `OrderId`, on the other hand, are both `int` and live in the same functions all the time. The checker enforcement is the whole point.

A useful framing: aliases solve a readability problem, `NewType` solves a correctness problem. If you find yourself adding lots of comments that say "this is the customer id, not the order id," you have a `NewType` use case.

<h1 id="when-to-use-newtype-in-practice">When to Use NewType in Practice</h1>

The strongest case for `NewType` is **domain primitives**: things that are technically `int` or `str` but represent meaningfully different concepts in your domain. An e-commerce backend is full of them.

Money is a classic example. Half the bugs in financial code come from mixing dollars and cents, or worse, treating two currencies as interchangeable:

```python
from typing import NewType

Cents = NewType("Cents", int)
Dollars = NewType("Dollars", float)

def charge_cents(amount: Cents) -> None:
    print(f"Charging {amount} cents")

def display_dollars(amount: Dollars) -> str:
    return f"${amount:.2f}"

# At the boundary, convert explicitly
def dollars_to_cents(d: Dollars) -> Cents:
    return Cents(round(d * 100))

price_dollars = Dollars(29.99)
price_cents = dollars_to_cents(price_dollars)

charge_cents(price_cents)            # OK
# charge_cents(2999)                 # error: int is not Cents
# charge_cents(price_dollars)        # error: Dollars is not Cents
print(display_dollars(price_dollars))
```

Every conversion between units now has to go through an explicit function. The checker won't let you pass a `Dollars` to `charge_cents` no matter how many times you write `29.99`. Bugs that historically required code review and integration tests to catch become syntactically impossible.

The same pattern fits IDs of any kind:

```python
from typing import NewType

CustomerId = NewType("CustomerId", int)
OrderId = NewType("OrderId", int)
ProductId = NewType("ProductId", int)

def get_orders_for_customer(customer: CustomerId) -> list[OrderId]:
    # Look up orders for a customer
    return [OrderId(1001), OrderId(1002)]

def cancel_order(order: OrderId) -> None:
    print(f"Cancelling order {order}")

customer = CustomerId(42)
orders = get_orders_for_customer(customer)

for order in orders:
    cancel_order(order)  # OK

# cancel_order(customer)  # type checker error: CustomerId is not OrderId
```

The whole flow gets typed properly. Even when a function happens to take and return integers, the checker tracks which kind of integer is going where.

Validated strings are another fit. An `Email` is a `str`, but a `str` is not necessarily a valid `Email`. By making `Email` a `NewType` and only constructing it through a validator, you push correctness into the type system:

```python
from typing import NewType
import re

Email = NewType("Email", str)

def make_email(value: str) -> Email:
    if not re.fullmatch(r"[^@\s]+@[^@\s]+\.[^@\s]+", value):
        raise ValueError(f"Invalid email: {value!r}")
    return Email(value)

def send_receipt(to: Email, total_cents: int) -> None:
    print(f"Sending receipt to {to} for ${total_cents / 100:.2f}")

customer_email = make_email("alice@example.com")
send_receipt(customer_email, 2999)

# send_receipt("not-an-email", 2999)  # type checker error: str is not Email
```

Now every place that takes an `Email` has a runtime guarantee that the value passed validation, because the only way to get an `Email` is through the validator. The type system documents an invariant the codebase actually upholds.

Where `NewType` doesn't fit:

- **One-off types used in a single function.** The bookkeeping overhead isn't worth it if there's no risk of confusion.
- **Types where the underlying primitive is already specific.** A `URL` newtype over `str` makes sense; a `Person` newtype over a `dataclass` doesn't, because you'd just use a subclass.
- **Codebases without type checking enabled.** `NewType` does nothing useful at runtime. If no one runs mypy or pyright, the constructor calls are a tax that buys nothing.

<h1 id="limitations-of-newtype">Limitations of NewType</h1>

`NewType` is intentionally minimal. It is **not** a class, and that bounds what you can do with it.

You can't add methods or attributes:

```python
from typing import NewType

UserId = NewType("UserId", int)

# This fails at runtime
# UserId.format_for_display = lambda self: f"User #{self}"
```

If you find yourself wanting methods, you've outgrown `NewType`. Either use a real class:

```python
class UserId(int):
    def format_for_display(self) -> str:
        return f"User #{self}"

uid = UserId(42)
print(uid.format_for_display())
```

Or use a `dataclass` if the value carries more than one field. The boundary is: `NewType` for "this is a kind of int", a real class for "this has behavior or structure of its own."

You also can't use `NewType` in `isinstance` checks:

```python
from typing import NewType

UserId = NewType("UserId", int)
value = UserId(42)

# This raises TypeError
try:
    print(isinstance(value, UserId))
except TypeError as e:
    print(f"TypeError: {e}")
```

At runtime, `UserId` is a function, not a type. `isinstance(value, UserId)` doesn't make sense because there's no class to check against. If you need a runtime check, check against the underlying type (`isinstance(value, int)`) or use a real class.

`NewType` doesn't compose with `Generic` either. You can't write `NewType("Cart", dict[int, T])` with a `TypeVar` `T` and expect it to behave like a generic class. For generic distinct types, you'd write a real generic class or use a generic type alias instead.

> **Note:** `NewType` over `NewType` works, but it's rare. `AdminUserId = NewType("AdminUserId", UserId)` creates a distinct subtype of `UserId`, which is itself a subtype of `int`. An `AdminUserId` can be passed where `UserId` is expected, which can be passed where `int` is expected. The chain holds.

For generic aliases, the `type` statement in 3.12+ has its own syntax:

```python
# Python 3.12+
type Cart[T] = dict[int, T]

product_cart: Cart[float] = {42: 29.99, 17: 14.99}
quantity_cart: Cart[int] = {42: 2, 17: 1}

print(product_cart)
print(quantity_cart)
```

Wait, that output is wrong. Let me show the actual behavior:

```python
type Cart[T] = dict[int, T]

product_cart: Cart[float] = {42: 29.99, 17: 14.99}
quantity_cart: Cart[int] = {42: 2, 17: 1}

print(product_cart)
print(quantity_cart)
```

`Cart[T]` is a generic alias parameterized by `T`. Each instantiation gives you a different concrete shape. The generic alias is still an alias; values of `Cart[float]` and `dict[int, float]` are interchangeable as far as the checker is concerned.
