<h1 id="the-primitive-built-in-types">The Primitive Built-in Types</h1>

Python's core scalar types each have a single, lowercase name that works as a type hint with no import. The same name is both the runtime type and the annotation, which keeps the syntax tight.

| Type    | What it represents                    | Example value                 |
| ------- | ------------------------------------- | ----------------------------- |
| `int`   | Whole numbers, unbounded precision    | `42`, `-1`, `10_000`          |
| `float` | Double-precision floating point       | `3.14`, `19.99`, `0.0`        |
| `str`   | Text, immutable Unicode strings       | `"Alice"`, `"Wireless Mouse"` |
| `bool`  | Truth value, subclass of `int`        | `True`, `False`               |
| `bytes` | Immutable sequence of raw byte values | `b"PNG\x89"`                  |
| `None`  | The only `NoneType` value             | `None`                        |

A quick sweep of variable annotations using each one:

```python
order_id: int = 1042
order_total: float = 89.97
customer_name: str = "Alice"
is_premium: bool = True
product_image: bytes = b"\x89PNG\r\n\x1a\n"
last_error: None = None

print(order_id, order_total, customer_name, is_premium, len(product_image), last_error)
```

Two of these deserve a closer look. `bool` is a subclass of `int`, which means `True == 1` and `False == 0` everywhere. A function that takes an `int` will accept a `bool` and the type checker won't complain, because of inheritance. This can cause issues when the value flows somewhere that treats `True` as `1`.

```python
def warehouse_count(boxes: int) -> int:
    return boxes * 12

# Both calls type-check. The bool argument is rarely intentional.
print(warehouse_count(5))
print(warehouse_count(True))
```

If a parameter must be exactly an `int` and not a `bool`, a runtime check is required; the type system won't help there.

`bytes` is the type used for file contents, network responses, image data, or anything binary. It's distinct from `str` and the two don't mix without an explicit `.encode()` or `.decode()`. A function that processes raw upload data uses `bytes`; one that reads a username uses `str`.

```python
def product_image_size(data: bytes) -> int:
    return len(data)

def product_slug(name: str) -> str:
    return name.lower().replace(" ", "-")

print(product_image_size(b"\x89PNG\r\n\x1a\n"))
print(product_slug("Wireless Mouse"))
```

The annotation `None` is the trickiest of the primitives. Used as a value, `None` is a singleton. Used as a type, it's a shorthand for `type(None)`, which type checkers accept anywhere a type is expected. The most common use is as a return annotation for functions that don't produce a useful value.

```python
def log_order(order_id: int) -> None:
    print(f"Order {order_id} placed")

log_order(101)
```

A `-> None` function should not have an explicit `return some_value` statement. Either omit the return entirely or use a bare `return` to exit early. Type checkers will flag a `-> None` function that returns anything other than `None`.

<h1 id="annotating-function-parameters-and-returns">
  Annotating Function Parameters and Returns
</h1>

The full shape of a function annotation is `def name(param: Type, ...) -> ReturnType:`. Every piece is optional, but mixing annotated and unannotated parameters in the same function is a smell. Annotate everything or nothing. Half-annotated signatures confuse readers and give the type checker less to work with.

```python
def apply_discount(price: float, percent: float, max_discount: float = 50.0) -> float:
    raw_discount = price * percent / 100
    discount = min(raw_discount, max_discount)
    return price - discount

print(apply_discount(100.0, 10))
print(apply_discount(1000.0, 25))
```

Default values sit in the usual place, after the annotation. The annotation describes the parameter's type; the default supplies a value when the caller omits the argument. The two are independent: a parameter can have a default without an annotation, or an annotation without a default.

Keyword-only and positional-only markers (`*` and `/`) work alongside annotations exactly as they do in plain function definitions:

```python
def place_order(
    customer_id: int,
    /,
    product: str,
    quantity: int = 1,
    *,
    gift_wrap: bool = False,
) -> dict[str, int | str | bool]:
    return {
        "customer_id": customer_id,
        "product": product,
        "quantity": quantity,
        "gift_wrap": gift_wrap,
    }

print(place_order(42, "Wireless Mouse", quantity=2, gift_wrap=True))
```

The annotation `dict[str, int | str | bool]` is doing a lot of work there, and it shows why specific types are worth the effort. A reader can tell from the signature alone that the result is a dict with string keys whose values can be one of three primitive types, without scrolling through the body to find out.

Variable-argument parameters use their unpacked element type, not the container. `*args` is implicitly a tuple, so the annotation describes one element; `**kwargs` is implicitly a dict, so the annotation describes one value.

```python
def total_for_categories(*categories: str, multiplier: int = 1) -> int:
    return len(categories) * multiplier

def update_product(**fields: str) -> dict[str, str]:
    return fields

print(total_for_categories("electronics", "books", "toys"))
print(update_product(name="Wireless Mouse", color="black", brand="Logitech"))
```

`*categories: str` means each positional argument is a string, so the tuple `categories` is implicitly `tuple[str, ...]`. `**fields: str` means each keyword argument value is a string, so the dict `fields` is implicitly `dict[str, str]`.

<h1 id="variable-annotations">Variable Annotations</h1>

Variables outside function signatures can also be annotated. The form is `name: Type = value`, and the value half is optional. A bare annotation declares intent without storing a value.

```python
running_total: float = 0.0
cart_items: list[str] = []
last_order_id: int

for price in [29.99, 14.99, 9.99]:
    running_total += price

last_order_id = 1042
print(running_total, cart_items, last_order_id)
```

The bare `last_order_id: int` line doesn't create a runtime variable. It only records the intended type in the enclosing scope's `__annotations__`. Reading `last_order_id` before assigning to it raises `NameError`, the same as any unbound name.

Annotations at module scope go into the module's `__annotations__` dict. Annotations inside a function are local: they're parsed and stored, but `__annotations__` for a function body isn't exposed in the same way (CPython evaluates and discards them for performance, so they're useful as documentation but not introspectable).

Class-body annotations are the most useful of the three because they double as attribute declarations that type checkers and tools like `dataclasses` consume:

```python
class Product:
    name: str
    price: float
    in_stock: bool = True

    def __init__(self, name: str, price: float) -> None:
        self.name = name
        self.price = price

print(Product.__annotations__)
```

The `in_stock: bool = True` line both declares the attribute's type and gives it a default at the class level. The `name: str` and `price: float` lines declare types without creating class attributes, which is the standard pattern when `__init__` will set them per instance.

<h1 id="container-types-with-built-ins">Container Types with Built-ins</h1>

Container annotations describe both the container and what it holds. Since Python 3.9 (PEP 585), the built-in container types support subscript syntax directly. This is the form to use in any code targeting 3.9 or later.

| Annotation         | Meaning                                     |
| ------------------ | ------------------------------------------- |
| `list[int]`        | List of integers                            |
| `list[str]`        | List of strings                             |
| `dict[str, float]` | Dict mapping strings to floats              |
| `tuple[str, int]`  | Two-element tuple: string then int          |
| `tuple[int, ...]`  | Variable-length tuple of ints               |
| `set[str]`         | Set of strings                              |
| `frozenset[int]`   | Frozen set of ints                          |
| `type[Product]`    | The `Product` class itself, not an instance |

These work anywhere a type goes: parameter annotations, return annotations, variable annotations, class-body annotations.

```python
def average_rating(ratings: list[float]) -> float:
    return sum(ratings) / len(ratings)

def best_sellers(sales: dict[str, int], top_n: int) -> list[str]:
    return sorted(sales, key=sales.get, reverse=True)[:top_n]

ratings = [4.5, 4.1, 3.8, 4.6, 4.7]
sales = {"Wireless Mouse": 1200, "USB Cable": 870, "Charger": 1500, "Webcam": 540}

print(f"Average rating: {average_rating(ratings):.2f}")
print(f"Top sellers: {best_sellers(sales, 2)}")
```

Tuples are the one container where annotation shape matters in a non-obvious way. A tuple's length is part of its type, so the type system has two distinct forms:

```python
# Fixed-length, each position has its own type
shipping_address: tuple[str, str, str, int] = ("123 Main St", "Apt 5", "Springfield", 62701)

# Variable-length, homogeneous
product_ids: tuple[int, ...] = (101, 204, 318, 425)

# One-element tuple, exactly one int
singleton: tuple[int] = (42,)

print(shipping_address)
print(product_ids)
print(singleton)
```

`tuple[int, ...]` says "any number of ints, possibly zero". `tuple[int]` says "exactly one int". The ellipsis is part of the typing grammar, not a placeholder you fill in later.

Container generics nest. A function that takes a dict mapping customer IDs to a list of their order totals looks like this:

```python
def loyalty_status(orders: dict[int, list[float]]) -> dict[int, str]:
    status = {}
    for customer_id, totals in orders.items():
        spent = sum(totals)
        if spent > 1000:
            status[customer_id] = "gold"
        elif spent > 250:
            status[customer_id] = "silver"
        else:
            status[customer_id] = "bronze"
    return status

orders = {
    42: [29.99, 99.99, 49.50, 1200.00],
    101: [14.99, 9.99, 39.99],
    202: [499.00, 250.00],
}
print(loyalty_status(orders))
```

`dict[int, list[float]]` reads naturally: a dict whose keys are ints and whose values are lists of floats. The return `dict[int, str]` is the same shape with different inner types.

Subscripting a built-in like `list[int]` creates a small `GenericAlias` object every time the code runs. It's cheap, but constructing annotations dynamically inside a hot loop is wasteful. Annotations on function signatures are evaluated once at function-definition time, so this only matters when building types in user code, which is unusual.
