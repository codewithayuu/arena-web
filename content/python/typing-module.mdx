<LessonCard>

This lesson is about the `typing` module, the standard library module that fills in everything basic generics don't cover: optional values, multiple allowed types, function signatures as values, and the abstract collection types you should reach for when writing function parameters. We'll also cover the modern `|` operator, which has quietly replaced most of `typing.Union` and `typing.Optional` in idiomatic 3.10+ code.

<h1 id="what-the-typing-module-gives-you">What the typing Module Gives You</h1>

Before Python 3.9, the built-in collection types like `list` and `dict` couldn't be parameterized. If you wanted to say "list of strings", you had to import `List` from `typing` and write `List[str]`. Since 3.9, plain `list[str]` works, and since 3.10 the `X | Y` syntax replaces `Union[X, Y]`.

So what's left in `typing` that you still need? Quite a bit:

| Construct                                     | Purpose                                           | Modern alternative      |
| --------------------------------------------- | ------------------------------------------------- | ----------------------- |
| `Optional[X]`                                 | Value is either `X` or `None`                     | `X \| None` (3.10+)     |
| `Union[X, Y]`                                 | Value is one of several types                     | `X \| Y` (3.10+)        |
| `Callable[[A, B], R]`                         | A callable with given arg and return types        | No built-in replacement |
| `Iterable[T]`, `Iterator[T]`                  | Anything you can loop over once or step through   | No built-in replacement |
| `Sequence[T]`, `Mapping[K, V]`                | Read-only list-like or dict-like input            | No built-in replacement |
| `Any`, `NoReturn`, `Never`                    | Special types with no built-in equivalent         | No built-in replacement |
| `TypeVar`, `Generic`, `Protocol`, `TypedDict` | Building blocks for generic and structural typing | No built-in replacement |

The right mental model: `typing` is now a module for the things that aren't plain collection generics. The built-in generics handle the common case of "list of products" or "dict of name to price". `typing` handles everything else.

```python
from typing import Optional, Union, Callable, Iterable, Sequence, Mapping

def total(prices: Iterable[float]) -> float:
    return sum(prices)

def find_product(product_id: int) -> Optional[str]:
    catalog = {1: "Wireless Mouse", 2: "USB Cable"}
    return catalog.get(product_id)

print(total([29.99, 14.99, 9.99]))
print(find_product(1))
print(find_product(99))
```

Each of those typing constructs answers a real question. `Optional` says "this lookup might miss". `Iterable` says "I'll accept anything you can loop over, not just a list". The rest of this lesson walks through them one at a time.

<h1 id="legacy-generic-aliases-list-dict-tuple">
  Legacy Generic Aliases (List, Dict, Tuple)
</h1>

Before Python 3.9, parameterizing a collection required importing its capitalized alias from `typing`:

```python
from typing import List, Dict, Tuple, Set, FrozenSet

def cart_total(items: List[float]) -> float:
    return sum(items)

def product_prices() -> Dict[str, float]:
    return {"Wireless Mouse": 29.99, "USB Cable": 4.99}

def shipping_address() -> Tuple[str, str, str]:
    return ("221B Baker Street", "London", "NW1 6XE")

def unique_categories(items: List[str]) -> Set[str]:
    return set(items)

def fixed_tags(tags: List[str]) -> FrozenSet[str]:
    return frozenset(tags)

print(cart_total([29.99, 14.99]))
print(product_prices())
print(shipping_address())
print(unique_categories(["electronics", "electronics", "cables"]))
print(fixed_tags(["sale", "new"]))
```

Every one of those capitalized aliases maps to the equivalent lowercase built-in:

| Legacy (`typing`)    | Modern (built-in)    | Since |
| -------------------- | -------------------- | ----- |
| `List[T]`            | `list[T]`            | 3.9   |
| `Dict[K, V]`         | `dict[K, V]`         | 3.9   |
| `Tuple[T1, T2, ...]` | `tuple[T1, T2, ...]` | 3.9   |
| `Set[T]`             | `set[T]`             | 3.9   |
| `FrozenSet[T]`       | `frozenset[T]`       | 3.9   |
| `Type[X]`            | `type[X]`            | 3.9   |

The same function in modern style:

```python
def cart_total(items: list[float]) -> float:
    return sum(items)

def product_prices() -> dict[str, float]:
    return {"Wireless Mouse": 29.99, "USB Cable": 4.99}

def shipping_address() -> tuple[str, str, str]:
    return ("221B Baker Street", "London", "NW1 6XE")
```

No imports needed. The capitalized aliases are still in `typing` and still work, mostly because removing them would break years of existing code. PEP 585 (the change that allowed `list[int]` to work as a type) explicitly says the typing aliases will be deprecated but kept around indefinitely.

When you read old code, you'll see the capitalized forms everywhere. When you write new code on 3.9 or later, use the lowercase built-ins. Mixing both in the same project works fine, but the type checker will sometimes complain if you use the capitalized form in a brand-new file.

> **Note:** Python 3.7 and 3.8 still require `from __future__ import annotations` to use `list[int]` as a runtime annotation. If you're stuck on 3.8, the capitalized aliases are your only option without the future import. Anything 3.9+ supports both styles freely.

<h1 id="optional-for-values-that-may-be-none">
  Optional for Values That May Be None
</h1>

`Optional[X]` means "either an `X` or `None`". It's the single most useful construct in `typing` because the `None` case shows up everywhere: lookups that miss, fields that aren't set yet, parameters that default to `None`, return values that mean "not found".

```python
from typing import Optional

def find_product_name(product_id: int) -> Optional[str]:
    catalog = {1: "Wireless Mouse", 2: "USB Cable", 3: "HDMI Cable"}
    return catalog.get(product_id)

found = find_product_name(2)
missing = find_product_name(999)

print(found)
print(missing)
```

The return type `Optional[str]` is exactly equivalent to `Union[str, None]`. The `Optional` form exists because the "value or None" pattern is so common that it earned its own shorthand.

A second classic use case is parameters that default to `None`:

```python
from typing import Optional

def add_to_cart(product: str, quantity: int = 1, note: Optional[str] = None) -> dict:
    item = {"product": product, "quantity": quantity}
    if note is not None:
        item["note"] = note
    return item

print(add_to_cart("Wireless Mouse"))
print(add_to_cart("Webcam", quantity=2, note="Gift wrap, please"))
```

The `note` parameter accepts a string or `None`. The default is `None`, which means "no note provided". Without `Optional`, a checker would flag the default value because `None` isn't a `str`.

One common mistake worth flagging: `Optional[X]` does **not** mean "this parameter is optional in the function-call sense". It only describes the value's type. A parameter that has a default value is optional to the caller; a parameter typed `Optional[X]` is one whose value might be `None`. These are independent concepts that happen to share a word.

```python
from typing import Optional

# Required parameter that might be None
def log_event(event_type: str, customer_id: Optional[int]) -> None:
    if customer_id is None:
        print(f"Event: {event_type} (anonymous)")
    else:
        print(f"Event: {event_type} (customer {customer_id})")

# Caller must pass something, but None is allowed
log_event("page_view", None)
log_event("page_view", 42)
```

Here `customer_id` has no default, so the caller must pass an argument. That argument can be an `int` or `None`. The function signature documents both halves of that statement.

<h1 id="union-for-multiple-allowed-types">Union for Multiple Allowed Types</h1>

`Union[X, Y]` says the value is one of several types. The classic case is a value that comes in two representations and you handle both.

```python
from typing import Union

def apply_discount(price: float, discount: Union[int, float]) -> float:
    # discount can be an int (cents off) or float (fraction off)
    if isinstance(discount, int):
        return price - (discount / 100)
    return price * (1 - discount)

print(apply_discount(29.99, 500))      # 500 cents off
print(apply_discount(29.99, 0.10))     # 10% off
```

The `discount` parameter accepts either an `int` (interpreted as cents) or a `float` (interpreted as a fraction). The function branches on the actual type at runtime. The type checker knows that inside the `if isinstance(discount, int)` block, `discount` is narrowed to `int`, and in the `else` branch it's narrowed to `float`. This is called type narrowing, and it's one of the main reasons static type checkers exist.

`Union` accepts more than two types:

```python
from typing import Union

def format_product_id(pid: Union[int, str, bytes]) -> str:
    if isinstance(pid, bytes):
        return pid.decode("utf-8")
    return str(pid)

print(format_product_id(42))
print(format_product_id("SKU-9921"))
print(format_product_id(b"SKU-9921"))
```

Three branches in the union, three branches in the function. The pattern of "isinstance-check then handle each case" is how you safely use a `Union` parameter.

One useful fact: `Union[X, X]` collapses to `X`, and `Union[X, None]` is the same as `Optional[X]`. The order also doesn't matter; `Union[int, str]` and `Union[str, int]` are the same type.

> **Note:** A function returning `Union[int, str]` is harder for callers to use than one returning just `int` or just `str`. Every caller has to check which type they got. Use unions when the two representations genuinely matter to the caller, not as a shortcut around picking a single return type.

<h1 id="the-operator-python-310">The | Operator (Python 3.10+)</h1>

Python 3.10 introduced the `|` operator as a shorthand for `Union`. It works directly on types, no import needed.

```python
def apply_discount(price: float, discount: int | float) -> float:
    if isinstance(discount, int):
        return price - (discount / 100)
    return price * (1 - discount)

def find_product_name(product_id: int) -> str | None:
    catalog = {1: "Wireless Mouse", 2: "USB Cable"}
    return catalog.get(product_id)

print(apply_discount(29.99, 500))
print(find_product_name(1))
print(find_product_name(99))
```

The two forms are exactly equivalent. The `|` form has three practical advantages:

1. **No import.** `int | float` works in any file without touching `typing`.
2. **Reads naturally.** "A `str` or `None`" maps cleanly to `str | None` in a way `Optional[str]` doesn't quite match.
3. **Composes cleanly.** `int | str | bytes` is shorter than `Union[int, str, bytes]`.

In modern Python codebases, `|` is the default. Reach for `Optional` and `Union` from `typing` only when you have to support Python 3.9 or older.

```python
# Modern (3.10+)
def add_to_cart(product: str, note: str | None = None) -> dict:
    item = {"product": product}
    if note is not None:
        item["note"] = note
    return item

# Legacy-compatible (works on 3.8+)
from typing import Optional

def add_to_cart_legacy(product: str, note: Optional[str] = None) -> dict:
    item = {"product": product}
    if note is not None:
        item["note"] = note
    return item

print(add_to_cart("Mouse", "Gift wrap"))
print(add_to_cart_legacy("Mouse", "Gift wrap"))
```

Same behavior, two style choices. If your team's minimum supported version is 3.10 or later, prefer the pipe. If you need to ship libraries that still support 3.8 or 3.9 at runtime, use `Optional` and `Union`.

The decision is mechanical: if your target Python version is 3.10 or higher, the pipe wins on every axis. Otherwise the typing-module forms still work.

<h1 id="callable-for-function-types">Callable for Function Types</h1>

A function in Python is a value, like any other. You can pass it as an argument, store it in a list, or return it from another function. To type-hint these "function-typed" values, you use `Callable` from `typing`.

`Callable[[arg_types], return_type]` is the form. The arg types go in a bracketed list (even if there's only one), and the return type comes after the closing inner bracket.

```python
from typing import Callable

def apply_to_price(price: float, transform: Callable[[float], float]) -> float:
    return transform(price)

def round_up(price: float) -> float:
    import math
    return math.ceil(price)

def add_tax(price: float) -> float:
    return price * 1.08

print(apply_to_price(29.99, round_up))
print(apply_to_price(29.99, add_tax))
print(apply_to_price(29.99, lambda p: p * 0.9))
```

The `transform` parameter is any function that takes a `float` and returns a `float`. The three calls pass three different callables: a named function, another named function, and a lambda. All three match the signature.

A more interesting case: building a discount strategy where the caller supplies the rule.

```python
from typing import Callable

def total_with_discount(
    prices: list[float],
    discount_rule: Callable[[float], float],
) -> float:
    return sum(discount_rule(p) for p in prices)

# Different rules the caller can choose between
def flat_10_percent(price: float) -> float:
    return price * 0.9

def free_under_5(price: float) -> float:
    return 0.0 if price < 5 else price

def bulk_discount(price: float) -> float:
    if price > 50:
        return price * 0.8
    if price > 20:
        return price * 0.9
    return price

prices = [29.99, 4.99, 14.99, 59.99]

print(f"Flat 10%:     {total_with_discount(prices, flat_10_percent):.2f}")
print(f"Free under 5: {total_with_discount(prices, free_under_5):.2f}")
print(f"Bulk:         {total_with_discount(prices, bulk_discount):.2f}")
```

Each rule has the same shape, `float -> float`, so any of them slots into the `discount_rule` parameter. The type checker enforces the shape across all three call sites. If someone tried to pass `bulk_discount` as a `Callable[[str], float]` somewhere else, the checker would catch it.

A few signature variations worth knowing:

| Annotation                   | Meaning                                                              |
| ---------------------------- | -------------------------------------------------------------------- |
| `Callable[[], int]`          | No arguments, returns `int`                                          |
| `Callable[[float], float]`   | One `float` argument, returns `float`                                |
| `Callable[[str, int], bool]` | Two arguments, returns `bool`                                        |
| `Callable[..., float]`       | Any arguments, returns `float` (when you don't care about arg types) |
| `Callable[[float], None]`    | Takes a `float`, returns nothing useful (procedure-style)            |

The `...` form is an escape hatch. It says "this is callable, but I don't want to constrain how it's called". Use it sparingly; you lose most of the safety the annotation was supposed to provide.

```python
from typing import Callable

def run_callback(cb: Callable[..., None], *args, **kwargs) -> None:
    cb(*args, **kwargs)

def log_order(order_id: int, status: str) -> None:
    print(f"Order {order_id}: {status}")

run_callback(log_order, 1001, "shipped")
run_callback(log_order, 1002, status="delivered")
```

The `Callable[..., None]` annotation accepts callables with any signature that returns `None`. Useful for generic dispatch, less useful when you want the checker to verify the call sites match.

> **Note:** `Callable` checks the call signature, not whether the value is literally a function. Anything with a compatible `__call__` method, including a class instance with `__call__` defined, satisfies a `Callable` annotation. The checker doesn't care if you wrote `def`, `lambda`, or a class; it only cares about the call shape.

<h1 id="abstract-collection-types-iterable-sequence-mapping">
  Abstract Collection Types (Iterable, Sequence, Mapping)
</h1>

When you write a function parameter typed `list[float]`, the checker rejects anything that isn't a `list`. Pass a tuple, generator, or NumPy array, and the checker complains, even if your function only iterates the input and never calls list-specific methods.

The fix is to type your parameters by the **abstract capability** you need, not the concrete type. The `typing` module exports a set of abstract types that describe what an object can do, not what it is:

| Annotation             | Means the value supports...                  | Example types that match                       |
| ---------------------- | -------------------------------------------- | ---------------------------------------------- |
| `Iterable[T]`          | Being looped over once (`for x in obj`)      | list, tuple, set, generator, dict (keys), file |
| `Iterator[T]`          | Being stepped through with `next()`          | generator, `iter(some_list)`                   |
| `Sequence[T]`          | Indexing (`obj[i]`), `len()`, iteration      | list, tuple, str, range                        |
| `Mapping[K, V]`        | `obj[k]`, `k in obj`, `.keys()`, `.values()` | dict, `types.MappingProxyType`                 |
| `MutableMapping[K, V]` | Mapping plus `obj[k] = v`, `del obj[k]`      | dict                                           |
| `MutableSequence[T]`   | Sequence plus `.append`, `.remove`, etc.     | list                                           |

The rule of thumb: **for function inputs, use the most abstract type that still gives you everything you need. For function outputs, use the concrete type.**

```python
from typing import Iterable, Sequence, Mapping

# Iterable: I'll loop over the prices once
def cart_total(prices: Iterable[float]) -> float:
    return sum(prices)

# Sequence: I need to index, get the length, or iterate
def first_n_products(products: Sequence[str], n: int) -> list[str]:
    return list(products[:n])

# Mapping: I need to look up by key
def lookup_prices(catalog: Mapping[str, float], names: Iterable[str]) -> list[float]:
    return [catalog[name] for name in names if name in catalog]

# All three are happy with concrete inputs
print(cart_total([29.99, 14.99]))                  # list
print(cart_total((29.99, 14.99)))                  # tuple
print(cart_total(p for p in [29.99, 14.99]))       # generator

print(first_n_products(["Mouse", "Cable", "Webcam"], 2))   # list
print(first_n_products(("Mouse", "Cable", "Webcam"), 2))   # tuple

print(lookup_prices({"Mouse": 29.99, "Cable": 4.99}, ["Mouse"]))
```

Each function accepts a wider range of inputs than its `list`/`dict` counterpart would. `cart_total` doesn't care whether the caller has a list, a tuple, or a generator. The function only iterates, and `Iterable` documents exactly that.

The contrast with the concrete-type version is worth seeing:

```python
def cart_total_strict(prices: list[float]) -> float:
    return sum(prices)

# This works at runtime but a type checker would flag it
cart_total_strict((29.99, 14.99))   # passing a tuple to a list parameter
```

The function runs fine because `sum()` doesn't care about the container, but a static checker treats the call as a type error. The `list[float]` annotation is a stricter promise than the function actually needs.

A second example, with a function that processes orders. It only needs to read the order ID and the items, never mutate the input:

```python
from typing import Sequence, Mapping

def order_summary(order: Mapping[str, object]) -> str:
    order_id = order["id"]
    items: Sequence[str] = order["items"]   # type: ignore[assignment]
    return f"Order {order_id}: {len(items)} item(s)"

order = {
    "id": 1001,
    "items": ["Wireless Mouse", "HDMI Cable", "Charger"],
}

print(order_summary(order))
```

The function reads keys from a `Mapping`. It doesn't insert, delete, or replace anything, so `Mapping` is correct and `MutableMapping` would over-promise.

The same principle for outputs, in reverse: when you return a value, be concrete.

```python
from typing import Iterable

def discounted_prices(prices: Iterable[float], rate: float) -> list[float]:
    return [p * (1 - rate) for p in prices]

print(discounted_prices((29.99, 14.99, 9.99), 0.10))
```

The input is `Iterable[float]` so callers can pass any iterable. The return is `list[float]` because that's what the function actually builds, and the caller can rely on list-specific behavior like indexing or appending. Returning `Iterable[float]` here would force callers to convert the result themselves.

This "accept widely, return narrowly" pattern is sometimes called the **robustness principle** of API design. The function is generous with what it accepts and specific about what it produces.

One gotcha with `Iterable`: a generator can be iterated only once. If your function iterates the input twice, `Iterable` is technically the wrong type. Use `Sequence` (which can be re-iterated) or convert to a list inside the function.

```python
from typing import Iterable

def report_prices(prices: Iterable[float]) -> None:
    # Bug: iterating twice over the same Iterable doesn't work for generators
    total = sum(prices)
    count = sum(1 for _ in prices)   # second pass yields nothing for a generator
    print(f"Total: {total}, Count: {count}")

prices_gen = (p for p in [29.99, 14.99, 9.99])
report_prices(prices_gen)
```

The first `sum(prices)` exhausts the generator. The second pass sees zero items. The fix is either to require `Sequence`, which guarantees multi-pass iteration, or materialize the input:

```python
from typing import Iterable

def report_prices(prices: Iterable[float]) -> None:
    prices = list(prices)   # one-shot conversion to a re-iterable container
    total = sum(prices)
    count = sum(1 for _ in prices)
    print(f"Total: {total}, Count: {count}")

report_prices(p for p in [29.99, 14.99, 9.99])
```

The conversion is a tradeoff: you accept any iterable but pay the cost of materializing it. Pick the type that matches what your function actually does.

> **Cost:** Materializing an `Iterable` into a list with `list(prices)` is O(n) in both time and memory. For a small cart this is free. For a million-row report you might want `Sequence` (so callers must pass something re-iterable, but you don't allocate) or two parameters (count and a fresh iterator each time).
