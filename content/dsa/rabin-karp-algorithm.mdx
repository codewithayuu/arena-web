<LessonCard>

KMP is fast for one pattern but searching for 1,000 patterns in the same text means 1,000 passes through it. Rabin-Karp takes a different approach: hash each window of the text and compare the hash to the pattern's hash. Equal hashes trigger a character-by-character verification; unequal hashes are skipped in O(1). With a rolling hash, the hash of each new window is computed from the previous one in O(1).

This chapter covers the rolling hash, modular arithmetic, the full algorithm, collision handling, and multi-pattern search.

<h2 id="the-core-idea-hashing-substrings">The Core Idea: Hashing Substrings</h2>

The strategy:

1. Compute the hash of the pattern.
2. For each window of length m in the text, compute the window's hash.
3. If the window's hash equals the pattern's hash, verify character by character.
4. If not, slide the window forward without comparing characters.

Comparing two numbers is O(1); comparing two strings of length m is O(m). A good hash function makes most windows differ from the pattern in their hash value, so the O(m) verification fires rarely.

Two different strings can produce the same hash, a **collision**. When the hashes match but the strings do not, that is a **spurious hit**. Verification handles them. With a good hash function, spurious hits are rare.

<h2 id="rolling-hash-the-key-to-efficiency">
  Rolling Hash: The Key to Efficiency
</h2>

Computing each window's hash independently is O(m) per window and O(n\*m) overall, the same as brute force. A rolling hash computes the next window's hash from the current one in O(1), because consecutive windows differ by exactly two characters: one leaves the left edge, one enters the right.

**Polynomial Hash Function**

Each character's contribution depends on its position:

```text
hash(s[0..m-1]) = s[0] * d^(m-1) + s[1] * d^(m-2) + ... + s[m-1] * d^0
```

Here `d` is the base (often the alphabet size, like 256 for ASCII), and `s[i]` is the numeric value of the character (ASCII code).

The polynomial form is better than a simple sum of character values because it makes the hash sensitive to position: "ABC" and "CBA" sum to the same value but have different polynomial hashes. It is also what makes the O(1) rolling update work.

Example with d = 256 and pattern "ABC":

```text
hash("ABC") = 'A' * 256^2 + 'B' * 256^1 + 'C' * 256^0
            = 65 * 65536 + 66 * 256 + 67
            = 4,294,144 + 16,896 + 67
            = 4,311,107
```

**The Rolling Update**

Sliding the window one position right removes the leftmost character and adds a new rightmost character:

```text
hash(s[i+1..i+m]) = (hash(s[i..i+m-1]) - s[i] * d^(m-1)) * d + s[i+m]
```

Step by step:

1. **Remove the leftmost character**: subtract `s[i] * d^(m-1)`, the outgoing character's contribution at the highest power.
2. **Shift everything left**: multiply by `d`. Every remaining character's power increases by 1.
3. **Add the new character**: add `s[i+m]` at the lowest power (d^0).

Analogous to a sliding window sum, but with a polynomial instead of a plain sum.

<h2 id="modular-arithmetic-avoiding-overflow">
  Modular Arithmetic: Avoiding Overflow
</h2>

The polynomial values grow quickly. With d = 256 and m = 20, the leading term is 256^19, a 46-digit number that no primitive integer holds.

Fix: pick a large prime `q` (commonly 10^9 + 7 or 10^9 + 9) and do every hash operation modulo q:

```text
hash(s[0..m-1]) = (s[0] * d^(m-1) + s[1] * d^(m-2) + ... + s[m-1]) mod q
```

The rolling update becomes:

```text
hash_new = ((hash_old - s[i] * d^(m-1) mod q) * d + s[i+m]) mod q
```

Two details to get right:

**1. Pre-compute d^(m-1) mod q**

Compute it once before the main loop using modular exponentiation.

**2. Handle negative remainders**

Subtracting `s[i] * d^(m-1)` can make the intermediate value negative. In C, C++, Java, JavaScript, and most languages, `%` of a negative number returns a negative result. Fix:

```text
hash = ((hash % q) + q) % q
```

This keeps the hash in [0, q-1]. Python's `%` already returns a non-negative result for a positive divisor, so the correction is a no-op there.

Skipping this correction is a common Rabin-Karp bug. If the hash goes negative, the algorithm reports wrong matches without crashing.

<h2 id="the-complete-algorithm">The Complete Algorithm</h2>

Two phases: preprocessing (compute pattern hash and first window hash) and searching (slide the window, comparing hashes).

Full implementation:

```java
public static List<Integer> rabinKarp(String text, String pattern) {
    List<Integer> result = new ArrayList<>();
    int n = text.length();
    int m = pattern.length();
    if (m > n) return result;

    int d = 256;         // alphabet size
    long q = 1000000007; // large prime modulus

    // Compute d^(m-1) mod q
    long h = 1;
    for (int i = 0; i < m - 1; i++) {
        h = (h * d) % q;
    }

    // Hash of pattern and first window
    long patternHash = 0;
    long windowHash = 0;
    for (int i = 0; i < m; i++) {
        patternHash = (patternHash * d + pattern.charAt(i)) % q;
        windowHash = (windowHash * d + text.charAt(i)) % q;
    }

    // Slide the window
    for (int i = 0; i <= n - m; i++) {
        if (windowHash == patternHash) {
            boolean match = true;
            for (int j = 0; j < m; j++) {
                if (text.charAt(i + j) != pattern.charAt(j)) {
                    match = false;
                    break;
                }
            }
            if (match) {
                result.add(i);
            }
        }

        // Rolling update
        if (i < n - m) {
            windowHash = ((windowHash - text.charAt(i) * h % q + q) * d
                          + text.charAt(i + m)) % q;
        }
    }

    return result;
}
```

<h2 id="step-by-step-trace">Step-by-Step Trace</h2>

```text
Text:    A B C C D A B C D
Pattern: A B C D
d = 256, q = 101 (small prime for illustration)
ASCII: A=65, B=66, C=67, D=68
```

**Preprocessing:**

Compute `h = d^(m-1) mod q = 256^3 mod 101`.

```text
256^1 mod 101 = 54        // 256 - 2*101 = 54
256^2 mod 101 = (54 * 256) mod 101 = 13824 mod 101 = 88
256^3 mod 101 = (88 * 256) mod 101 = 22528 mod 101 = 5

So h = 5
```

Pattern hash for "ABCD":

```text
patternHash = 0
patternHash = (0 * 256 + 65) mod 101  = 65        // 'A' = 65
patternHash = (65 * 256 + 66) mod 101 = 16706 mod 101 = 41
patternHash = (41 * 256 + 67) mod 101 = 10563 mod 101 = 59
patternHash = (59 * 256 + 68) mod 101 = 15172 mod 101 = 22
```

First window hash ("ABCC"):

```text
windowHash = 0
windowHash = (0 * 256 + 65) mod 101  = 65         // 'A'
windowHash = (65 * 256 + 66) mod 101 = 41         // 'B'
windowHash = (41 * 256 + 67) mod 101 = 59         // 'C'
windowHash = (59 * 256 + 67) mod 101 = 15171 mod 101 = 21  // 'C'
```

**Searching:**

One character-by-character verification out of six windows. The other five were ruled out by hash comparison alone.

No spurious hits in this example. With a small modulus like 101, spurious hits are more likely. In practice, q = 10^9 + 7 makes the chance of a spurious hit at any window roughly 1 in a billion.

<h2 id="collision-handling">Collision Handling</h2>

A **spurious hit** is a window whose hash matches the pattern's hash but whose characters differ. Different strings can land on the same hash because the hash function maps a large space (all strings of length m) to a smaller one (integers from 0 to q-1).

For a single window, the probability of a spurious hit is about 1/q. Across n - m + 1 windows, the expected number is (n - m + 1) / q. With q = 10^9 + 7 and a text of length 10^6, that is fewer than 0.001 spurious hits on average.

The worst case for Rabin-Karp comes from one of two situations:

1. **Many true matches.** Text = "AAAA...A" (n A's) and pattern = "AAA" (m A's, m < n). Every window is a real match, so verification fires at every window. Each verification is O(m), so total time is O(n\*m). This is the realistic worst case in practice.
2. **Adversarial input that triggers hash collisions.** An attacker who knows the hash parameters (d, q) can construct text and pattern strings that share the same hash value at many windows without being equal. Without that knowledge (e.g., by randomizing the hash parameters per run), this case is astronomically unlikely.

The "AAAA...A" text with "AAA...AB" pattern is sometimes cited as a worst case but is not: those two strings differ in their last character, so their polynomial hashes are typically different and verification rarely fires.

**Mitigating Collisions**

- **Choose a large prime modulus**: q = 10^9 + 7 is standard. A larger q means fewer collisions.
- **Double hashing**: compute two independent hashes (different base + prime). A spurious hit requires both to collide, dropping the probability to roughly 1/q^2.
- **Prime base**: d as a prime (31, 37) instead of 256 improves distribution on inputs with structure.
- **Randomize parameters at runtime**: pick d and q randomly each run, defeating adversarial inputs.

Rabin-Karp's O(n+m) is expected, not guaranteed. KMP's O(n+m) is guaranteed regardless of input. The trade-off is worth taking when the multi-pattern capability matters.

<h3 id="double-hashing-in-practice">Double Hashing in Practice</h3>

A single hash with q = 10^9 + 7 gives a collision probability of about 10^-9 per window. Double hashing drives that to about 10^-18, low enough that many implementations skip the character-by-character verification entirely and trust the double hash. The cost is one extra multiply and modulo per window.

```java
public static List<Integer> rabinKarpDoubleHash(String text, String pattern) {
    List<Integer> result = new ArrayList<>();
    int n = text.length(), m = pattern.length();
    if (m > n) return result;

    // Two independent (base, modulus) pairs
    long d1 = 256, q1 = 1_000_000_007L;
    long d2 = 257, q2 = 998_244_353L;

    // d^(m-1) for each hash
    long h1 = 1, h2 = 1;
    for (int i = 0; i < m - 1; i++) {
        h1 = (h1 * d1) % q1;
        h2 = (h2 * d2) % q2;
    }

    long ph1 = 0, ph2 = 0;
    long wh1 = 0, wh2 = 0;
    for (int i = 0; i < m; i++) {
        ph1 = (ph1 * d1 + pattern.charAt(i)) % q1;
        ph2 = (ph2 * d2 + pattern.charAt(i)) % q2;
        wh1 = (wh1 * d1 + text.charAt(i)) % q1;
        wh2 = (wh2 * d2 + text.charAt(i)) % q2;
    }

    for (int i = 0; i <= n - m; i++) {
        // Both hashes must match. Skip the character verification.
        if (wh1 == ph1 && wh2 == ph2) {
            result.add(i);
        }
        if (i < n - m) {
            wh1 = ((wh1 - text.charAt(i) * h1 % q1 + q1) * d1
                   + text.charAt(i + m)) % q1;
            wh2 = ((wh2 - text.charAt(i) * h2 % q2 + q2) * d2
                   + text.charAt(i + m)) % q2;
        }
    }
    return result;
}
```

```rust
    let (d1, q1): (i64, i64) = (256, 1_000_000_007);
    let (d2, q2): (i64, i64) = (257, 998_244_353);

    let mut h1: i64 = 1;
    let mut h2: i64 = 1;
    for _ in 0..m - 1 {
        h1 = (h1 * d1) % q1;
        h2 = (h2 * d2) % q2;
    }

    let mut ph1: i64 = 0;
    let mut ph2: i64 = 0;
    let mut wh1: i64 = 0;
    let mut wh2: i64 = 0;
    for i in 0..m {
        ph1 = (ph1 * d1 + p[i] as i64) % q1;
        ph2 = (ph2 * d2 + p[i] as i64) % q2;
        wh1 = (wh1 * d1 + t[i] as i64) % q1;
        wh2 = (wh2 * d2 + t[i] as i64) % q2;
    }

    for i in 0..=n - m {
        if wh1 == ph1 && wh2 == ph2 {
            result.push(i);
        }
        if i < n - m {
            wh1 = ((wh1 - t[i] as i64 * h1 % q1 + q1) * d1 + t[i + m] as i64) % q1;
            wh2 = ((wh2 - t[i] as i64 * h2 % q2 + q2) * d2 + t[i + m] as i64) % q2;
        }
    }
    result
}
```

For safety-critical code (cryptographic tools, plagiarism detection where false positives matter), keep the character verification even with double hashing. For typical competitive-programming or batch-processing use cases, skipping it is fine.

<h2 id="multi-pattern-search">Multi-Pattern Search</h2>

Multi-pattern is where Rabin-Karp beats KMP. Searching for k patterns with KMP means k passes over the text, O(n\*k). Rabin-Karp scans for all k patterns in a single pass.

Approach:

1. Compute the hash of each pattern. Store all hashes in a HashSet (or a HashMap mapping hash → list of patterns with that hash, for collision handling).
2. Slide a window across the text and maintain a rolling hash.
3. At each window, check if its hash is in the HashSet. O(1) lookup.
4. On a hit, verify against patterns with that hash.

Assuming all k patterns have the same length m, total time is O(n + k*m): O(k*m) to hash the patterns, then O(n) to scan the text.

For patterns of different lengths, group them by length and run one pass per distinct length. **Aho-Corasick** is the standard algorithm when you have many patterns of varying lengths and need the lowest possible asymptotic cost; it runs in O(n + total pattern length + number of matches) in a single pass.

**Real-world workloads** that use multi-pattern hashing:

- **Plagiarism detection**: check if any of thousands of known passages appear in a submitted document.
- **Virus scanning**: match a database of virus signatures against file contents.
- **Dictionary matching in NLP**: find all dictionary words appearing in a text.
- **Code clone detection**: find duplicated code blocks across a codebase.

<h2 id="comparison-with-kmp">Comparison with KMP</h2>

KMP preprocesses the pattern into a failure function and avoids redundant character comparisons. Rabin-Karp preprocesses the pattern into a hash value and enables O(1) window comparisons.

| Aspect               | KMP                                    | Rabin-Karp                                  |
| -------------------- | -------------------------------------- | ------------------------------------------- |
| Worst-case time      | O(n + m), guaranteed                   | O(n \* m), due to collisions                |
| Average-case time    | O(n + m)                               | O(n + m)                                    |
| Multi-pattern search | O(n \* k) for k patterns               | O(n + k \* m) with HashSet                  |
| Space complexity     | O(m) for failure function              | O(1) for single pattern                     |
| Preprocessing        | Builds failure function                | Computes hash value                         |
| Depends on           | Pattern structure                      | Hash function quality                       |
| Implementation       | Moderate (failure function is tricky)  | Moderate (modular arithmetic is tricky)     |
| Best for             | Single pattern, guaranteed performance | Multiple patterns, average-case performance |

**KMP** when worst-case time matters: a single pattern, possibly adversarial input.

**Rabin-Karp** when searching many patterns at once, or when the rolling hash is useful for related problems (longest duplicate substring, content-defined chunking, similarity hashing).

<h2 id="complexity-analysis">Complexity Analysis</h2>

**Time Complexity:**

- **Preprocessing**: O(m) to compute the pattern hash and the first window hash.
- **Searching (expected)**: O(n - m + 1) for the rolling hash updates, plus O(m) for each true match verification. If there are `occ` occurrences, the total expected time is O(n + occ \* m). For a constant number of occurrences, this simplifies to O(n + m).
- **Searching (worst case)**: O(n \* m) when every window produces a hash collision, forcing character verification at every position.

**Space Complexity:**

- **Single pattern**: O(1) extra space (just a few hash variables).
- **Multi-pattern with k patterns**: O(k) for the HashSet of pattern hashes.

**Comparison with brute force:**

| Metric        | Brute Force | Rabin-Karp (expected) | Rabin-Karp (worst) |
| ------------- | ----------- | --------------------- | ------------------ |
| Time          | O(n \* m)   | O(n + m)              | O(n \* m)          |
| Space         | O(1)        | O(1)                  | O(1)               |
| Preprocessing | None        | O(m)                  | O(m)               |

Expected O(n + m) makes Rabin-Karp competitive with KMP for single patterns and better for multi-pattern search. The O(n \* m) worst case is a theoretical concern that rarely shows up in practice with a good hash function and large prime.
