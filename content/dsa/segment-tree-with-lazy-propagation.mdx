<LessonCard>

If a later operation never recurses into that subtree before another update overwrites it, the deferred work is dropped entirely. The same idea shows up in write-back caches and copy-on-write: do nothing until something forces you to.

<h3 id="lazy-markers-on-a-tree">Lazy Markers on a Tree</h3>

Here is what a segment tree looks like after a range update with lazy propagation. Some nodes carry "lazy" values, meaning they have pending updates that have not been pushed to their children yet.

The orange nodes have lazy markers. Their children have not been updated yet, but the parent's sum already reflects the pending addition. When we eventually need to access a child, we push the lazy value down at that point.

<h1 id="how-it-works-core-operations">How It Works: Core Operations</h1>

<h3 id="the-lazy-array">The Lazy Array</h3>

In addition to the `tree[]` array that stores node values, we maintain a `lazy[]` array of the same size. Each entry in `lazy[]` stores the pending update for that node. Initially, all values are 0, meaning no pending updates.

<h3 id="push-down-propagate">Push Down (Propagate)</h3>

Push down is the operation that turns a deferred update into actual values on child nodes. Before accessing any child, we check if the current node has a pending update. If it does, we:

1. Apply the pending update to both children's values
2. Pass the lazy value to both children (adding to their existing lazy)
3. Clear the current node's lazy value

In this example, Node 1 covers a segment of length 3 (indices [0,2]). Its left child covers [0,1] (length 2) and right child covers [2,2] (length 1). When we push down:

- Left child's sum increases by 3 \* 2 = 6 (lazy value times segment length)
- Right child's sum increases by 3 \* 1 = 3
- Both children receive lazy = 3
- Parent's lazy resets to 0

The parent's sum does not change during push down. It was already updated when the lazy was first applied.

<h3 id="range-update">Range Update</h3>

The range update follows the same three-case logic as a range query, with one critical addition: we set lazy markers instead of recursing all the way down.

1. **No overlap:** The update range does not intersect this node's segment. Return immediately.
2. **Total overlap:** The update range completely covers this node's segment. Update the node's value (add `val * segment_length`), set the lazy marker (add `val` to existing lazy), and return. Do NOT recurse further.
3. **Partial overlap:** Push down the current node's lazy first, then recurse into left and right children, then merge results back up.

The total overlap case is what makes range updates O(log n). Instead of recursing into potentially thousands of leaf nodes, we stop at the node that fully covers the update, record a marker, and return.

<h3 id="range-query">Range Query</h3>

Querying works exactly like the standard segment tree query, with one addition: before recursing into children during a partial overlap, push down the current node's lazy value first. This ensures the children have up-to-date values before we read from them.

<h1 id="example-walkthrough">Example Walkthrough</h1>

Let us work through a concrete example with the array `[1, 3, 5, 7, 9, 11]` (6 elements, 0-indexed).

<h3 id="step-1-build-the-segment-tree">Step 1: Build the Segment Tree</h3>

Building works exactly as in a standard segment tree. Each leaf holds one element, and internal nodes hold the sum of their children.

```text
Initial Tree (sum segment tree):
                    [0,5]=36
                   /        \
             [0,2]=9        [3,5]=27
            /      \        /      \
        [0,1]=4  [2,2]=5 [3,4]=16 [5,5]=11
        /    \            /    \
    [0,0]=1 [1,1]=3  [3,3]=7 [4,4]=9

All lazy values = 0
```

<h3 id="step-2-range-update-add-3-to-range-1-4">
  Step 2: Range Update, Add 3 to Range [1, 4]
</h3>

We call `updateRange(1, 4, 3)`. Let us trace through the recursion:

```text
At node [0,5]: partial overlap with [1,4]. Push down (lazy=0, nothing to do). Recurse both children.

  At node [0,2]: partial overlap with [1,4]. Push down (lazy=0, nothing). Recurse both.

    At node [0,1]: partial overlap with [1,4]. Push down (lazy=0, nothing). Recurse both.

      At node [0,0]: NO overlap with [1,4]. Return.

      At node [1,1]: TOTAL overlap with [1,4].
        -> sum = 3 + 3*1 = 6, lazy = 3. Return.

    Back at [0,1]: merge up. sum = 1 + 6 = 7.

    At node [2,2]: TOTAL overlap with [1,4].
      -> sum = 5 + 3*1 = 8, lazy = 3. Return.

  Back at [0,2]: merge up. sum = 7 + 8 = 15.

  At node [3,5]: partial overlap with [1,4]. Push down (lazy=0, nothing). Recurse both.

    At node [3,4]: TOTAL overlap with [1,4].
      -> sum = 16 + 3*2 = 22, lazy = 3. Return.

    At node [5,5]: NO overlap with [1,4]. Return.

  Back at [3,5]: merge up. sum = 22 + 11 = 33.

Back at [0,5]: merge up. sum = 15 + 33 = 48.
```

After this update, the tree looks like:

```text
Tree State After updateRange(1, 4, 3):
                    [0,5]=48
                   /        \
            [0,2]=15       [3,5]=33
            /      \        /      \
       [0,1]=7  [2,2]=8 [3,4]=22 [5,5]=11
       /    \    lazy=3   lazy=3
   [0,0]=1 [1,1]=6
            lazy=3

Nodes [1,1], [2,2], and [3,4] have lazy=3.
Nodes [3,3] and [4,4] have NOT been touched.
```

Node [3,4] was totally covered by [1,4], so we stopped there and set its lazy to 3. Nodes [3,3] and [4,4] were never visited; if no future query needs them, the work to apply +3 to those leaves never happens.

<h3 id="step-3-range-query-sum-of-2-5">Step 3: Range Query, Sum of [2, 5]</h3>

We call `queryRange(2, 5)`. Let us trace it:

```text
At node [0,5]: partial overlap with [2,5]. Push down (lazy=0, nothing). Recurse both.

  At node [0,2]: partial overlap with [2,5]. Push down (lazy=0, nothing). Recurse both.

    At node [0,1]: NO overlap with [2,5]. Return 0.

    At node [2,2]: TOTAL overlap with [2,5].
      -> Return sum=8. (Lazy=3 stays, we only read.)

  Return from [0,2]: 0 + 8 = 8.

  At node [3,5]: TOTAL overlap with [2,5].
    -> Return sum=33. (Lazy stays on children, does not matter.)

Return from [0,5]: 8 + 33 = 41.
```

The answer is 41. Let us verify: the original array was [1, 3, 5, 7, 9, 11], and we added 3 to indices [1,4], giving [1, 6, 8, 10, 12, 11]. Sum of [2,5] = 8 + 10 + 12 + 11 = 41. Correct.

Notice that during this query, we never had to push down any lazy values because we never hit a partial overlap on a node with a pending lazy. The lazy values on [1,1], [2,2], and [3,4] were never disturbed.

<h3 id="step-4-second-range-update-add-2-to-range-0-2">
  Step 4: Second Range Update, Add 2 to Range [0, 2]
</h3>

Now let us see how lazy values compose. We call `updateRange(0, 2, 2)`:

```text
At node [0,5]: partial overlap with [0,2]. Push down (lazy=0, nothing). Recurse both.

  At node [0,2]: TOTAL overlap with [0,2].
    -> sum = 15 + 2*3 = 21, lazy = 0 + 2 = 2. Return.
    (Note: this node already had lazy=0, now it has lazy=2.)

  At node [3,5]: NO overlap with [0,2]. Return.

Back at [0,5]: merge up. sum = 21 + 33 = 54.
```

But wait. Node [1,1] already had lazy=3 from the previous update. And now node [0,2] has lazy=2. What happens when we eventually push down from [0,2]?

When [0,2] pushes down, its children [0,1] and [2,2] each receive lazy += 2. Node [2,2] already has lazy=3, so it will become lazy=5. Node [0,1] had lazy=0 (its children [0,0] and [1,1] handled their own lazy), so it will become lazy=2. Then when [0,1] pushes down, node [1,1] with lazy=3 will receive lazy += 2, becoming lazy=5.

Because addition is associative and commutative, two pending lazy values compose by summing them. The order in which they were applied does not matter.

```text
Tree State After updateRange(0, 2, 2):
                    [0,5]=54
                   /        \
            [0,2]=21       [3,5]=33
            lazy=2          /      \
            /      \    [3,4]=22 [5,5]=11
       [0,1]=7  [2,2]=8 lazy=3
       /    \    lazy=3
   [0,0]=1 [1,1]=6
            lazy=3
```

If we later query a range that forces a push down from [0,2], the lazy values cascade correctly through the tree.

<h1 id="implementation">Implementation</h1>

Here is the complete implementation of a segment tree with lazy propagation. It supports range updates and range sum queries, with a `lazy` array holding pending updates and a `pushDown` step that propagates them to children only when needed. Comments mark what is **NEW** compared to a basic segment tree.

```java
class SegmentTreeLazy {
    int[] tree;
    int[] lazy;  // NEW: stores pending updates
    int n;

    SegmentTreeLazy(int[] arr) {
        n = arr.length;
        tree = new int[4 * n];
        lazy = new int[4 * n];  // NEW: initialized to 0
        build(arr, 1, 0, n - 1);
    }

    void build(int[] arr, int node, int start, int end) {
        if (start == end) {
            tree[node] = arr[start];
            return;
        }
        int mid = start + (end - start) / 2;
        build(arr, 2 * node, start, mid);
        build(arr, 2 * node + 1, mid + 1, end);
        tree[node] = tree[2 * node] + tree[2 * node + 1];
    }

    // NEW: push pending lazy value to children
    void pushDown(int node, int start, int end) {
        if (lazy[node] != 0) {
            int mid = start + (end - start) / 2;
            int leftChild = 2 * node;
            int rightChild = 2 * node + 1;

            // Apply to left child
            tree[leftChild] += lazy[node] * (mid - start + 1);
            lazy[leftChild] += lazy[node];

            // Apply to right child
            tree[rightChild] += lazy[node] * (end - mid);
            lazy[rightChild] += lazy[node];

            // Clear current node's lazy
            lazy[node] = 0;
        }
    }

    // NEW: range update instead of point update
    void updateRange(int node, int start, int end, int l, int r, int val) {
        if (r < start || end < l) {
            return;  // No overlap
        }
        if (l <= start && end <= r) {
            // Total overlap: update and mark lazy
            tree[node] += val * (end - start + 1);
            lazy[node] += val;
            return;
        }
        // Partial overlap: push down first, then recurse
        pushDown(node, start, end);  // NEW
        int mid = start + (end - start) / 2;
        updateRange(2 * node, start, mid, l, r, val);
        updateRange(2 * node + 1, mid + 1, end, l, r, val);
        tree[node] = tree[2 * node] + tree[2 * node + 1];
    }

    int queryRange(int node, int start, int end, int l, int r) {
        if (r < start || end < l) {
            return 0;  // No overlap
        }
        if (l <= start && end <= r) {
            return tree[node];  // Total overlap
        }
        // Partial overlap: push down first, then recurse
        pushDown(node, start, end);  // NEW
        int mid = start + (end - start) / 2;
        int leftSum = queryRange(2 * node, start, mid, l, r);
        int rightSum = queryRange(2 * node + 1, mid + 1, end, l, r);
        return leftSum + rightSum;
    }

    // Convenience methods
    void updateRange(int l, int r, int val) {
        updateRange(1, 0, n - 1, l, r, val);
    }

    int queryRange(int l, int r) {
        return queryRange(1, 0, n - 1, l, r);
    }
}
```

class SegmentTreeLazy:
    def __init__(self, arr):
        self.n = len(arr)
        self.tree = [0] * (4 * self.n)
        self.lazy = [0] * (4 * self.n)  # NEW: stores pending updates
        self._build(arr, 1, 0, self.n - 1)

    def _build(self, arr, node, start, end):
        if start == end:
            self.tree[node] = arr[start]
            return
        mid = start + (end - start) // 2
        self._build(arr, 2 * node, start, mid)
        self._build(arr, 2 * node + 1, mid + 1, end)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    # NEW: push pending lazy value to children
    def _push_down(self, node, start, end):
        if self.lazy[node] != 0:
            mid = start + (end - start) // 2
            left_child = 2 * node
            right_child = 2 * node + 1

            # Apply to left child
            self.tree[left_child] += self.lazy[node] * (mid - start + 1)
            self.lazy[left_child] += self.lazy[node]

            # Apply to right child
            self.tree[right_child] += self.lazy[node] * (end - mid)
            self.lazy[right_child] += self.lazy[node]

            # Clear current node's lazy
            self.lazy[node] = 0

    # NEW: range update instead of point update
    def update_range(self, l, r, val, node=1, start=None, end=None):
        if start is None:
            start, end = 0, self.n - 1

        if r < start or end < l:
            return  # No overlap
        if l <= start and end <= r:
            # Total overlap: update and mark lazy
            self.tree[node] += val * (end - start + 1)
            self.lazy[node] += val
            return

        # Partial overlap: push down first, then recurse
        self._push_down(node, start, end)  # NEW
        mid = start + (end - start) // 2
        self.update_range(l, r, val, 2 * node, start, mid)
        self.update_range(l, r, val, 2 * node + 1, mid + 1, end)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def query_range(self, l, r, node=1, start=None, end=None):
        if start is None:
            start, end = 0, self.n - 1

        if r < start or end < l:
            return 0  # No overlap
        if l <= start and end <= r:
            return self.tree[node]  # Total overlap

        # Partial overlap: push down first, then recurse
        self._push_down(node, start, end)  # NEW
        mid = start + (end - start) // 2
        left_sum = self.query_range(l, r, 2 * node, start, mid)
        right_sum = self.query_range(l, r, 2 * node + 1, mid + 1, end)
        return left_sum + right_sum

    fn new(arr: &[i64]) -> Self {
        let n = arr.len();
        let mut st = SegmentTreeLazy {
            tree: vec![0; 4 * n],
            lazy: vec![0; 4 * n], // NEW: initialized to 0
            n,

        st.build(arr, 1, 0, n - 1);

    }

        self.build(arr, 2 * node, start, mid);
        self.build(arr, 2 * node + 1, mid + 1, end);

            // Apply to left child
            self.tree[left_child] += self.lazy[node] * (mid - start + 1) as i64;
            self.lazy[left_child] += self.lazy[node];

            // Apply to right child
            self.tree[right_child] += self.lazy[node] * (end - mid) as i64;
            self.lazy[right_child] += self.lazy[node];

            // Clear current node's lazy
            self.lazy[node] = 0;
        }
    }

    // NEW: range update instead of point update
    fn update_range_rec(&mut self, node: usize, start: usize, end: usize, l: usize, r: usize, val: i64) {
        if r < start || end < l {
            return; // No overlap
        }
        if l <= start && end <= r {
            // Total overlap: update and mark lazy
            self.tree[node] += val * (end - start + 1) as i64;
            self.lazy[node] += val;
            return;
        }
        // Partial overlap: push down first, then recurse
        self.push_down(node, start, end); // NEW
        let mid = start + (end - start) / 2;
        self.update_range_rec(2 * node, start, mid, l, r, val);
        self.update_range_rec(2 * node + 1, mid + 1, end, l, r, val);
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1];
    }

    fn query_range_rec(&mut self, node: usize, start: usize, end: usize, l: usize, r: usize) -> i64 {
        if r < start || end < l {
            return 0; // No overlap
        }
        if l <= start && end <= r {
            return self.tree[node]; // Total overlap
        }
        // Partial overlap: push down first, then recurse
        self.push_down(node, start, end); // NEW
        let mid = start + (end - start) / 2;
        let left_sum = self.query_range_rec(2 * node, start, mid, l, r);
        let right_sum = self.query_range_rec(2 * node + 1, mid + 1, end, l, r);
        left_sum + right_sum
    }

    // Convenience methods
    fn update_range(&mut self, l: usize, r: usize, val: i64) {
        self.update_range_rec(1, 0, self.n - 1, l, r, val);
    }

    fn query_range(&mut self, l: usize, r: usize) -> i64 {
        self.query_range_rec(1, 0, self.n - 1, l, r)
    }
}

<h3 id="code-explanation">Code Explanation</h3>

Compared to a basic segment tree, the structural changes here are surprisingly small. The entire technique boils down to two additions: the `lazy[]` array and the `pushDown()` function.

<h4 id="how-pushdown-works">How pushDown Works</h4>

The `pushDown` function is called whenever we are about to recurse into a node's children. It checks whether the current node has any pending updates (lazy != 0). If it does:

1. **Update children's values.** For a sum segment tree, a child covering a segment of length L gets `lazy[node] * L` added to its sum. This is because every element in that segment needs to increase by `lazy[node]`.
2. **Transfer lazy to children.** Each child's lazy value increases by the parent's lazy value. This ensures future push-downs cascade correctly.
3. **Clear the parent's lazy.** The parent has done its job by delegating to children.

<h4 id="how-lazy-values-compose">How Lazy Values Compose</h4>

For addition-based lazy propagation, composition is simple: just add the new lazy to the existing one. If a node already has lazy=3 and receives another update of 5, its lazy becomes 8. This works because addition is associative and commutative. Adding 3 then adding 5 is the same as adding 8.

This simplicity is specific to the "add" operation. Other operations like "set to value X" require different composition logic, which we cover in the Variations section.

<h4 id="how-node-values-update-during-range-update">
  How Node Values Update During Range Update
</h4>

When a range update totally covers a node's segment `[start, end]`, the sum increases by `val * (end - start + 1)`. The derivation is one line: each of the `(end - start + 1)` elements in the segment gains `val`, so the sum gains `val * length`. We never need to look at individual element values to perform the update.

<h1 id="complexity-analysis">Complexity Analysis</h1>

<h3 id="range-update-olog-n">Range Update: O(log n)</h3>

At each level of the tree, we visit at most 4 nodes (a proof similar to the standard segment tree query applies). The tree has O(log n) levels, so we visit O(log n) nodes. At each node, we do O(1) work (push down, update value, set lazy). Total: O(log n).

Without lazy propagation, updating a range of length k costs O(k log n) because we perform k individual point updates. For k close to n, this degrades to O(n log n), which is no better (and sometimes worse) than updating the raw array.

<h3 id="range-query-olog-n">Range Query: O(log n)</h3>

Same analysis as the standard segment tree query. The push down at each node adds O(1) extra work, so the overall complexity remains O(log n).

<h3 id="space-on">Space: O(n)</h3>

We need two arrays of size 4n: one for the tree and one for the lazy values. Total space is O(n).

<h3 id="comparison">Comparison</h3>

| Operation    | Without Lazy | With Lazy |
| ------------ | ------------ | --------- |
| Point Update | O(log n)     | O(log n)  |
| Range Update | O(k log n)   | O(log n)  |
| Range Query  | O(log n)     | O(log n)  |
| Space        | O(n)         | O(n)      |
| Build        | O(n)         | O(n)      |

Where k is the length of the update range. For k = n, the difference is O(n log n) vs O(log n), a dramatic improvement.

<h1 id="variations-and-extensions">Variations and Extensions</h1>

<h3 id="setassign-lazy">Set/Assign Lazy</h3>

Instead of adding a value, sometimes you need to set all elements in a range to a specific value. The key difference is in composition: a new "set" operation completely overwrites any pending lazy, whether it was an add or a previous set.

For a set operation:

- Node value becomes `val * (end - start + 1)` (not added, but replaced)
- Lazy stores the assigned value, plus a flag indicating whether a set is pending
- When composing, a new set replaces the old lazy entirely

You can mark "no pending set" two ways. A sentinel like `INT_MIN` or `None` works but breaks if the actual data ever contains that value. The cleaner approach is a parallel `boolean[] hasLazy` array of the same size as `lazy[]`. `hasLazy[node]` is true when a set is pending, and `lazy[node]` holds the value. Push-down checks `hasLazy[node]`, applies the set to children, sets their `hasLazy` to true, and clears the parent's flag. The extra `boolean[]` is cheap and removes any restriction on what values you can store.

<h3 id="multiply-lazy">Multiply Lazy</h3>

For multiplication operations (multiply all elements in a range by `val`):

- Node value becomes `tree[node] * val`
- Lazy stores the multiplier, initialized to 1 (identity element for multiplication)
- Composition: multiply the new value with the existing lazy

<h3 id="composing-different-lazy-operations">
  Composing Different Lazy Operations
</h3>

Some problems require both addition and multiplication on the same segment tree. This is significantly more complex. You maintain two lazy values per node (one for multiply, one for add) and apply them in a fixed order: multiply first, then add.

When composing, if a new operation is "multiply by m":

- multiply_lazy \*= m
- add_lazy \*= m (because existing additions get scaled by the multiplication)

If a new operation is "add a":

- add_lazy += a

This composition order matters. Getting it wrong produces subtle bugs.

<h3 id="lazy-propagation-with-minmax-segment-trees">
  Lazy Propagation with Min/Max Segment Trees
</h3>

For min/max queries with range add updates, lazy propagation works similarly. The key difference is in how the node value updates:

- For range add: `tree[node] += val` (no segment-length multiplier needed)
- Push down works the same way

The reason the formula is `tree[node] += val` and not `tree[node] += val * length`: min and max are _translation-invariant_ under addition. If you add the same constant to every element in a segment, the minimum and maximum of that segment shift by the same constant. Sum, by contrast, is not translation-invariant: adding `val` to each of `length` elements increases the sum by `val * length`. The lazy formula always mirrors how the aggregate responds to a uniform shift.

For range set with min/max:

- Node value becomes the assigned value
- All elements become the same, so min = max = assigned value

<h3 id="comparison-of-lazy-operation-types">
  Comparison of Lazy Operation Types
</h3>

| Operation Type | Identity | Composition  | Node Update             |
| -------------- | -------- | ------------ | ----------------------- |
| Add            | 0        | lazy += val  | sum += val \* len       |
| Set            | sentinel | lazy = val   | sum = val \* len        |
| Multiply       | 1        | lazy \*= val | sum \*= val             |
| XOR (binary)   | 0        | lazy ^= val  | depends on bit count    |
| Add + Multiply | (1, 0)   | see above    | sum = sum _ m + a _ len |

<h1 id="common-patterns-and-applications">Common Patterns and Applications</h1>

<h3 id="pattern-1-range-add-range-sum">Pattern 1: Range Add + Range Sum</h3>

This is the classic application we have been discussing. Given an array, support adding a value to all elements in a range and querying the sum of a range. Problems like "Range Sum Query" with range updates fall into this category.

<h3 id="pattern-2-range-set-range-query">Pattern 2: Range Set + Range Query</h3>

Assign a value to all elements in a range, then query sum/min/max. This appears in problems involving painting intervals, where you "paint" a range with a color (value) and later ask about the state of a range.

<h3 id="pattern-3-interval-paintingcoloring">
  Pattern 3: Interval Painting/Coloring
</h3>

Given a number line, paint intervals with different colors. Query how many distinct colors exist in a range, or what color a specific point has. This uses lazy propagation with the "set" operation, where painting a range overwrites all previous colors.

<h3 id="pattern-4-flip-operations-on-binary-arrays">
  Pattern 4: Flip Operations on Binary Arrays
</h3>

Given a binary array (0s and 1s), support flipping all elements in a range (0 becomes 1, 1 becomes 0) and querying the count of 1s in a range. The lazy value is a boolean flag indicating whether a flip is pending. Composition: two flips cancel out (XOR with 1 twice returns to original).

<h1 id="summary">Summary</h1>

- Lazy propagation extends segment trees to support O(log n) range updates, turning them from a query-only data structure into a fully dynamic one.
- The technique works by deferring updates: when a range update fully covers a node's segment, mark it and stop. Only propagate to children when forced to by a later operation.
- The implementation adds just two things to a basic segment tree: a `lazy[]` array and a `pushDown()` function called before any recursive descent into children.
- For addition-based lazy, values compose by summing. For set-based lazy, new values overwrite old ones. Combined operations need careful ordering.

| Aspect            | Key Detail                                  |
| ----------------- | ------------------------------------------- |
| Time (update)     | O(log n) per range update                   |
| Time (query)      | O(log n) per range query                    |
| Space             | O(n) (two arrays of size 4n)                |
| Lazy identity     | 0 for add, 1 for multiply, sentinel for set |
| Push down timing  | Before any recursive call into children     |
| Composition (add) | New lazy = old lazy + val                   |
| Composition (set) | New lazy = val (overwrite)                  |
