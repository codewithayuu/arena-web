<LessonCard>

You have a data structure of employee information, including the employee's unique ID, their importance value, and their direct subordinates' IDs.

You are given an array of employees `employees` where:

- `employees[i].id` is the ID of the `i-th` employee.
- `employees[i].importance` is the importance value of the `i-th` employee.
- `employees[i].subordinates` is a list of the IDs of the direct subordinates of the `i-th` employee.

Given an integer `id` that represents an employee's ID, return the total importance value of this employee and all their direct and indirect subordinates.

\***\*Example 1:\*\***

- **Input:** `employees = [[1,5,[2,3]],[2,3,[]],[3,3,[]]]`

- **Input:** `id = 1`

- **Output:** `11`

Employee 1 has an importance value of 5 and has two direct subordinates: employees 2 and 3. They both have an importance value of 3. The total importance value of employee 1 is 5 + 3 + 3 = 11.

\***\*Example 2:\*\***

- **Input:** `employees = [[1,2,[5]],[5,-3,[]]]`

- **Input:** `id = 5`

- **Output:** `-3`

Employee 5 has an importance value of -3 and has no subordinates. The total importance is -3.

\***\*Constraints:\*\***

- `1 <= employees.length <= 2000`
- `1 <= employees[i].id <= 2000`
- All `employees[i].id` are unique.
- `-100 <= employees[i].importance <= 100`
- One employee has at most one direct leader and may have several subordinates.
- The employees have no cycles in their subordination structure.
- `id` is guaranteed to be a valid employee ID in the input.

<h1 id="approach-1-dfs-recursive">Approach 1: DFS (Recursive)</h1>

<h3 id="intuition">Intuition</h3>

The total importance of an employee equals their own importance plus the total importance of each of their direct subordinates. That definition is already recursive: each subordinate's total is computed the same way, and the recursion bottoms out at employees with no subordinates.

Before we can traverse, we need a way to jump from a subordinate ID to the actual employee object. The input gives us a list, and scanning it for every lookup would cost O(n) each time. So we first build a hash map from employee ID to employee object. After that, the DFS is short: look up the target, add their importance, recurse on each subordinate ID.

> Each employee has at most one direct leader, so any ID appears in at most one subordinates list. There is exactly one path from the target down to each employee in their subtree, which means the recursion visits each of those employees once, with no visited set needed. The no-cycles guarantee ensures the recursion terminates.

<h3 id="example-walkthrough">Example Walkthrough</h3>

Trace `employees = [[1, 5, [2, 3]], [2, 3, [4]], [3, 4, []], [4, 1, []]]` with `id = 1`. Employee 4 is an indirect subordinate of employee 1, reachable only through employee 2, so the recursion has to go two levels deep on that branch.

<h3 id="code">Code</h3>

> - **Time Complexity:** O(n). Building the hash map takes O(n). The DFS visits each employee in the target's subtree at most once, doing O(1) work per visit. Total subordinate edges processed across all visits is at most n - 1.
> - **Space Complexity:** O(n). The hash map stores all n employees. The recursion call stack goes as deep as the height of the subtree, which in the worst case (a chain) is O(n).

Recursive DFS is optimal in time, but it spends call-stack space proportional to the depth of the hierarchy, and a long management chain can overflow the stack. The next approach replaces the implicit call stack with an explicit queue.

<h1 id="approach-2-bfs-iterative">Approach 2: BFS (Iterative)</h1>

<h3 id="intuition">Intuition</h3>

Instead of recursing into subordinates, we can use a queue to process employees iteratively. Start by adding the target employee's ID to the queue. Then, while the queue is not empty, dequeue an ID, look up the employee, add their importance to a running total, and enqueue all their subordinate IDs. This explores the entire subtree without any risk of stack overflow.

BFS and DFS visit the same set of employees in a different order. BFS processes the target first, then all direct subordinates, then all employees two levels down, and so on. The total importance ends up the same regardless of traversal order because addition is commutative.

<h3 id="example-walkthrough">Example Walkthrough</h3>

The same input as before: `employees = [[1, 5, [2, 3]], [2, 3, [4]], [3, 4, []], [4, 1, []]]` with `id = 1`. BFS reaches employee 3 before employee 4, the reverse of the DFS order, and still arrives at the same total of 13.

<h3 id="code">Code</h3>

> - **Time Complexity:** O(n). Building the hash map is O(n). The BFS visits each employee in the target's subtree once, doing O(1) work per employee. Total subordinate IDs enqueued across all visits is at most n - 1.
> - **Space Complexity:** O(n). The hash map stores all n employees. The queue holds at most O(n) employee IDs in the worst case (a very wide tree where the target has all others as direct subordinates).
