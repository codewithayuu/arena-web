<LessonCard>

You are given a string `s`, which contains stars `*`.

In one operation, you can:

- Choose a star in `s`.
- Remove the closest non-star character to its left, as well as remove the star itself.

Return the string after all stars have been removed.

**Note:**

- The input will be generated such that the operation is always possible.
- It can be shown that the resulting string will always be unique.

\***\*Example 1:\*\***

- **Input:** `s = leet**cod*e`

- **Output:** `lecoe`

**Explanation:** Performing the removals from left to right: The closest character to the 1st star is 't'. s becomes "lee\*cod\*e". The closest character to the 2nd star is 'e'. s becomes "lcod\*e". The closest character to the 3rd star is 'd'. s becomes "lcoe". There are no more stars, so we return "lcoe".

\***\*Example 2:\*\***

- **Input:** `s = erase*****`

**Explanation:** The entire string is removed.

\***\*Constraints:\*\***

- `1 <= s.length <= 10^5`
- `s` consists of lowercase English letters and stars `*`.
- The operation above can always be applied (i.e., there will always be a non-star character to the left of each star).

<h1 id="approach-1-brute-force-simulation">
  Approach 1: Brute Force Simulation
</h1>

<h3 id="intuition">Intuition</h3>

Simulate the operation literally: find a star, remove it along with the character to its left, then continue scanning. This mirrors the problem statement step for step.

The cost shows up in the removals. Deleting a character from the middle of a string or list shifts every element after it, and a fresh scan has to resume near the deletion point because positions changed. With many stars, that shifting work dominates.

<h3 id="visualization-and-code">Visualization and Code</h3>

<InteractiveAnimation />

> - **Time Complexity:** O(n^2). In the worst case, stars are clustered at the end. Each removal shifts elements in the list, costing O(n) per removal. With up to n/2 stars, that gives O(n^2) total.
> - **Space Complexity:** O(n). We store a mutable copy of the input string.

The repeated shifting is the bottleneck. The next approach builds the result in a single pass instead, touching each character exactly once.

<h1 id="approach-2-stack-stringbuilder">Approach 2: Stack (StringBuilder)</h1>

<h3 id="intuition">Intuition</h3>

Build the result in a single pass using a stack. As we scan left to right, a letter gets pushed onto the stack, and a star pops the top element. The pop discards the most recent surviving letter, which is the closest non-star to the left of that star.

After the scan, the stack holds the answer in order. Because every operation only adds to or removes from the end, a StringBuilder (or list) serves as the stack, with no shifting or rescanning.

> The pop is always safe. The problem guarantees a non-star character to the left of every star, so any surviving letter to a star's left is still on the stack, meaning the stack is non-empty when we reach a star.
>
> The pop also removes the correct character. The top of the stack is the most recently pushed surviving letter, which is the nearest non-star to the left of the current star. Letters that no star removes stay on the stack in their original order, so the final stack reads left to right as the answer.

<InteractiveAnimation />

> - **Time Complexity:** O(n). We iterate through the string once. Each character is either pushed or triggers a pop, both O(1) operations.
> - **Space Complexity:** O(n). The stack can hold up to n characters in the worst case (when there are no stars).

The stack approach runs in O(n) time but allocates a separate structure for O(n) extra space. The next approach removes that allocation by treating the input array itself as the stack, using a single write pointer.

<h1 id="approach-3-in-place-with-write-pointer">
  Approach 3: In-Place with Write Pointer
</h1>

<h3 id="intuition">Intuition</h3>

Reuse the character array as the stack. A `write` pointer marks where the next surviving character belongs, and the loop variable acts as the read pointer scanning left to right.

For a letter, store it at index `write` and advance `write`. For a `*`, decrement `write`, which logically removes the last stored character so the next letter overwrites it. At the end, indices `0` through `write - 1` hold the result.

> The invariant `write <= read` holds throughout. The read pointer advances by one every iteration, while `write` either advances by one (on a letter) or decreases (on a star), so it can never move ahead of `read`. We therefore only overwrite positions at or before the current read index, never a character still waiting to be read.
>
> The prefix `arr[0..write)` is the same stack from the previous approach, stored in the array instead of a separate buffer.

<InteractiveAnimation />

> - **Time Complexity:** O(n). A single pass over the string, with O(1) work per character.
> - **Space Complexity:** O(n) for the mutable character array in languages with immutable strings (Java, Python, C#, Go, Rust, JavaScript). In C++, the string is mutable and we overwrite it directly, so the extra space beyond the output is O(1).
