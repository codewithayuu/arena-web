Given an array `intervals` where `intervals[i] = [l_i, r_i]` represent the interval `[l_i, r_i)`, remove all intervals that are covered by another interval in the list.

The interval `[a, b)` is covered by the interval `[c, d)` if and only if `c <= a` and `b <= d`.

Return the number of remaining intervals.

**Example 1:**

- **Input:** `intervals = [[1,4],[3,6],[2,8]]`

- **Output:** `2`

**Explanation:** Interval [3,6] is covered by [2,8], so it is removed. The remaining intervals are [1,4] and [2,8].

**Example 2:**

- **Input:** `intervals = [[1,4],[2,3]]`

- **Output:** `1`

**Explanation:** [2,3] is covered by [1,4], so only [1,4] remains.

**Example 3:**

- **Input:** `intervals = [[1,2],[1,4],[3,4]]`

- **Output:** `1`

**Explanation:** [1,2] is covered by [1,4], and [3,4] is covered by [1,4]. Only [1,4] remains.

**Constraints:**

- `1 <= intervals.length <= 1000`
- `intervals[i].length == 2`
- `0 <= l_i < r_i <= 10^5`
- All the given intervals are unique.

<h1 id="approach-1-brute-force">Approach 1: Brute Force</h1>

<h3 id="intuition">Intuition</h3>

For each interval, check whether any other interval in the list covers it. An interval [a, b) is covered by [c, d) if c &lt;= a and b &lt;= d. If we find such a covering interval, we mark the current one as covered and do not count it.

This is O(n^2) because for each of the n intervals, we compare it against up to n - 1 others. With n up to 1,000, that is about a million comparisons, which runs well within typical limits.

> - **Time Complexity:** O(n^2). For each of the n intervals, we compare it against up to n - 1 other intervals. In the worst case, every pair gets checked.
> - **Space Complexity:** O(1). We only use a few variables for counting and loop control. No additional data structures are needed.

The brute force repeats comparisons because the intervals have no ordering to exploit. Sorting them so that every potential coverer appears before the intervals it might cover reduces the work to a single pass.

<h1 id="approach-2-sort-and-greedy-optimal">
  Approach 2: Sort and Greedy (Optimal)
</h1>

<h3 id="intuition">Intuition</h3>

If we sort intervals by start point ascending, then any interval that could cover another must start at the same position or earlier. Ties on the start point need care. If two intervals share the same start, the longer one (larger end) should come first, so the shorter one appears after it and reads as covered.

The sorting rule is therefore: sort by start ascending, and break ties by end descending. After sorting, we track the maximum end point seen so far. If the current interval's end is within that maximum, it is covered. Otherwise it survives, and we update the maximum.

> The sorting guarantees that every interval able to cover interval `i` appears before `i` in the sorted list. A coverer needs a start &lt;= `i`'s start, which the ascending start sort guarantees, and an end >= `i`'s end. When starts differ, an earlier interval has a strictly smaller start, so the survivor with the largest end so far reaches at least as far. When starts tie, the descending end tie-break places the larger end first. Either way, the farthest end among all intervals that start at or before `i` has already been recorded in `maxEnd` by the time we examine `i`.
>
> Tracking that single number is enough. If `i`'s end fits within `maxEnd`, some interval that starts at or before `i` ends at or after `i`, so it covers `i`. If `i`'s end exceeds `maxEnd`, no earlier interval reaches far enough, so `i` is not covered and survives.
