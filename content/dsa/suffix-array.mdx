<LessonCard>

A suffix array is the lexicographically sorted order of every suffix of a string. The LCP (longest common prefix) array sits alongside it and records, for every pair of adjacent suffixes in the sorted order, how many characters they share at the start.

Together they form one of the most useful preprocessing structures in string algorithms. With a suffix array and LCP array you can:

- Pattern-match in O(m log n) per query after one-time O(n log n) preprocessing.
- Find the longest repeated substring in O(n).
- Count distinct substrings in O(n).
- Find the longest common substring of two or more strings in O(n).
- Replace many uses of suffix trees with a structure that takes half the memory.

This chapter covers the definition, a practical O(n log^2 n) construction algorithm, Kasai's O(n) LCP construction, and the most common applications.

<h2 id="what-is-a-suffix-array">What Is a Suffix Array?</h2>

Given a string S of length n, the suffix array SA is an array of integers of length n such that SA[i] is the starting position of the i-th smallest suffix of S in lexicographic order.

**Example: S = "banana"**

The six suffixes are:

```text
Index:  Suffix
  0     banana
  1     anana
  2     nana
  3     ana
  4     na
  5     a
```

Sorting them lexicographically:

```text
Rank:  Suffix     Starting index
  0    a              5
  1    ana            3
  2    anana          1
  3    banana         0
  4    na             4
  5    nana           2

SA = [5, 3, 1, 0, 4, 2]
```

The suffix array is `[5, 3, 1, 0, 4, 2]`. Reading it: the smallest suffix starts at index 5, the next at index 3, then 1, 0, 4, 2.

Storing starting indices instead of the suffix strings themselves matters for two reasons. The suffixes overlap: storing them all explicitly takes O(n^2) memory, while storing only their starting indices takes O(n). And every algorithmic operation needed for substring problems (pattern matching, LCP computation, substring queries) works on starting indices, dipping into the original string by index only when a character comparison is required.

The companion structure is the **rank array**, the inverse of SA. Rank[i] is the rank of the suffix starting at position i. If `SA[r] = i`, then `Rank[i] = r`. For `S = "banana"`:

```text
i:        0   1   2   3   4   5
Suffix:   ban anan na  ana na  a
SA:       5   3   1   0   4   2
Rank:     3   2   5   1   4   0
```

Read Rank as "where does the suffix starting at position i land in sorted order?" The suffix starting at index 0 ("banana") is the 4th smallest (rank 3), the suffix at index 5 ("a") is the smallest (rank 0), and so on.

<h2 id="naive-construction">Naive Construction</h2>

The most direct way to build the suffix array is to generate every suffix as a string and sort them.

```text
Naive suffix array:
1. For i = 0 to n-1, build suffix S[i..n-1]
2. Sort the suffixes lexicographically
3. SA[i] is the starting index of the i-th sorted suffix
```

Generating all suffixes is O(n^2) characters of total work. Sorting them with the default comparison-based sort costs O(n log n) comparisons, each comparing strings of up to n characters, for O(n^2 log n) overall. For n = 10^5, that is roughly 10^11 character comparisons. Hopeless.

The naive approach is correct, easy to write, and useful for unit testing the fast version on small inputs. For real workloads it is replaced by rank doubling.

<h2 id="rank-doubling-on-log2-n-construction">
  Rank Doubling: O(n log^2 n) Construction
</h2>

The standard practical algorithm sorts suffixes by **rank pairs** instead of by their full strings, doubling the prefix length being compared on each iteration.

The idea in one paragraph:

1. Compute the rank of each suffix by its first character. Ties exist when characters repeat.
2. Now compare suffixes by their first 2 characters by looking at the rank of their first character and the rank of the suffix starting one position later (which we already have from step 1).
3. Update ranks, then compare by their first 4 characters using the same trick (rank at i, rank at i+2).
4. Double the prefix length each iteration. After `log(n)` iterations, every suffix has a unique rank and the sort is complete.

Each iteration sorts n suffixes by a pair of integers. A comparison-based sort costs O(n log n) per iteration. With O(log n) iterations, the total cost is O(n log^2 n).

<h3 id="why-rank-pairs-work">Why Rank Pairs Work</h3>

Suppose we already know the rank of every suffix based on its first `k` characters. To compare two suffixes by their first `2k` characters, look at:

- The rank of the suffix starting at position i (based on its first k characters), and
- The rank of the suffix starting at position i + k (also based on its first k characters).

These two ranks describe the first k and second k characters of the suffix starting at i. Two suffixes can be compared by these two pairs of ranks in O(1), no character comparison needed.

The diagram below illustrates the doubling.

Suffixes that fall off the end of the string (when `i + k >= n`) are padded with rank `-1`, treated as smaller than any real character. This is the lexicographic convention: shorter strings come first when one is a prefix of the other.

<h3 id="implementation">Implementation</h3>

The implementation has two helper structures: a pair `(rank[i], rank[i + k])` for each suffix, and a sort by that pair. After each pass we reassign ranks based on the sorted order, breaking ties only when the pair is identical.

```java
public static int[] buildSuffixArray(String s) {
    int n = s.length();
    Integer[] sa = new Integer[n];
    int[] rank = new int[n];
    int[] tmp = new int[n];

    for (int i = 0; i < n; i++) {
        sa[i] = i;
        rank[i] = s.charAt(i);
    }

    for (int k = 1; k < n; k *= 2) {
        final int kk = k;
        final int[] r = rank;
        Arrays.sort(sa, (a, b) -> {
            if (r[a] != r[b]) return Integer.compare(r[a], r[b]);
            int ra = a + kk < n ? r[a + kk] : -1;
            int rb = b + kk < n ? r[b + kk] : -1;
            return Integer.compare(ra, rb);
        });

        tmp[sa[0]] = 0;
        for (int i = 1; i < n; i++) {
            tmp[sa[i]] = tmp[sa[i - 1]];
            int prev = sa[i - 1], cur = sa[i];
            int prevSecond = prev + k < n ? rank[prev + k] : -1;
            int curSecond  = cur  + k < n ? rank[cur  + k] : -1;
            if (rank[prev] != rank[cur] || prevSecond != curSecond) {
                tmp[sa[i]]++;
            }
        }
        System.arraycopy(tmp, 0, rank, 0, n);
        if (rank[sa[n - 1]] == n - 1) break;   // all ranks distinct
    }

    int[] result = new int[n];
    for (int i = 0; i < n; i++) result[i] = sa[i];
    return result;
}
```

```python
def build_suffix_array(s: str) -> list[int]:
    n = len(s)
    sa = list(range(n))
    rank = [ord(c) for c in s]
    tmp = [0] * n

    k = 1
    while k < n:
        def key(i):
            return (rank[i], rank[i + k] if i + k < n else -1)
        sa.sort(key=key)

        tmp[sa[0]] = 0
        for i in range(1, n):
            tmp[sa[i]] = tmp[sa[i - 1]]
            prev, cur = sa[i - 1], sa[i]
            prev_second = rank[prev + k] if prev + k < n else -1
            cur_second  = rank[cur  + k] if cur  + k < n else -1
            if rank[prev] != rank[cur] or prev_second != cur_second:
                tmp[sa[i]] += 1
        rank = tmp[:]
        if rank[sa[n - 1]] == n - 1:
            break
        k *= 2

    return sa
```

```go
    sa := make([]int, n)
```

```rust
pub fn build_suffix_array(s: &str) -> Vec<usize> {
    let bytes = s.as_bytes();
    let n = bytes.len();
    let mut sa: Vec<usize> = (0..n).collect();
    let mut rank: Vec<i32> = bytes.iter().map(|&b| b as i32).collect();
    let mut tmp: Vec<i32> = vec![0; n];

    let mut k = 1usize;
    while k < n {
        let kk = k;
        let r = rank.clone();
        sa.sort_by(|&a, &b| {
            if r[a] != r[b] {
                return r[a].cmp(&r[b]);
            }
            let ra = if a + kk < n { r[a + kk] } else { -1 };
            let rb = if b + kk < n { r[b + kk] } else { -1 };
            ra.cmp(&rb)
        });

        tmp[sa[0]] = 0;
        for i in 1..n {
            tmp[sa[i]] = tmp[sa[i - 1]];
            let prev = sa[i - 1];
            let cur = sa[i];
            let prev_second = if prev + k < n { rank[prev + k] } else { -1 };
            let cur_second  = if cur  + k < n { rank[cur  + k] } else { -1 };
            if rank[prev] != rank[cur] || prev_second != cur_second {
                tmp[sa[i]] += 1;
            }
        }
        rank.copy_from_slice(&tmp);
        if rank[sa[n - 1]] == (n as i32) - 1 {
            break;
        }
        k *= 2;
    }
```

```javascript
function buildSuffixArray(s) {
  const n = s.length;
  let sa = Array.from({ length: n }, (_, i) => i);
  let rank = Array.from(s).map((c) => c.charCodeAt(0));

        tmp[sa[i]]++;
      }
```

Three implementation details worth pointing out:

- The early-exit check `rank[sa[n - 1]] == n - 1` says "every suffix already has a unique rank, no more doubling needed." This often saves a couple of iterations on random strings.
- The initial rank is the ASCII (or Unicode) code of each character. For multi-byte inputs, work on byte arrays (as the Rust version does) or normalize to fixed-width integers.
- The `tmp` array is the new rank vector after the sort. It is built incrementally by comparing each suffix to its predecessor in the sorted order. Tied pairs share a rank; new pairs increment.

<h3 id="faster-variants">Faster Variants</h3>

Several construction algorithms give better asymptotic complexity than O(n log^2 n). They are mentioned here for completeness; for interview-sized inputs (n up to about 10^6) the simpler rank-doubling above is fast enough.

- **O(n log n) with counting sort**. Replace the comparison sort with counting sort on the rank pairs. The constant factor is larger, the code is significantly longer, and the saved factor of `log n` rarely matters until n exceeds 10^7.
- **DC3 (Difference Cover)**. Karkkainen and Sanders, 2003. True O(n) construction. Conceptually elegant but the implementation is involved.
- **SA-IS (Suffix Array by Induced Sorting)**. Nong, Zhang, Chan, 2009. The current standard for production work. O(n) time, small constants, used in tools like `samtools` and the Burrows-Wheeler-based `bzip2`.

A working SA-IS implementation is roughly 200 lines and is best learned from a clean reference (Yuta Mori's C implementation is the canonical one). For interview or competitive-programming inputs, rank doubling is sufficient.

<h2 id="building-the-lcp-array">Building the LCP Array</h2>

The LCP array is what makes the suffix array genuinely powerful for substring problems. Given a suffix array SA of S, the LCP array LCP has length n - 1 (or n, with LCP[0] = 0 by convention), where:

`LCP[i] = the length of the longest common prefix of the suffixes at SA[i - 1] and SA[i]`.

For S = "banana":

```text
Rank  SA  Suffix     LCP (with previous suffix)
  0    5  a           -
  1    3  ana         1   (common with "a")
  2    1  anana       3   (common with "ana": "ana")
  3    0  banana      0   (common with "anana": none)
  4    4  na          0   (common with "banana": none)
  5    2  nana        2   (common with "na": "na")

LCP = [-, 1, 3, 0, 0, 2]   (LCP[0] is undefined)
```

The maximum value in the LCP array is the length of the longest substring that appears at least twice in S. For "banana", that maximum is LCP[2] = 3, corresponding to "ana", which appears at indices 1 and 3.

<h3 id="why-adjacent-suffixes-carry-all-the-lcp-information">
  Why Adjacent Suffixes Carry All the LCP Information
</h3>

This is the key property: for any two suffixes (not just adjacent ones), the LCP equals the **minimum** of all LCP values between them in the sorted order.

`LCP(SA[i], SA[j]) = min(LCP[i + 1], LCP[i + 2], ..., LCP[j])`, for `i < j`.

So the LCP array between adjacent suffixes captures everything you need to answer LCP queries for any pair, by combining with a range-minimum structure (sparse table, segment tree, or even a sqrt decomposition).

<h2 id="kasais-algorithm-on-lcp-construction">
  Kasai's Algorithm: O(n) LCP Construction
</h2>

Building the LCP array naively (comparing each pair of adjacent sorted suffixes character by character) costs O(n^2). Kasai's algorithm builds it in O(n) by walking through the suffixes in **original-string order**, not sorted order.

The insight: if the suffix starting at position i has LCP h with its neighbor in the sorted array, then the suffix starting at position i + 1 has LCP at least h - 1 with its own sorted neighbor.

Why? The suffix at i + 1 is the suffix at i with its first character removed. If positions i and its sorted-neighbor share h characters, dropping one character from the front still leaves h - 1 matching characters between i + 1 and its sorted-neighbor. The amortized argument is: across all positions, `h` decreases by at most 1 each iteration and increases by at most n total, so the total work is O(n).

<h3 id="implementation">Implementation</h3>

```java
public static int[] buildLCP(String s, int[] sa) {
    int n = s.length();
    int[] rank = new int[n];
    int[] lcp = new int[n];

    for (int i = 0; i < n; i++) rank[sa[i]] = i;

    int h = 0;
    for (int i = 0; i < n; i++) {
        if (rank[i] == 0) {
            h = 0;
            continue;
        }
        int j = sa[rank[i] - 1];
        while (i + h < n && j + h < n && s.charAt(i + h) == s.charAt(j + h)) {
            h++;
        }
        lcp[rank[i]] = h;
        if (h > 0) h--;
    }
    return lcp;
}
```

The trace of Kasai's on "banana" matches the example table above. The total number of character comparisons is bounded by 2n: each successful comparison increments `h`, which can grow at most n times total; each failure ends an inner loop iteration, of which there are at most n.

<h2 id="applications">Applications</h2>

<h3 id="pattern-matching-om-log-n-per-query">
  Pattern Matching: O(m log n) per Query
</h3>

Given a sorted suffix array, finding all occurrences of a pattern P of length m is a binary search problem. Pattern P is a prefix of some suffix S[i..n-1] if and only if i is an occurrence of P in S. So:

1. Binary-search for the lowest rank such that the suffix at that rank starts with P.
2. Binary-search for the highest rank such that the suffix starts with P.
3. Every suffix between those two ranks corresponds to an occurrence of P.

Each binary-search step compares P (m characters) with one suffix, so the total per query is O(m log n). Multiple-pattern matching is the same cost per pattern.

```java
public static int[] searchSuffixArray(String s, int[] sa, String pattern) {
    int n = s.length(), m = pattern.length();
    int lo = 0, hi = n;
    while (lo < hi) {
        int mid = (lo + hi) / 2;
        if (s.substring(sa[mid], Math.min(sa[mid] + m, n)).compareTo(pattern) < 0) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    int start = lo;

    lo = 0; hi = n;
    while (lo < hi) {
        int mid = (lo + hi) / 2;
        if (s.substring(sa[mid], Math.min(sa[mid] + m, n)).compareTo(pattern) <= 0) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    int end = lo;

    int[] occ = new int[end - start];
    for (int i = 0; i < occ.length; i++) occ[i] = sa[start + i];
    Arrays.sort(occ);
    return occ;
}
```

<h3 id="longest-repeated-substring">Longest Repeated Substring</h3>

The longest substring that appears at least twice in S is the substring corresponding to the maximum entry in the LCP array.

```java
        if (lcp[i] > maxLen) {
            maxLen = lcp[i];
            idx = sa[i];
        }
```

<h3 id="number-of-distinct-substrings">Number of Distinct Substrings</h3>

The total number of substrings of S is `n * (n + 1) / 2`. The number of duplicate substrings is the sum of the LCP array. So:

`Number of distinct substrings = n * (n + 1) / 2 - sum(LCP)`

For "banana": `6 * 7 / 2 - (1 + 3 + 0 + 0 + 2) = 21 - 6 = 15` distinct substrings.

```java
public static long countDistinctSubstrings(String s) {
    int n = s.length();
    int[] sa = buildSuffixArray(s);
    int[] lcp = buildLCP(s, sa);
    long total = (long) n * (n + 1) / 2;
    long duplicate = 0;
    for (int v : lcp) duplicate += v;
    return total - duplicate;
}
```

<h3 id="longest-common-substring-of-two-strings">
  Longest Common Substring of Two Strings
</h3>

Concatenate S and T with a separator that does not appear in either: `U = S + '#' + T`. Build the suffix array and LCP array of U. The longest common substring of S and T is the maximum LCP[i] such that SA[i - 1] and SA[i] come from different sides of the separator.

The same trick extends to k strings, using k different separators or one separator plus a "source" tracking array.

<h3 id="substring-comparison-in-o1-after-preprocessing">
  Substring Comparison in O(1) After Preprocessing
</h3>

With a sparse table built over the LCP array, the LCP between any two suffixes is `min(LCP[i + 1..j])` in O(1) per query. Combined with rank lookup, comparing any two substrings of S takes O(1).

This speed-up applies to problems that need many substring comparisons: longest common substring in queries, palindrome substring queries, smallest cyclic rotation, and similar.

<h2 id="comparison-with-other-string-structures">
  Comparison with Other String Structures
</h2>

| Structure                | Build Time                             | Memory               | Pattern Match        | Notes                                                                       |
| ------------------------ | -------------------------------------- | -------------------- | -------------------- | --------------------------------------------------------------------------- |
| **KMP failure function** | O(n + m)                               | O(m)                 | O(n + m) per pattern | Single fixed pattern matched against streaming text                         |
| **Z-array**              | O(n)                                   | O(n)                 | O(n + m)             | Same use case as KMP, different implementation                              |
| **Manacher's algorithm** | O(n)                                   | O(n)                 | (palindromes only)   | Longest palindromic substring in O(n)                                       |
| **Suffix Array + LCP**   | O(n log n) practical, O(n) theoretical | O(n)                 | O(m log n) per query | Best general-purpose substring structure. Half the memory of suffix tree.   |
| **Suffix Tree**          | O(n)                                   | O(n), large constant | O(m) per query       | Same use cases as suffix array; faster matching but larger constant memory. |
| **Suffix Automaton**     | O(n)                                   | O(n)                 | O(m) per query       | Same expressive power as suffix tree. Handles online updates.               |

Practical guidance:

- For a one-time substring problem on a single string of length up to a few million, build a suffix array with rank doubling.
- For repeated substring queries on a fixed text, the same suffix array works, with the LCP array providing extra power.
- For pattern-matching problems where the text is fixed but the patterns change, the suffix array beats KMP or Aho-Corasick when the patterns are many and short and the text is long.
- For palindrome-specific problems, use Manacher's algorithm instead. The suffix array of `S + reverse(S)` also works but is overkill.
- For multi-pattern matching where patterns are known up front, use Aho-Corasick rather than a suffix array.

`O(n)` for the suffix array, rank array, and LCP array together. The constant factor is much smaller than a suffix tree, which is the main reason suffix arrays are preferred in production systems.
